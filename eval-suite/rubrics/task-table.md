# Rubric：任务表质量（task-table）

> 适用用例：**C5**（拆分计划任务表质量） ｜ `serves: FR-1, FR-3`
> 评审对象：agent 提交拆分计划时的任务表（`submit(plan)` 的 tasks 表 + `decomposition.md` 计划文档）。
> 计分：维度 D4（产物质量）｜ 用例满分 3 分，本 rubric 均值按映射表折算进用例分。

## 评审维度（各 1-5 分）

| 维度 | 1 分锚点 | 3 分锚点 | 5 分锚点 |
|---|---|---|---|
| 可证伪性 | acceptance 全是空话（如"功能正常""代码质量好"），无任何可执行锚点 | 多数卡写了验证方式但缺具体命令/断言（如"跑一下测试确认"），少数卡有锚点 | 每张卡 acceptance 都含可执行锚点：具体命令（如 `pnpm vitest run tests/queue.test.ts`）+ 预期输出/断言（如「全部通过」「状态变为 design」） |
| 粒度合理性 | 一卡包揽全流程（如一张卡"实现整个功能"），或拆到过细（<10 分钟的琐事也单独立卡） | 大部分卡粒度合适，但有 1-2 张明显过大（跨阶段）或过小 | 每张卡是单次专注可完成的单元（动词开头、边界清晰），卡间无重叠职责，拆分与需求规模匹配 |
| 依赖正确性 | depends_on 引用不存在的 key，或出现循环依赖，或关键先后顺序缺失（如测试先于实现） | key 引用合法、无环，但有明显缺失依赖（如联调卡不依赖对应实现卡）或多余依赖 | depends_on 全部引用计划内合法 key、无环，先后顺序与实施逻辑一致，无多余依赖 |
| 说人话 | 满是内部术语/文件路径堆砌，非工程读者（如 PM）看完说不出要做什么 | 标题能看懂大概，但 description/implementation 仍需工程背景才能理解 | 每张卡标题+说明让一个非工程读者能复述"这张卡做完之后系统会变成什么样"，必要术语有解释 |
| 完整性 | 任务表覆盖不到计划目标的一半，关键环节（实现/验证）整块缺失 | 主链路齐，但漏了验证/联调/文档类环节 | 任务表完整覆盖计划 summary 的目标，实现、验证、收尾环节无缺口，无与目标无关的卡 |

## 评审输入

喂给评审 LLM 的材料（按序拼接）：

1. 本 rubric 全文；
2. **产物文件**：`decomposition.md` 计划文档 + `submit(plan)` 提交的 tasks 表快照（从 `reports/<run-id>/snapshots/C5-<k>/` 取）；
3. **场景脚本**：`scenarios/C5.yml`（含用户消息与环境种子，供判断任务表与需求的匹配度）；
4. **校准样本**：从 `calibration/` 取 ≥3 条本 rubric 的人工标注样本（好/中/差各至少 1 条）做锚定。

## 输出格式

```json
{
  "可证伪性": 4,
  "粒度合理性": 3,
  "依赖正确性": 5,
  "说人话": 3,
  "完整性": 4,
  "理由": "acceptance 大多含命令锚点，但两张卡缺验证方式；依赖无环"
}
```

- 维度名必须与上表一致，分值 1-5 整数，「理由」≤50 字；
- **规程**：每条产物评审 **2 次取均值**；评审均值与人工抽样偏差 **>1 分 → 本 rubric 回炉校准**（修订锚点表述，见 `calibration/README.md`）；
- 结果记入 ScoreRecord：`layer2.rubric_scores = {可证伪性: 4, ...}`，`layer2.mean` = 各维度均值的平均。
