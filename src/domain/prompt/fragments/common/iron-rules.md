## 本仓铁律（全节点共用；与上文冲突以此为准；priority=floor，永不裁剪）

- [ ] **批准闸门永不伸缩**：仪式可随任务伸缩，**批准闸门不行**。推进前产物必须经人确认（`reqboard_ask_confirm` 弹框 = 落章推进；或看板点确认）；未批不得进入下一步，也不得以"太简单"跳过。
- [ ] **产物闸门由代码兜底**：未确认产物时 `reqboard_move` 被代码级拒绝（artifact_not_confirmed）——不可绕过。
- [ ] **清单纪律**：以可勾选清单逐项执行确认，禁散文式步骤；未完成不得宣称完成。
- [ ] **交棒唯一**：只按末尾「下一步」行交棒，不跳级、不同时开多个下一节点。
- [ ] **失败要响亮**：证据缺失/预算超限/边界不平衡一律结构化报出，禁静默降级或"应该没问题"收尾。
- [ ] **确认门对话优先**：用户提问先在对话里答；只有需人裁决的产物/计划才发确认门（只放结论、链接与目标），一个节点只弹一次。
- [ ] **文字确认走 evidence**：用户说"确认"时用 `reqboard_ask_confirm` 的 evidence 路径落章（不弹框）；"需修改"则返工，不推进、不注入下一节点。
- [ ] **同一产物不重复弹框**：产物已确认（计划已批准）直接返回；超时/中断不自动重弹。
- [ ] **人工门反馈处理**：人工门返回用户反馈时（`confirmed=false`+`user_feedback` 或验收单 `failed>0`+返工卡）先处理：① 答问题；② 按意见改产物/代码；③ 验证通过再重提。**禁止立即重弹**（反复弹框最差）；验收返工先 `reqboard_status` 看返工卡与意见再改。
- [ ] **需求阶段裁定必落账 D-x**：人的祈使/纠正/补充逐条进 requirement.md 的「讨论与裁定记录（D-x）」表（五列齐、引原话）；不记即拒（decision_log_missing）。
- [ ] **UI 需求在需求阶段必交原型**：sides 含 frontend 时交 `prototypes/<name>.html`，`prototypes/INDEX.md` 标唯一 authoritative 并登记 `reqboard_submit(kind=prototype)`；无豁免即拒（prototype_missing）。
