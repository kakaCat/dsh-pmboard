# REQ-261006130057-7a43 成本与耗时诊断

> 诊断对象：`REQ-261006130057-7a43《PM 插件需求详情页 UI 优化（原型先行）》`
> 主窗口会话：`session-d71bdc25-ede6-48a2-a4ca-49637f67c9eb`（2026-10-06 12:58 → 10-07 09:57，跨度 21.0h）
> 数据来源：`~/.dsh/sessions/--Users-mac-Documents-ai-dsh-dsh-pmboard--/*/session.v4.jsonl.zstd`（主窗口 + 30 个子代理会话）
> 口径：每个会话只统计**自身**请求（`event.time >= session.createdAt`），避免 fork 把父上下文的历史 usage 重复计入

## 0. 结论

1. 这条需求一共打了 **2,324 次 LLM 请求**（主窗口 517 + 30 个子代理 1,807），**输入 412.2M tokens / 输出 1.40M**，输入:输出 = **294 : 1**；平均每次请求要重发 **177K** 输入 token，主窗口到后期每次 **~500K**。
2. 时间不是花在模型上：21.0h 里，主窗口回合内 13.4h = **工具等待 11.3h**（其中阻塞式提问独占 8.57h）+ 模型生成/排队 2.2h。
3. 真正的花钱主体是「**轮次数量 × 全量重发**」，不是缓存失效：即使全部命中缓存（按 1/10 价折算），等效成本仍有 ~90% 来自那 2,324 轮的重复输入。缓存失效类浪费约占等效成本 **10%**，但它是**唯一可以一行改动砍掉**的那 10%。

- 未命中率只有 **2.3%** —— 前缀缓存整体是生效的。
- 主窗口上下文**全程没有压缩**：单次输入从 25K 单调涨到 512K，中间没有任何一次下降（无 compact 事件、无 prompt 回落）。
- 子代理分层（按各自请求数）：实现类 13 个 / 1,285 次请求 / 182.6M 输入；复核 fork 8 个 / 174 次请求 / 52.7M；原型 6 个 / ~12M。

## 2. 贵在哪：五个根因（均带日志证据）

### R1 · system prompt 每阶段/每任务重写 → 前缀缓存整段作废（可一行改动修掉）

主窗口一共发生 **30 次 `system/message` 注入，产生 16 个不同版本的 system prompt**（长度 6,414 → 27,257 → 12,136 → 11,314 → 13,338 → 14,028 …）。
system prompt 位于上下文最头部，DSH 是「就地更新进历史」（deepseek 会话的 `request/context` 明确写着 `systemPromptUpdate: "in-history"`），于是**头部一变，后面全部前缀缓存失效**，整段 ~13 万–35 万 token 按全价重发。

日志里每一处都长这样（`cache=16,384`、`uncached≈整段上下文`）：

```
14:28:29 system/message            ← 阶段 brainstorming→design，system prompt 换版
14:29:15 turn9 step9   uncached=120,025  cache=16,384
14:42:05 system/message            ← design→decomposing
14:43:22 turn9 step30  uncached=148,641  cache=16,384
14:47:22 system/message            ← 开工 t1（「当前任务执行中」段出现）
14:47:55 turn9 step40  uncached=160,995  cache=16,384
17:31:28 system/message            ← 又一张卡收尾
17:31:51 turn13 step48 uncached=298,077  cache=16,384
```

- 16 次「未命中 ≈ 全上下文」的请求合计 **3.90M**，占主窗口未命中输入的 **88%**；其中紧跟在 system prompt 重写之后、未命中 >20K 的 13 次合计 **3.21M（72%）**。
- 更糟的是**来回翻版**：`16:45:34`（13,338 字）→ `16:45:58`（13,897 字）→ `16:52:39`（13,338 字）→ `16:53:50`（13,897 字），20 秒内翻两次、7 分钟内翻两轮，每一翻都是一次全量重算。
- 代码位置：`src/application/internal/capture-section.ts`（「📋 PM · 项目看板」段的三处变体：L148 已绑定 / L320 检测到新输入 / L375 未绑定）+ `src/gate-wiring.ts:216` 每轮装配。插件把「阶段纪律正文 + 当前任务执行中 + 看板状态行」全塞进 system prompt，这些东西**天然每换一次阶段/任务就变**。

### R2 · 上下文无压缩 + 轮次太多（成本主体）

- 平均每次请求输入 177K，主窗口后期 ~500K；512K 的窗口额度用掉一半，单窗口跑满 21h 不换人。
- 主窗口按「上一批工具」归因 prompt 消耗：

| 触发工具 | 请求数 | prompt 合计 | 占比 |
|---|---:|---:|---:|
| bash | 199 | 61,813,731 | 43.8% |
| reqboard_task_move | 54 | 15,655,383 | 11.1% |
| reqboard_task_report | 36 | 10,714,424 | 7.6% |
| edit | 35 | 7,946,726 | 5.6% |
| （纯文本回合） | 28 | 7,375,363 | 5.2% |
| read_image | 26 | 7,235,555 | 5.1% |
| read | 22 | 5,258,332 | 3.7% |
| subagent(+fork) | 24 | 5,973,527 | 4.2% |
| reqboard_submit / task_tree / ask_confirm 等 | 21 | 4,545,526 | 3.2% |

  **插件自己的记账往返（reqboard_*）≈ 120 次请求 / 33M prompt = 主窗口的 23%**。任务状态机每推一步就是一个完整 round-trip。

### R3 · 子代理长链：每张卡从零摸仓库，每步一个工具

- 30 个子代理共 1,807 次请求 / 265.9M 输入；13 个实现类子代理平均 **99 次请求**，最长 157 次。
- 子代理首请求基线只有 ~18.8K token，但它们各自把上下文**长到 150K–260K** 再跑上百轮——和主窗口同样的病。
- 典型：`10-07 09:44` 同时开 4 个返工代理（A/B/C/D）修 4 个小 UI 问题，**15 分钟内各跑 101–147 次请求，合计 ≈ 72M 输入**（占全树 17%）。

### R4 · fork 复核把父上下文整段带过去（首次请求全价）

8 个 `subagent_fork` 复核代理，首请求 prompt 218K–350K、且 `cacheRead=0`（继承来的历史在服务端没有缓存）：

```
033c3bc3 t3 复核   首请求 uncached=321,847
f2381397 t6 复核   首请求 uncached=298,532
20dacea9 t8 复核   首请求 uncached=260,781
e7165550 t4 复核   首请求 uncached=225,988
9842eb49 t5 复核   首请求 uncached=202,144
```

8 个 fork 的首请求未命中合计 **≈1.7M tokens**，纯粹是「把父窗口上下文重新讲一遍」。复核本身只干了 13–42 次请求——为了让它看得见上下文，付了 8 次全量重传。

### R5 · 阻塞与重试把时间拉长（token 的次要项，体感的大头）

- **一次 `ask_user_question` 阻塞 30,829s = 8.57h**（10-07 01:10 → 09:43），整个窗口挂死等用户睡觉醒来。
- 5 次 LLM 重试：kimi `stream idle timeout after 300000ms` ×1、deepseek `transport failed` ×4；另有 1 次 `403` 直接让 turn 16 以 error 结束，之后中断 3.5h。
- 插件 60s 「批量关闭节流」（`doneThrottleMs`，`src/application/internal/support.ts:770`）逼出 `bash: sleep 40 && echo waited  # Wait out the 60s close throttle`——40 秒等待换来一次 ~300K 的全量重发。

## 3. 慢在哪：21 小时时间分解

```
会话跨度                 21.0 h
├─ 主窗口回合内           13.4 h
│  ├─ 工具等待            11.3 h
│  │  ├─ ask_user_question 阻塞   8.57 h  ← 一次跨夜提问
│  │  ├─ subagent 等待           90.0 min（20 次）
│  │  ├─ subagent_fork 等待      35.5 min（9 次）
│  │  └─ bash                    31.9 min（211 次）
│  └─ 模型生成/排队        2.2 h（129.8 min；平均 15.4 s/次，最慢 449.7 s）
└─ 回合之间人不在          4.1 h（含 403 事故后的 3.5h 空档）
```

体感「特别慢」的直接来源不是模型慢（生成只占 10%），而是**排队式串行**：一次工具一次往返、一次确认跨夜挂死、子代理一跑 20 分钟到 11 小时。

## 4. 台账可见量 ≠ 真实用量（约 4 倍缺口）

需求台账 `tokenUsage` 记录：

| 阶段 | 未命中 | 命中缓存 | 输出 |
|---|---:|---:|---:|
| brainstorming | 131,668 | 7,410,992 | 33,532 |
| design | 151,095 | 3,104,000 | 17,934 |
| decomposing | 150,970 | 181,248 | 6,332 |
| implementing | 3,937,982 | 94,129,180 | 111,969 |
| **合计** | **4,371,715** | **104,825,420** | **169,767** |

- 该台账**只统计 owner 窗口**（正好约等于主窗口），**不含 30 个子代理**（子代理另有未命中 5.03M / 命中 260.9M）。
- 且 `updatedAt` 停在 10-07 01:06，之后 4 个返工代理（≈72M 输入）完全没进账。
- 结论：看板显示 109M 输入，真实全树 **412M**——**可见度只有 26%**。用户在看板上看到的数字，天然低估 4 倍。

## 5. 改进清单（按 ROI 排序）

### A. 插件层（本仓代码）

> **更正（2026-10-07，本需求实施期实测）**：R1 的因果链是**供应商相关**的，不是普遍规律。
> 本项目另一条窗口（`session-57f49896`，模型 `deepseek-flash`）同源发生 **9 次 system prompt 重写（8 个版本）**，
> 但每次重写后首次请求**命中缓存 37.9 万、未命中仅 4.6 千**（逐次实测：重写 13,361→13,968 字符后紧邻请求
> `uncached=5,292 / cache=384,384`）——**前缀缓存并未被作废**。

> ⇒ 正确表述应为：**「重写头部是否让前缀缓存失效」取决于模型/供应商**。kimi-coding/k3 上代价真实且巨大（本文 3.9M 全价）；
> deepseek-flash 上实测代价≈0。因此 FR-1/FR-2 的**token 收益是供应商相关的**；其与供应商无关的价值在于
> 消除 30 次冗余注入、让头部确定可断言，以及团队切换到「会对头部变化失效」的模型时不再付这笔钱。
