# 需求说明（REQ-261006201920-2adc 让验收不再形式合规：堵住占位符验收与空事实裁决）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。
> 核心原则：**用户能看懂**——不写技术术语，用场景和结果说话。

## TL;DR <!-- serves: FR-1 -->

- **是什么**：验收单上写着「`npx vitest run <相关测试文件>` → 全绿」这种**没填完的模板**，门禁却判绿；裁决栏里只写着「通过」两个字，也算通过。
- **为什么**：门禁只认「含命令字样」，于是**占位符 + 命令词**就是一张通行证；返工卡更是从旁门落库，绕过了全部质量门。
- **得到什么**：验收标准里不再出现没填的尖括号占位符；「通过」两个字不再算实测结果；系统报出的缺口不写处置就归档不了。

## 现象与取证（本次审计实测，逐条可复跑）

| 现象 | 实测读数 | 复跑方式 |
|---|---|---|
| 验收标准带未替换占位符 | **944 / 2005** 张任务卡的「验收标准」段落命中 `/<[^>]{2,40}>/` | 扫 `docs/requirements/**/tasks/*.md` 的验收段 |
| 占位符集中在少数几个 | `<本卡改动涉及的测试文件>` 365、`<相关测试文件>` 361、`<REQ>` 367、`<本卡接口/契约对应的测试文件>` 185 | 同上，按命中词聚合 |
| 占位符的**产生源**是模板字面量 | `STAGE_ACCEPTANCE.dev` 里就写着 `npx vitest run <本卡改动涉及的测试文件>` | 读 `src/domain/task/SubtaskTemplate.ts` 与 `src/application/internal/lazy-expand.ts` |
| 门禁为何判绿 | `VERIFIABLE_ANCHOR` 含 `npx` / `vitest`，命令字样即通过，尖括号占位符不参与判定 | 单测：`checkAcceptance('T', 'npx vitest run <相关测试文件>').ok === true` |
| 返工卡绕过质量门 | 返工卡 `acceptance` 直接取验收项判据原文、`implementation` 拼「按验收意见修复：…」，不经任何校验 | 读 `AcceptanceSheetSpec.reworkSpecFor` 与 `application/internal/verdicts.ts` |
| 裁决结果不成事实 | 「实际结果」列全项只写「通过」两个字 | 读台账 `verification.json` 的 `sheet.items[].result` |

## 业务流程图 <!-- serves: FR-1 -->

```
修前：模板占位符一路通行，最后只剩两个字

                    │
                    └─▶ 懒展开落子卡：模板原文照抄 <相关测试文件>
                              │
                              └─▶ 人看验收单：标准里是尖括号，实际结果写「通过」
                                        │
                                        └─▶ 归档 —— 没有一处拦得住

修后：三处各堵一段，缺口必须被处置
  计划提交 ──▶ checkAcceptance（占位符 = 打回，并给出该填什么）
  懒展开   ──▶ 用父卡 acceptance 里的真实测试文件 + 需求 id 回填占位符
                    │
  裁决     ──▶ 结果无可复核锚点 ⇒ 记「未复核」，不冒充通过
                    │
                    └─▶ 系统缺口项通过 ⇒ 必须写处置（补了 X / 确认无需，因为 Y）
                              └─▶ 处置为空 ⇒ 不可归档
```

## 产品定义 <!-- serves: FR-1 -->

**验收单是这条流水线的收口**：人靠它判断「这活到底做完没有」，归档与否由它放行。它一旦形式化，整条流水线的质量承诺就一起失效。

核心价值：把「验收标准可执行」「裁决结果可复核」从**修辞要求**变成**机器拦得住的事实**。

与现状的区别：现状是三层各自漏——计划期只查「有没有命令字样」、子卡落库不回填模板、裁决期只要有字就算数；
本需求不新增流程，而是在这三层各自补上真实判据，并给每一条配可复跑的用例。

**三要素检查清单**：

- [x] 说清楚"是什么"：占位符门禁 + 子卡回填 + 返工卡过检 + 裁决锚点与处置模板
- [x] 说清楚"核心价值"：验收标准能照着跑、裁决结论有据可查、系统缺口不被静默吞掉
- [x] 说清楚"与现状的区别"：不新增状态与门类，只把既有三层的判据从「形式」改成「事实」

**FR-1: 未替换占位符不得进验收标准**

验收标准里**命令的操作数仍是未替换占位符**时（形如 `npx vitest run <相关测试文件>`、`npx tsx scripts/<脚本>.mts`），
计划提交必须被拒绝，并在拒绝原因里给出**该填什么**的具体指引；同时，父卡懒展开落子卡时，子卡验收标准里的
占位符必须按**声明式词表**全部回填（父卡验收标准里真实点名的测试文件 / 本需求 id / 本卡 id / 声明的兜底形态），
落库即无占位符。

**判据口径（收窄，附实测依据）**：**不**按裸 `/<[^>]{2,40}>/` 一刀切。实测反例（都在合法验收标准里）：

| 反例 | 为什么合法 | 裸正则的后果 |
|---|---|---|
| `Record<StageKind,string>`、`Map<realKey, Promise>`、`Promise<void>` | TypeScript 泛型实参 | 把合法标准打回 |
| 「每个值恰 1 个 `<svg>`」、「`grep -c` 命中 `<ts>` 字面量」 | 描述产品自身的字面量格式 | 同上 |
| `prototypes/<name>.html`、`rtm-implementing/<id>.yml` | 路径**形态**模板（带真实后缀） | 同上 |
| 「断言 hint 不含子串 `<单册>` 与 `<数据根>`」 | 断言某串**不出现** | 同上 |

实测：裸正则在 2005 张任务卡里命中 944 张；本收窄口径命中 **921 张（97.6%）**，
且命中的 token 全部是真模板占位符（`<本卡改动涉及的测试文件>` 365、`<REQ>` 361、`<相关测试文件>` 361、
`<本卡接口/契约对应的测试文件>` 185…），上表反例**全部被放过**。

- **使用场景**：计划作者图省事写 `npx vitest run <相关测试文件>`；子卡由模板自动展开、作者根本没机会手填。
- **操作流程**：提交计划 → 判「命令操作数」占位符（有则打回并点名）→ 落库时展开子卡 → 按词表回填 → 子卡标准为具体文件列表。
- **预期结果**：**新落库的卡里尖括号残留数为 0**；打回原因里能读到「把 `<X>` 换成真实路径/编号」。
- **边界条件**：**存量卡不追溯、不改写**（历史 944 张保持原样，只对本次之后新落库的卡生效）；
  父卡验收标准里没有任何测试文件时，回填必须落到**声明的兜底形态**（仍可跑的命令），不得留空、不得留占位符；
  模板里的占位符必须是**声明式闭集**——出现词表外的尖括号 token 即报错（否则「残留为 0」不可证）。

**判据**：`npx vitest run tests/acceptance-placeholder.test.ts tests/lazy-expand-backfill.test.ts` 全绿；
且**反向演练**——把占位符判据分支注释掉后对应用例当场变红，还原即绿。

**FR-2: 返工卡与其它卡同门**

验收不通过生成的返工卡，落库前必须与普通卡走**同一套**可证伪判据与「怎么验」判据；
并继承来源卡的**体量声明（footprint）**与**需求条款引用（requirementRefs）**。
验收项本身没有来源卡时（需求级项、原型对照项、裁定对照项），返工卡必须落到一条**可证伪**的标准上。

- **使用场景**：验收单里「与裁定对照（逐条说明如何落实）」这类判据被判不通过，系统自动生成返工卡。
- **操作流程**：裁决不通过 → 生成返工规格 → **过两道判据** → 继承来源卡体量声明与条款引用 → 落库。
- **预期结果**：返工卡的验收标准一律含可复核锚点，零锚点返工卡数量为 0；返工卡能追溯到它服务哪条需求条款。
- **边界条件**：不得因为判据不过就把人的「退回返工」动作卡死——必须有可落地的兜底标准，且兜底标准本身可证伪。

**判据**：`npx vitest run tests/rework-gate.test.ts` 全绿，用例须覆盖「来源卡判据不可执行」与「验收项没有来源卡」两种形态。

**FR-3: 裁决结果必须可复核**

裁决时，一项的「实际结果」若**没有可复核锚点**（命令、文件路径、明确计数），不得记为通过，应记为**未复核**；
「只能人看」的项禁收无事实的短句（典型是「通过」两个字）并给出可读拒绝原因；
人**覆盖** agent 实测结果时，必须同时给出**变更理由**，且 agent 原文不得丢失。

- **使用场景**：agent 已逐项落章实测结果，人复核时发现不符需要改写；或人复核界面视觉项只能自己填结论。
- **操作流程**：人填空点通过 → 判锚点 → 无锚点记未复核（附「该补什么」）→ 覆盖场景必须填变更理由 → 原文留档。
- **预期结果**：验收单里不再出现「无可复核锚点的通过」；被覆盖的 agent 原文在台账里查得到。
- **边界条件**：**记录「未复核」不是拒绝**——它不阻断人继续裁决其它项，只是不放行归档；
  覆盖场景缺变更理由时**拒绝该次覆盖**并给出修法（可不覆盖、或补理由）。

**两类项的判据分开（实测校准）**：

| 项类 | 判据 | 为什么不同 |
|---|---|---|
| 普通项（agent 能自证） | 文本必须含**可复核锚点**：命令 / 文件路径 / 明确计数 | agent 本该跑过命令，给不出锚点即等于没跑 |
| 只能人看的项（`needsHuman`） | 文本必须含**观察事实**：长度 > 6 且含现象或证据形态（一致/不一致/可见/显示/出现/缺失/错位/对照/截图/如图，或证据路径） | 界面视觉**给不出命令**——强求命令锚点等于逼人编命令 |

**实测依据**（台账全量 `verification.json`）：

- 无锚点的「通过」共 **112** 项：其中 **86** 项文本是「（未附实际结果：…待补复核）」（自己都写着待补复核却记了通过），**25** 项就是「通过」两个字 → 这两类正是本 FR 要翻成 `未复核` 的形态。
- `needsHuman` 项已通过的实测结论原文含「通过」（2 项）→ 不足以当事实；同时存在「我对照原型看过：一致」这类**合法观察**，故 needsHuman 分支必须按「事实形态」判，不能按命令锚点判。

**判据**：`npx vitest run tests/verdict-result-anchor.test.ts tests/result-override-reason.test.ts` 全绿；
反向演练：把锚点判据分支注释掉，断言「结果=通过 ⇒ 状态=通过」的用例当场变红。

**FR-4: 系统缺口项通过必须写处置**

系统报出的缺口项（E2E 缺口、孤儿用例、三方一致性、追溯断链）点通过时，处置文字必须命中处置模板
（「已处置」或「确认无需」两义之一 + 给得出对象或理由）；处置为空的系统缺口项**不得放行归档**。

- **使用场景**：机器报出「缺 E2E 用例」，人判断这次确实不需要补。
- **操作流程**：点通过 → 判处置是否命中模板 → 不命中即拒绝并给出两种合法写法 → 命中则放行。
- **预期结果**：归档门读到的系统缺口项处置一律非空；缺口被吞掉这件事在台账上看得见。
- **边界条件**：**只对系统缺口项**生效；普通项的通过不受处置模板约束；
  「不可验收（not_verifiable）」仍按其原有规则（必须写原因），不被本模板覆盖。

**处置模板的两种语义形态**（不锁死措辞，锁死**有没有给出结论**）：

| 形态 | 认得的写法 | 判据 |
|---|---|---|
| 已处置 | 补了 / 已补 / 补上 / 新增 / 加了 / 修了 / 已覆盖 | 须同时给出**补了什么**（长度 > 6） |
| 确认无需 | 确认无需 / 无需 / 不需要 / 不适用 / 暂不 / 不做 | 须同时给出**为什么**（长度 > 6） |

**实测依据（这是一次行为变更，必须知情）**：台账全量 `verification.json` 里 gapKind 项已通过 **106** 条，
命中上述两义模板的有 **0 条**——现状是把**证据原文**（命令输出）粘进处置栏，或干脆空着。
所以本 FR 上线后，**系统缺口项的通过写法会变严**（历史记录不追溯、不改写）。

**判据**：`npx vitest run tests/system-item-disposition.test.ts` 全绿，且含一条**逆验证用例**：
构造「系统项已通过但处置为空」的验收单 ⇒ 放行归档的判据必须报**不可归档**。

## 失败与并发路径 <!-- serves: FR-1 -->

**失败路径**：

- **回填找不到测试文件**：父卡验收标准未点名任何测试文件时，回填必须落到可跑的兜底形态（整目录跑测），
  不得留占位符、不得留空——留空会让「有标准」退化成「没有标准」。
- **兜底标准本身不可执行**：返工卡兜底标准必须自身含可复核锚点；若连兜底都构造不出，
  必须**响亮报错并给出修法**（先修订来源卡的验收标准），不得静默落一张零锚点卡。
- **判据文件缺失**：`checkAcceptance` / `checkHowToVerify` 抛错时，不得吞异常伪造成「通过」。

**并发与重复**：

- **同一项被并发裁决**：沿用既有 `applyVerdicts` 的整批前置校验语义——**先整批验证、后落状态**，
  中途失败不留半批已改记录（既有不变量，本需求不改）。
- **重复覆盖同一项**：第二次覆盖时变更理由**必须重新给出**（不沿用上一次的理由），
  且原文保留字段取**最初那次** agent 原文，不被中间覆盖冲掉。
- **子卡重复展开**：沿用既有幂等（名下已有子卡即跳过），重复开工不产生第二套子卡、不重复回填。

**状态机**：本次不新增状态。裁决状态五值（`pending` / `passed` / `failed` / `not_verifiable` / `unverified`）逐字不变；
本需求只是让 `passed` 的**进入条件**变严（有锚点），并让 `unverified` 在更多形态下被如实使用。

**写路径**：被判据拒绝时**台账零改动**（拒绝发生在落状态之前）；回填与继承在**同一次落库**内完成，
不产生「卡落了、字段半截」的中间态。

## 边界（不做什么） <!-- serves: FR-1 -->

- **不追溯改写存量卡**：历史 944 张带占位符的卡**原样保留**（证据优先）。原因：改写历史会让「当时的标准是什么」不可考，也让本需求的验收失去对照。
- **不碰原型门**：原型的适用性判据、豁免通道、比较逻辑一律不动（那是另一窗口的在飞面）。
- **不碰归档校验**：归档材料清单、合并去向、必填文档的判据一律不动；本需求只让「处置为空」这一条**被归档门读到**，不改归档门自身的规则。
- **不碰测试基线**：不刷新基线、不删改既有失败用例、不调整基线判据脚本。
- **不放宽任何既有门**：`VERIFIABLE_ANCHOR`（计划期）、`HOW_TO_VERIFY`（验收期）、四道人工门、内容门逐字不变；本需求只**新增**占位符这一条判据。
- **不引入第二套锚点词汇表**：本需求复用既有的可核验锚点词表并显式声明与它的分工，不另起一套；两处口径不一致时以**公开说明的差集**为准，并有用例锁住。
- **不做「自动补齐占位符」的批量脚本**：不做存量批量回填工具——那是改写历史，理由同上。

## 讨论与裁定记录（D-x） <!-- serves: FR-1 -->

## 非功能需求 <!-- serves: FR-1 -->

- **兼容**：已归档与在飞需求的历史台账**逐字可读**；不新增必填字段导致旧台账解析失败。
- **性能**：占位符判据是单次正则匹配，不引入 IO；懒展开回填在同一次落库内完成，不新增轮次。
- **可测**：每条 FR 至少一条可跑用例；判据分支都留有反向演练位（注释掉即变红）。
- **回滚**：改动集中在领域判据与两处落库点，回滚 = 还原这几个文件，无数据迁移、无 schema 变更。

## 验收标准（整体） <!-- serves: FR-1 -->

1. 计划作者写 `npx vitest run <相关测试文件>` 提交 → **被拒**，原因里点名占位符并给出该填什么。
   反例对照：含 `Record<StageKind,string>` 或「断言不含 `<单册>`」的合法标准**照旧放行**。
2. 父卡验收标准点名 `tests/x.test.ts` → 触发懒展开 → 子卡验收标准里出现 `tests/x.test.ts`，**无尖括号残留**；
   父卡未点名测试文件时 → 落到声明的兜底形态（仍可跑），同样无尖括号残留。
3. 存货卡对照：改动后新落库的卡占位符残留数为 **0**；历史 944 张**逐字节不变**。
4. 验收项判据为「与裁定对照（逐条说明如何落实）」被判不通过 → 生成的返工卡**含可复核锚点**且能追溯到需求条款。
5. 裁决：实际结果写「通过」两个字 → 该项落成**未复核**，不进入可归档集合。
6. 人工项（原型对照）输入 ≤6 字无事实文本 → **被拒**，提示写现象 + 证据路径。
7. 人改写 agent 实测结果 → 必须填变更理由；agent 原文在台账可查。
8. 系统缺口项点通过但处置为空 → **拒绝**；处置写「确认无需，因为…」→ 放行。
9. 反向演练：注释掉占位符判据分支 → 对应用例**当场变红**；还原 → 绿。
10. `npx vitest run tests/acceptance-sheet*.test.ts tests/sheet-*.test.ts` 与本需求新增用例**全绿**；
    `pnpm typecheck` 不新增错误；`pnpm build` 退出码 0；改了客户端源码时 `pnpm build:client` 见 `[verify-client] OK`。

## 关键决策与取舍

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 占位符判据的口径 | 裸 `/<[^>]{2,40}>/` 一刀切（委派底稿的字面写法） | 只判**命令操作数**仍是占位符 | 裸正则会误伤 TS 泛型 / HTML 字面量 / 路径形态模板 / 「断言某串不出现」四类合法标准（反例与实测见 FR-1）；收窄后仍覆盖 921/944 = 97.6% 的真实问题 |
| 占位符怎么消失 | 存量批量回填脚本 | 只堵新落库 + 懒展开按词表回填 | 改写历史会让「当时的标准」不可考；D-1 的边界也指向不追溯 |
| 回填词表 | 自由正则替换任意 `<...>` | **声明式闭集**，出现词表外 token 即报错 | 闭集才让「残留为 0」可证；自由替换会把合法尖括号一起吃掉 |
| 回填找不到文件时怎么办 | 留占位符 / 留空 | 落到声明的兜底可跑形态（如 `npx vitest run tests/`） | 留空 = 没有标准；判据必须**更强**而不是消失 |
| 判据不过的返工卡 | 直接拒绝、把人的退回动作卡死 | 兜底标准 + 响亮说明 | 人工门不能因为机械判据变成死路（本仓既有纪律：硬拦必须配修复路径） |
| 覆盖 agent 结果的理由 | 只卡文本形态（不新增字段） | 结构化 changeReason 全链路 | D-3 的原话选择；理由要可查、可审计，不是靠句式猜 |
| 无锚点的通过 | 直接拒绝整批裁决 | 记「未复核」 | 拒绝会把人的裁决动作卡在机械判据上；未复核已经能挡住归档 |
| 锚点词表 | 另起一套 result 专用词表 | 复用既有词表 + 显式声明差集 | 本仓「两份真相」的老账；差集公开并用例锁住 |

## 技术方案与亮点

需求层面已拍板的结论（细节见 `design/`）：

| 结论 | 亮点（与常规做法的差异） | 可核验指向 |
|---|---|---|
| 判据判「有没有可核验的东西」，不判「够不够好」 | 机械层只堵「一句空话也算验收」，质量判断留给人 | `checkAcceptance` / `checkHowToVerify` 既有分工逐字不变 |
| 占位符词表与回填器同放一处 | 产生占位符的模板与判占位符的判据不再各写一份 | 同一文件内的常量与函数 |
| 回填来源是父卡验收标准里的真实文件 | 不去猜「应该跑哪个测试」，只搬运父卡已经写明的 | 懒展开落库路径 |
| 覆盖必须带理由且原文留档 | 从「静默覆盖」改成「可审计的更正」 | 台账字段可查 |
| 处置模板只有两种合法写法 | 逼出结论（补了还是不用补），而不是「知道了」 | 处置模板判据 |

## 依赖与约束 <!-- serves: FR-1 -->

**依赖**：

- 既有计划期判据 `checkAcceptance` 与验收期判据 `checkHowToVerify`（强依赖，本需求在其上新增占位符一条）。
- 父卡懒展开落子卡的既有唯一落库点（强依赖，回填挂在这里才覆盖全部子卡）。
- 验收单裁决的既有单一实现 `applyVerdicts`（强依赖，规则放这里才能同时覆盖看板与工具两条通道）。
- 既有的可核验锚点词表（弱依赖，复用其共享核心并声明差集）。

**约束**：

- 改动面限于验收标准与卡片质量一片：原型门、归档校验、测试基线不得触碰。
- 工作树里有别的窗口的在飞改动，提交时不得夹带。
- 客户端源码有改动时必须重建 bundle 并看到验证输出。
- 台账字段只**新增**（原文留档、变更理由），不得改既有字段含义。

**接缝约定（与其它窗口）**：

- 另一窗口正在建设的「可核验锚点」词表若与本需求的 result 锚点口径重合，收尾时**并到一处**；
  本需求先在自己的改动面内定义并写明与它的分工，不 import 未提交的文件。
