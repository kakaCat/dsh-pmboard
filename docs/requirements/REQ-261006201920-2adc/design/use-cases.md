# 用例（REQ-261006201920-2adc）

> 本文档面向：产品、测试、验收。每条用例写「谁 → 做什么 → 看到什么」，并给出失败路径。

## UC-1 计划作者提交含占位符的计划 <!-- serves: FR-1 -->

**角色**：写拆分计划的窗口 agent。

**主流程**：

1. 作者在任务表的验收标准里写 `npx vitest run <相关测试文件>` 并提交计划。
2. 计划提交预检逐条跑 `checkAcceptance`。
3. 该条命中占位符判据 → 提交被拒。
4. 拒绝文案点名占位符原文，并说明「换成真实路径/编号」。

**预期结果**：计划无法带着未替换的命令操作数落库。

**失败路径 / 边界**：

- 作者写 `Record<StageKind,string>` 或「断言不含 `<单册>`」→ **放行**（不是命令操作数）。
- 作者写 `npx vitest run tests/x.test.ts` → 放行。
- 计划里没有命令但有可验证断言（既有口径允许）→ 不受本判据影响。

## UC-2 父卡开工展开子卡 <!-- serves: FR-1 -->

**角色**：执行窗口 agent（调 `reqboard_task_run` 触发父卡开工）。

**主流程**：

1. 父卡开工 → 懒展开按阶段生成子卡链。
2. `makeChild` 在落库前用父卡验收标准 + 需求 id + 本卡 id 回填模板占位符。
3. 子卡落库，验收标准里是**具体文件路径**。

**预期结果**：新落库的子卡里尖括号 token 数为 0；父卡标准里点名的测试文件出现在子卡标准里。

**失败路径 / 边界**：

- 父卡未点名任何测试文件 → 回填落到兜底 `tests/`，命令仍可跑。
- 回填后仍有残留 / 遇到词表外 token → **抛错**（响亮失败），不落库半成品。
- 已落库的历史子卡（含带占位符的）→ **逐字节不变**。

## UC-3 验收不通过生成返工卡 <!-- serves: FR-2 -->

**角色**：人（看板或弹框裁决）+ 系统（自动物化返工卡）。

**主流程**：

1. 人对某项判「不通过」并写意见。
2. 系统按该项生成返工规格。
3. 规格构造时跑 `checkAcceptance` + `checkHowToVerify`；不过则按优先级改用来源卡标准或合成标准。
4. 返工卡落库，并继承来源卡的条款引用、原型锚点、裁定引用与体量声明。

**预期结果**：返工卡的标准一定可照着验；卡上带着它服务哪条 FR。

**失败路径 / 边界**：

- 判据不通过且来源卡标准也不可执行 → 合成「修复对象 + 可跑命令 + 期望读数」三段式，仍过判据。
- 验收项**没有来源卡**（需求级项 / 原型对照项 / 裁定对照项）→ 走合成标准，`acceptanceSource='synthesized'`。
- 人的「退回返工」动作**不会被判据卡死**。

## UC-4 人裁决一项只有「通过」两字的结果 <!-- serves: FR-3 -->

**角色**：人（看板或弹框）。

**主流程**：

1. 某项的「实际结果」是 agent 写的两个字「通过」（或「（未附实际结果…待补复核）」）。
2. 人点「通过」。
3. 服务端判结果锚点：无命令 / 路径 / 计数 → **记「未复核」**。

**预期结果**：该项不进入可归档集合；验收单上能看到它是「未复核」而非「已通过」，并知道该补什么。

**失败路径 / 边界**：

- 人补一句 `npx vitest run tests/x.test.ts → 12 passed` → 记「通过」。
- **记录「未复核」不是拒绝**：不阻断人继续裁决其它项。
- 归档被未复核项拦住时，提示语指向「补上实际结果」。

## UC-5 人覆盖 agent 的实测结果 <!-- serves: FR-3 -->

**角色**：人。

**主流程**：

1. 某项已有 agent 实测结果（`resultSource='agent'`），看板把原文预填进意见框。
2. 人**编辑**了这段预填值并点「通过」——构成覆盖。
3. 系统要求给出**变更理由**：看板就地展开理由输入；弹框通道补问一轮。
4. 补上理由 → 覆盖生效：人的文本进 `result`、来源置 `human`、agent 原文进 `resultSuperseded`、理由进 `resultChangeReason`。

**预期结果**：agent 的原始证据**不被静默抹掉**；谁改的、为什么改，台账可查。

**失败路径 / 边界**（D-3 原话：「A. 结构化 changeReason 全链路（推荐）」）：

- 不填理由 → **拒绝该次覆盖**（code `result_change_reason_required`），文案给「可不覆盖 / 或补理由」两条路。
- 人**没改**预填值（点通过没动输入框）→ 不算覆盖，三个新字段一个都不写。
- 重复覆盖 → `resultSuperseded` 保留**最初那次** agent 原文。
- 旧版看板不传理由 → 不报错：覆盖不生效、agent 原文保留、裁决照常记录。

## UC-6 系统缺口项点通过 <!-- serves: FR-4 -->

**角色**：人。

**主流程**：

1. 验收单里有机器报出的缺口项（E2E 缺口 / 孤儿用例 / 三方一致性 / 追溯断链）。
2. 人点「通过」并写处置。
3. 系统判处置是否命中两义模板（已处置 / 确认无需，且给出对象或理由）。
4. 命中 → 放行；不命中 → 拒绝并给出两种合法写法各一例。

**预期结果**：缺口不会被「点一下通过」静默吞掉。

**失败路径 / 边界**：

- 写「好的」「知道了」或留空 → 拒绝。
- 写 `确认无需 E2E：纯函数模块，无外部接口` → 通过。
- 写 `补了 E2E 用例：tests/e2e-x.test.ts` → 通过。
- **普通项**的通过不受处置模板约束。

## UC-7 归档被拦住 <!-- serves: FR-4 -->

**角色**：人（准备验收通过并归档）。

**主流程**：

1. 验收单里存在「已通过但处置为空/未命中模板」的系统项（历史数据或非本通道写入）。
2. 人尝试走验收通过与归档。
3. 放行判据（`isFullyDecided` / `sheetGateStatus`）把该项算作**未裁决**。
4. 归档被拦，页面点名是哪一项。

**预期结果**：归档门读到的系统缺口项处置一律有效——缺口要么被补、要么被明确判定「无需」。

**失败路径 / 边界**：

- 该项被改写为合法处置 → 放行。
- 该项被改为「不可验收」并写原因 → 按既有规则算已裁决（不阻断归档）。
