# REQ-261003203909-55f2 · 子卡阶段模板补充：新段 + 一等声明 + 凭证形态补族

> **TL;DR**：40 个需求、627 张子卡的实战数据证明阶段模板有三处错位——e2e/人工核对/发版
> 反复出现却没段承接（≥10/≥6/≥3 个需求），运维五段永不可达（0 次触发），高频裁剪组合只能
> 手写逃生舱（35 次）。本需求补三段、立一等声明、凭证门补采集族；得到的是「计划声明什么就
> 落什么链」与真实工作分布对齐。

> 立项原话：「dev/integrate/review/test 这个不满足所有内容，需要补充，你调研看看需要补充什么，
> 你可以看所有 session 的内容来判断。」本文档是该调研的结论与落地范围。

```

        现状：35 次手写            现状：16 段中 6 段 0 触发         现状：探针/截图
```

## 一句话目标 + 可证伪判定标准

**目标**：让「计划侧声明什么、懒展开落什么链」与真实工作分布对齐——新增 `e2e`/`manual`/`release`
三段、把高频逃生舱组合固化为一等声明、打通运维段的触发路径、凭证门补「采集族」。

**判定标准（跑什么、看到什么算完成）**：

1. `npx vitest run tests/domain/subtask-template.test.ts tests/subtask-template-acceptance.test.ts tests/stage-boundary.test.ts tests/subtask-contract.test.ts tests/stage-colors.test.ts` → 全绿（新段五个登记点全部有用例）。
2. 新段登记点**类型强制**：`STAGE_SCOPE_RULE` 改为 `Record<StageKind,string>` 后，删掉任一新段的边界规则 → `npx tsc --noEmit` 报错（现状是 `?? ''` 静默落空）。
3. 计划任务表的一等声明字段落地：`reqboard_submit(kind=plan)` 用新字段提交 → `reqboard_decompose` 落库 → `docs/requirements/<REQ>/queue.json` 里父卡带该字段、开工懒展开落出对应链（端到端可复跑）。
4. 复跑台账分析脚本（本调研用的 queue.json 统计）：新增段与组合可不经手写 `stages` 数组触发。

## 边界

**做**（≤3 条）：

1. 新增 `e2e`、`manual`、`release` 三个 stageKind 及全部登记点（标签/验收模板/证据族/颜色/边界规则/脚本 schema 族）。
2. 计划任务表支持**一等声明**（`template` 字段或设计阶段裁定的等价机制），固化高频组合：
   `dev+review`（实测手写 19 次）、`verify` 单段验收卡（3 次）、运维组合（`prepare/run/verify` 等目前 0 次可达）。
3. 凭证门补**采集族**证据形态（探针/截图/基线：凭证 = 采集产物路径 + 摘要），并打通 `prepare/run/change/dryrun/apply` 的触发路径。

**不做**：

1. 不改需求分类枚举（6 类不动）、不动五道人工门、不改凭证门「写入族/结论族」既有判定逻辑。
2. 不动实施链调度/锁/引擎可达性——锁 stale 双跑归 REQ-261003222428-3556，批内并行/死代码归另一窗口的优化需求。
3. 不给 `ui`/`implement` phase 加盲映射（实测 8 张 ui 卡两种形态都有：2 张联调有真实产出、6 张本就裁掉联调——「有没有接口面」仍是计划侧才能声明的事实）；回滚演练、数据迁移、跨仓、事故处置**不新增段**（迁移用 `dryrun/apply/verify` 组合，跨仓维持「另立需求」升级口径，事故处置归护栏）。

## 产品定义

子卡阶段模板（`src/domain/task/SubtaskTemplate.ts`）是父卡开工时懒展开子卡链的**唯一契约起点**：
受控 stageKind 枚举（现 16 个）+ 卡型/phase/side → 段集合的映射表 + 每段的验收模板、证据族、
边界规则。它决定每条实施链「分几步、每步干什么、拿什么凭证过关」。

**问题**：枚举与映射是 2026-09 设计的，40 个需求、627 张子卡的实战数据证明它与真实分布有
三处错位（见「调研证据」）：该有段承接的工作没有段（e2e/人工核对/发版）、该可达的段不可达
（运维五段 0 次触发）、高频裁剪组合只能每次手写逃生舱（35 张父卡显式 stages）。

## 用户与角色

| 角色 | 与本需求的关系 |
|---|---|
| 计划撰写者（agent，人批准） | 拆分计划时声明每张父卡的链；今天只能手写 `stages` 数组，无模板可引用、无段可表达 e2e/人工/发版 |
| 执行子代理（workflow run） | 按段边界规则与验收模板干活；新段的边界规则必须同步登记，否则静默无边界 |
| 凭证门（宿主侧判定） | 按段的证据族验收；采集族缺失导致探针/截图类工作只能挤进写入族或结论族 |
| 验收人 | 按段的证据形态复核；manual 段让「这步归人」从潜规则变成显式契约 |

## 调研证据（40 需求目录 · 627 张子卡 + 全量 notes/reviews/verification 扫描）

### E-1 实际使用分布（queue.json 统计）

- 主力四段：dev 182 / review 185 / test 154 / integrate 94；bug 链 repro/fix/regress 各 3；collect/analyze 各 1。
- **0 次触发**：`probe`/`prepare`/`run`/`change`/`dryrun`/`apply` —— 其中 prepare/run/change/dryrun/apply
  经需求分类**永不可达**（分类枚举只有 feature/bug/doc/refactor/spike/chore，而模板键 research/data/ops
  不在枚举内，是死配置）；spike→probe 名义可达，但实测唯一 spike 需求（deab）全部卡走 doc phase 兜底。
- 结论族健康度：integrate/review/test 有完工结论的比例 85–87%——段本身好用，问题是组合与覆盖。

### E-2 逃生舱是常态不是例外（35 张父卡显式 stages）

| 组合 | 次数 | 典型场景 |
|---|---|---|
| `['dev','review']` | ~19 | 文案/契约/纯函数/常量类卡（事实上的第二默认模板，只能手写） |
| `['dev','review','test']` | ~8 | 无接口可联调的研发卡 |
| `['verify']` | 3（跨 3 需求） | 链尾总验收卡：全量回归 + 浏览器人工核对 |
| `['dev','test']` / `['dev','integrate','review']` | 各 2 | 裁复核 / 裁测试 |
| `skipIntegration` | ≥6 需求逐卡使用 | 「无接口可联调」是高频事实 |

### E-3 无段承接的工作（按证据强度排序）

| 工作类型 | 证据 | 判断 |
|---|---|---|
| **E2E 端到端验证** | ≥10 REQ 的验收系统项「E2E 覆盖」反复判缺口（06fd/8475/b918/a3fb/cecb/3219/1441/8f8b/5d36/a5ef/3766）；1441 整卡「一条真端到端断言当门禁」 | **新增 `e2e` 段**：与 test 段语义不同（test=失败数≤基线；e2e=场景断言全过） |
| **真机/浏览器人工核对** | ≥6 REQ：a3fb t5 整卡人工核对；9e04 多卡「真机需人重载，agent 不擅自重启」；8f8b/a5ef 如实登记「人工端到端未执行」 | **新增 `manual` 段**：「这步归人」显式化，不再塞 verify 或验收材料兜底 |
| **发版/构建门禁** | ≥3 REQ：8475 全需求承认打包/构建/发版无承接；25c6 t4 发版门禁硬塞四段；C-11「发版前必须构建」反复出现 | **新增 `release` 段**：含回滚方式声明（897b/ba52 回滚演练证据并入其验收口径） |
| 数据迁移 | 3 REQ（277d t6 迁移脚本卡、e94a 迁移门、8f8b t5 兼容验证） | 不新增枚举：用现有 `dryrun/apply/verify` 组合 + 打通触发路径 |
| 探针/截图/基线采集 | ≥4 REQ（71be headless 探针、1ab8 四档截图、81d0/ba52 基线采集） | **不是阶段问题，是凭证形态问题**：新增「采集族」并入凭证门 |
| 性能验证 | 仅设计层提及，无独立卡 | 证据不足，不成段 |
| 跨仓 / 事故处置 | 各 2 处 | 维持体系外（另立需求 / 修护栏） |

### E-4 已排除的误改方向

- **不给 ui phase 加盲映射**：8 张 ui 卡中 2 张联调有真实文件产出（前后端接线）、6 张本就该裁——
  「有没有接口面」只能由计划侧声明（2026-09-28 教训：代码猜 = 静默削段）。
- **不删结论族段**：85–87% 完工结论率，健康。
- **integrate 默认段策略**（默认四段 vs 默认三段+计划侧显式声明）证据冲突，列为待裁定决策 D-1，不在需求阶段拍死。

## 功能点

- **FR-1: 新增 `e2e` 段**——端到端场景断言（写/跑真端到端用例），结论族；与 `test` 段（失败数≤基线）语义区分写进验收模板与边界规则。
- **FR-2: 新增 `manual` 段**——承接真机/浏览器人工核对：凭证 = 人工核对记录（核对清单 + 结果 + 截图路径），机器不自动判过。
- **FR-3: 新增 `release` 段**——承接打包/构建/发版门禁：验收含构建戳/版本号断言与回滚方式声明。
- **FR-4: 计划任务表一等声明字段**——提交计划时可引用模板组合（替代手写 `stages` 数组）；与 `stages`/`skipIntegration` 的优先级在设计阶段定死并写进工具 schema。
- **FR-5: 固化高频组合**——`dev+review`（文案契约类）、`verify` 单段（链尾验收卡）、运维组合（prepare/run/verify 与 dryrun/apply/verify）成为可引用的一等模板，消除死配置（research/data/ops 键经此可达或被显式清理）。
- **FR-6: 凭证门补「采集族」**——探针/截图/基线类子卡的凭证 = 采集产物路径 + 摘要（区别于写入族的 mtime 判定与结论族的 completed 判定）。
- **FR-7: 新段登记点类型强制**——`STAGE_SCOPE_RULE` 改 `Record<StageKind,string>`（漏登记 = 编译错）；登记点清单（枚举/标签/验收/证据族/颜色/边界规则/schema 族/eval fixtures）沉淀进 `docs/knowledge/conventions.md`。

## 迁移与兼容

- 存量台账零改写：stageKind 是新增枚举值，旧卡原样渲染（客户端 `STAGE_LABELS` 单点自动跟随，未知值回落原词不崩）。
- 模板映射调整只影响**新开工**的父卡（懒展开在开工时）；在跑的链不受影响。
- 回滚路径：新段与一等字段均为纯增量，回滚 =  revert；无数据迁移。
