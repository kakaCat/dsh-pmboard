# 需求说明（REQ-261004222448-292a 需求详情页重构：从「证据面」改为「工作汇报」）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。
> 本文替代此前按「测评证据面 + 排版」写的版本（那份写歪了：把附件当主体）。

## TL;DR

- **这是什么**：把需求详情页重做成一眼能读懂的**工作汇报**——用汇报的**读法**组织（为何做 → 解决什么 → 怎么做 → 做到哪 → 结果如何），但**它不是一份报告**（不加封面、不加章节编号、不做导出）。
- **为什么现在做**：现在的详情页是「证据面」——6 个 Tab 按数据来源堆着，而一个项目最先被问的六句话几乎答不出来（为何做 / 解决什么 / 思路 / 取舍 / 边界 / 结果）。用户的原话说明了正确口径：**聊天是会议记录、文档是确定文档、DAG 是工作步骤、token 是项目花费，详情页是工作汇报**。
- **做完得到什么**：打开一屏知道「这个项目是什么、为什么、到哪了、结果如何、花了多少」；想深挖再展开佐证；页面不慢、刷新不重置、看不到的东西会明说"没有"。

## 产品定义

**一句话**：需求详情页 = **工作汇报**。主干回答「为何做、解决什么、怎么做、做到哪、结果如何」；聊天/文档/DAG/提示词是**佐证**；token 是**花费**。

| 痛点（实测） | 本次解决 |
|---|---|
| 一个项目最先被问的六句话答不出来（为何/问题/思路/取舍/边界/结果） | 主干六条常驻（FR-1～FR-5） |
| 附件抢了主体的位置：6 个 Tab 按数据来源堆着 | 附件降为「默认收起、点开才看」（FR-6～FR-9） |
| 打开一屏读不出"现在怎么样" | 首屏：状态 + 一行结论 + 缺口 + 入口行（FR-3、FR-4） |
| 内容太多、一页全铺 → 慢，且读不完 | 分层取数 + 分页 + 正文点开才取（FR-11） |
| agent 跑动时页面反复重置 | 局部更新（FR-11） |
| 看不到"它到底被告知了什么" | agent 运行块：提示词组段/被裁 + 注入来源与后果 + 上下文（FR-9） |
| 数字不可信：不可得时显示 0 | 诚实空态三态（FR-12） |

**与现状的区别**：

| 维度 | 现状 | 本次之后 |
|---|---|---|
| 页面性质 | 证据面（Tab 堆数据） | 工作汇报（汇报读法组织） |
| 组织依据 | 数据来源（概览/执行/时间线/归档/追溯/Token） | 读者的六个问题 |
| 主干 | 无落点 | 六条常驻 |
| 附件 | 与主体混在一起、部分常驻 | 默认收起，点开才取 |
| 取数 | 整页一次取全 + 整页重绘 | 分层取数 + 局部更新 |
| 空态 | 留白 / 显示 0 | 三种空态各有说辞 |

### FR-1: 主干四条（为何做 / 解决什么 / 实现思路 / 范围边界）

**功能描述**：页面常驻一段「项目是什么」的摘要，四条各自**一句话到一小段**，点开回到原文：

| 条 | 内容 | 来源 |
|---|---|---|
| 为何有这个项目 | 由来与触发场景（谁在何时因什么提出，含源窗口与立项方式） | 需求文档 + 立项评论/弹框作答 |
| 解决什么问题 | 问题定义 + 现状痛点 + 影响面/收益预期 | 需求文档「产品定义」节 |
| 实现思路 | 方案主线（一段话）+ 关键模块划分 | 设计文档「架构 / 接口」节 + 计划 summary |
| 范围边界 | **明确不做什么**（防"以为没做"） | 需求文档「边界」节 |

**抽取纪律**：主干来自**从文档抽取的结构化摘要**，不是把全文搬上来；**抽不到时如实显示「文档未提供该节」**，不许编。

**判定**：渲染断言锁定四条各有一句摘要 + 「点开原文」入口；构造"文档缺该节"的标本 → 显示「文档未提供该节」而非空白或编造。

### FR-2: 关键决策与取舍

**功能描述**：列出这条需求做过哪些取舍、否掉了什么、为什么；来源两处：① 文档「关键决策与取舍」节（见 FR-13）；② **人工门往返留痕**（计划被退回的理由、验收意见、文档变更说明）。

**判定**：至少一条来源有内容即渲染；两处都没有时显示「未见决策留痕」。

### FR-3: 做到哪了（阶段 + 一行结论 + 操作条）

**功能描述**：常驻一屏内给出：8 态阶段条 + 当前阶段**停留时长** + 距上次变更；**一行结论**：在跑什么 / 谁在跑 / **几件事等人** / **下一步谁动手**；以及**操作条与跳转入口**。

**操作条（**现有能力，重构不得回退** —— 2026-10-04 用户复核原型时指出原稿把它们丢了）**：

| 元素 | 说明 |
|---|---|
| `← 看板` | 返回看板（现有） |
| **本阶段合法动作按钮** | 按当前状态给出：立项取消 / → 下一阶段 / 退回上阶段 / 批准计划 / 退回计划 / 验收通过 / 退回返工；**每个按钮说清后果** |
| **等人处理的提示** | 有挂起确认时显式标出（如「去确认设计 v2（待人处理）」）与**被拦住的写路径**（`REQBOARD_CONFIRM_PENDING`） |
| **窗口跳转按钮** | 席位表里**每个窗口**一个可点按钮（owner / worker / observer 带角色）；已归档会话仍可点（先恢复再打开）；跳转失败给明确原因，不静默 |
| **只读态** | 终态（archived / canceled / done）一律只读：只留 `← 看板`，不渲染任何动作按钮 |
| **observer 席位** | 只读：不渲染写动作（保留跳转与查看） |

**为什么**：这是打开页面最高频的问题，成本极小（一行字 + 一行按钮），却能让"证据面"变成"工作汇报"；而**按钮是页面唯一能"做事"的地方**，丢了它页面就退化成只读展示。

**判定**：① 首屏（1200×800，不滚动）能看到阶段条、一行结论与操作条；②「几件事等人」的数字与 FR-4 缺口条数一致；③ 席位表里每个窗口各有一个 `jump-session` 按钮（含角色标注）；④ 终态标本下动作按钮数为 0 且无空壳容器。

### FR-4: 缺口清单

**功能描述**：列出「该有而没有」的项，按严重度排序（🔴 阻塞 / 🟡 待处理 / ⚪ 观察）：未被任何任务接收的条款、当前阶段必备产物未登记/未确认、验收材料缺失、归档清单未对账、条款→设计→任务→测试的断链、挂起确认未作答。首屏放前 3~5 条，完整清单在块内；**无缺口时明确显示"无缺口"**，不画空表格。

**判定**：构造"有挂起确认 + 有未接收条款"标本 → 两条都出现在首屏且不被折叠；构造全通过标本 → 显示"无缺口"一行。

### FR-5: 结果与成效

**功能描述**：终态（验收/归档后）给出：验收结论（通过 / 返工后通过）+ 逐项结果（通过数 / 不通过项）+ **遗留问题与后续**（未做的、转入别的需求的、已知限制）。未到验收段时显示解释性空态，不画空表格。

**判定**：终态标本显示结论 + 逐项 + 遗留；在途标本显示"尚未到验收段"并说明何时出现。

### FR-6: 附件 · 会议记录（一条流）

**功能描述**：**像微信那样的一条连续时间线，不按窗口分组**：

- 只取「人说的话」+「agent 的**文本回复**」；**排除** `tool/call`、`tool/result`、推理过程、`run_code` 与"正在读取文件…"这类过程叙述；
- **机器事件作为「系统消息」混排在同一条流**（灰底小字、居中、不可回复）：阶段推进、计划退回、窗口交接、中断与恢复、验收裁决；
- 每条带时间与 actor（人 / agent + 窗口码）；默认最近 20 条，向上滚动取更早；支持**页内关键词检索**。

**判定**：渲染产物中不含工具调用/推理类事件；系统消息与人类消息在同一容器内按时间排序；分页参数生效。

### FR-7: 附件 · 确定文档 + 核验 + 门禁裁决留痕

**功能描述**：三部分合一：

- **文档清单**：类型 / 路径 / 登记时间 / 可打开（正文点开才取）；
- **核验**：验收单逐项（标准 / 实际结果 / 证据 / 来源 agent\|human / 需人工 / 意见 / 裁决）；
- **门禁裁决留痕**：每道人工门**谁批的、何时、什么方式**（弹框 / 看板 / 文字 evidence）、**退回理由**、改版变更说明、旧批准作废；归档（目录 / 清单 / 合并去向 / 索引条目 / 说明书更新点 / 清单对账）。

**判定**：确认方式与确认人在渲染中出现；退回理由可读；文档正文请求只在点开时发生（用请求计数断言）。

### FR-8: 附件 · 工作步骤 DAG + 每步执行结果

**功能描述**：DAG 给出层级 / 依赖 / 每节点状态（几层、几张卡、并行度）；**每个节点挂执行结果**：谁做（窗口码）、耗时、成败、产出条目、汇报四要素（summary / completed / filesChanged / nextStep）；子卡链（dev → review → test）与关键路径。

**判定**：节点详情默认不在首屏请求里（点开才取）；失败与零产出节点有显式标记。

### FR-9: 附件 · agent 怎么跑的

**功能描述**：三部分：

- **系统提示词**：本次组了哪几段（逐段列名）、每段字符与估算 tokens、**被预算裁掉的段**、每段正文（点开才取）；
- **注入留痕**：时间 / 来源（闸门 · 节点 · 轮次）/ 窗口 / **后果（真投递进会话 vs 只留痕）** / 命中片段逐段列名 / 字符 / **被裁片段** / 正文；未留痕的类别如实显示「未留痕（采集缺口）」；
- **上下文**：每回合上下文水位、压缩次数与策略、节点隔离留痕（替换 / 跳过 / 拒绝）、输入包大小。

**判定**：每段正文可展开（`<pre>` 非空）；后果列存在（不把"只留痕"当成"已投递"）；上下文块在配置关闭时不渲染而非显示 0。

### FR-10: 花费（按阶段）

**功能描述**：**以「阶段」为主视图**回答"每个阶段花了多少"（用户原话：token 应该是每个阶段花了多少，之后可以是优化的数据）：

| 列 | 说明 |
|---|---|
| 阶段 | 需求分析 / 设计 / 拆分 / 实施 / 验收 / 归档 |
| 调用 / 输入 / 输出 / 合计 / 占比 | 该阶段的量与占比（实施段通常是最大头） |
| **每次调用均** | 该阶段平均单次消耗——**跨阶段横向可比**，用于发现"上下文重复" |
| **缓存命中** | 该阶段缓存命中率——命中低 = 重复上下文多 |

**再往下钻**：阶段 → 任务执行 → 单次调用。**再往上汇总**：本条需求合计 + 墙钟 / 窗口数 / 轮次 / 零产出执行。

**可优化数据（自动推导，本条的第二个用途）**：给出可行动的结论，而不是只摆数字，例如
「实施段占 54% 且缓存命中最低（59%），每次调用均是需求分析段的 2 倍 → 子卡间上下文重复度高，建议节点隔离/输入包裁剪」
「设计段 9 次调用中 2 次是 v2 补充重跑 → 一次写全可省 ≈76K」
「零产出执行 1 次（10m）→ 空转成本 ≈42K，建议给 review 段加"无产出即停"」。
每条优化点必须**写明依据的数字**（哪段、多少、与谁比），不做无凭据的建议。

**可得性三态**：快照齐（正常）/ 快照缺但可兜底（标「部分数据」+ 缺哪段 + 为下界）/ 完全不可得（「无 token 快照」）；**归档后默认不展开**。

**判定**：① 阶段视图的"占比合计"与总计一致；② **每次调用均**与缓存命中两列存在（缺一即不满足"优化数据"）；③ 三态各一条渲染断言，且"不可得"态下页面**不出现 `0`**；④ 优化点条目均含可核对的数字。

### FR-11: 分层取数与性能

**功能描述**：八条具体做法（2026-10-04 用户裁定：**附件以 Tab 承载**——Tab 是对的）：

1. 首屏只发摘要（沿用 `/state` 只发摘要），进详情不拉全量；
2. **所有内容都是 Tab，且同级**（2026-10-04 用户裁定：「为何有这个项目」这一系列也是内容，就该和附件一样是一个 Tab）：
   **常驻头部**只留「现在怎么样 + 我该做什么」＝ 结论头 + 操作条 + 状态带（做到哪了 / 缺口清单 / 结果与成效）；
   下面是**六个同级 Tab**：**汇报**（为何做 / 解决什么 / 实现思路 / 范围边界 / 关键决策与取舍 / 技术方案 / 亮点与差异+成果清单，默认选中）· **文档** · **DAG** · **对话** · **Token** · **提示词**。
   **已进 Tab 的内容不在默认页重复展示**——例如「花费」只属于 Token Tab（Tab 角标已给 1.84M）；**同一个数字不在两处出现**；
3. **Tab 懒加载**：**切到某个 Tab 才请求该 Tab 的数据**；同一时刻只渲染一个面板（**不允许"渲染全部再 CSS 隐藏"**——那正是"内容多 + 性能差"的老路）；
4. Tab 标题带**角标关键数字**（如「对话 42」「Token 1.84M」），让默认页不切 Tab 也能看出"有多少"；
5. 每个 Tab **独立取数、独立缓存、独立刷新**（不是"一个巨型请求换整页"）；
6. 长列表（会议记录 / 注入留痕 / 执行记录）**分页**（"加载更早"按钮或滚动到顶再取），默认只渲染最近 N 条；
7. **一律铺开，不做内层滚动**（2026-10-04 用户裁定）：文档清单（15 份）、门禁裁决（5 道）、验收单（12 项）、按阶段 Token 表、**提示词正文块**全部逐行/整段铺开；
   长了就用**页面滚动**，或用外层 `<details>` 收起（点开才显示）。理由：内层滚动条会**藏住内容**（原稿把 6 张任务卡压成「tasks/ 4 份 + 滚动」，看上去只有 6 份文档）、
   也会让"有多少"变成**不可数**——与本设计"缺口/数量必须可数"的目标直接冲突。
   **分页 ≠ 内层滚动**：分页有明确计数与"还有多少"；**限高滚动条一律不要**（包括提示词正文块）；
8. **正文一律点开才取**（提示词正文、文档原文、验收证据）；点开后**整段铺开**，不再限高。
9. **聚合在服务端算**（token 汇总、覆盖度、缺口判定），前端不做全量遍历；**局部更新**：台账变更只替换受影响的那块，不整页重绘——滚动位置、展开态、阅读位置由此天然保住。

**判定**：① 首屏请求数 ≤ 1 且不含正文；② **切 Tab 才产生该 Tab 的请求**（请求计数断言）；③ 未激活的 Tab 面板**不在 DOM 中渲染**（或断言其内容为空）；④ 长列表首屏渲染条数 ≤ N；⑤ 渲染断言：SSE 更新后滚动位置、折叠态不变；⑥ **无内层滚动断言**：Tab 面板内不存在 `overflow: auto|scroll` 的滚动容器（列表只受页面滚动约束），且文档清单行数 == 台账实际文档数。

### FR-12: 诚实空态与降级

**功能描述**：所有"取不到"都必须有说辞，三类分开：

| 情形 | 页面怎么写 |
|---|---|
| 未采集 | 「无留痕 / 未采集」+ 原因（端口未装配 / 需求早于该功能）——**不写「0 条」** |
| 不可得（降级） | 「不可用」+ 原因（文件 ENOENT / 服务 unavailable）——与"有但为空"区分 |
| 文档未提供该节 | 「文档未提供该节」——**不编、不留白** |

**判定**：三态各一条渲染断言；反例断言：页面任何位置不得用 `0` 表示"未知/未采集"。

### FR-13: 文档模板新增「关键决策与取舍」「技术方案与亮点」两节

**功能描述**：在 `templates/design/*.md`（至少 `architecture.md`）与 `templates/brainstorming/*.md`（按类型）加入两节：

- **「关键决策与取舍」**：做了哪些取舍、否掉了什么、为什么；
- **「技术方案与亮点」**：技术栈与关键依赖、模块划分、用到的设计模式、关键实现手法、攻克的难点、**与常规做法的差异**（每条差异要有可核验的指向：文件 / 测试 / 评审）。

页面 FR-2、FR-14、FR-15 直接抽取这两节。**这两节必须由人/agent 在写文档时填**——页面不替它编。

**判定**：模板文件含两节标题；新建需求产出的文档包含两节；页面能从两节抽出摘要；缺节时页面显示「文档未提供该节」。

### FR-14: 主干 · 技术方案

**功能描述**：一段「怎么做的（工程视角）」摘要，包含：

| 项 | 内容 | 来源 |
|---|---|---|
| 技术栈 | 语言 / 框架 / 运行时 / 关键依赖（含为什么选它） | 设计文档「技术方案与亮点」节 |
| 模块划分 | 这次动了哪几个模块、各自职责 | 设计文档「架构」节 + 改动文件清单 |
| 设计模式 | 用了什么模式、解决哪个问题（**写不出就写"未使用"，不硬凑**） | 设计文档「技术方案与亮点」节 |
| 关键实现手法 | 非显然的几处实现（为什么这么做） | 同上 + 代码地图/知识层 |

**纪律**：这一条是**给工程读者看的"怎么干的"**，不是营销文案；**没有的内容显示「文档未提供该节」**。

**判定**：四项各有摘要或显式"未提供"；`设计模式` 为"未使用"时也照实渲染。

### FR-15: 主干 · 亮点与差异 + 成果清单

**功能描述**：回答用户的原话要求——「让我知道你干了什么、怎么干的，比普通的有什么不同，**你是否在应付我的需求**」。分两块：

**① 亮点与差异**（每条 = 一句差异 + **证据指针**）

| 字段 | 说明 |
|---|---|
| 差异点 | 与"常规/默认做法"相比，这里不同在哪 |
| 为什么 | 不这么做会怎样（代价 / 风险） |
| **证据指针** | 指向可核验处：改动文件路径、测试用例、评审记录、台账留痕 |

**② 成果清单**：这次实际改了什么（模块 / 文件数 / 新增能力 / 变更的能力），由改动记录与产物清单汇总得出。

**反应付机制（本条的核心）**：**亮点必须指得出证据**——指不出来就渲染「未提供证据」，**不允许页面上出现无法核验的"亮点"或形容词式自夸**。这样读者可以自己判断"这是不是应付"，而不用信任文案。

**判定**：构造"亮点无证据指针"的标本 → 渲染「未提供证据」；构造"缺该节文档"的标本 → 渲染「文档未提供该节」；成果清单的条数与改动文件清单一致。

## 接口与数据契约

| 项 | 契约 |
|---|---|
| **存储形态（先弄清，2026-10-04 核实）** | 详情页的数据**跨三处**：① **需求台账**——支持双后端 `json`（分片，默认）/ **`sqlite`**（`SqliteRequirementStore`，设置里切、**重启生效**、切换过人工确认门）；② **任务 DAG**——每个需求目录的 `docs/requirements/<REQ>/queue.json`；③ **留痕**——`~/.dsh/state/prompt-injection-log.json` 与 `node-isolation-log.json`（ring buffer） |
| **双后端一致性（硬约束）** | 因为台账后端可切换，**任何新增读取都必须在 `json` 与 `sqlite` 两条实现上语义一致**（走同一 `RequirementStore` 端口 + 共享用例）。新字段要同时落 `sqliteSchema` 与分片格式，并给出迁移/降级路径；**不许只实现一条腿** |
| 首屏 | 复用现有摘要接口（`/state` 的摘要字段）+ 详情按需取全文；**首屏不取正文** |
| 块级取数 | **每个 Tab 一个只读端点**，切到才请求；各自可分页；沿用既有「`available=false` 降级」纪律 |
| 会议记录 | 从会话事件抽 `user/message` + `assistant/message` 的**文本块**（现有 `SessionProbeAdapter` 已有 `snapshotEvents()` / `persistence.open→read()` 两条读法）；系统消息来自状态事件 / 交接 / 中断 / 人工门留痕；**排除工具与推理事件** |
| 主干摘要 | 从需求文档「产品定义 / 边界」与设计文档「架构 / 关键决策与取舍」抽结构化摘要；**抽取失败 → 「文档未提供该节」**；**读时算、不落库**（与现有 `systemPrompt.assemble` 同款） |
| 新增留痕字段 | 注入留痕补 `origin`（gate-h3 / dive-node / dive-round）+ `delivered` + `text`（正文，单条 ≤8 000 字符，超出截断并标注）；**旧条目缺字段 → 显示"来源未知 / 内容不可得"** |
| 模板 | 新增「关键决策与取舍」「技术方案与亮点」两节（设计 + 需求模板）；**不改既有节名**，只新增 |
| 兼容 | 旧需求（无留痕 / 无快照 / 文档缺节）全部走显式降级；台账 `queue.json` 结构不变 |

## 非功能需求

- **一屏定调**：首屏（1200×800）必须能答出「是什么 / 到哪了 / 卡在哪 / 缺什么」。
- **诚实**：三类空态各有说辞；禁 0 冒充、禁留白、禁编造摘要。
- **性能**：首屏请求数 ≤ 1 且不含正文；长列表分页；聚合在服务端。
- **稳定**：局部更新；刷新不丢滚动 / 展开态 / 阅读位置。
- **可跳转**：文档、会话（现有窗口跳转入口保留，不额外扩展）、看板。

## 边界（不做什么）

1. **不做成"一份报告"**：不加封面、不加章节编号、不做导出报告页、不做"一键生成汇报文档"——要的是汇报的**读法**，不是汇报的**形态**。
2. **不做测评证据展示**：轨迹表 / 六维结论 / 终态对账 / 必经序列归「测评证据对外接口」（另立需求）。
3. **不搬会话全文与工具日志**：会议记录只留人机文本往返；工具调用、推理、过程叙述一律不进页面。
4. **不动台账数据模型与状态机**：只新增注入留痕字段；不改 `queue.json` 结构、不改五道人工门语义。
5. **不重做 DAG 画布与追溯矩阵**：只搬家与补挂执行结果，不重写图形算法；不做移动端适配（只做窄/宽两档）。

## 验收标准（整体，可跑）

1. `pnpm test` 全绿；新增渲染断言覆盖 FR-1～FR-5、FR-12、FR-15 的文案与三态。
2. 首屏性能断言：进入详情**首屏请求数 ≤ 1 且响应不含文档/提示词正文**（请求计数断言）。
3. 长列表断言：会议记录 / 注入留痕默认渲染条数 ≤ N，滚动后追加。
4. 稳定断言：模拟一次 SSE 更新后，滚动位置、展开态、阅读位置不变。
5. 会议记录口径断言：渲染产物中**不含** `tool/call`、`tool/result`、`reasoning`、`run_code` 字样；系统消息与人类消息同容器按时间序。
6. 诚实空态断言：三类空态各一条；且"未知"不得渲染为 `0`。
7. 模板断言：设计模板与需求模板含**「关键决策与取舍」「技术方案与亮点」两节**。
8. **反应付断言**：亮点条目缺证据指针时渲染「未提供证据」；构造"形容词式亮点"（无指针）标本 → 断言页面不把它当亮点展示。
9. 渲染探针（仿 `scripts/list-responsive-probe.mts`）在**两档宽度 × 在途/终态**下断言：无横向溢出、首屏四问可答；退出码非 0 即失败。

## 依赖与约束

- **重档依据**：动数据契约（注入留痕新增字段）、动文档模板、动取数架构（分层取数 + 局部更新）→ **不走轻档**。
- 可复用：既有 `injection-log` / `IsolationTraceFile`（环形留痕 + 原子写）、`open-doc`、`req-detail-store`（按需取数）、`dag/view-state`（视图状态）、`conversation-progress`（会话头部档）。
- 设计参照（原型，非实现依据）：`prototype/detail-refactor.html`（整页稿）；内容清单：`notes/content-inventory.md`。
- 待 design 阶段定：缺口判定项最终清单；会议记录与注入留痕的默认条数；Token 下钻层级；主干摘要的抽取方式（规则 vs 模型）。
