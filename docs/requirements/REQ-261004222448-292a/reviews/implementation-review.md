## 二、主要发现与处置

1. **【真缺陷·已修】两个评论框撞车** → 头部与对话面板各渲染一个 `[data-role="comment-input"]`，
   而提交与草稿都按「第一个」取值 → 在对话面板里打字点发送会**静默不提交**。
   处置：按被点按钮所在的表单取值 + 草稿按表单分槽（切走再切回也不丢）。
2. **【设计冲突·已化解】设计门禁要求每个二级标题带 `serves`，而页面按字面节名抽取** →
   抽取端改为「剥装饰后按前缀匹配」（H1 仍只认全等），并补了真实形状的用例；
   另发现模板里那一节的真实标题是「目标与总体方案」而抽取端写的是「架构」→ **加写死的别名表**
   （这处缺口此前会让「实现思路」对任何真实文档都抽不到设计侧内容，且不报错）。
3. **【计划漏项·已补】六条端点里的 `prompts` 查询没有任何卡承接**（接线卡只接线、前端卡只渲染）→
   在接线卡内补齐并声明。
4. **【守门过严·已修】端点 `:id` 校验自写的正则比仓内唯一判据更严** → 存量短 id 需求会在六端点上
   一律 400。处置：改用 `isRequirementId`（它同时是路径穿越防线）。
5. **【口径冲突·已裁】「几件事等人」**：契约注释写「红条数」、需求判定写「缺口条数」→ 按**需求条款**
   统一为缺口条数，两个口径都钉在用例里防后人误改。
6. **【两处设计口径未落地·已声明】**：① 在途态 Tab 栏落在首屏之外（取设计首屏判定集的窄口径）；
   ② 窄档「三格退化为单栏」未加 `@media`——强推会让 900 档的缺口格掉出首屏，与「首屏答出卡在哪」
   直接冲突，两口径冲突时取产品判据。
7. **【卡面要求被有理由拒绝】**：要求让 `renderProcessFold` 从死代码变被调用。它需要 `StageDetail`
   （artifacts/timeline/tasks），而提示词端点的响应没有这些字段；拿空数据喂它会把每条动作算成
   「未见记录」= 用缺数据**伪造否定结论**。处置：把它的三段内容与标记迁进提示词面板，不调用它。
8. **【既有红·未掩盖】**：全量套件 74 条失败（开工前 81 条），逐条可在开工前提交上复现；
   单文件 400 行的尺寸门禁开工前就是红的（28 个历史超限文件），本次让清单变长但未改变其状态。
   两者都写进了验收证据，没有"顺手修"也没有藏。
