为何有这个项目

由来与触发场景文档

背景：验收单只能「整体通过 / 整体退回」，单项有问题就得整轮重来。

触发：逐项返工时人要手工建卡，意见只留在评论里跟不走——本仓最近 3 次验收都出现漏项与责任不清。

解决什么问题

问题定义 · 影响面文档

问题：单项不通过时，无法把「意见 + 责任卡」跟着返工走，验收信息散在评论里。

影响面：所有走验收段的需求（本仓在此之前的 6 条需求里 4 条返工过一次）。

收益预期：返工不再需要人工建卡；验收意见可追溯。

实现思路

方案主线（业务视角）文档

主线：驳回 → 建卡 → 回流，三段直线，不做状态机之外的流程编排。

① 前端驳回面板逐项收意见；② 服务端按意见生成返工卡并挂到原任务下；③ RTM 收到卡状态变更后重算覆盖度。

不改什么：不动台账模型、不动五道人工门语义——只新增一个卡关系与两次产物登记。

范围边界

明确不做什么文档

不做：① 多级审批；② 跨需求返工合并；③ 验收单模板自定义；④ 返工卡的自动指派策略（仍由人 / 链决定）。

为什么划这条界：本需求只解决"单项驳回能带着责任走"；其余三项会把验收段变成流程编排，收益不成比例。

来源：requirement.md「边界」节 4 条　点开看原文 →

关键决策与取舍

否掉了什么、为什么人工留痕节新增

取舍 1：返工卡挂到原任务下（而非新建父卡）——追溯清晰 vs DAG 会变深。选前者，理由是"责任卡"必须唯一。

取舍 2：意见写进卡字段（而非写进评论）——可被 RTM 统计 vs 改动面更大。选前者。

被退回一次：计划 v1「粒度太细」→ 按子卡链模板重拆为 dev / review / test 三段（22:56 → 23:02）。

技术方案

栈 / 模块 / 模式 / 手法文档节新增

技术栈：TypeScript + 手写 HTML 字符串模板（无框架）+ Canvas DAG；测试 vitest。选它的原因：与既有插件一致，避免为一张面板引入框架依赖。

模块划分：client/views/acceptance/sheet.ts（驳回交互）· domain/requirement/rework.ts（返工卡规则）· application/rtm/（覆盖度回流）。

设计模式：策略（三种驳回动作可插拔）· 观察者（RTM 在卡状态变更时收到通知）。

关键手法：子卡用 parentId 反查、父卡不存子卡列表——单一事实源，避免父子双向写。
