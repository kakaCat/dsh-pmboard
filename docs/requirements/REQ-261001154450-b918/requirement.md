## 产品定义

**验收纪律**：人工裁决必须留下"看到了什么"，"通过了但没记"不是裁决，是盖章。

**收尾闭环**：需求从"代码交付"到"知识沉淀 + 材料归档"是一条链；缺最后一环就不算完成，且要在看板上看得出来。

**自动化优先**：批准计划就是把骨牌推倒，链路自己跑；人肉 `move` 只作为异常路径的补救手段。

**实测证据**：本需求所有"通过"结论必须由命令输出/文件内容复现，禁止"应该没问题"。

## 功能点

**FR-1: 验收通过必须附实际结果，占位文案不得计入通过**

通过路径在无用户文本时不得静默降级：该项记为未复核（`unverified`），需求级"全通过"判定必须排除未复核项。

**FR-2: 需求级系统项通过必须带书面处置**

系统项（缺「怎么验」/E2E 缺口/追溯断链等）裁决为通过时，意见必须非空；否则整批拒绝并说明缺哪一项的处置。

**FR-3: 计划批准后自动投递一次实施链**

`plan.approvedAt` 落章后自动触发一次投递（无需 agent 再调 `reqboard_task_run`）；未装配推进器时如实报 `dispatched:false + reason`。

**FR-4: 批量关闭节流的拒绝文案给出可执行指引**

节流命中时返回剩余等待秒数与合规路径（等待后可关 / 单次只关一张 / 正确的批量入口），让 agent 不必猜 `sleep 62`。

**FR-5: 陈旧挂起确认自动失效并可显式作废**

挂起确认有 TTL，过期不再拦写路径；未作答时可通过取回执入口获得"过期/作废"结论与恢复指引。

**FR-6: 归档材料未提交时不得视为收尾闭环**

需求 archived 但缺 `kind=archive` 产物时，状态与看板必须显示"收尾未闭环"（红），并提供下一步指引；不出现完成态观感。

**FR-7: 计划覆盖表必须机器可解析并落库为 requirementRefs**

提交计划时校验覆盖表可解析；落库后每张卡 `requirementRefs` 非空，FR→任务链无断点；解析失败即拒绝（响亮失败）。

**FR-8: 规范条目的期望必须当前可达或显式声明基线**

新增/修改的 C 条目其「期望」必须能机器判定且当前可达，或在条目内显式声明基线豁免（如"与 HEAD 基线对比零新增错误"）；不可达期望在 `kb:check` 被打回。
