# 用例设计（REQ-261007133149-0716）

> 用户与角色见 [requirement.md](../requirement.md) 的「用户与角色」。本文件写**用例**：
> 谁、在什么场景、走哪几步、看到什么。所有用例都按"agent 少读代码、少犯错"这条主线组织。

## UC-1 改一个组件的外观（窗口 agent · 主线用例） `serves: FR-1, FR-2`

**场景**：人给一句「详情页卡片描边再淡一点」。

1. agent 打开 [anatomy.html](../prototypes/anatomy.html)，找到目标组件卡（例：`head 常驻头部`），
   读到三样：DOM 根、它的分片文件、**改它时不必读**的行段清单。
2. 只读该分片（约 100~250 行）+ 一条契约，改取值（本例：卡的描边令牌）。
3. 跑判据：`pnpm build:client` → `npx tsx scripts/report-style-snapshot.mts --write`（外观确实变了，
   显式更新基线）→ 逐组件报告显示**只有目标组件**的键变化。
4. 人看 diff：报告里"哪个组件哪条属性变了"一眼可见。

**看到什么**：改动只影响目标组件；如果无意间影响到别的组件，快照的逐组件报告会当场点名。

**边界**：如果目标外观其实写在 `shared.ts`（口径处处相同的那类），地图会指到 `shared.ts`
——那时改的是"所有卡的统一口径"，必须重跑**全部**面板的快照（不是只跑一个面板）。

## UC-2 新增一个 Tab 面板（窗口 agent） `serves: FR-4`

**场景**：要加一个「成本」Tab。

1. 在 `panels/` 下新建 `cost.ts`，实现 `Panel` 接口（`key/label/icon/badge/render`）。
2. 在 `REPORT_TABS` 注册表里加一项（**唯一清单**）。
3. `pnpm typecheck`：漏实现任一成员 → 编译期红，当场发现。
4. `npx vitest run`（契约用例）：键重复 / 顺序错 / 未知键回落行为 → 用例红。
5. 取数端点名自动同源（不再需要手改第二份清单）。

**看到什么**：加一个 Tab 只动"面板文件 + 注册表一处"；不再有"漏改第二处清单导致取不到数"。

**边界**：本次**不做**目录自包含（样式/标本/用例同目录，已落 D-5 排除）；新增面板的样式仍按
UC-1 的规则落到 `panels/<key>.ts`。

## UC-3 改外观（人 · 复核视角） `serves: FR-3, FR-5`

**场景**：人要判断"这次重构是不是真的没动外观"。

1. 跑 `npx tsx scripts/report-style-snapshot.mts --check`。
2. 读逐组件报告：`键数 / 不同键数`；不同键数全 0 = 外观零变更。
3. 若某个组件有差异 → 报告直接给 `组件 · 选择器 · 属性 · 基线值 → 现值`，不需要人去翻 CSS。

**看到什么**：零变更这件事有**读数**，不靠提交者自述；有差异也能一眼定位到组件。

## UC-4 分片越界 / 判据变红（窗口 agent · 失败用例） `serves: FR-2, FR-5`

**场景**：agent 图省事，把 `verify` 的选择器写进了 `panels/docs.ts`。

1. `npx tsx scripts/report-style-ownership.mts` → 退出码 1。
2. 输出点名：`分片 panels/docs.ts · 选择器 .dsh-pm-rtm-… · 依据：它属于 verify`。
3. agent 把它挪回 `panels/verify.ts`，重跑 → 退出码 0。

**看到什么**：越界在**提交前**被拦；而不是等人看页面发现"文档 Tab 里长出了验收的样式"。

**边界**：公共件（按钮 / 提示文字 / 芯片）走**逐条带理由**的白名单；不接受宽泛豁免。

## UC-5 回滚分片（窗口 agent · 安全网） `serves: FR-6`

**场景**：分片过程中发现某条规则搬错了、快照红。

1. 用拼接产物（按固定顺序 join）覆盖 `report.ts`，删掉 `report/` 目录。
2. 跑三条判据：`npx tsx scripts/req-report-probe.mts`、`npx vitest run`（页面套件）、
   `npx tsx scripts/report-style-snapshot.mts --check`。
3. 三条全绿 = 与改造前逐字等价。

**看到什么**：回滚是**机械的**（拼接 = 逆操作），不需要人工重新推导层序。

## UC-6 人审一条需求的详情页（人 · 既有主场景，回归用例） `serves: FR-3, FR-6`

**场景**：改造后，人打开详情页做阶段裁决。

1. 首屏四段（头部 / 状态带 / Tab 栏 / 最近评论）与改造前逐键相同（快照 + 探针）。
2. 七个 Tab 的内容、懒加载、分段替换行为不变（探针 A1~A13 + 页面用例）。
3. 窄窗（≤1280）适配行为不变（既有 "详情页不适配" 修复的成果不得回退）。

**看到什么**：人**感知不到**这次改造——这正是本需求的验收形态。

## 关键决策与取舍 `serves: FR-1, FR-5`

| 取舍 | 候选 | 裁定 | 理由 |
|---|---|---|---|
| 用例组织 | 按功能罗列 vs 按"读面/犯错面"组织 | **按读面与犯错面** | 本需求的价值就在这两件事上，用例必须能验收它们 |
| 失败用例 | 只写正例 vs 正例 + 违规例 | **各配一条违规例** | 门禁会退化成装饰，除非有"故意违规必红"的用例（见 test-cases） |

## 技术方案与亮点 `serves: FR-1, FR-5`

- UC-1 与 UC-4 是同一件事的两面：**顺路**（改对了）与**越界**（改错了）都能被机械判据当场判出来。
- UC-3 把"零外观变更"从承诺变成读数；UC-5 把"回滚"从人肉推导变成机械逆操作。
