# 需求说明（REQ-261007133149-0716 详情页组件化改造：单文件单组件 + 契约显式化）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。
> 本轮特殊之处：**用户可见外观必须一点不变**。交付的是「代码结构 + 判据」，不是「新版界面」；
> 判定标准不是「更好看 / 更现代」，而是**agent 改一处要读多少、错一次要多久被发现**。

## TL;DR

- **这是什么**：把看板「需求详情页」（`src/client/views/report-tabs.ts` 装配的壳 + 7 个 Tab
  面板 + 常驻头部 / 状态带 / Tab 栏）按**组件**重新切一遍：样式一组件一片、面板契约用类型钉住、
  判据跟着组件走。
- **为什么现在做**：同一个面板的改动今天要跨 **6~9 处**找线头（含单个 **2387 行**样式文件，
  以及片尾 **17 条一次点名 ≥3 个组件**的覆盖规则）；改错了常常要靠人在页面上肉眼发现。
- **做完得到什么**：改一个组件只需读**它自己的分片 + 一条契约**；「改了没生效 / 漏改 /
  外观漂移」由机械判据当场点名到组件粒度，且**页面外观逐键不变**（可机械证明）。

## 业务流程图

```
人给一句改动（例：「这页卡片改白底」）
        |
        v
窗口 agent ──读─▶ prototypes/anatomy.html   ← 组件地图：谁拥有哪块界面（本需求交付物）
        |
        +──读─▶ 该组件的样式分片（约 100~250 行，含属于它的覆盖规则）
        +──读─▶ Panel 契约（显式接口 + 注册表；漏实现/键漂移 编译期即红）
        |
        v
     改代码 ──▶ pnpm typecheck ──▶ npx vitest run（该组件用例）──▶ 外观快照比对
                    |                      |                          |
              类型/契约红              行为用例红                 外观漂移红（点名到组件）
```

**与现状的差别**：今天读完上面这些还不敢动手——还要通读 2387 行样式并推断「哪条规则赢了」；
分片 + 归属门禁之后，这一层推理被结构消掉。

## 边界

```
需求详情页（report shell，src/client/views/report-tabs.ts 装配）
 |
 +-- head 常驻头部 ............... 组件 1  标识行/标题行/闸门条/结论行/下一步/阶段条/最近评论
 +-- band 状态带三格 ............. 组件 2  做到哪了 / 缺口（焦点）/ 结果与成效
 +-- tabs 进度带 + Tab 栏 ........ 组件 3
 +-- 面板区（各自一个组件） ....... 组件 4~10
      +-- trunk 汇报 / docs 文档 / dag DAG / dialogue 对话
      +-- verify 验收 / token Token / prompts 提示词
 |
 +-- 公共层 ....................... 基底 / 令牌 / 公共件 / 焦点环 / 窄档 / 目标尺寸 / 动效 / 字阶
                                    （只允许写「每处都一样的口径」，不许写具体组件取值）
```

**本次范围**：上面 10 个组件的**外观归属**与**渲染契约**（含把散在片尾的覆盖规则按组件归位）。

**不在本次范围**（明确划掉，避免顺手扩面）：

- 取数协议：`src/client/api.ts` 的 URL / 响应形状（只把「Tab 键 ↔ 端点名」的**重复清单**收敛为单点推导，不改任何请求语义）。
- 后端（`src/**` 其它节点）、SSE、台账写路径。
- 看板其它页面、任务详情页、旧详情页（`src/client/views/stage-detail.ts`）。
- DAG 画布本体（`src/client/dag/`）：只保留「详情页内的收口规则」，不重绘画布。
- 任何**可见外观改动**：本轮不允许出现（见 FR-3）。

## 产品定义

这是一次**面向 agent 可维护性的结构改造**：把「详情页长什么样」从「2387 行 + 多层覆盖 + 判据在
别处」变成「**一个组件一个分片一份判据**」。

- **是什么**：详情页的组件切分与归属契约（10 个外观组件 + 1 个显式公共层）。
- **核心价值**：把 agent 的**必读面**与**犯错面**同时缩小——读面从「跨 6~9 处、含 2387 行」降到
  「该组件一个分片 + 一条契约」；犯错面从「靠人眼在页面上发现」变成「类型 / 契约 / 快照三级判据当场点名」。
- **与现状的区别**：现状在功能上也能改（过去几轮都改成了），代价是**每次都要重新推导一遍全局**；
  本需求把这份推理**一次性固化成结构 + 门禁**，之后每改一次都省一遍。

**三要素检查清单**：

- [x] 说清楚「是什么」：组件切分 + 归属契约 + 门禁（不是新版 UI）。
- [x] 说清楚「核心价值」：读面缩小、犯错面缩小、外观零变更可证明。
- [x] 说清楚「与现状的区别」：现状靠人/agent 每次重新推理全局；本需求把推理固化为结构与判据。

### 条款详述 · FR-1 组件边界落定并成文

**功能描述**：详情页切成 10 个外观组件，每个组件的 DOM 根、拥有的选择器、依赖谁，写成 agent 改前读的唯一一页。

**详细说明**：

- **使用场景**：窗口 agent 接到「改某个 Tab 的某处样式」时，先读这一页定位组件，再只读该组件分片。
- **操作流程**：
  1. agent 打开组件地图（`prototypes/anatomy.html`）。
  2. 找到目标组件卡：DOM 根选择器 + 拥有的外观（对应样式分片）+ 改它时不必读的清单。
  3. 只读该分片与契约后动手。
- **预期结果**：
  - 10 个组件边界一目了然（含 3 个壳内组件 head/band/tabs 与 7 个面板）。
  - 公共层单独列出，并写明它「只许写统一口径」。
- **边界条件**：
  - 组件地图**不新增** DOM 契约：用的选择器全部是既有 `data-*` 与既有类名（不许为了画图改渲染）。
  - 画布（`src/client/dag/`）与其它的详情页内收口，标注为「沿用既有分片」，不列为新组件。

**验收标准**：

1. 跑 `npx tsx` 用现有标本页（`scripts/fixtures/req-detail-specimen.mts`）在 headless Chrome 里
   数 DOM 根 → 观察值 `componentRootCount = 10`，与地图里列的 10 个组件一一对应。
2. 地图里每个组件的 DOM 根选择器，在真实渲染里都能 `querySelector` 命中（命中数 ≥1，逐条点名）。
3. `docs/requirements/REQ-261007133149-0716/prototypes/INDEX.md` 标 `authoritative`，服务条款 FR-1~FR-6。

### 条款详述 · FR-2 样式按组件分片且覆盖层归位

**功能描述**：每个组件的外观（含今天散在片尾的覆盖规则）只出现在它自己的分片里，拼接出口与对外名字不变。

**详细说明**：

- **使用场景**：agent 要改某组件外观（例如卡片底色）；人要看「这个组件到底长什么样」。
- **操作流程**：
  1. 分片目录按组件拆开（壳内 3 个 + 面板 7 个 + 公共层若干）。
  2. 片尾那几层跨组件覆盖规则，按它**实际服务的组件**拆进对应分片，并保持该组件内原有先后顺序。
  3. 拼接出口 `REPORT_CSS` 名字与用法不变（调用方零改动）。
- **预期结果**：
  - 读一个组件的外观 = 从头读它一个分片到底，不需要跨文件推断「谁盖谁」。
  - 公共层只含「每处都一样的口径」（焦点环 / 窄档 / 目标尺寸 / 动效 / 字阶 / 基底）。
- **边界条件**：
  - 拆 `:is(A,B,C)` 这类组选择器时**必须保持特异性不变**（否则会静默改变胜者）。
  - 不顺手删任何规则（死规则清理不在本期，避免与「零变更」冲突）。
  - 分片数量与命名以组件地图为准，不许新造第二套命名。

**验收标准**：

1. 跑归属门禁脚本 → 退出码 0，输出「组件越界 0 处 / 公共层含具体组件取值 0 处」。
2. `npx tsx scripts/req-report-probe.mts` → 退出码 0（4/4 组合 + A13 六面板）。
3. `pnpm build:client` → `[verify-client] OK … 样式归属章在场, CSS 分片完整`。

### 条款详述 · FR-3 外观零变更可机械证明

**功能描述**：分片与归位前后，逐组件「计算样式 + 几何」快照逐键相同。

**详细说明**：

- **使用场景**：任何人（人或 agent）声称「只重构、不改外观」时，用读数而不是感觉来证明。
- **操作流程**：
  1. 改造前采集基线：七个面板 × {1280, 900} × {在途 implementing, 终态 archived} + 首屏四段。
  2. 每个组件采集两类读数：**计算样式**（该组件 DOM 根及其子树的关键属性）与**几何**（盒尺寸 / 位置）。
  3. 改造后重采，逐键比对；不一致必须逐条给出原因或修回。
- **预期结果**：
  - 快照比对退出码 0，`diff` 为空。
  - 快照成为「外观的当前事实」，之后改外观必须显式更新它（见 FR-5）。
- **边界条件**：
  - 浏览器版本差异：快照固定采集口径（同一 Chrome、同一 device scale、同一视口），
    跨版本差异必须**显式登记**，不许静默放宽阈值。
  - 不把「采样到 0 元素」当成「没变化」：某组件在某个态下不存在时，快照里写成显式缺失。

**验收标准**：

1. 外观快照比对脚本（本期新建，落点与命名在 design 节点定）→ 退出码 0（基线与现状逐键相同）。
2. 逐组件粒度：报告里能按组件列出「键数 / 不同键数」，而不是一个总数。
3. 反向验证：故意改一条组件规则（临时）→ 同一脚本退出码非 0 且**点名到组件与属性**，然后还原。

### 条款详述 · FR-4 面板契约类型钉住

**功能描述**：面板契约写成显式接口，Tab 键与取数端点从注册表单点推导，漏实现/键重复/顺序漂移即红。

**详细说明**：

- **使用场景**：新增一个 Tab、或给已有面板加一个可选能力时。
- **操作流程**：
  1. 面板按显式接口实现（注册即装配），漏实现任何必需成员 → 类型检查即红。
  2. Tab 键联合类型与取数端点名**从注册表推导**，删掉手写的重复清单。
  3. 契约用例守住：键唯一、注册顺序即展示顺序、每个面板都实现全接口。
- **预期结果**：
  - 「加一个 Tab」只需改一处（注册表 + 面板文件），不再有「漏改第二处清单导致静默回落」。
  - 未知键的既有行为不被改变：**不允许静默变成第一个 Tab**（今天靠显式守卫，契约用例要把它钉住）。
- **边界条件**：
  - 只收敛类型与清单，**不改任何请求语义**（URL、参数、响应形状、缓存键语义全部不变）。
  - 面板目录自包含（样式/标本/用例同目录）**不在本期**，留作后续。

**验收标准**：

1. `pnpm typecheck` → 退出码 0；且故意漏实现一个成员时**编译失败**（反向验证）。
2. 面板契约用例（本期新建，落点与命名在 design 节点定）→ 全绿（键唯一 / 顺序 / 全接口实现 / 未知键不静默回落）。
3. `npx vitest run tests/report-tabs.test.ts tests/report-shell.test.ts` → 全绿（既有行为不回退）。

### 条款详述 · FR-5 防复发门禁

**功能描述**：外观快照基线与分片归属两条判据入库，改外观必须更新快照、越界写法当场红。

**详细说明**：

- **使用场景**：以后任何人改详情页外观或加组件时。
- **操作流程**：
  1. 改外观 → 快照必然变化 → 必须显式更新基线，人能在 diff 里看到「哪个组件哪条样式变了」。
  2. 写样式 → 归属门禁检查「这个选择器属不属于它所在的分片」，越界即红（公共层禁写组件取值）。
- **预期结果**：
  - 两条门禁都能在 CI / 本地一条命令跑，并在违规时**点名到组件与属性**。
  - 门禁本身有反向验证（故意违规必须红），避免「恒绿装饰」。
- **边界条件**：
  - 公共件（按钮 / 提示文字 / 芯片等跨组件件）需要显式白名单，**逐条写明理由**，不许宽泛豁免。
  - 门禁判据与阈值只放在门禁脚本里，组件分片里不放阈值。

**验收标准**：

1. 两条门禁正常态：`退出码 0`。
2. 反向验证：① 改一条组件规则不更新快照 → 快照门禁红且点名组件；② 把某组件选择器写进别的分片 → 归属门禁红且点名。
3. 两条门禁都写进维护指南（读者知道什么时候跑、红了怎么办）。

### 条款详述 · FR-6 可逆与兼容

**功能描述**：分片可退回单文件（逐字节相同）；不改取数协议、写路径与其它页面。

**详细说明**：

- **使用场景**：任一步骤出问题时需要回滚；或需要把分片形态换回单文件。
- **操作流程**：
  1. 拼接顺序固定且可复现 → 分片按序拼回 = 今天单文件的内容（逐字节相同）。
  2. 契约类型化只动类型与清单推导，不动运行时行为 → 回滚只回类型层。
- **预期结果**：回滚后探针 / 用例 / 快照三条判据全绿，与改造前完全等价。
- **边界条件**：回滚演练只在本需求文件面内进行（不动其它页面、不动台账数据）。

**验收标准**：

1. 拼接回单文件后与改造前 `report.ts` 内容**逐字节相同**（`diff` 为空 / 校验和一致）。
2. 回滚状态下 `req-report-probe.mts` 与页面用例全绿。
3. 取数协议对照：改造前后 `src/client/api.ts` 的 URL 与响应形状**零差异**。

## 失败与并发路径

**失败路径（宁可响亮红，不许静默降级）**：

| 失败场景 | 症状 | 处置 |
|---|---|---|
| 拆 `:is()` 组改变了特异性 | 某组件某属性胜者变了（外观漂移，快照逐键比对会红） | 回滚该分片，改用「等价特异性包装」后重试；不许改快照放过 |
| 快照跨浏览器版本漂移 | 同一份代码在两台机器读数不同 | 固定采集口径（同 Chrome / 同 DSF / 同视口）；差异逐条登记，不许放宽阈值 |
| 归属门禁误报（公共件被判越界） | 门禁红但写法正确 | 写进**逐条带理由**的白名单；不许写宽泛豁免 |
| 契约推导与运行时守卫不一致 | 未知 Tab 键静默变成第一个 Tab（今天是显式守卫挡住） | 契约用例必须钉住「未知键不静默回落」；不改既有守卫 |
| 快照采样到 0 元素 | 某组件在某态不存在，快照误判「无变化」 | 快照显式记录缺失态；0 元素 = 红，不是通过 |
| 反向验证不红 | 门禁脚本恒绿（装饰品） | 门禁必须自带「故意违规必须红」的演练，写进验收判据 |

**并发与竞态**：

- **无并发写**：本仓按窗口串行作业，同一时刻只有一个窗口改详情页；分片后「同一组件的外观只有一处」，
  反而把并发冲突面从「同一大文件」缩到「同一分片」。
- **并发读**：分片不影响运行时（浏览器只吃拼好的 `REPORT_CSS` 一份），故不存在运行时竞态。
- **边界**：若将来有第二个窗口同时改同一组件分片，冲突表现为普通的文件冲突（可见、可解），
  不会像今天这样表现为「读到一个中间态的覆盖顺序」。
