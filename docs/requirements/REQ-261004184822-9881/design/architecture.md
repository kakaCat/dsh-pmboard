# 架构设计（REQ-261004184822-9881 看板泳道滚动位置记忆）

> 面向：前端开发、测试。轻档：只讲模块落点、边界与渲染时序。

## 目标与不改动面 <!-- serves: FR-1, FR-2, FR-3 -->

**一句话目标**：看板泳道被整段重绘后，把用户上一次的横向与列内纵向滚动位置回填回去，且这份记忆只属于泳道视图。

- **不改**：刷新触发机制（SSE / 20 秒轮询 / 手动「刷新」）、取数路径、看板 DOM 结构与事件委派契约、台账与服务端。
- **新增**：一个纯客户端记忆模块 + `render()` 前后两次调用；样式表泳道段两条规则（FR-4）。

## 模块落点 <!-- serves: FR-1, FR-2 -->

| 路径 | 内容 | 新增/改动 | 落此处的理由 |
|---|---|---|---|
| `src/client/board-scroll.ts` | 泳道滚动位置记忆（capture / restore + 单条快照） | 新增 | 与 `dag/view-state.ts` 同层同形（会话内前端记忆），但**独立模块**——FR-2 要求与 DAG 记忆隔离，复用同一张表就等于把「泳道 = 某个 DAG 画布」这种假关系写进数据模型 |
| `src/client/board-mount.ts` | `render()` 里 `innerHTML` 赋值前后各调一次 | 改动 | 重绘点唯一，取点 / 回填必须贴着重绘那一行 |
| `src/client/styles/base.ts` | §泳道两条规则（列高铺满） | 改动（FR-4） | 泳道样式单一来源，不另起文件 |

## 渲染时序 <!-- serves: FR-1, FR-2, FR-3 -->

```
onClick / SSE / 20 秒轮询 / fetchAll() 取数完成
        │
        ▼
   render()
        ├─ ① captureBoardScroll(viewEl)            ← 读旧 DOM（无 .dsh-pm-lanes = 静默跳过）
        ├─ ② viewEl.innerHTML = buildBoard(...)    ← 旧节点全部销毁（位置随之丢失）
        └─ ③ restoreBoardScroll(viewEl)            ← 写新 DOM（同一任务内、同一帧）
```

三条纪律：

- **只认 DOM 事实，不认模式变量**：两个函数都以「DOM 里有没有 `.dsh-pm-lanes`」为唯一判据——列表视图 / 需求详情天然不命中，不必把 `boardView` 传进来，也不会因模式变量写错而串位。
- **capture 不写零**：找不到泳道容器时**不更新记忆**。否则从需求详情返回看板时，一次"零"会把真位置冲掉（FR-2 的隔离与保真都靠这条）。
- **restore 只回填、不创建**：找不到容器 / 列就返回；绝不为回填插入 DOM（FR-4 的不引入新层级同源纪律）。

## 与既有机制的边界 <!-- serves: FR-2 -->

| 既有机制 | 关系 |
|---|---|
| `dag/view-state.ts`（DAG 画布记忆） | 井水不犯河水：不同模块、不同表、互不引用（FR-2 用单测断言两键互不影响） |
| `sessionStorage` 视图偏好（`dsh-pmboard:view` / `dsh-pmboard:list`） | 只读不改：那是"用户偏好"（可跨会话留），本记忆是"当前在哪"（会话内、绝不落盘） |
| `panel-hydrate.ts`（会话面板位置修复） | 同款问题的另一处修复；本需求**不改**它，只沿用它的纪律（找不到钩子静默返回） |

## 回滚路径 <!-- serves: FR-1, FR-4 -->

一次提交即可整体回滚：删掉 `render()` 里的两次调用（回到"位置归零"的今天），样式段还原两条规则（回到"列只包内容"）。无数据迁移、无台账痕迹、无服务端影响。
