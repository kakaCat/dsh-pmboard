# REQ-261004154937-2ca3 · token 统计纳入子代理消耗（跨会话聚合口径）

## TL;DR

- **是什么**：pmboard 的 token 读数现在只算**执行窗口自己那一个会话**，子代理（subagent）花的量一分钱都不计——而子代理恰恰是把活干完的主力。
- **实测多严重**：本工作区 88 个会话里 **33 个是子代理会话**；样例窗口 `session-5c6b1a8b` 自身日志累计 141.1M，它的 **14 个子代理另有 85.3M**——约 **38%** 的消耗不在父会话投影里，也就进不了节点/任务/需求的任何数字。
- **得到什么**：数字变成**真实总量**（本窗口 + 其全部后代子代理会话）；并且如实标明「本需求上线前的历史数字不含子代理」。

## 升级为重档的声明（按纪律，不偷偷按轻档做完）

本需求触发了两条单向升级信号：**要动数据口径（快照语义）+ 出现了第二个未定决策**（子会话在阶段中途生灭时怎么归属）。
因此按**重档**执行：需求分析写全（方案对比 + 归属规则 + 兼容与回滚），设计阶段先做**可行性取证**再定契约。
（升级是单向的：即便后面发现代码量很小，也不降回轻档。）

## 目标链路（一眼看明白改哪一环）

```
        执行窗口会话 windowKey
                |
                |  按 parentSession 取传递闭包（含多层）
                v
   +--------------------------+----------------------------+
   |            主会话 A      |   子代理 B (depth 1)       |
   |                          |      +-------------------+ |
   |                          |      |  孙会话 D(depth 2)| |
   |                          |      +-------------------+ |
   |                          |   子代理 C (depth 1)       |
   +--------------------------+----------------------------+
                |
                |  tokenTotals(windowKey) = A + B + C + D      <-- 本需求改这里
                |                                              （现状只算 A）
                v
     +------------------------+   +----------------------------+
     | 节点 / 任务 / 需求     |   | 起链预算闸                 |
     | 三级快照差值（展示）   |   | 仍按 cacheRead 旧口径      |
     | 含子代理               |   | 不含子代理（另议）         |
     +------------------------+   +----------------------------+
```

## 一句话目标 + 可证伪判定标准

**目标**：pmboard 的 token 快照口径从「执行窗口单会话」改为「执行窗口会话 **+ 其全部后代子代理会话**（按 `parentSession` 传递闭包）」，使节点 / 任务 / 需求三级读数反映真实消耗；同时**不改**起链预算闸的判据（闸门另议），并把这条口径差异写在 UI 与文档里。

**判定标准（跑什么、看到什么算完成）**：

1. **聚合可证伪**：给定「主会话 + 2 个子代理会话」的夹具，需求累计 `tokenTotal` == 主 + 子1 + 子2（单测断言数字相等，不是"包含"这种模糊说法）。
2. **多层血缘**：子会话的子会话（`delegationDepth ≥ 2`）也在合计里——3 层夹具逐层验证。
3. **集合变化有规则**：构造「第一次快照时只有 1 个子会话、第二次快照前又新起 1 个」的场景，差值**不重复计**旧子会话、且新子会话按其**创建时刻起**的用量计入（规则要定死并有用例锁住；不允许"看情况"）。
4. **缺失不补 0**：某子会话用量取不到（缓存未命中的路径失败）→ 该子会话标记为不可得、快照标 `degraded`，数字**不凭空增加**；面板与卡面不出现"凭空翻倍"。
5. **真数据取证**：对本机真实窗口（如 `session-5c6b1a8b`：自身 141.1M + 14 子 85.3M）跑取证脚本，聚合结果与独立复算一致（偏差必须能解释）。
6. **口径差异写在明处**：UI 与文档同时写明「**展示含子代理 / 起链预算闸不含**」与本需求上线时间点（历史数字不含子代理）。

## 方案对比（为什么选聚合而不是分开显示）

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A 聚合（选定）** | 快照直接返回「主 + 后代」合计 | 需要定死「集合变化」的归属规则；数字会整体变大，且与上线前的历史值**不可直接比** | ✅ 用户要的就是"真实消耗"，一个数最省认知 |
| B 分开展示 | 主窗口一个数、子代理另一个数（如 `12.7M（含子代理 3.2M）`） | 不必解决归属规则，但每处展示都要多一个概念，卡面/流程图/详情三处都要改 | ✗ 增量认知成本高，用户没要求 |
| C 只标注 | 不改数字，仅注明"不含子代理" | 最轻，但"到底烧了多少"仍然答不出来 | ✗ 不满足诉求 |

## 产品定义

**是什么**：对 token 读数**口径**的一次修正——从"这个窗口自己花了多少"改成"这个窗口连同它派出去的子代理一共花了多少"。

**核心价值**：pmboard 的 token 数字被用来判断"这个需求值不值/要不要拆小"。子代理是主力（实测占约 38%），漏计会让判断**系统性偏向乐观**——这是口径错误，不是显示瑕疵。

**与现状的区别**：现状快照来源 `SessionProbeAdapter.tokenTotals(windowKey)` 只读该窗口会话的 `tokenUsage` 投影（且 DSH 投影本身也是会话级）；改后按 `parentSession` 传递闭包把后代会话的用量一并合计。

## 用户与角色

| 角色 | 什么场景用 | 痛点（现状） |
|---|---|---|
| 看板使用者 / PM | 判断某需求烧了多少、要不要继续投入 | 数字只有主会话，子代理（主力）不计——系统性低估 |
| Agent（各窗口） | 自证消耗、判断要不要拆小任务 | 同上；子代理跑得越多，偏差越大 |
| 插件维护者 | 改快照口径 | 展示口径与预算闸口径会分叉，必须显式登记差异 |

## 边界

- **不做**：**不改起链预算闸**的判据与阈值（`maxCacheReadTokens` 仍按现有 `tokenUsage.totals.cacheReadTokens` 累计；口径分叉写进文档，闸门另议）。
- **不做**：**不改 DSH 本体**（不请求 token-meter 增加血缘聚合）；聚合只在 pmboard 侧做。
- **不做**：**不回填历史快照**——本需求上线前落库的数字保持"不含子代理"，页面与文档写明这条时间分界（避免出现"同一需求前后数字不可比却没人说"）。

没写进上述边界的，即本次不做。

### 详细说明

**FR-1: 快照口径改为跨会话聚合**
`SessionProbe.tokenTotals(windowKey)` 的语义从「该窗口会话的累计用量」改为「该窗口会话 **+ 其全部后代子代理会话**的累计用量之和」（四桶逐分量相加）。调用方（节点/任务/需求三级快照差值链路）不改签名，只改语义。
判据：主 + 2 子夹具下 `tokenTotal == 主 + 子1 + 子2`。

**FR-2: 后代集合的枚举与归属规则**
枚举：`ctx.sessionPersistence.list()` 取全部会话 header（含 `id` / `parentSession` / `origin` / `delegationDepth`），从本窗口会话出发取 `parentSession` 的**传递闭包**（含多层）。
归属规则（**本需求的核心决策，必须定死**）：
- 每次快照记录**集合指纹**（`[{sessionId, seq}]` 或等价的稳定摘要）；
- 相邻两次快照的差值 = Σ(本次各成员快照 − 上次同名成员快照)，**新出现在集合里的成员按其"创建以来"的累计计入本次差值**，**消失的成员不计负值**（与既有 `subBuckets` 负分量截断为 0 的口径一致）；
- 由此产生的已知偏差（新子会话的早期消耗会被算进"它首次出现在快照之间的那个阶段"）必须写进文档。
判据：单测锁住上述三条（新增/消失/同名成员）。

**FR-3: 缺失不补 0**
任一后代会话的用量取不到（缓存未命中且冷读失败）→ 该成员**不参与合计**，同时快照标 `degraded`（复用既有 degraded 语义），UI 照实显示"口径不完整"。
判据：注入一个"永远取不到"的后代 → 合计等于可得成员之和，且 degraded 为真；数字不得凭空增加。

**FR-4: 口径差异写在明处**
① 会话头部详情的 Token tab 与看板卡面注明「含子代理」；② 起链预算闸仍按旧口径 → 在文档里写明「展示口径 ⊃ 闸门口径」这条差异与原因；③ 写明本需求上线时间点：此前的历史数字不含子代理。
判据：UI 文案存在（结构断言）+ 文档章节存在。

**FR-5: 可证伪回归**
单测：聚合（主 + 2 子）、多层血缘（≥2 层）、集合变化（新增/消失）、缺失（不补 0）；
真数据取证：对本机真实窗口复算，输出"聚合值 vs 独立复算值"两个数字与偏差解释。
判据：命令退出码 0 且上述四类用例全绿。

## 现状证据（E）

- **E-1**：子代理是独立会话。日志头 `origin:"subagent"` / `delegationDepth:1` / `parentSession:<父会话 id>`（`~/.dsh/sessions/<workspace>/<id>/session.v4.jsonl.zst` 首行可核）。
- **E-2**：父会话**收不到**子代理的用量。`subagent-settled` 通知只有文本字段（`session-format-v0-to-v1/src/payload-validation.ts` 的键表：`kind/form/summary/senderSessionId`，无 usage）。
- **E-3**：pmboard 的快照只读本窗口会话——`src/adapters/SessionProbeAdapter.ts` 的 `tokenTotals()` → `sessionProjections.stateOf(session,'tokenUsage')`。
- **E-4**：DSH 的 `tokenUsage` 投影是**会话级**（`packages/llm/token-meter/src/usage-projection.ts` 只折叠本会话事件）。
- **E-5**：量级实测（按与 token-meter 同规则的折叠复算）：本工作区 **88 会话 / 33 个为子代理**；`session-5c6b1a8b` 自身 141.1M + **14 个子代理 85.3M ≈ 38%** 未计入。
- **E-6**：**可行性已探明（关键）**：
  - 枚举零日志读：`ctx.sessionPersistence.list()` 返回 header（`session-persistence/src/index.ts:201` 抽象方法，`:47` 起是 `SessionPersistenceSnapshot{header, revision, eventCount?, sizeBytes?}`）；
  - 单会话用量：`ctx.sessionProjectionCache.cachedSnapshot(meta, ['tokenUsage'])` 缓存命中零读（`session-projection-cache/src/index.ts:161`）；未命中走 `coldSnapshot(meta, inheritedEventCount, events)`（同文件 `:287`，**需要读该会话日志**，这是本需求的主要成本项）。

## 待裁定项（design 阶段必须给出结论）

1. 后代用量取数策略：只用缓存（快、可能陈旧）／缓存未命中就冷读（准、可能要读多个会话日志）／分层（活跃子会话走 live 投影、已结束走缓存）。
2. 集合指纹的稳定形态与比较方式（顺序无关、缺员容错）。
3. `degraded` 的呈现：只在详情页标注，还是卡面也标注。
