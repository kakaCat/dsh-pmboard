## 产品定义 <!-- serves: FR-1 -->

**是什么**：一次「让归档这一步的声明与磁盘事实对账」的加固需求，覆盖归档提交校验、知识层自检、归档目录呈现三段。

**核心价值**：归档是需求生命周期的**最后一个可信承诺**——「这批结论并进了项目文档」。
承诺无法被机器核验时，它既不能拦住假的（申报的文档从未存在），也不能证明真的（代码在、文档不在）。

**与现状的区别**：不是新增一道人工门，而是让**已有的机械门禁**第一次真的碰文件系统与项目身份：

- 现在：`target.startsWith(prefix)` 是唯一判据（`src/shared/protocol.ts:2088`），`SubmitArchive` 里 `existsSync` 零命中。
- 之后：合并去向按**该需求自己的** `workspaceRoot` 解析后判存在与非空；说明书更新点收敛为 `path#anchor` 且锚点必须真实存在。

**三要素检查清单**：

- [x] 说清楚"是什么"：归档声明 ↔ 磁盘事实的对账，以及知识层对归档的覆盖度自证
- [x] 说清楚"核心价值"：让最后一道可信承诺可证伪，让「代码在、文档不在」当场暴露
- [x] 说清楚"与现状的区别"：不加人工门，把字符串前缀判据升级为按项目身份的文件系统判据

### FR-1: 合并去向必须在该需求自己的工作区根下真实存在且非空

**功能描述**：提交归档材料时，每个 `merged_into` 都按**这条需求自己的**工作区根解析后判「存在且非空」；不满足即当场拒绝，并在消息里点名是哪一条路径、解析到了哪个根。

**详细说明**：

- **使用场景**：任何窗口调 `reqboard_submit(kind=archive)` 申报合并去向时。
- **操作流程**：
  1. agent 按约定申报 `merged_into: ['docs/architecture/<doc>.md']`。
  2. 校验按 `rootOfRequirement(deps, record)` 取根（`projectId` → 项目条目 `path`；无 id 回落记录自带 `workspaceRoot`，**并标注 `by='path-fallback'`**）。
  3. 目标不存在、或是 0 字节文件 → 拒绝，消息含**该路径 + 生效的根 + 判据来源**。
  4. 通过 → 照常写入归档记录。
- **预期结果**：
  - 结果 1：反向演练——把 `merged_into` 改成不存在的路径，提交被拒且消息点名该路径（退出码非 0）。
  - 结果 2：`REQ-260929184406-2084` 那条形态（申报从未落盘的文档）在提交时即被拦下。
  - 结果 3：跨项目需求（`workspaceRoot` = `dsh-notice-webhook`）按**它自己的根**判定，不误报、也不放行。
- **边界条件**：
  - 边界 1：**存量 37 条不追溯**——不在提交期回溯翻旧账，不改写既有台账（只读核对见 FR-8）。
  - 边界 2：非空判据是「不是 0 字节」，不做内容质量判定（内容质量不是机械可判的）。
  - 边界 3：解析根**不得**退回路径字符串比较（见「红线」），判据来源必须进拒绝消息与回执。

**验收标准**：

1. 反向演练脚本：把一条需求的 `merged_into` 改成 `docs/architecture/__no_such_doc__.md` → 归档提交返回拒绝，消息含该路径；还原后通过。
2. 新增用例覆盖「目标存在但 0 字节」「跨项目根下存在」「本仓不存在但在别项目根下存在」三态。
3. `grep -rn "existsSync" src/application/use-cases/SubmitArchive.ts` 非 0 命中，或存在等价的按根探测调用点。

### FR-2: 说明书更新点收敛为 `path#anchor`，锚点必须存在，`path` 纳入白名单

**功能描述**：`manualUpdates[].path` 与 `section` 合并为 `path#anchor` 形态并强制校验锚点在目标文档里真实存在；`path` 同时受该需求类型的 `mergeTargets` 白名单约束。

**详细说明**：

- **使用场景**：`feature` / `refactor` / `spike` 类需求申报「项目认知增长了哪一节」时。
- **操作流程**：
  1. agent 写 `manual_updates: [{ path: 'docs/architecture/project-manual.md#<anchor>', summary: '…' }]`。
  2. 校验：形态必须含 `#`；`path` 部分落在 `mergeTargets` 白名单内（与 `merged_into` 同一份规则，**不新增第二份白名单**）；锚点在目标文档的标题锚点集合里。
  3. 任一不满足 → 拒绝并点名（缺锚点 / 白名单外 / 锚点不存在分三种消息）。
- **预期结果**：
  - 结果 1：`REQ-261003150739-b98d` 那条形态（`path = CLAUDE.md`）在提交时被白名单拦下。
  - 结果 2：`REQ-260930155231-0862` 那条形态（`section = 二、四个关键决策`，文档已改名「十个」）在提交时即红，而不是漂移几周后被人肉发现。
- **边界条件**：
  - 边界 1：**兼容既有形态**——历史台账里的自由文本 `section` 不被追溯改写；读侧渲染照旧能显示旧值（见 FR-5 的降级呈现）。
  - 边界 2：兼容层只在**读**（渲染）与**存量**上存在；**新提交**一律走 `path#anchor`，不提供「自由文本仍可提交」的旁路。
  - 边界 3：锚点计算复用知识层既有实现（`src/domain/knowledge/slug.ts` 的 `headingAnchor` / `listHeadingAnchors`），不新写一套 slug 规则。

**验收标准**：

1. 反向演练：`manual_updates[].path` 写 `docs/architecture/<不存在>.md#<anchor>` → 提交被拒并点名。
2. 反向演练：锚点写成不存在的字符串 → 提交被拒且消息区分「锚点不存在」与「路径不在白名单」两种原因。
3. 用例覆盖旧形态（自由文本 `section`）在**读侧**仍可渲染，不因本次收紧而崩。

### FR-3: 知识层自检新增「归档沉淀覆盖度」检查

**功能描述**：`scripts/kb-probe.mts` 新增一条检查：每条**有归档材料**（台账存在 `archive.json`）的需求，必须在 `docs/knowledge/entries/` 里至少有 1 条 `req:` 指向它的条目；缺则该项红、退出码 1。

**详细说明**：

- **使用场景**：维护者在改知识层后跑 `pnpm kb:check`；以及任何人在验收材料里引用知识层健康读数时。
- **操作流程**：
  1. 自检读台账（`<DSH_HOME|~/.dsh>/reqboard/archive/<REQ>/` 与 `requirements/<REQ>/`）取「有归档材料的需求」集合。
  2. 扫 `docs/knowledge/entries/*.md` 的 `req:` 头部字段，建「已沉淀」集合。
  3. 差集非空 → 打印缺哪几条需求（点 id），失败。
  4. **台账不可达**（无台账目录 / 环境变量指向空）→ 按既有纪律记为「读数不可得、不判」（不制造假红），并在输出里写明原因。
- **预期结果**：
  - 结果 1：反向演练——删掉本检查分支，对应用例必须变红（不得是「无覆盖」）。
  - 结果 2：以当前台账跑，红名单恰为 6 条：`d718 0fbe 19b6 344a b98d b918`（如实报出，不在本需求内补齐）。
- **边界条件**：
  - 边界 1：**编号偏差（已与用户确认）**——`K12` 已被 `REQ-261006123819-3af3` 占用（「页面小节 ↔ 索引行完整性」），本检查落为 **K13**，既有 K12 不改名、不改语义。
  - 边界 2：**只判覆盖度，不判内容质量**——条目的结论对不对、指针准不准由既有 K4/K6/K8 管。
  - 边界 3：本需求**不补齐**那 6 条沉淀（补沉淀是内容工作，属另立需求）；本次只让缺口可见。

**验收标准**：

1. 反向演练：注释掉 K13 分支 → 指定用例变红；恢复 → 复绿（用例名与断言写进验收材料）。
2. `pnpm kb:check` 在补齐前如实红（点名 6 条）或经裁定改为「报告但不阻断」——二选一必须在设计阶段定死并留痕。
3. 台账不可达时输出「读数不可得」而非「全部通过」。

### FR-4: 知识条目「失效条件」必须可判定

**功能描述**：条目的「失效条件」小节必须含可判定锚点（反引号字面量 / 文件路径 / 命令 / 明确的 supersede 目标）；不含者标 `unverifiable` 并从 `INDEX.md` 降权。

**详细说明**：

- **使用场景**：任何读知识层取前例的 agent，以及 K6 的复核期限判定。
- **操作流程**：
  1. 自检逐条解析「失效条件」小节。
  2. 命中可判定锚点 → 正常。
  3. 未命中 → 该条目标 `unverifiable`（状态或标签，形态在设计阶段定），索引行降权（不再作为 active 前例展示），并计入自检报告。
- **预期结果**：
  - 结果 1：58/60 条同模板话的条目被如实标出（当前读数），不再「永不过期地」混在 active 前例里。
  - 结果 2：新增一条真含锚点的条目 → 不被标 `unverifiable`。
- **边界条件**：
  - 边界 1：**降权 ≠ 删除**——条目文件与索引行都保留，可追溯；只改「算不算 active 前例」。
  - 边界 2：不追溯改写 60 条存量条目的正文（只加标注与降权读数）。
  - 边界 3：判据必须与 K2（索引行语法）兼容——索引行形态变了会连带 K2，设计阶段必须先定形态再动生成器。

**验收标准**：

1. 用例：构造「失效条件 = 模板句」与「失效条件 = 含 `src/x.ts` 锚点」两条，前者 `unverifiable`、后者正常。
2. `pnpm kb:check` 与 `npx tsx scripts/kb-probe.mts --json` 的该检查项读数一致（同一口径）。

### FR-5: 归档时渲染 `archive.md` 进需求目录

**功能描述**：材料提交成功时，在需求目录生成 `archive.md`：一句话结论（`indexEntry`）、合并去向（`merged_into`，带存在性读数）、文档清单、说明书更新点、以及机器输入摘要（FR-6）。

**详细说明**：

- **使用场景**：人打开需求目录（或看板详情）想知道「这条需求收尾成了什么」。
- **操作流程**：
  1. 材料校验全部通过 → 写台账（既有顺序不变）。
  2. 渲染 `archive.md` 写入需求目录（**幂等**：内容相同不重写；重写走既有 `change_note` 纪律）。
  3. `archive.md` 进归档 `docs` 清单（`kind: notes` 或既有可用 kind，设计阶段定）。
- **预期结果**：
  - 结果 1：新归档的需求目录里 `archive.md` 存在率 100%（对照基线 3/80）。
  - 结果 2：人不必读台账即可看到结论与合并去向。
- **边界条件**：
  - 边界 1：**渲染失败不得造成半截状态**——沿用既有「先沉淀再记录、写失败即抛」的纪律，要么都成要么都拒。
  - 边界 2：不追溯为存量 37 条补渲染（存量不动；补渲染若需要，另立需求）。
  - 边界 3：`archive.md` 是**渲染物**，不是新的事实源——它的内容一律从台账派生，禁止在其中写台账没有的信息。

**验收标准**：

1. 反向演练：一次成功的归档提交后，`docs/requirements/<REQ>/archive.md` 存在且含 `indexEntry` 原文与每条 `merged_into`。
2. 幂等：同一材料重复提交，`archive.md` mtime 不变（或在内容一致时不重写）。
3. 渲染失败场景（只读目录 / 权限）→ 提交整体失败且台账零写入（不留半截）。

### FR-6: 归档材料把机器产物折叠呈现、`queue.json` 裁成摘要

**功能描述**：`archive.md` 与归档清单把 `queue.json` / `rtm-*` / `state/` 归入「机器产物」分区折叠呈现，并对 `queue.json` 生成一段**摘要**（任务数 / 状态分布 / 体积），人读面不再被机器产物淹没。

**详细说明**：

- **使用场景**：人翻需求目录判断「这 260 个文件里哪些是给我看的」。
- **操作流程**：
  1. 归档时统计目录内文件，按既有豁免规则（`ARCHIVE_EXEMPTIONS`）识别机器产物。
  2. `archive.md` 分「人读材料 / 机器产物」两区；机器产物区只列**类别 + 数量 + 体积 + 摘要**，不逐文件铺开。
  3. `queue.json` 摘要（任务数、状态分布、字节数）写进 `archive.md`。
- **预期结果**：
  - 结果 1：人读面从 44% 噪声降到「一行一类」。
  - 结果 2：`239KB` 的单文件不再需要在人读清单里被逐行扫过。
- **边界条件**：
  - 边界 1：**不搬迁既有文件**（D-2 裁定）——`rtm-*` / `state/` 仍有既有读路径（产物发现、追溯视图），物理搬迁会造出第二套位置口径。
  - 边界 2：**不删除**任何机器产物；摘要不替代原文件。
  - 边界 3：若人要求物理搬迁到 `machine/`，本 FR 只做呈现层折叠，搬迁另立需求。

**验收标准**：

1. 一次归档提交后，`archive.md` 含机器产物分区与 `queue.json` 摘要；原文件位置与数量不变（`find` 计数与提交前一致）。
2. 摘要内容与 `queue.json` 实际内容一致（任务数对得上）。

### FR-7: 看板归档条按项目身份标注来源，不在本仓时显示「在别处」

**功能描述**：看板底部「已归档」条的每个条目，按该需求的项目身份（`projectId` → `workspaceRoot`）显示来源项目名；当该需求的目录**不在当前工作区**时，显示「在别处」而不是空白/报错。

**详细说明**：

- **使用场景**：人在本仓看板回看时，看到 `dsh-notice-webhook` / `quantsys-v2` 的归档条目。
- **操作流程**：
  1. 归档条目渲染时读该需求解析出的根。
  2. 根 == 当前工作区根 → 不额外标注（或标「本仓」）。
  3. 根 != 当前工作区根 → 标来源项目名 + 「在别处」态。
  4. 根**解析不出**（记录无 `projectId` 也无 `workspaceRoot`）→ 标「归属未知」，**不冒充本仓**。
- **预期结果**：
  - 结果 1：3 条无 `workspaceRoot` 字段的记录显示「归属未知」，6 条 `dsh-notice-webhook` 与 1 条 `quantsys-v2` 显示来源项目 + 「在别处」。
  - 结果 2：点开不再空白——至少能看出「在别处」，而不是让人以为文件丢了。
- **边界条件**：
  - 边界 1：**不改成跨项目读文件**——本次只把「在别处」**说清楚**，不越界去读别的项目的工作区。
  - 边界 2：样式沿用既有 `dsh-pm-archived-chip` 分片，新增态用既有设计令牌，不引入新视觉体系（见原型）。
  - 边界 3：`sides` 含 frontend → 需求阶段必须先交原型（见「原型」节）。

**验收标准**：

1. 渲染用例：构造三种根（本仓 / 他项目 / 解析不出），产出的 HTML 分别不含标注 / 含「在别处」+ 项目名 / 含「归属未知」。
2. 跨项目点开一次，页面出现「在别处」提示文案（不再是空白块）。

  理由：编号已在另一条需求的任务卡与验收材料里被引用；改名会制造文档与代码互相说谎。
- **不做归档提交的人工门改造**（不新增人工确认步骤）。
  理由：本次是把机械判据修可信，不是加人工程序；加门会拖慢每一天的归档操作。

## 非功能需求 <!-- serves: FR-1 -->

- **可回滚**：FR-1 / FR-2 的收紧只影响**新提交**——回滚 = 恢复前缀判据；不涉及数据迁移（存量台账一字不动）。
- **兼容**：读侧必须能渲染历史自由文本 `section`（FR-2 边界 1）；`archive.md` 是新渲染物，旧需求没有它不报错。
- **失败要响亮**：渲染失败、探测失败、台账不可达一律结构化报出，**禁静默放行**（不得把「读不到」当「没问题」）。
