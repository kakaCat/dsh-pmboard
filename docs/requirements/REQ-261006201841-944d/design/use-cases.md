## UC-1 提交归档材料时申报了一个从未落盘的合并去向 `serves: FR-1`

**谁**：提交归档材料的 agent（本仓任意窗口）。

**处境**：结论其实活在源码里，而它申报并入的架构文档**从未落盘**——这正是 `REQ-260929184406-2084` 的历史形态。

**触发**：`reqboard_submit(kind=archive, merged_into: ['docs/architecture/pm-toolview-visualization.md'])`。

1. `applyRequirementWorkspaceRoot` 先把 `deps.docs` 的根校正到**这条需求自己的**根。
2. 形态判定（`assertArchiveMaterials`，零 IO）先过 `mergeTargets` 白名单前缀。
3. 事实判定 `assertArchiveTargetsOpenable` 逐条探测：`assertArtifactOpenable` + `stat(path).size`。
4. 全部通过 → 照常写台账，回执带逐条读数（`resolved_targets.merged_into[].{path, ok, bytes}`）。

**失败 / 降级时看到**：

| 情形 | 看到什么 |
|---|---|
| 目标不存在 | 提交被拒（退出码非 0），消息含**路径 + 生效根 + 判据来源**三要素 |
| 目标存在但是 0 字节 | 同类拒绝，原因写作「是空文件〔0 字节〕」——「不存在」与「空文件」是两种事实 |
| 项目表未装配 / `list()` 抛错 | 回落记录自带 `workspaceRoot`，`by='path-fallback'`、`attributed=false` 如实标注 |
| 记录连 `workspaceRoot` 都没有 | 转 UC-4：当前工作区兜底 + 「归属未知」，**不冒充本仓** |
| 全部通过 | 回执 `archive_manifest.written=true`；台账写入，目录出现 `archive.md` |

**后置条件**：被拒时台账零写入，需求目录里不出现 `archive.md`（归档是原子承诺）。

**牵涉条款**：FR-1（含失败路径 F-2 / F-4 的语义、D-4 的「禁止路径字符串比较」红线）。

## UC-2 提交的说明书更新点指向 `CLAUDE.md` 或已改名的章节 `serves: FR-2`

**谁**：`feature` / `refactor` / `spike` 类需求的 agent，申报「项目认知增长了哪一节」。

**处境**：更新点过去是无锚点自由文本，于是 `path` 能写 `CLAUDE.md`（`REQ-261003150739-b98d` 形态）、`section` 能写已被改名的章节（`REQ-260930155231-0862` 形如「二、四个关键决策」，而文档已改名「十个」）。

**触发**：两次提交——A 写 `path: 'CLAUDE.md#收尾门'`；B 写 `path: 'docs/architecture/project-manual.md#二、四个关键决策'`。

1. 形态判定：`path` 恰好一个 `#`、两侧非空、`#` 前部分落 `mergeTargets` 白名单（**与 `merged_into` 同一份规则，不新增第二份白名单**）。
2. 事实判定：`#` 前路径存在且非空；锚点落在 `listHeadingAnchors(read(path))` 里。
3. 任一不过 → 拒绝并点名，且两种原因**消息不同**。

**失败 / 降级时看到**：

| 情形 | 看到什么 |
|---|---|
| A：`CLAUDE.md#收尾门` | 白名单拒绝：列出本类型的 `mergeTargets` 前缀清单 + 原值 + 该类型 note |
| B：章节已改名、锚点不存在 | 锚点拒绝：写「锚点不存在」，并给出目标文档现有标题锚点（与白名单拒绝**不是同一条消息**） |
| 旧形态（`path` + 自由文本 `section`，无 `#`） | 形态拒绝：「`section` 已废弃，锚点写进 `path`」+ 原值 |
| 历史台账里的自由文本 `section`（读侧） | 照旧渲染为 `path（旧：section）`，**不因本次收紧而崩**（R-5） |

**后置条件**：新提交一律走 `path#anchor`，不提供「自由文本仍可提交」的旁路；历史数据一字不改。

**牵涉条款**：FR-2（读侧兼容呈现接 FR-5 的渲染物）。

## UC-3 跨项目需求（另一个工作区）提交归档材料 `serves: FR-1, FR-8`

**谁**：在 `dsh-notice-webhook` 工作区里干活的窗口（台账里 6 条），或本仓窗口替 `quantsys-v2` 那条复核。

**处境**：`deps.docs` 是宿主级单例，根会被别的窗口改掉；若拿本仓当判据，这一类需求会被误拦或误放。

**触发**：该需求提交归档材料（`merged_into` 指向**它自己项目根下**的文档）。

1. `rootOfRequirement` 取这条需求自己的根（`projectId` → 项目条目 `path`）。
2. 把 `deps.docs` 的根校正到该项目根，再走三道闸。
3. 判定、拒绝消息、回执全部用**同一个**生效根。

**失败 / 降级时看到**：

| 情形 | 看到什么 |
|---|---|
| 目标在该项目根下真实存在 | 放行；回执 `resolved_targets.root` = 该项目根、`by='project-id'`、`attributed=true` |
| 目标只在本仓存在、在它自己的根下不存在 | 拒绝，生效根是**别项目**的绝对路径——不写成「本仓没有」 |
| 该记录无 `projectId`、只有 `workspaceRoot` | `by='path-fallback'`、`attributed=false` 如实标注（F-2） |
| 别的窗口刚改走宿主级根 | 每次提交前按记录校正根；用例断言「另一个项目的目录零访问」（R-1） |

**后置条件**：跨项目需求既不误拦也不放行；判据来源（`project-id` / `path-fallback`）进拒绝消息与回执。

**牵涉条款**：FR-1（判定）、FR-8（存量报告用同一取根口径，避免「报告一套、门禁一套」）。

## UC-5 人打开一条已归档需求的目录想知道「结论去哪了」 `serves: FR-5, FR-6`

**谁**：需求裁决者。

**处境**：工作区需求目录 5795 个文件里 44% 是机器产物，`archive.md` 仅 3/80 存在——结论不在需求目录里，人只能翻台账。

**触发**：打开 `docs/requirements/<REQ>/`，或在看板点开该需求详情。

1. 归档材料校验全部通过 → 渲染 `archive.md` 并写盘（**渲染在写台账之前**）。
2. 渲染是纯派生（`renderArchiveManifest`，不碰时钟、不碰文件系统），内容一律从台账派生。
3. 机器产物按既有豁免规则分类，折叠成「一行一类」，不逐文件铺开。

**看到的人读三件套（外加两节）**：

| `archive.md` 小节 | 内容 |
|---|---|
| 一句话结论 | `indexEntry` 原文逐字 |
| 合并去向 | 逐条：路径 + ✅ 存在 N 字节 / ❌ 不存在 + 生效根与判据来源 |
| 人读材料 | `docs` 清单按 kind 分组，并与机器产物计数对照 |
| 说明书更新点 | `path#anchor` + summary；旧形态渲染为 `path（旧：section）` |
| 机器产物（可重建，折叠） | `rtm-reports` / `rtm-dir` / `ledger-mirror` / `runtime-state` 一行一类（数量 · 体积） |
| `queue.json` 摘要 | 任务数 / 依赖边数 / 就绪数 / 生成时间 / 字节数 |

**失败 / 降级时看到**：

| 情形 | 看到什么 |
|---|---|
| 目录只读 / 权限失败 | 整体拒绝、台账零写入——绝不出现「台账说归档了、目录里没有 `archive.md`」（F-4） |
| 同一材料重复提交 | `archive_manifest.written=false`，内容相同不重写（幂等，mtime 不变） |
| 两窗口并发提交同一需求 | `mutateIfPresent` 单点写入；`archive.md` 以最后一次材料为准（F-3） |
| `queue.json` 解析失败 | 只报体积 + 「无法解析」，**不抛错**（归档不因一个镜像文件坏掉而失败） |
| 存量 37 条没有 `archive.md` | 不报错——它是渲染物、非必填产物；不追溯补渲染 |

**后置条件**：机器产物文件位置与数量**不变**（不搬迁、不删除，D-2）；`archive.md` 随材料进归档 `docs` 清单（`kind: notes`）。

**牵涉条款**：FR-5（渲染物落盘）、FR-6（分区折叠与摘要）。

## UC-6 维护知识层的人跑 `pnpm kb:check` `serves: FR-3, FR-4`

**谁**：维护知识层的人；也包括在验收材料里引用知识层健康读数的人。

**处境**：自检过去只查格式 / 漂移 / 死链——6 条有归档材料的需求零沉淀、58 条失效条件是同一句模板话，`pnpm kb:check` 仍 exit 0。

**触发**：改完知识层后跑 `pnpm kb:check`（或 `npx tsx scripts/kb-probe.mts --json`）。

1. K13 = 「有归档材料的需求 − 有 `req:` 条目的需求」的集合差，判据是 `实测缺口 ⊆ 基线`。
2. K14 = 「失效条件不可判定」集合差，基线 `docs/knowledge/unverifiable.baseline.txt`。
3. 退出码语义不变：0 = 全绿，1 = 有检查失败。

**失败 / 降级时看到**：

| 情形 | 看到什么 |
|---|---|
| K13 有新增缺口 | `ok=false`、exit 1：点名缺哪几条需求 id（现基线 6 条）+ 提示「补一条 `req: <id>` 条目，或 `--refresh-coverage` 承认现状」 |
| K14 有新增不可判定 | `ok=false`：点名条目 id + 它们的失效条件原文（现基线 58 条同模板句） |
| 已补齐（`基线 \ 实测` 非空） | 检查通过 + 「已补齐，可刷新基线」提示——**不静默** |
| 台账不可达（CI / 别的机器无 `~/.dsh/reqboard`） | 两项 `ok=true` + detail「读数不可得、不判（原因：…）」；**不得**输出「全部通过」，也不因环境问题制造假红（F-5） |
| 删掉 K13 分支 | 指定用例变红（反向演练 ②），不是「无覆盖」 |

**后置条件**：6 条零沉淀与 58 条模板句**只被报出、不被补齐**（补沉淀属另立需求）；检查只判覆盖度与可判定性，不判内容质量。

**牵涉条款**：FR-3（K13）、FR-4（K14 读数）。

## UC-7 后续需求的 agent 取前例 `serves: FR-3, FR-4`

**谁**：另一个需求的 agent，开工先 `reqboard_kb` 取前例。

**处境**：过去「失效条件」永不过期地混在 active 前例里，取到的可能是早已失效的结论。

**触发**：检索某个主题的既有结论。

1. 条目「失效条件」小节逐条过 `isDecidableInvalidation`（反引号字面量 / 文件指针 / 命令 / `kb-NNNN` supersede 目标）。
2. 不可判定 → 条目标 `unverifiable`，`INDEX.md` 条目行**节内排序**：可判定在前、`unverifiable` 沉底。
3. 条目文件与索引行都保留，只改「算不算 active 前例」。

**失败 / 降级时看到**：

| 情形 | 看到什么 |
|---|---|
| 条目失效条件含 `` `src/x.ts` `` / `` `pnpm kb:check` `` / `kb-NNNN` | 正常，排在节内前面，作为 active 前例 |
| 条目是模板句 | 标 `unverifiable`、沉底——仍可查到，但不作为 active 前例首屏 |
| `INDEX.md` 已超预算（实测 8190 > 8000） | 降权只做节内排序、**零字符增量**，避免把 K1 顶红（F-6 / R-2） |
| `pnpm kb:build --check` 报 INDEX 漂移 | 属预期：按 C-13 重生成后再比对——漂移本身就是要暴露的信号（R-6） |

**后置条件**：降权 ≠ 删除；60 条存量条目正文一字不改；新沉淀的条目由 `DepositKnowledge` 直接生成可判定的失效条件，不再生产模板话。

**牵涉条款**：FR-4（可判定性与降权）、FR-3（覆盖度读数与取前例同源）。

## UC-8 人看本仓看板回看归档条 `serves: FR-7`

**谁**：本仓使用者。

**处境**：过去归档条只渲染 id + 标题，跨项目那 9 条点开是空白——分不清「文件丢了」还是「在别处」。

**触发**：打开看板、滚到「已归档」条。

1. 服务端 `GET /` 派生 `origins`（`rootOfRequirement` + `sameProjectRoot`，判据只在服务端一处）。
2. 客户端 `renderArchivedBar(cards, limit, origins)` 按 `origins` 渲染三态。
3. 既有 `data-action` / `data-req` / `data-status` / `title` 逐字保留。

**三态（对照原型 `prototypes/archive-source-label.html`，唯一 authoritative）**：

| 态 | 判据 | 看到 |
|---|---|---|
| `local` | 解析出的根 == 当前 docs 根 | 不额外标注（或「本仓」），`data-src="local"` |
| `elsewhere` | 解析成功但属别的项目 | 「别处·`dsh-notice-webhook`」（项目名 = 根末段名）；点开有提示块：来源项目 / 需求根 / 下一步 |
| `unknown` | 既无 `projectId` 也无 `workspaceRoot`（3 条） | 「归属未知」 |

**失败 / 降级时看到**：

| 情形 | 看到什么 |
|---|---|
| 旧服务端 payload 无 `origins`（或缺该 req 键） | 该条不渲染标注，逐字等价旧行为（不报错、不空白） |
| 有人想在客户端自己比路径 | 红线：判据只在服务端一处，客户端不得比较路径字符串 |
| 点开他项目需求 | 出现「在别处」提示块（不再是空白块）；**不越界读**别的项目工作区 |

**后置条件**：新增选择器仅 4 条、令牌全部既有（不引入新视觉体系）；跨项目只「说清楚在别处」。

**牵涉条款**：FR-7（三态呈现）；人读面小样与 FR-5 / FR-6 的 `archive.md` 呈现同款。

## UC-9 做横向审计的人要一份可复现的存量读数 `serves: FR-8`
