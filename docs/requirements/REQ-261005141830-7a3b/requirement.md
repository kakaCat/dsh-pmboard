# 需求说明（REQ-261005141830-7a3b）

> 本文档面向：多项目并行的窗口使用者、插件维护者、驱动 Dive 的 Agent 窗口。
> 一句话：把「是不是同一个项目」的判据，从**路径字符串比较**换成**项目 id 相等**——
> 映射是 **`session → projectId → workspaceRoot`**：会话只解析出 `projectId`，根挂在项目上（`projectId` 里带着 `workspaceRoot`）。

## TL;DR

- **这是什么**：给 pmboard 补一层**项目身份映射**——`session → projectId → workspaceRoot`：多个窗口（N）解析到同一个 `projectId`（1）；`projectId` 里带着该项目的 `workspaceRoot`；需求记录只记 `projectId`。
- **为什么现在做**：判据是路径与进程内共享根，多窗口多项目并行时会互相覆盖、互相误判，产物可能算到错项目。
- **做完得到什么**：同一项目的多个窗口天然归一，跨项目不再串；判定用的判据可解释、可留痕。

## 业务流程图

```
  窗口 A（session-x）──┐
  窗口 B（session-y）──┼─▶ projectId = w-1 ─▶ 项目 w-1 ─ workspaceRoot = /…/dsh-pmboard
  窗口 C（session-z）──┘         ▲              （1 个项目 ↔ N 个窗口：同项目多窗口是常态）
                                 │
  窗口 D（session-w）───────▶ projectId = w-2 ─▶ 项目 w-2 ─ workspaceRoot = /…/dsh-notice-webhook

需求 REQ-A（projectId = w-1）──┐
需求 REQ-B（projectId = w-1）──┼─▶ 项目 w-1 ─▶ 用它的 workspaceRoot 读 / 写 / 扫描
需求 REQ-C（projectId = w-1）──┘   （1 个项目 ↔ N 条需求：各归各位、互不影响）
        │
        ├─ 归属判定（**项目级**）：本条记录的 projectId == 本窗口解析出的 projectId ？
        │        ├─ 相等（同项目，**无论哪个窗口**）─▶ 取 w-1 的 workspaceRoot 工作（不读共享单例当前值）
        │        └─ 不等（跨项目）─────────────────▶ 跳过（留痕）或拒绝（写侧 fail-closed）
        ├─ 起轮 / 投递（**窗口级**，不放宽）───────▶ 仍按需求绑定的窗口 / 席位：同项目多窗口不重复起轮
        └─ 任一侧解析不出 projectId ─▶ 路径形状比较兜底，并如实标注「未归属」
```

### 查找链路（谁在什么时候查什么）

> 两个方向、两次查表：**窗口 → 项目 → 根**（立项 / 看板 / 起轮）与**需求 → 项目 → 根**（读盘 / 写盘 / 门禁 / 执行链）。
> 关键点：`projectId` 与 `workspaceRoot` 是**同一条项目条目上的两个字段**（一次查表同时拿到），不需要"先查 id 再按路径反推根"。

```
【方向一】窗口 → 项目 → 根            触发者：立项 / 看板请求 / Dive 的 idle 拍 / 派席校验
   windowKey（= 会话 id）
        │
        │ ① 查项目表：workspaceRegistry.list() 里 sessionIds 含本会话的那一条（N 个窗口 → 1 条）
        ▼
   项目条目 { id, path, sessionIds }
        ├──▶ projectId = 条目.id        （② 同一次查表顺带拿到，不用再查）

        ├─ Dive：projectId 与 record.projectId 比对   （归属项目级；起轮仍按席位/窗口）

        │
        │ ③ 按 id 取记录（台账）
        ▼
   record.projectId
        │
        │ ④ 查项目表：条目.id == projectId → 取条目.path
        ▼

【判据分叉】"是不是同一个项目"（全仓唯一判据 sameProjectOf）
```

## 映射基数（谁对谁，几对几）

> 「现状」列是**本次改动前**的实情，不是目标态——凡标 ❌ 的都是本次要实现或补齐的。

| 映射 | 基数 | 现状 | 说明 |
|---|---|---|---|
| `session` → `projectId` | **N : 1** | ❌ 未实现（无 `projectId`） | 同一项目下可以开多个窗口；窗口不唯一标识项目 |
| `projectId` → `workspaceRoot` | 1 : 1 | ❌ 未实现 | 根挂在项目上，由 `projectId` 带出（项目改路径则根随之变） |
| `需求` → `projectId` | **N : 1** | ❌ **未实现（本次重点）** | 一个项目下多条需求；现状记录无 `projectId`，只能拿路径比，**"按项目聚合需求"做不到** |
| `需求` → `窗口` | N : N | ✅ 已实现（席位 `seats`） | 一条需求可有多个窗口（owner / worker / observer） |
| `projectId` → `窗口` | **1 : N** | ❌ 未实现 | 同项目多窗口**不得**被判成两个项目；也不得被当成"一条需求只有一个窗口" |

两条**不可混用**的规则（N:1 与 1:N 真正的坑）：

1. **归属判定用项目级**（`projectId` 相等）：同项目的任一窗口都算"本项目"，看板可见、可读、可写。
2. **起轮 / 投递 / 弹框 / 席位仍用窗口级**（`windowKey`）：不能把 `projectId` 当窗口用，否则同项目两窗口会重复起轮、互相冒充 owner。

而"一个项目下多条需求"还引出一条**守卫语义**必须澄清（现状已存在、但从未写明）：

| 守卫 | 现状语义 | 本次要求 |
|---|---|---|
| `REQBOARD_WINDOW_BOUND` | **窗口级**：本**窗口**已绑定进行中需求即拒（`reqboard_capture` 的 `second` 分支可显式跳过） | 保持窗口级——**不得**推广成"一个项目只能有一条需求"；一个项目下多条需求是正常态 |

## 产品定义

一句话：**项目身份层**——会话解析出 `projectId`，`projectId` 带着项目的 `workspaceRoot`；「同一项目」按 id 相等判定，路径只负责回答"文件在哪"。

三要素：

| 要素 | 内容 |
|---|---|
| 是什么 | 映射链 `session → projectId → workspaceRoot`：**N 个窗口 → 1 个 `projectId`**（同项目多窗口是常态）；**根是项目的属性**（`projectId` 里带着 `workspaceRoot`）；需求记录只携带 `projectId`；「同一项目」按 id 相等判定 |
| 核心价值 | 多窗口多项目并行时不再串项目：同项目的 N 个窗口天然归一（同 `projectId` → 同一根），不同项目不会被共享根或同形路径误判 |
| 与现状的区别 | 现状把**路径**当身份（记录上的 `workspaceRoot` 字符串 + `sameProjectRoot` 形状比较），`session` 与 `workspaceRoot` 之间**没有 id 这一跳**；路径是**位置**不是**身份**——软链 / 相对写法 / 移动 / 复制都会让"同一项目"裂成两个身份，而共享单例根的当前值又曾被当判据（REQ-261005123641-3982 的 34 秒串根事故） |

## 用户与角色

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 多项目并行的使用者 | 同时开 2+ 个窗口，分别在不同项目里干活 | 一个窗口的动作会改掉另一个窗口的根与判定，产物可能落到错项目，排查只能靠翻日志 |
| 插件维护者 / 开发 | 改根解析、看板扫描、知识层自举这些跨项目链路 | 每个判定点各写一套路径比较，改动时数不清还有几处旁路 |
| Agent 窗口（Dive 驱动） | 起轮 / 投递 / 写盘时判断"这条需求是不是我这个项目的" | 只能读共享单例根或路径字段，判据不稳，出错时现场无声 |

## 现状与根因（为什么会有这个需求）

现状（已核实）：

- 唯一权威是需求记录上的 `workspaceRoot`（路径）：**缺 `session → projectId → workspaceRoot` 这条映射链**——根直接挂在记录上，见 [读盘闸门的根解析](../gate-read-root.md) 与 REQ-261005123641-3982。
- **`需求 → projectId` 这条映射今天不存在**（记录上没有 `projectId`）：实测台账 72 条记录里 **56 条** `workspaceRoot` = `/Users/mac/Documents/ai/dsh/dsh-pmboard`（**同一项目下多条需求今天已是常态**），而带 `projectId` 的记录 **0 条**——所以"这个项目下有哪些需求"只能逐条比路径，跨项目还会误判；按项目聚合、按项目统计都做不了。
- 「同一项目」的判定函数是 `sameProjectRoot`：只做字符串形状归一（反斜杠、重复斜杠、尾斜杠），**不注入 realpath**。
- `deps.docs` / `deps.queueRepo` 是**宿主级、跨窗口共享**单例，根会被别的窗口改掉；初始根是插件宿主的 `process.cwd()`。

根因三条：

| 编号 | 根因 | 证据 / 位置 |
|---|---|---|
| R-1 | **路径被当成身份**：同一项目换一种写法（软链、相对、尾斜杠）就是两个身份；项目移动 / 复制则身份漂移 | `sameProjectRoot` 无 realpath 分支；`REQ-261001203710-0fbf` 已把"软链算两个键"记为已知边界 |
| R-2 | **共享单例的当前值曾参与判定**：读侧靠"先按记录校正"补救、写侧靠"先校正再核验"补救——补救的前提仍是"路径可信" | `gate-read-root.md`（读侧 7 处接线）与 REQ-261005123641-3982（写侧现行口径） |
| R-3 | **宿主早就给了项目 id，判定链一处没用**：`workspaceRegistry.list()` 的 `id` + `path`（= 项目的 `workspaceRoot`）+ `sessionIds` 只在开窗落点用到 | `SessionWindowOpener.resolveSourceProject`（`sessionIds` 反查 `workspace.id`）；`path` 未参与任何归属判定 |
| R-4 | **"一个项目下多条需求"缺归属层**：需求已经在同一项目里成堆（改不动的是"怎么问出来"），记录无 `projectId` ⇒ 只能各自拿路径认领，"本项目有哪些需求"答不出 | 实测 2026-10-05：`~/.dsh/reqboard/**/record.json` 共 72 条，其中 56 条 `workspaceRoot` = 本项目、带 `projectId` 的 **0 条**；台账查询过滤只有可选 `workspaceRoot`，没有 `projectId` |
| R-5 | **席位 / 交接没有项目校验**：`reqboard_bind` 只校验"调用者是不是 owner"与席位上限，**不校验被派席窗口属于哪个项目** ⇒ 可以把别的项目的窗口派成本项目需求的 worker（那个窗口随后替本项目写盘），这是"多窗口不同项目串"的一条**合法入口** | `BindSeat.ts` 全文件零 `project` / `workspace` 字样；错误码只有 `NO_BOUND_REQ` / `NOT_BOUND_TO_WINDOW` / `SEAT_LIMIT` / `INVALID_INPUT` / `MUTATION_FAILED` |

#### 立项即定身份（FR-1）

- **FR-1: 立项即定身份（capture / create 写入项目 id）**

**功能描述**：人在某窗口立项后，系统把该窗口所属项目的 id 写进需求记录。

**详细说明**：
- **使用场景**：多项目并行时，人在窗口 A（项目 P1）用 `reqboard_capture` 立项。
- **操作流程**：
  1. 弹框作答 → 系统用窗口会话 id 解析项目 id。
  2. 记录只写 `projectId`（根**不落在记录上**——要用根时由 `projectId` → 项目 → `workspaceRoot` 取；存量兜底见 FR-8）。
  3. 解析不到项目 id（窗口不属于任何 workspace）→ **不写** `projectId`，在立项评论里如实标注"未归属项目"。
- **预期结果**：记录一出生就带身份；日志与立项评论能看出这条需求属于哪个项目。
- **边界条件**：
  - 窗口不属于任何 workspace（宿主"未分组"）→ 不猜、不编 id，走未归属路径。
  - 第五问填的绝对工作区路径与 `projectId` 带的 `workspaceRoot` 冲突时，**以 `projectId` 为准**（根由 id 带出，人填的那份不作数）。

**验收标准**：
1. 在已归属 workspace 的窗口立项 → 记录 `projectId` 非空且等于该 workspace 的 `id`。
2. 用"无 workspace 归属"的假会话立项 → 记录无 `projectId`，且评论出现"未归属项目"字样。
3. 用该记录的 `projectId` 取根 → 等于项目实体的 `workspaceRoot`，而不是窗口 cwd。

#### 会话→项目 id 解析端口（FR-2）

- **FR-2: 会话→项目 id 解析端口（宿主注册表反查）**

**功能描述**：新增只读端口，把会话 id 解析成项目 id。

**详细说明**：
- **使用场景**：任何"知道窗口、要知道项目"的判定点（立项、看板请求、Dive 起轮）。
- **口径**：与 `SessionWindowOpener.resolveSourceProject` 同源——`workspaceRegistry.list()` 中 `sessionIds` 含该会话的那条 → `workspace.id`（数字 id 归一为字符串）。
- **预期结果**：命中返回 id；未装配注册表 / `list` 抛错 / 未命中 → 返回 `undefined`。
- **边界条件**：绝不编造 id；不在 application 层 import 宿主包（端口 + 适配器，沿用层边界门禁）。

**验收标准**：
1. 假注册表（两条 workspace）→ 各会话解析出各自 id。
2. 注册表未装配 / `list` 抛错 / 会话不在任何 `sessionIds` → `undefined`（断言"不抛、不编造"）。

#### 项目 id → workspaceRoot（FR-3）

- **FR-3: 项目 id → workspaceRoot（身份带出根，不靠路径反推）**

**功能描述**：拿到 `projectId` 就能取到该项目的 `workspaceRoot`（工作区根路径），供文件读写定位。

**详细说明**：
- **映射关系**：`session → projectId → workspaceRoot`——根存在**项目实体**上（`projectId` 里带着 `workspaceRoot`），**不在需求记录上**，也不靠路径反查项目。
- **操作流程**：
  1. 用 `projectId` 从项目实体取 `workspaceRoot`。
  2. 项目实体取不到（注册表未装配 / 项目已删）→ 回落该记录自带的 `workspaceRoot`（存量兜底）并标注来源。
  3. 两者都拿不到 → 结构化报出（不静默回落宿主目录）。
- **覆盖所有按根定位的调用点**：不只文件读写——**执行链给子代理的 prompt 根、队列文件（`<root>/docs/requirements/<REQ>/queue.json`）、验收 / 归档路径、看板请求的读根**一律用 `projectId` 带出的根，不用共享单例的当前值（现状 `ExecuteTask` 就取 `deps.docs.workspaceRoot()`）。
- **预期结果**：同一项目无论从哪个窗口调用，取到的根一致；根来自"哪个项目"，不来自"最后一个调用的窗口"。
- **边界条件**：项目已删但记录仍留旧路径 → 按 ② 回落并标注；回落也没有 → 拒绝并给修复指引。

**验收标准**：
1. 同一项目两个窗口分别调用 → 取到的根一致，且等于项目实体的 `workspaceRoot`。
2. 项目实体缺失 + 记录有 `workspaceRoot` → 回落该路径并标注来源。
3. 两者都缺 → 返回结构化失败码（断言错误码，而不是空串）。
4. 共享根被另一项目的窗口改走时，执行链给子代理的 prompt 根、队列文件位置仍等于本条需求项目的根（断言不含别的项目路径）。

#### 同一项目判据单点收敛（FR-4）

- **FR-4: 同一项目判据单点收敛（id 优先、路径兜底）**

**功能描述**：把"是不是同一个项目"的判定收敛到一个实现，判据优先级写死。

**详细说明**：
- **判定顺序**：两侧都有 `projectId` → 比 id 相等（根不参与比较，同一 id 必然同一根）；任一侧缺 id → 路径形状比较（沿用 `sameProjectRoot`）并标 `attributed=false`。
- **同项目多窗口（N:1）**：窗口 A 与窗口 B 同属一个 `projectId` → 判**同一项目**（不得因为窗口不同而裂成两个项目）；归属是项目级的，窗口只作投递与席位键。
- **预期结果**：软链 / 相对写法 / 尾斜杠不再产生第二个身份；调用方不必各写一套。
- **边界条件**：id 缺失是**如实降级**而非静默放行——跨项目命中要留痕（FR-9）。

**验收标准**：
1. 同一项目、两种路径写法（含软链）→ 判同一项目。
2. 两个不同项目、路径字符串恰好同形 → 判不同项目（id 优先）。
3. 两侧都缺 id → 走路径比较，且结果标注"未归属"。
4. **同一 `projectId` 的两个窗口（A/B）→ 判同一项目**，且取到的根相同；窗口 `session-x` 与 `session-y` 的差异不得影响判定。

#### 写侧按项目 id 校正共享根（FR-5）

- **FR-5: 写侧按项目 id 校正共享根（保持 fail-closed）**

**功能描述**：写入前把共享单例的根校正到"这条记录的项目根"（由 id 解析），校正失效才拒绝。

**详细说明**：
- **操作流程**：按需求 id 取记录 → 有 `projectId` 就由它带出项目根（FR-3：projectId → workspaceRoot），无 id 沿用现有 `workspaceRoot` 口径 → 把 `docs` / `queueRepo` 校正到该根 → 复核。
- **预期结果**：写盘永远落在"记录自己的项目"；共享根的当前值不参与判定（只作缓存）。
- **边界条件**：校正失效（端口无 `setWorkspaceRoot`）→ `REQBOARD_PROJECT_ROOT_MISMATCH`（给两个绝对路径）；声明根不可用 → `REQBOARD_INVALID_WORKSPACE`。

**验收标准**：
1. 模拟"另一窗口把共享根改走"→ 本次写入仍落在本记录项目，且无异常。
2. 端口不支持换根 → 抛 `PROJECT_ROOT_MISMATCH`（反向用例，防"短路 exists"式假修复）。

#### 看板扫描与知识层自举按项目 id 分区（FR-6）

- **FR-6: 看板扫描与知识层自举按项目 id 分区**

**功能描述**：看板扫产物、知识层自举的"这是不是我项目"判定改按项目 id。

**详细说明**：
- **操作流程**：`ArtifactSync` 的分区输入从"比较路径"改为"比较项目 id"（无 id 回路径）；`KnowledgeBootstrap` 的去重键从归一路径改为项目 id。
- **预期结果**：扫描不会拿本项目根去扫别人家的同名目录；同一项目的知识层只自举一次。
- **边界条件**：无 id 的存量记录仍按路径处理并计数标注（FR-8）。

**验收标准**：
1. 两个项目各有一个同名目录 → 扫描结果只登记本项目产物（沿用 `tests/project-scope.test.ts` 的判别断言）。
2. 同一项目两个窗口触发自举 → 只跑一次（并发合并为同一 promise）。

#### Dive 驱动归属按项目 id（FR-7）

- **FR-7: Dive 驱动：归属按项目 id、起轮仍按窗口**

**功能描述**：Dive 的**归属判定**（能不能读 / 写 / 扫描这条需求）按项目 id；**起轮与投递**仍按需求绑定的窗口 / 席位，不因同项目而放宽。

**详细说明**：
- **操作流程**：
  1. 驱动拍（idle）里用窗口会话 id 解析 `projectId`。
  2. 归属：与需求记录的 `projectId` 比对 → 相等（同项目，**任一窗口都算**）才允许读 / 写 / 扫描；不等 → 跳过并留痕，绝不投递。
  3. 起轮：仍看"这条需求绑的是哪个窗口 / 席位"——同项目的另一个窗口即使 idle，也不重复起轮（避免双窗口重复投递）。
- **预期结果**：多项目并行时，窗口 A 的 idle 拍不会推进 / 写盘到别的项目的需求上；同项目多窗口也不会重复起轮。
- **边界条件**：任一侧缺 id → 走路径兜底 + 留痕说明（FR-4 / FR-9）；`projectId` 不可当窗口用。

**验收标准**：
1. 两个项目各一条 armed 需求 + 两窗口 idle → 各自只推进自己的需求（断言投递次数与目标窗口）。
2. 需求与窗口 `projectId` 不等 → 零投递 + 一条留痕（断言无投递、有记录）。
3. **同一项目两个窗口同时 idle** → 归属判定都为"本项目"，但**起轮仍只发生一次**（断言不重复投递）。

#### 存量兼容（FR-8）

- **FR-8: 存量兼容（路径兜底 + 未归属如实标注）**

**功能描述**：没有项目 id 的老记录不迁移、不拒写，继续可用。

**详细说明**：
- **预期结果**：老记录的读 / 写 / 扫描行为与今天一致，只是判定结果标注"未归属（按路径）"。
- **边界条件**：`REQBOARD_SCHEMA_VERSION` 维持 9（可选字段 + 读端折算，与 `seats` 同款先例），不升版。

**验收标准**：
1. 造一条无 `projectId` 的记录 → 读、写、推进全通（与改造前逐字一致）。
2. 返回体或评论里能看到"未归属"标注。

#### 判据可观测（FR-9）

- **FR-9: 判据可观测（用 id 还是路径兜底，说出来）**

**功能描述**：判定链的每一处把"本次用了哪个判据"暴露出来；跨项目命中必留痕。

**详细说明**：
- **操作流程**：工具返回体 / 需求评论 / 日志字段带 `projectId` 与判据来源（`project-id` / `path-fallback`）。
- **预期结果**：出问题时不靠翻日志猜——现场就能看出判据与两侧取值。
- **边界条件**：不得因此新增"面向用户的项目管理页面"（见边界）。

**验收标准**：
1. 一次跨项目拒绝 → 返回体或评论含两侧项目 id 与判据来源。
2. 走路径兜底 → 文案含"未归属"。

#### 同一项目下多条需求（FR-10）

- **FR-10: 同一项目下多条需求（按项目聚合，多条互不影响）**

**功能描述**：一个项目（一个 `projectId`）下可以有**多条需求**：能按 `projectId` 列出该项目全部需求，多条之间互不影响；建立新需求不受"本项目已有需求"阻拦。

**详细说明**：
- **现状缺口**：`需求 → projectId` 这条映射今天**不存在**（实测：台账 72 条记录里 56 条同属本项目，带 `projectId` 的 0 条），所以"这个项目下有哪些需求"答不出，只能逐条比路径。
- **操作流程**：
  1. 立项时写入 `projectId`（FR-1）→ 同一项目的多条需求因此共享同一 `projectId`。
  2. 台账查询 / 看板扫描 / 知识层自举按 `projectId` 过滤，得到该项目的需求集合（不再逐条比路径）。
  3. 守卫语义保持**窗口级**：`REQBOARD_WINDOW_BOUND` 判的是"本窗口是否已有绑定需求"，**不是**"本项目是否已有需求"。
- **预期结果**：同项目下 5 条需求各归各位：看板能按项目切出这 5 条；推进其中一条不改另一条的产物归属与根。
- **边界条件**：
  - 同一窗口仍受"一窗口一需求"守卫约束（要在一个项目里开第二条，走既有的 `second` / 新窗口分支）。
  - 无 `projectId` 的存量需求不进"按项目聚合"的结果，另行按路径兜底并标注（FR-8）。

**验收标准**：
1. 造同一 `projectId` 下 3 条需求 → 按 `projectId` 查询返回 3 条；按另一个 `projectId` 查询返回 0 条。
2. 在同项目另一窗口立项 → **不被"本项目已有需求"拒绝**（只有"本窗口已绑定"才拒）。
3. 推进其中 1 条 → 另 2 条的 `projectId`、根与产物归属零变化（断言前后快照相等）。

#### 席位与换绑按项目校验（FR-11）

- **FR-11: 席位与换绑按项目校验（跨项目默认拒绝）**

**功能描述**：派席（`reqboard_bind`）与交接（`reqboard_handoff`）时，被派 / 接管的窗口必须与需求属于**同一个 `projectId`**；跨项目默认拒绝并如实报出。

**详细说明**：
- **现状缺口（R-5）**：`BindSeat` 只校验"调用者是不是 owner"和席位上限，**不看项目**——owner 在 P1 可以把 P2 的窗口派成 worker，那个窗口随后就能替 P1 写盘，这是"多窗口不同项目串"的**合法入口**。
- **操作流程**：
  1. 派席 / 交接前解析两侧 `projectId`：需求的（记录字段）+ 目标窗口的（FR-2，按 `sessionIds` 反查注册表——**冷会话也能查**，不需要活体 agent）。
  2. 两侧相等 → 放行（同项目多窗口是常态，见 D-7）。
  3. 不等 → 拒绝 `REQBOARD_CROSS_PROJECT_SEAT`，文案给**两个 `projectId`** 与各自根，说明"跨项目不得派席"。
  4. 任一侧解析不出 `projectId` → 不拒也不放行得含糊：按路径兜底判定并**在回执里标注判据**（FR-9）。
- **预期结果**：跨项目窗口不可能成为本项目需求的席位；同项目窗口照常可派席。
- **边界条件**：`remove=true`（解绑）不因项目变化而拒绝（只做减法，不引入新写入方）。

**验收标准**：
1. 需求属 P1、目标窗口属 P2 → 派席被拒，错误码 `REQBOARD_CROSS_PROJECT_SEAT`，文案含两个 `projectId`。
2. 需求属 P1、目标窗口也属 P1（不同 session）→ 派席成功（断言 `changed=true`）。
3. 目标窗口查不到 `projectId` → 走路径兜底且回执标注"未归属"（不静默放行）。
4. 交接（handoff）到跨项目窗口 → 同样被拒，且台账零改动。

## 接口与数据契约

| 项 | 变更 | 必填性 / 默认 | 兼容 |
|---|---|---|---|
| `RequirementRecord.projectId` | 新增可选字段（宿主 workspace id，字符串）——**记录上唯一的归属字段** | 可选；缺省 = 未归属 | 读端折算；schema 维持 9 |
| `RequirementRecord.workspaceRoot` | 角色降级：由「判定唯一权威」降为「存量兜底 + 来源标注」（新记录不再靠它定位） | 可选 | 老记录照旧可用（路径兜底） |
| 需求摘要 `RequirementSummary` | 同步带 `projectId` | 可选 | 老分片缺键 → undefined |
| 端口 `ProjectIdentityPort` | 新增：`projectIdOf(sessionId)`（会话→id）、`workspaceRootOf(projectId)`（id→根） | 未装配 → 判定走路径兜底 | 老装配零行为变化 |
| 判定函数 | 新增单点（id 优先、路径兜底）；`sameProjectRoot` 降为兜底分支 | — | 现有调用方语义不变 |
| 错误码 | 新增 `REQBOARD_CROSS_PROJECT_SEAT`（跨项目派席 / 交接被拒） | — | 新码；既有码语义不变 |
| 台账查询过滤 | 新增按 `projectId` 过滤（与既有可选 `workspaceRoot` 过滤并列） | 可选；不传 = 全量（老行为） | 老调用方零变化 |
| 判定 vs 投递的键 | **归属 = `projectId`（项目级，N 窗口共享）**；**投递 / 席位 / 弹框 = `windowKey`（窗口级）** | — | 现有席位语义不变；两者不得互相冒充 |
| 工具返回体 | 增 `projectId` / `projectSource` 字段 | 可选 | 前端不读也不报错 |

## 迁移与兼容

- 存量记录：**不迁移**（无 id 继续路径兜底），符合用户裁定 D-3。
- `workspaceRoot` 的角色变化：从「判定的唯一权威」降为「存量兜底 + 来源标注」；判据与定位都以 `projectId` 起步（`session → projectId → workspaceRoot`）。
- 新字段可选 → 不升 `REQBOARD_SCHEMA_VERSION`；老分片 / 老 SQLite 行缺键即 undefined。
- 回滚：判定函数保留路径分支；去掉 `projectId` 装配即回到改造前行为（无需数据回滚）。
- 宿主能力缺失（无 workspace 注册表）：全局降级为路径兜底 + 标注，功能不中断。

## 边界（不做什么）

- **不做 DSH 宿主改造，也不自铸项目 id**：项目实体就用宿主 `workspaceRegistry` 的那一条（`id` + `path`(= `workspaceRoot`) + `sessionIds`），`projectId` 即 `workspace.id`（裁定 D-2）；pmboard 不发明第二套身份。
- **不做存量台账迁移**：没有项目 id 的老记录一律路径兜底 + 如实标注，不因缺 id 拒写（裁定 D-3）。
- **不改需求的对外 id、不加项目页面**：`REQ-xxxxxx` 仍是需求唯一 id；本次只加"项目归属"这一维。
