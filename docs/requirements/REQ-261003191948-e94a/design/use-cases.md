# 用例 · 谁在什么场景下拿到什么（REQ-261003191948-e94a）

## UC-1 · 升级后打开看板：从"一个 404"到"一条可跑的命令" `serves: FR-1, FR-2, FR-3, FR-4`

**角色**：插件使用者（本次事故的当事人）。
**前置**：数据根只有 v9 单册（`~/.dsh/dsh-reqboard.json`），`~/.dsh/reqboard/meta.json` 不存在。

流程：

1. 用户重启宿主 → `apply()` 预检命中迁移门 → 进入未就绪态（**不抛、插件已加载**）。
2. 用户点侧栏看板图标 → 客户端半边正常加载（apply 没抛 ⇒ 客户端 bundle 进了启动图）。
3. 页面首次拉 `/state` → **503** + `{error, code, hint}`。
4. 客户端 `unwrap` 把服务端文案与命令带上来 → 页面显示「台账未迁移」+ 一行可复制命令。
5. 用户复制命令、跑完迁移、在宿主里重新加载插件 → `/state` 返回 **200** 与真实需求条数。

**可观测结果**：第 4 步页面上**看不到** "HTTP 503" / "HTTP 404" 字样，只看到原因与命令。

**边界**：若客户端页面此时并未打开（无人看），宿主侧仍有 `logger.error` 与诊断日志一条（UC-4）。

## UC-2 · 全新安装：完全不受影响 `serves: FR-1, FR-5`

**角色**：第一次装这个插件的用户。
**前置**：单册与数据根**都不存在**。

流程：

1. 预检 `ok:true`（`migrationGate.ts` 表格第三行：不在 / 不在 → 正常启动）。
2. 走原有装配：建存储、注册工具、注册正常路由。
3. `/state` 返回 200 与空册——**这是合法的空册**（全新安装），与降级态的空册没有任何关系。

**可观测结果**：未就绪代码路径**一次都没执行**（T11b 用出现次数锁死）。

## UC-3 · 已完成迁移的用户：逐字节不变 `serves: FR-1, FR-5`

**角色**：已经跑过迁移的用户（含本次事故修复后的当事人）。
**前置**：单册在、`meta.json` 也在。

流程：

1. 预检 `ok:true`（表格第四行：在 / 在 → 正常启动）。
2. 原有装配全量执行，`hint` 字段从不被构造。

**可观测结果**：`git diff` 后跑 `npx vitest run tests/reqboard/migration-gate.test.ts` 全绿；
HTTP 响应体与改动前逐字节相同（不含 `hint` 字段）。

## UC-4 · 排查者：HTTP 与日志两条路都能拿到同一句话 `serves: FR-2, FR-3, FR-6`

**角色**：排查者（人或 agent）。
**前置**：同 UC-1。

流程：

1. 排查者 `curl -i http://127.0.0.1:19387/dashboard/api/reqboard/health` → **503** 且 body 含
   `code` 与 `hint`（**不需要**先知道要去看哪个日志文件）。
2. 若 curl 不可用，排查者读 `~/.dsh/state/reqboard-capture-diag.log` 末行 →
   得到与 HTTP 响应体**同一条** `code` 与 `hint`（不再是「apply function STARTED」半句话）。
3. 照 `hint` 跑迁移即可恢复。

**可观测结果**：两条通道的信息**同源**（都来自 `MigrationFailure`），不会出现"日志说 A、接口说 B"。

## 反例用例（明确不成立的路径） `serves: FR-5`

- **UC-X1**：未就绪态下 `reqboard_capture` 弹框 —— **不存在**。降级态不注册工具，
  模型根本看不到这些工具（T10b 从接线侧断言未注入 `tools`）。
- **UC-X2**：未就绪态下点看板「+ 需求」按钮创建需求 —— POST 同前缀 → 503 + 原因；
  客户端把同一个失败信封呈现出来。**不会**写进任何空册。
- **UC-X3**：假装恢复了（页面显示空看板） —— 不可能：503 不是 200，
  `unwrap` 直接抛错，走的是错误呈现分支而不是 `buildBoard` 空态分支。
