# 需求说明（REQ-261007100513-6749 PM 插件 token 与耗时治理（缓存前缀稳定化 + 记账合并））

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。
> 本需求**没有界面产出**（sides=backend）：只改窗口 agent 与子代理的请求成本与行为，不产原型。
> 输入证据：`docs/reviews/REQ-261006130057-7a43-token-cost-diagnosis.md`（同口径全树统计）。

## TL;DR

- **这是什么**：治理 reqboard 驱动下「一条需求从立项到交付」的模型开销——让同一阶段内 system prompt 不再变化，易变状态只以增量进入会话；记账往返合并；子卡有请求预算。
- **为什么现在做**：实测基线（REQ-261006130057-7a43，含 30 个子代理）**2,324 次请求 / 输入 412.2M / 输出 1.40M（294:1）/ 墙钟 21.0h**。主窗口未命中输入的 **88%** 由 system prompt 重写打掉前缀缓存造成；**65%** 的输入被子代理长链吃掉。
- **做完得到什么**：同一阶段内 system prompt 版本数 = 1；同口径的未命中输入、请求数、墙钟显著下降，且留痕与门禁一条不少。

## 业务流程图

```
owner 窗口 ──每轮请求──▶ systemPrompt 头部（只随绑定关系变化，同阶段逐字节稳定）
     │                          │
     │                          └── 易变段（看板状态 / 当前任务 / 阶段纪律正文）
     │                                  └─▶ inbox「next-step」尾部注入（仅内容变化时）
     ├── 记账 ──▶ reqboard_task_move(批量) ──回执自带受影响的父子卡状态──▶ 1 次往返
     └── 派卡 ──▶ 子代理（预算 60 次/卡）
                        │
                        └── 到顶 ──▶ 停下汇报（卡评论 + 通知 owner）──▶ owner 显式放行 ──▶ 续跑
```

## 产品定义

reqboard 的窗口 agent 每推进一步都要重发整段上下文；本需求把「每轮重发什么」从
「整段 system prompt + 整段历史」收紧为「稳定头 + 增量尾部」，并给子卡装上预算与超限汇报。

核心价值：把当前 294:1 的输入输出比与 21h 的串行墙钟压下来，**同时不牺牲任何留痕与门禁**
（阶段纪律照旧进会话、状态照旧可查、超限照旧不静默）。

与现状的区别：现状每次阶段切换或任务切换都重写 system prompt 头部（实测 16 个版本），
前缀缓存整段作废；本需求改为稳定头 + 尾部增量，并让子卡成本可预期。

**三要素检查清单**：

- [x] 说清楚"是什么"：reqboard 驱动的请求成本治理（缓存前缀 / 记账往返 / 子卡预算）。
- [x] 说清楚"核心价值"：同等人力同等质量下，token 与墙钟显著下降且可回归。
- [x] 说清楚"与现状的区别"：不再重写头部、不再一次一问一答地记账、子卡不再无限跑。

### 功能点详细说明

### 同一阶段内 system prompt 头部逐字节稳定（FR-1）

**功能描述**：窗口 agent 在同阶段同任务下，system prompt 头部段内容不变。

**详细说明**：

- **使用场景**：owner 窗口正在 brainstorming/design/implementing 任一阶段推进一条需求。
- **操作流程**：
  1. 窗口绑定需求后，头部段写入「已绑定需求（id / 标题）」。
  2. 阶段推进、任务开工收尾、看板状态变化时，头部段**保持逐字节不变**。
  3. 易变内容按 FR-2 从尾部进入。
- **预期结果**：
  - 同一需求同阶段内，头部段版本数 = 1（实测基线为 16 个版本）。
  - 除会话首请求、跨夜缓存过期、模型切换外，不再出现「命中缓存 ≈16K + 未命中 ≈整段上下文」的请求。
- **边界条件**：
  - 窗口解绑 / 换绑（handoff、二次立项）→ 允许头部段变化一次。
  - 需求标题被改写 → 允许变化一次（低频，接受）。

**验收标准**：

1. 跑一条新需求走完 brainstorming→implementing，统计该会话 `system/message` 事件的不同版本数 → 同阶段内为 1。
2. 统计同会话中 `cacheReadTokens < 20000 且 inputTokens > 40000` 的请求数 → 0（排除首请求 / 间隔 >30 分钟 / 换模型三类）。

### 易变状态改尾部增量注入（FR-2）

**功能描述**：看板状态 / 当前任务 / 阶段纪律正文只在内容变化时进会话尾部。

**详细说明**：

- **使用场景**：阶段推进（brainstorming→design…）、任务开工与收尾、看板状态变化。
- **操作流程**：
  1. 组装易变段文本，与该窗口上一次已投递文本比对。
  2. 有变化 → 走 **inbox `next-step` 尾部注入**（追加到历史尾部，不动前缀）。
  3. 无变化 → 不注入。
- **预期结果**：
  - 注入**不新起 agent 回合**（不得使用 `agent.followup()` 一类会起新 loop 的路径）。
  - 每次注入只增加该段自身的 token，不再触发整段上下文重算。
- **边界条件**：
  - inbox 通道不可得（窗口不活跃 / 子代理调用）→ 退回头部注入并告警，**不得静默丢弃纪律文本**。
  - 单轮内头部与尾部都要变 → 尾部去重按内容哈希，重复内容不注入。

**验收标准**：

1. 连续两次组装得到同一文本 → session 日志中该窗口 `agent/inbox/spliced` 只出现 1 次。
2. 注入后紧邻请求的 `inputTokens` 增量 ≤ 该段字符数对应的估算 token 数（不再出现整段重算）。

### 阶段与任务切换不再翻版（FR-3）

**功能描述**：同一内容不重复注入，连续来回切换合并为一次。

**详细说明**：

- **使用场景**：一张卡收尾、下一张开开工，或「无在制任务 ↔ 有在制任务」两态来回。
- **操作流程**：
  1. 切换时先算新文本，与上一版比对。
  2. 文本等价（含空白差异）→ 不产生新版本。
  3. 短时间内两态反复 → 以最终态为准合并投递一次。
- **预期结果**：实测基线里 20 秒内翻两次、7 分钟内翻两轮的现象不再出现。
- **边界条件**：两态确实都要送达（如「无任务」→「任务 A」→「任务 B」）→ 允许各投递一次。

**验收标准**：

1. 构造「关一张卡 → 开下一张卡」序列 → 该窗口 `system/message` 或尾部注入的版本数 = 状态真实变化次数，无重复版本。
2. 构造「有任务 → 无任务 → 有任务」20 秒内往返 → 注入次数 ≤ 2（合并后）。

### 记账往返合并（FR-4）

**功能描述**：`task_move` 支持批量，推进回执自带受影响的父子卡状态。

**详细说明**：

- **使用场景**：子卡链同一批次多张卡一起收尾；或收尾后需要看父子链状态再决定下一张。
- **操作流程**：
  1. owner 一次调用提交多张卡的推进（每张卡带自己的目标状态与理由）。
  2. 回执**逐项**返回结果，并附带受影响的父卡与其子卡链状态摘要。
  3. 常规「推进一张卡 → 再看树」由一次调用完成，不再分两次。
- **预期结果**：
  - 记账类请求占 owner 窗口 prompt 的比例从 23% 降到 ≤10%。
  - 单卡推进的旧调用形态继续可用（行为与现状一致）。
- **边界条件**：
  - 批量中部分卡非法（非法边 / 节流 / 未满足前置）→ 合法卡照常落账，非法卡逐项给出原因码，**不整体回滚**。
  - 同一卡在同一批量里出现两次 → 拒绝该重复项并给原因。

**验收标准**：

1. 一次批量推进 3 张子卡 → 回执含 3 条逐项结果，且含父卡与子卡链状态摘要；台账 3 张卡状态正确。
2. 批量中混入 1 张非法边的卡 → 该卡返回错误码，其余 2 张落账成功。
3. 旧单卡调用 `{task_id, to}` → 行为与改造前一致（既有测试全绿）。

### 收尾节流不再逼出空转等待（FR-5）

**功能描述**：60s 节流窗口内给出可做之事或明确剩余时间，禁止靠 sleep 规避。

**详细说明**：

- **使用场景**：同一需求内多张卡需要在 60 秒内连续收尾（节流为防「一次调用关 4 个任务」的事故）。
- **操作流程**：
  1. 被节流拒绝时，回执给明确剩余毫秒数与可做的事（例如先做不涉及收尾的动作）。
  2. 允许在节流窗口内批量收尾（与 FR-4 合并成一次调用），不再一次一卡撞节流。
- **预期结果**：实测基线中的 `sleep 40`（规避节流）不再需要出现。
- **边界条件**：节流判据本身（同需求 60 秒内已有其他卡被本窗口关闭 → 拒）不改——它是事故 C 的防线。

**验收标准**：

1. 连续两次单卡收尾被节流 → 第二次回执含 `throttleRemainingMs > 0` 与可做之事文案。
2. 用批量收尾一次关 3 张卡 → 不触发节流拒绝（或返回可解释的合并口径），且不出现等待型命令。

### 子卡请求预算软门禁（FR-6）

**功能描述**：默认 60 次请求/卡，到顶先汇报，续跑需 owner 显式放行。

**详细说明**：

- **使用场景**：自动链派发子卡（研发 / 复核 / 测试 / 返工）执行时。
- **操作流程**：
  1. 卡开工，计数窗口开始；预算默认 60 次请求，可由卡上字段覆盖（便于测试与特殊卡）。
  2. 达到上限 → 子代理**停止发起新请求**，先汇报：做了什么 / 卡在哪 / 还差什么。
  3. 汇报写进卡评论，并通知 owner。
  4. owner 显式放行（一次可留痕的操作）→ 计数窗口重置，允许继续；未放行则卡停在原地。
- **预期结果**：
  - 超限必留痕：卡评论出现「预算到顶汇报」，owner 收到通知。
  - 不出现静默超限，也不硬杀正在收尾的卡。
- **边界条件**：
  - 汇报必须发生在**停止之后**（先停再汇报，不是汇报完继续跑）。
  - 放行幂等：重复放行不叠加无限预算，每放行一次对应一次明确的追加窗口。

**验收标准**：

1. 把某卡预算设为 3 次跑测试 → 第 3 次请求后子代理不再发起新请求，卡评论含汇报文本。
2. 未放行时该卡保持停止；执行一次放行 → 计数窗口重置且卡评论留痕。
3. 重复放行同一卡 → 不产生两个叠加窗口（幂等）。

## 失败与并发路径

- **注入失败**：inbox 通道不可得或投递被拒 → 退回头部注入，并在日志与卡评论写明「已退回头部注入」；**不得静默丢弃阶段纪律正文**（丢了窗口 agent 会越界推进）。
- **并发注入同一窗口**：两处同时组装（阶段切换 + 任务切换）→ 按内容哈希去重后串行投递；后到者内容等价则不投递。
- **批量写部分失败（FR-4）**：逐项落账，合法项照常生效；返回体含每项 `ok` 与错误码。**不做整体回滚**——整批回滚会把已合法推进的卡退回去，制造「状态倒退」这一更大的事故。
- **重复提交（FR-4）**：同一 `(task_id, to)` 重复出现 → 第二次被状态机拒（非法边）并给可读原因，台账零改动。
- **预算与续跑并发（FR-6）**：owner 放行与子代理恰好到顶同时发生 → 计数以台账为准原子递增；放行幂等（重复放行不叠加窗口）。
- **计数来源不可得（FR-6）**（会话事件缺失）→ 不阻断当前卡，但在卡评论标注「计数不可得」，不得静默按 0 处理。
- **状态机**：本需求不新增状态、不改既有合法边；FR-4 的批量项各走既有边，非法边一律拒绝并给原因（不静默改写）。

## 边界（不做什么）

- **不做复核输入包替代 fork（诊断 A4）**：复核改 fresh 子代理 + 紧凑输入包涉及派发口径与复核质量，**另立需求**——它比本需求更容易误伤复核深度，需要单独设计。
- **不做 Token Tab 的成本可视化（诊断 A7）**：本需求只交付可跑的 CLI 口径（见「非功能需求」的度量命令）；界面展示涉及 UI 与原型流程，**另立需求**。
- **不动流程纪律（诊断 B1/B2/B3）**：阻塞式确认的宽限、阶段边界换窗、截图合并属用法层纪律，不是代码改动，本需求不覆盖。
- **不改门禁判据与任务状态机合法边**：artifact_gates / DoneEvidenceSpec / 合法边是本仓事故防线，本需求只改「注入方式」与「往返次数」，判据一律不动。
- **不给子代理加硬杀**：FR-6 是软门禁（停下汇报），不是超时杀进程——硬杀会把快干完的卡提前干掉（已由 D-3 裁定）。

## 验收标准（整体）

1. 跑一条新需求走完 brainstorming→implementing（≥1 张父卡含子卡链），全程无人工干预。
2. 用「非功能需求」的同口径命令统计该需求全树 → 未命中输入与请求数相对基线下降，且不出现「缓存≈16K + 未命中≈整段」的请求（首请求/跨夜/换模型除外）。
3. 该需求的阶段纪律与当前任务指引全程可见（每次阶段/任务变化后，窗口 agent 的反应与新纪律一致）。
4. 子卡预算与超限汇报、owner 放行在卡评论中逐条可查。
5. `pnpm build` / `pnpm test`（基线比对）/ 类型检查全绿。

## 关键决策与取舍

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 易变内容怎么进会话 | 继续留在 system prompt 头部（现状） | 尾部 `next-step` 增量注入 | 头部一变整段前缀缓存作废：实测 16 次重写，其中 13 次请求合计 3.21M 全价未命中（owner 窗口未命中的 72%） |
| 子卡超预算怎么办 | 硬上限直接终止 / 只告警不阻断 | 软门禁：停下汇报 + owner 放行 | D-3 用户裁定；硬杀会提前干掉快完成的卡，只告警则约束力为零 |
| 批量推进失败怎么处理 | 整批回滚 | 逐项落账 + 逐项原因 | 整批回滚会让已合法推进的卡状态倒退，制造更大的状态事故 |
| 本轮范围 | 连 A4 复核输入包与 A7 界面可视化一起做 | 只做插件侧止血（A1/A2/A3/A6/A5） | D-2 用户裁定；A4 涉及复核质量口径，A7 涉及 UI 与原型流程，各自另立更安全 |
