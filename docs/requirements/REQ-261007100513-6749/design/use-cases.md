## UC-1 阶段推进时 system prompt 头部不再重写 `serves: FR-1`

**角色**：owner 窗口 agent（正在推进一条需求）。

**前置条件**：窗口已绑定需求，需求处于 brainstorming。

**步骤**：

1. 人确认需求文档，需求推进到 design（阶段变化）。
2. 窗口 agent 组装本轮 system prompt。
3. 继续推进到 decomposing、implementing（又两次阶段变化）。

**预期结果**：

- 头部段（system prompt section）在三步里**逐字节不变**，版本数 = 1。
- 会话日志中不出现「`cacheReadTokens` ≈ 16K 且 `inputTokens` ≈ 整段上下文」的请求。
- 阶段纪律正文与看板状态改由尾部注入送达（见 UC-2）。

**失败路径**：

- 若头部段仍随阶段变化 → 视为本条款未交付（阶段版本数 > 1 即失败）。
- 若阶段纪律正文**根本没进会话**（既没进头也没进尾）→ 视为注入丢失，比缓存失效更严重的缺陷。

## UC-2 任务切换只投递增量，且不重复投递 `serves: FR-2, FR-3`

**角色**：owner 窗口 agent。

**前置条件**：需求处于 implementing，已有子卡链在跑。

**步骤**：

1. 子卡 A 收尾（done），子卡 B 开工（in_progress），中间出现一次「无在制任务」的瞬间态。
2. 间隔数秒后又出现一次同样的两态往返。
3. 窗口 agent 组装易变段文本。

**预期结果**：

- 易变段走 **inbox `next-step` 尾部注入**，**不新起 agent 回合**（不出现「只有纪律、没有提问」的空转回合）。
- 同一文本连续两次组装 → 只投递 1 次（去重）。
- 两态往返合并 → 投递次数 ≤ 状态真实变化次数，不出现同一版本重复投递。
- 每次投递只增加该段自身 token，后续请求不再出现整段重算。

**失败路径**：

- 投递走 `agent.followup()` 一类会起新 loop 的路径 → 立即判失败（本仓已因它返工过一次，见 session-driver 注释）。
- 去重键用「时间窗」而不是「内容哈希」→ 内容真变了却被吞掉 → 判失败（纪律丢失比多投一次严重）。

## UC-3 一次批量收尾多张卡，不再撞 60s 节流 `serves: FR-4, FR-5`

**角色**：owner 窗口 agent。

**前置条件**：同一需求下 3 张子卡都已跑完各自的段，需要连续转 done。

**步骤**：

1. 一次调用提交 3 张卡的推进（每张带目标状态与理由）。
2. 回执逐项返回结果，并附带父卡与其子卡链状态摘要。
3. 其中 1 张因非法边被拒。

**预期结果**：

- 合法 2 张落账成功，被拒 1 张返回错误码与原因；**不整体回滚**。
- owner 不需要再单独调一次 `task_tree` 就能决定下一步（摘要已在回执里）。
- 不出现等待型命令（例如 `sleep 40`）来规避节流。

**失败路径**：

- 若批量调用在半途失败而整批回滚 → 已合法推进的卡状态倒退 → 判失败。
- 若节流拒绝文案不含「还要等多久」→ 判失败（既有 FR 已要求给出剩余时间）。

## UC-4 子卡跑到预算上限：先停下、再汇报、等放行 `serves: FR-6`

**角色**：子代理（领卡的研发/复核）、owner 窗口 agent。

**前置条件**：某张子卡的请求预算为 60 次（或测试用的低值）。

**步骤**：

1. 子代理领卡开工，逐次发起请求。
2. 达到预算上限。
3. owner 查看卡评论后决定放行。
4. owner 执行一次显式放行。

**预期结果**：

- 子代理在**达到上限后不再发起新请求**（先停），随后才汇报：做了什么 / 卡在哪 / 还差什么。
- 汇报写进卡评论，owner 收到通知。
- 未放行时该卡保持停止，不出现静默超限。
- 放行后计数窗口重置，卡继续；重复放行不叠加窗口（幂等）。

**失败路径**：

- 「先汇报后继续跑」→ 判失败（汇报不是免责声明）。
- 计数不可得（会话事件缺失）时按 0 处理 → 判失败；必须标注「计数不可得」。

## UC-5 注入通道不可得时的降级（失败路径） `serves: FR-2`

**角色**：owner 窗口 agent。

**前置条件**：窗口不活跃，或当前是子代理会话（无 inbox 通道权限）。

**步骤**：

1. 易变段内容发生变化，需要投放。
2. 尾部注入被拒或通道不可得。

**预期结果**：

- 退回 system prompt 头部注入，并在日志与卡评论写明「已退回头部注入」。
- 阶段纪律正文**不丢**：窗口 agent 仍能看到当前阶段纪律与任务指引。

**失败路径**：

- 静默丢弃纪律文本（窗口 agent 在无纪律状态下推进）→ 判失败；这类静默降级在本仓被明令禁止。

## 关键决策与取舍 `serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6`

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 易变内容落点 | 继续留头部（每次重写） | 尾部增量注入 | 头部重写打掉整段前缀缓存：实测 16 次，其中 13 次请求 3.21M 全价未命中 |
| 尾部注入的去重键 | 时间窗去重 | 内容哈希去重 | 时间窗会吞掉真实变化（纪律丢失），内容哈希只吞重复 |
| 注入通道不可得 | 静默跳过 | 退回头部 + 告警留痕 | 纪律文本丢失会让窗口越界推进，比缓存失效更贵 |
| 批量推进失败 | 整批回滚 | 逐项落账 + 逐项原因 | 回滚会造成已合法卡的状态倒退 |

## 技术方案与亮点 `serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6`

- **头部/尾部分层判据**：按「变化频率 × 文本体积」决定落点——窗口生命周期内不变的常量留在头部（吃缓存），高频小体积的增量走尾部（只付增量）。
- **实测支撑**：`system/message` 重写是**就地替换**（实测：13,338 字重写后下一次请求 prompt 215,924 → 215,832，Δ=−92，未增长整段），故头部重写必然使前缀缓存整段作废；而尾部注入不触碰前缀。
- **代价如实声明**：尾部注入会累积在历史里（每次约 30–3,300 token，按后续请求数放大）；本设计以「最小块 + 内容哈希去重」把它压到等效成本约 828K（现状 3.90M 全价，降幅约 79%）。
