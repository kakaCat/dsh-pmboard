## 背景与动机

本缺陷是 **REQ-260930182521-4fee 实施过程中发现**的旁路缺陷，与该需求本身的范围无关，故另立。

用户原话（2026-09-30）：

> 提交拆分计划时，若计划文档缺「需求条款 ↔ 接收任务」对照表会被 `requirement_uncovered` 拦下，提示信息已给出修法（已按提示补齐后通过）。

关键在于括号里那半句：**按提示补齐后就通过了**——这说明拦的不是"需求变更"，而是**门禁要求了一份提示词从未要求、且模板自带表结构又不被识别的表**。一份完全按拆分阶段提示词写出来的计划，必然被拦一次。

现场证据（`REQ-260930182521-4fee`，磁盘实测，同一份文档）：

- `docs/requirements/REQ-260930182521-4fee/decomposition.md:41` 有 `## 覆盖对照表`，表头 `| 需求条款 | 条款要点 | 接收任务 |`。
- 同文件 `:49` 有 `## 任务表`，表头 `| key | 标题 | phase | side | depends_on | serves |`。

结果：门禁**只读得懂**那张被事后补上的「覆盖对照表」（因为表头含「需求条款」+「接收任务」），而同文件里信息量等价、**本来就在提示词要求里的任务表读不到一个字**。

而插件自带模板 `templates/decomposing/decomposition.md` **三张表全部读不到**——实测（用真实 `taskRefsFromDecomposition` 直接跑模板文件）：

```
templates/decomposing/decomposition.md  →  taskRefsFromDecomposition(...) = []
```

模板里三张表逐张核对（每张都失败，**且失败原因各不相同**）：

| 模板表 | 表头（节选） | 实测结果 | 失败原因 |
|---|---|---|---|
| `:31` 任务表 | `计划 key / 任务 id / 标题 / 覆盖条款 / …` | `[]` | ①「覆盖条款」不在根编号同义词里 → `iRoot<0` 整表跳过；② 任务列是「任务 id」（落库前为占位「（落库后回填）」），计划键在「计划 key」列 → 无列可认 |
| `:41` 覆盖对照 | `需求条款 / … / 接收任务 / 完整性` | `[]` | ③ 接收任务格写作 `t1（1）`——括号里的**数量注记**过不了 `planKeysIn` 的标识正则 |

（`:13` 的「编号口径」说明表不含任务列，本就不参与，忽略。）

三条原因是**互相独立**的：修好任一条，另外两条仍然会让对应表读不到。这也解释了为什么现场那份计划**必须额外补一张干净形状的表**才能过门——它是三处失配下唯一能用的形状。

三处口径不同源（门禁读表口径 / 模板列名与格内写法 / 提示词交付要求），本需求要求**一起对齐并被测试锁住**，否则下次改模板、改提示词或改数量注记写法又会漂移。

本需求要修的条款：

- **BUG-1: 门禁列定位与格内写法覆盖模板自身口径**——`taskRefsFromDecomposition` 必须认得插件模板里真实存在的列名与格内写法，三者缺一不可：① 根编号列认「覆盖条款」；② 任务标识列认「计划 key」，并在「任务 id」为空/占位（「（落库后回填）」）时回落同行计划键；③ 任务标识格容忍数量注记写法（`t1（1）`、`t1, t2（2）`）而不整行丢弃。目标是**模板原样即可过门**。
- **BUG-2: 拆分阶段提示词把「覆盖对照表」写成显式交付要求**——提示词片段必须点名该表及其必需列（需求条款 ↔ 接收任务），与门禁同源；不得让报错文案承担"发现规格"的职责。
- **BUG-3: 三处口径的防漂移断言**——加测试锁住「模板任务表列名 → 门禁可解析」「提示词必含覆盖对照要求」，任一侧改动而另一侧没跟上即测试失败。

## 非目标

- N1 **不放松覆盖门禁的判定强度**——条款仍必须被任务接收或被显式标「本轮不做」，一个字不放宽。
- N2 不改 `requirement.md` 的条款定义行格式规范（`**FR-N: 名称**` 等）与编号连续性/唯一性门禁。
- N3 不改报错文案的 `what / why / how` 三件套结构——**本次正是它救了场**，是优点不是缺陷；本需求只让这句话不必再说一次。
- N4 不改模板的表结构（不删「覆盖对照」节、不改列语义、不改合计行口径）。

## 边界（不做什么）

**做**：

1. 门禁列定位与格内写法三处对齐：根编号列认「覆盖条款」；任务标识认「计划 key」并在「任务 id」占位时回落；任务标识格容忍数量注记（`t1（1）` → `t1`）。
2. 把「覆盖对照表」写进拆分阶段提示词片段，与门禁读表口径逐字对齐。
3. 加防漂移测试锁住上述两处 + 反向用例（该拦的仍拦）。

**不做**：

1. 不改 `checkClauseCoverage` 的覆盖判定与 `extractSkippedClauses` 的「本轮不做」裁剪口径。
2. 不改 RTM yaml 生成、`reqboard_decompose` 的落库与批准门、任务卡三要素门禁。
3. **不做「自动生成覆盖对照表」**——那会把人的"拉齐"动作变成机器的猜测，孤儿条款会被自动"认领"，正好抵消 N1 的意图。
4. 不改 `docs/requirements/<REQ>/decomposition.md` 的历史文档（存量计划不回填）。
5. 不动前端渲染与看板展示（覆盖状态本来就在看板上标红，本次只改"提交时是否误拦"）。

## 根因

代码级根因，三层（均为定位，不写修复代码）：

**① 门禁的「根编号」列定位不认模板自己的列名。**
`taskRefsFromDecomposition`（`application/internal/content-trace.ts:147`）：
`:152` `const iRoot = t.header.findIndex(h => h.includes('根编号') || h.includes('需求条款') || h.includes('需求编号'))`
——三个候选词里**没有「覆盖条款」**，而模板任务表（`templates/decomposing/decomposition.md:31`）用的恰恰是「覆盖条款」。
`iRoot < 0` → `:154` `continue` → **整张任务表被跳过**，不是少读几行。

**② 即使根编号列认出来，任务标识也取不到值。**
`:155` `const iTask = t.header.findIndex(h => h.includes('任务'))`：模板任务表里含「任务」的列是「**任务 id**」（该列在落库前的内容是占位「（落库后回填）」）；计划键在「**计划 key**」列，`includes('任务')` 匹配不到。
于是 `:171-176` 走到 `collectIds(taskCell)`（空）→ 回落 `planKeysIn(taskCell)`（中文占位符过不了标识正则）→ 空 → `:176` `continue`。
① 与 ② **同时失配**，任务表对门禁完全不可见——判别矩阵里 D/E 两行证明它们是**两条独立原因**，只修一条不够。

**③ 数量注记写法让格内标识解析失败（连干净形状的覆盖对照表也一起废掉）。**
`planKeysIn`（`:140-145`）的分词与净化：

```
cell.split(/[，,、\s|]+/)                        →  ['t1（1）']
   .map(s => s.replace(/^[（(]+|[）)]+$/g, ''))  →  't1（1）'（注记不在首尾，剥不掉）
   .filter(s => /^[A-Za-z][A-Za-z0-9_-]{0,39}$/.test(s))  →  丢掉
```

模板 `:41` 的覆盖对照表与现场计划都用「`t1（1）`」表示"该条款被 1 张任务接收"。该写法过不了标识正则 → 整行丢弃 → 表读成空。
判别矩阵 A/B 两行证明：**只去掉括号注记，同一张表立刻可解析**。这是第三条独立原因。

**④ 于是唯一可用的形状，恰好是提示词从未要求的那一张。**
门禁读得到的是 `## 覆盖对照表`（表头「需求条款」+「接收任务」，两个定位都命中；
`REQ-260930182521-4fee/decomposition.md:41` 即此形状）。
但拆分阶段提示词片段 `src/domain/prompt/fragments/decomposing/heavy.md` 的 §1–§6（改动盘点 / 批次依赖 / 每卡 implementation+acceptance / 边界校验 / 提交与批准门 / 交棒）**全文未出现「覆盖对照」**，只要求「`reqboard_submit(kind=plan)` 提交拆分计划（tasks=任务表）」。
⇒ **门禁依赖的表不在提示词的交付清单里**；合规作者只能靠 `requirement_uncovered` 的 `how` 文案被动发现。

**一句话**：门禁（列定位 + 格内写法）、模板（列名与注记写法）、提示词（交付要求）三处口径不同源。后果比"少读一张表"严重——**插件自带模板原样跑出的对应关系是空集**，即模板自己也过不了自己的门禁；判别矩阵 A–E 证明失败由**三条互相独立的原因**叠加而成。修法必须三处一起建立**同源关系**（且每条原因各有一条断言），而不是只改报错文案或只补一处同义词。

**为什么现场文档能通过**：`REQ-260930182521-4fee` 的计划里**额外**存在 `:41` 的「覆盖对照表」（按报错提示补的），且格内写法是干净的 `t1, t2`（无数量注记），三个条件恰好同时满足。任务表读不到不影响结果——这掩盖了缺陷，直到下一次没人提醒时再撞一次。
