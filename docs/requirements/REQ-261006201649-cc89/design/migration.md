# 迁移设计（REQ-261006201649-cc89）

> refactor 迁移篇：**改表 / 改 schema 吗？怎么回滚？存在什么兼容期？**
> 结论先行：**无表、无 schema 迁移、无迁移脚本**；迁移负担集中在
> 「存量需求（`createdAt` 早于规则生效日）行为逐字不变」的**证明**上。

## 是否改表 / 改 schema `serves: FR-4, FR-6`

| 问题 | 答案 | 依据 |
|---|---|---|
| 新增数据库表 / 列？ | **否** | 本仓台账是 JSON 分片（`~/.dsh/reqboard/requirements/<REQ>/*.json`），无关系 schema |
| 改既有 JSON 字段的**类型 / 必填性**？ | **否** | `StageArtifact.prototypeMeta.geometry[]` 只**新增两个加性可选键**（`shot` / `shotSha256`） |
| 需要迁移脚本（回填 / 改写旧分片）？ | **否** | 旧分片缺键 = **未采集**（`unverified`），不做补写——与 §9「兼容与迁移口径（零迁移）」同源 |
| 需要改 `schemaVersion`？ | **否** | 加性可选键不构成 schema 变更；`meta.json` 的 `schemaVersion` 不动 |
| 需要改协议必填字段？ | **否** | `VerificationItemSource` 形状不变；`CompareInputs` 形状不变 |

**为什么"缺键 = 未采集"而不是"缺键 = 违规"**：把缺键判成违规等价于**追溯存量**
（66 个分片、15 条有原型的需求全都会当场变红），而追溯存量违反本仓
「门禁上线 ≠ 追溯存量」纪律（`DocQualityRules.ts` 与 `rtm-health.ts` 两处注释都写明这条）。

## 兼容期行为 `serves: FR-3, FR-4`

| 面 | 兼容期口径 |

## 回滚路径 `serves: FR-1, FR-3, FR-4, FR-5`

本需求**每一步都可回滚**，且回滚不需要数据修复：

| 批 | 回滚动作 | 数据后果 |
|---|---|---|
| A（非骨架判据） | 撤掉锚点门内的第一问调用（一处 `if`） | 零——判据是**读时判定**，无写副作用 |
| B（对照项硬判据） | 恢复"按已登记 `.html` 产物条件化"的分支 | 零——已提交的验收单是快照，不回改 |
| C（几何量两键） | 撤 `observationEvidenceOf` 调用 | 零——新键是加性，旧读法照读 |
| D（对齐判据参数化） | 保留旧 `tests/prototype-parity.test.ts`（**本批不删该文件**） | 零——测试文件不进产物 |

**批间顺序约束（回滚安全性相关）**：B 依赖 A。
若 A 未上线而 B 先上线，会给「骨架原型的存量需求」强制生成对照项——
人只能对着骨架打勾，**那正是本需求要消灭的形态**。故 A 必须先合入。

## 灰度与观测 `serves: FR-1, FR-4`

不需要灰度（无流量影响、无写副作用），但**需要可观测**：

| 观测点 | 读数 | 用途 |
|---|---|---|
| 新码出现次数 | `prototype_placeholder` / `prototype_geometry_unverified` 在 rejected 反馈里的计数 | 上线后一眼看出"有多少需求被新判据拦下" |
| `unverified` 占比 | 几何量读数里 `unverified` ÷ 全部读数 | 判断存量何时自然衰减到 0 |
| 反向演练 | 两条演练的通过与失败（见 `test-cases.md`） | 证明判据**真的在量东西**（改不红 = 没量） |

**异常阈值**：若上线后 `prototype_placeholder` 命中数 **= 0 且** 反向演练 A 通过，
说明存量大面积"本来就是填过的"——**不视为异常**（读数如实）。
真正的异常形态是**反向演练 A 改不红**：那说明判据没接上。

## 关键决策与取舍 `serves: FR-1, FR-4`

本份主题相关的取舍（其余见 `architecture.md` 同名节）：

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 存量读数的处理 | 缺 `shot`/`sha256` 一律判违规 | 缺两键 ⇒ `unverified`（放行） | 一律判违规 = 追溯 66 个分片（假红）；假红会让真红失去信息量 |
| 新码 vs 复用旧码 | 复用 `prototype_anchor_missing` | 新码 `prototype_placeholder` | 两种坏的**补法不同**（填内容 vs 补锚点）；共码会让人靠读 gaps 猜 |
| 判据基线来源 | 另存一份"骨架指纹"常量 | 直接与 `PROTOTYPE_HTML_SKELETON` 比对 | 另存一份 = 两份真相；模板改了指纹不改必然漂移 |

## 技术方案与亮点 `serves: FR-4, FR-5`

与本份主题（迁移）相关的两点：

- **零迁移的加性键**：`shot` / `shotSha256` 是**读时校验**的加性可选键，因此
  "上线"与"回滚"都不触碰任何数据——这是本仓 §9 口径的直接复用，不是新发明。
- **可参数化判据的迁移价值**：FR-5 让"新需求要有对齐断言"从"再手写 194 行"
  变成"填三个字段"。这降低了**规则自身的迁移成本**——否则这条纪律上线后
  仍会因"太贵"而被跳过（现状 15 条有原型的需求只有 4 条真的对照过，就是代价的证据）。
