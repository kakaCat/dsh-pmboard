# 存量恢复演练记录（REQ-261006170150-52cc · t-0808ec）

> 结论先行：**零数据迁移**（真台账副本的树哈希前后逐字节相等），
> 且**恢复能力在真实历史记录上实测可用**（一条过期等待位 → 一趟心跳 → 清位 + 请求驱动恰 1 次）。

## 1. 演练要回答的两个问题

| 问题 | 为什么必须回答 | 本记录在哪答 |
|---|---|---|
| 新代码遇到**旧台账**会不会顺手迁移 / 改写它？ | 台账是生产数据，修复不该变成"一次隐式数据迁移" | §3 Phase A |
| 「过期后自动恢复」在**旧台账的真实记录**上真的成立吗？ | 台账早已写下这句承诺；只测新造数据不算兑现 | §4 Phase B |

## 3. Phase A · 零迁移（副本哈希前后相等）

在真台账副本（60 条需求 / 645 个文件）上跑一趟**真装配**的心跳（`ShardedRequirementStore` +
`createWakeHeartbeat`，`dialogInFlight` 接真 `PendingConfirmRegistry`）：

```text
[A 零迁移] 文件数：645 → 645（相等=true）
[A 零迁移] 树哈希：3f18d75a692ce9bacff28d26131c76e01b4d6595cf9f0696dc9d52ba307042a9
              → 3f18d75a692ce9bacff28d26131c76e01b4d6595cf9f0696dc9d52ba307042a9（相等=true）
[A 零迁移] 本趟心跳：resumed=0 skipped=4 woken=0 notifyDrivable=0
[A 零迁移] 旧台账里处于等待停手位的需求数：0
```

判读：

- **树哈希逐字节相等** ⇒ 读路径没有迁移、没有改写、没有新增字段（"无数据迁移"的可复核形式）。
- 本趟 `resumed=0` 是**正确**结果而非漏测：此刻旧台账里处于等待停手位的需求数为 **0**
  （即没有"卡在等人"的存量），所以没有任何东西需要恢复——这与 Phase B 的造场景正好互补。
- 树哈希按「相对路径 + 文件内容」排序后整体摘要，故它能同时捕捉"内容变了"与"文件增删/改名"。

> 读数边界：哈希值绑定**当次**台账内容。台账是活的（其他窗口在写），
> 因此每次复跑的具体哈希值可能不同；**判据是"同一次运行内前后相等"**，不是"等于本记录里的这串"。

## 4. Phase B · 恢复能力（在真实历史记录上造一条过期等待位）

另拷一份**丢弃副本**，从旧台账里挑一条**真实历史记录**（本次命中的是 `REQ-261006164732-6503`
——正是本需求依赖说明里提到的、当时被卡在等待位的那条），在它上面造一条**阻塞型**等待位，
把时钟推过阻塞档 TTL（60 分钟 + 1ms）后跑一趟心跳：

```text
[B 恢复能力] {"target":"REQ-261006164732-6503","stopWrittenBeforeExpiry":true,"resumed":true,
              "stopCleared":true,"recoveryComment":true,"notifyDrivableCalls":1}
```

逐项对上验收口径：

| 断言 | 读数 |
|---|---|
| 造等待位成功（前置） | `stopWrittenBeforeExpiry=true` |
| `resumed` 含该需求 | `true` |
| 停手位被清（非 awaiting） | `stopCleared=true` |
| 留下 `[Dive 恢复]` 且出口=`expired` 的台账评论 | `recoveryComment=true` |
| 清位后**请求一次驱动**（FR-2 的接点） | `notifyDrivableCalls=1`（恰 1 次） |

Phase B 与 Phase A **刻意分开**：A 的判据是"哈希前后相等"（证明零迁移），
而恢复的语义本身就是一次写入（清位 + 留痕）——混在一条判据里，两件事都说不清。
