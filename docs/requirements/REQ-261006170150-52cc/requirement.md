# 需求说明（REQ-261006170150-52cc 确认作答后不唤醒 agent：清位先于推进 + 清位即驱动 + 在途过期对账）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。

## TL;DR <!-- serves: FR-1 -->

- **是什么**：人点确认弹框后，状态**真的推进了**（brainstorming → design），但**没有新回合**——agent 停在原地，人必须手打一句「继续」。
- **为什么**：作答后清「弹框在途」停手位这一步被放在推进**之后**，于是推进触发的那次 `requirement-moved` 被自己的停手位挡下并丢弃；而清停手位是 `requirement-updated`，事件桥不转发 ⇒ 再没有任何触发。旧的三个唤醒实现里，两个已在 Dive 化中删空 / 硬跳。
- **得到什么**：确认（含后台弹框超宽限后作答）之后**无需人敲字**即续跑；过期弹框不再把需求永久钉在「等人」上；这条链断了要能从台账看出来。

## 业务流程图 <!-- serves: FR-1 -->

```
修前：确认能推进，但没人把 agent 叫起来
  submit(kind=requirement)
     └─自动弹框(宽限 2s)─▶ [停手位] driverHealth = paused / awaiting-confirm:pc-xxxx
                                │   agent 回合先结束（turn/end）
   人 29 秒后点「确认」           │
     └─▶ 落章 + 推进 brainstorming → design
           └─▶ requirement-moved ──▶ Dive drive()
                                      ├─ isDrivableRequirement? paused ⇒ false ← 挡下（本拍丢弃）
                                      └─ dialogInFlight? 仍 true      ⇒ 停手 ← 挡下
           └─▶ 清停手位（在 settle 之后）= requirement-updated ⇒ 桥不转发 ⇒ 无人再触发
   结果：状态=design、台账全绿、agent 不动；人只能手打「继续」

修后：清位先于推进，且清位本身请求一次驱动
   人作答 ─▶ ① 带本次 ref、await 清位（内存登记 + 台账停手位）
            ② 落章 + 推进（此时驱动那两道门都是开的）
            ③ 停手位被清 ⇒ 请求一次驱动 ⇒ round 半预留 → 投递 → 准入 ⇒ agent 续跑（无需人敲字）
```

## 产品定义 <!-- serves: FR-1 -->

**「人工门确认后的自动续跑」是这条流水线的引擎**：需求在 brainstorming → design → decomposing → implementing → accepting 之间前进时，每一次人工门确认之后都必须有人把 agent 从「停下等人」叫起来。

核心价值：把「点通过 = 流水线继续」变成**事实**，而不是靠人记得补一句「继续」。

与现状的区别：现状的三条唤醒实现只剩一条（Dive round 驱动器），而它唯一的自动触发会被这次确认**自己写下的停手位**吃掉；本需求不新增第四条路径，而是把断掉的时序与触发接回**既有**那条。

**三要素检查清单**：

- [x] 说清楚"是什么"：确认后不续跑的断链修复（清位时序 / 清位即驱动 / 在途过期对账）
- [x] 说清楚"核心价值"：人不再需要手打「继续」；停摆不再是静默的
- [x] 说清楚"与现状的区别"：不复活已删的投递路径，只补齐时序与触发，唤醒仍唯一经 round 半

## 用户与角色 <!-- serves: FR-1 -->

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 会话里的用户（需求方） | 弹框弹出时人在别处，回来才点「确认」 | 点完状态变了、agent 不动，只能自己敲「继续」；且得不到任何"为什么需要我敲"的解释 |
| 窗口 agent | 提交产物后等确认（后台弹框） | 它的回合已经结束，之后**不会**被叫起来；下一次被唤起完全取决于人是否恰好发了消息 |
| 维护者 | 加减唤醒触发点 / 改等待语义 | 「清位」与「驱动」是两条独立路径，靠约定而非机制对齐；断了只在进程日志里，台账无痕 |

## 功能点（需求条款） <!-- serves: FR-1 -->

| 编号 | 名称 | 一句话 | 优先级 |
|---|---|---|---|
| FR-1 | 作答即清位，且清位先于推进 | 任何确认通道在推进之前，必须带本次 ref、await 完成解除等待（内存登记 + 台账停手位两半） | P0 |
| FR-2 | 停手位被清即成驱动事件 | 停手位从 `awaiting-confirm:*` 变为 healthy 的那一刻，必须请求一次自动链驱动（走既有 round 半，不新增投递路径） | P0 |
| FR-3 | 在途登记的过期对账 | 在途登记按形态分档过期；过期即按"无人等待"恢复续跑，兑现台账里"过期后自动恢复"的承诺 | P0 |
| FR-4 | 断链可观测 + 回归锁 | 驱动本拍放弃要留可查、有界的痕迹；一条用例锁死「确认后无需人干预即起轮」并锁零回归 | P1 |

**FR-1: 作答即清位，且清位先于推进**

任何确认通道（会话弹框、Dive 门框、看板确认、文字证据、回执续跑）在写「落章 / 推进」之前，
必须先**带本次这票的 ref**、**await 完成**地解除等待：内存在途登记被移除，台账停手位
（`driverHealth = paused / awaiting-confirm:<ref>`）被清成 healthy。

- **使用场景**：后台弹框超宽限后由人作答（本次事故形态），或阻塞弹框超时后才作答。
- **操作流程**：人作答 → 收敛点清位（等它真的完成）→ 落章 → 推进 → 回执。
- **预期结果**：推进那次写发生时，该需求已「不在等人」。
- **边界条件**：只清**本次这票**；同需求若还有别的在途框，台账停手位**不得**被清（沿用现有 `stillWaiting` 语义）。

**判据**：构造「后台弹框转挂起 → 人作答」，断言台账停手位在推进那次写**之前**已非 `awaiting-confirm:*`，
且清位完成时 `inFlightFor(需求)` 已为 false；同需求第二票在场时停手位保持不动。

**FR-2: 停手位被清即成驱动事件**

当某需求的停手位从 `awaiting-confirm:*` 变为非该前缀（healthy）时，必须**请求一次自动链驱动**。
驱动仍走 round 半既有 `requestDrive`（预留 → 投递 → 准入），**不新增任何进会话的投递路径**，不绕过准入。

- **使用场景**：人手点确认（任一通道）、心跳对账清掉过期停手位。
- **操作流程**：清位成功 → 回调一次驱动请求 → round 半按既有条件判定 → 满足则起轮。
- **预期结果**：**无需人手发消息**，出现新回合（`source.kind='dive'` 回合消息 / `roundsInStage` +1）。
- **边界条件**：仍受既有四条件约束（`activation=armed`、健康非 paused、agent 闲置、无人门开着）；
  不满足则照旧不起轮。重复清位不叠加（`requestDrive` 自带合并语义）。

**判据**：单测 + 端到端用例：清位后不注入任何用户消息 ⇒ 起轮一次；同拍两次清位 ⇒ 仍只起一轮；
未 armed / 健康 paused 时清位 ⇒ **不起轮**（零回归）。

**FR-3: 在途登记的过期对账**

在途弹框登记必须有**分档过期**，且过期后 `inFlightFor` / `list` 按"无人等待"返回：

| 形态 | 判据字段 | 过期不得晚于 | 过期不得早于 |
|---|---|---|---|
| 挂起型（作答靠后台续跑） | `suspend=true` | 挂起票 TTL（现值 30 分钟） | — |
| 阻塞型（人在工具调用里等） | `suspend=false` | 阻塞宽限 + 余量（现值宽限 59 分钟） | 阻塞宽限（防"框还在屏幕上、agent 已经跑"） |

过期后由**既有**心跳对账路径（`exitAwaitingConfirm(reason='expired')`）恢复续跑，不新写第二套恢复语义。

- **使用场景**：人离开工位，弹框一直没人答；插件重启丢掉内存登记表之后又被重建。
- **操作流程**：时钟越过分档阈值 → 该登记视为过期 → 心跳一趟内清停手位并请求驱动。
- **预期结果**：需求不再永久停在「等人」；`resumed` 清单里能看到它。
- **边界条件**：未过期的阻塞型在途**不得**被误判过期；票 TTL 与弹框宽限三档语义**原样不变**（本 FR 只加另一张表的过期判定）。

**判据**：注入固定时钟，构造过期在途登记 ⇒ 一趟心跳后停手位非 awaiting、`resumed` 含该需求、且起轮；
构造**未过期**的阻塞型在途 ⇒ 不起轮、停手位保持。

**FR-4: 断链可观测 + 回归锁**

- **探针**：驱动在本拍放弃时（等弹框在途 / 停手位 / 不可驱动）必须留下**可查且有限（同因冷却，防刷屏）**的痕迹，
  使「确认后为什么没起轮」能从台账或诊断面回答。
- **回归锁**：一组用例锁死「人工门确认（含后台弹框超宽限后作答）→ 无需人手干预 → 必须起轮」，
  并锁零回归：首次确认照旧弹框落章推进、否定作答只留痕、看板确认照旧可用、四道门各至少一例。

**判据**：见「验收标准（整体）」。

## 边界（不做什么） <!-- serves: FR-1 -->

- **不复活被 Dive 化删除的投递路径**：不恢复 `pending-confirm.wake()` 的投递、不改 H4（仍 skip）。唤醒唯一经 round 半的预留 → 投递 → 准入。
- **不放宽也不收紧任何人工门判据**：内容门 / G2 完整性门 / 裁定门 / 拆分覆盖门逐字不变；本需求只管「清位 + 驱动」。
- **不改票 TTL 与弹框宽限口径**：30 分钟挂起票 TTL、auto-confirm 的 2 秒宽限、缺省宽限三档语义原样保留。
- **不新增门、不新增界面**：`reqboard_status` 字段与看板投影无新增键；不动客户端渲染。
- **不给 agent 新增"跳过驱动条件"的入口**：armed / 健康 / agent 闲置 / 无人门四条照旧。
- **不顺手修同族的「确认门重复弹出 / 审批台账被覆写」**：那是 REQ-261006164732-6503 的范围（见「依赖与约束」的接缝约定）。
- 不做 A（恢复真实唤醒投递）：与 Dive 化的既定裁定相反，且会多出一条进会话的路径（留痕与准入纪律要重做）——本轮明确否掉（D-1）。

## 非功能需求 <!-- serves: FR-1 -->

- **兼容**：未注入新端口（`dialogRef` / 清位回调）时行为与现状**逐字一致**；既有用例（含 `tests/ask-confirm-pending.test.ts` 的"作答后不投递"断言）不得变红。
- **性能**：清位回调只在"停手位真的被清"这一个事件上触发；`requestDrive` 自带串行合并，重复清位不产生额外回合。
- **可观测**：驱动放弃本拍留痕必须**有界**（同因冷却；不得每拍刷一条），且能被诊断面读出。
- **安全**：清位只由「作答 / 过期 / 取消」三类真实出口触发；任何过期判定都不得早于该形态的真实等待上限。

## 验收标准（整体） <!-- serves: FR-1 -->

端到端旅程（每步都有可观测结果）：

1. 造一条 brainstorming 需求，提交需求文档 → 后台确认弹框弹出（宽限 2 秒）→ **不作答**，等超宽限 ⇒ 台账出现 `awaiting-confirm:<ref>` 停手位，agent 回合正常结束。
2. 停手位在场时观察驱动 ⇒ **不起轮**（等人在答，行为正确）。
3. 在弹框上点肯定项 ⇒ 断言：台账停手位**先**被清、`status` 随后推进、**且无需任何人发消息就起了一轮**（`source.kind='dive'` / `roundsInStage` +1）。
4. 反面：否定作答 ⇒ 不落章、不推进、不因本改动起轮（零回归）。
5. 过期面：注入固定时钟造一条过期在途登记 ⇒ 一趟心跳后停手位清空、`resumed` 含该需求并起轮。
6. 存量面：对一条当前被卡在 `awaiting-confirm:*` 的需求，跑一趟心跳即恢复续跑（本次事故里的 REQ-261006165125-23a9 与 REQ-261006164732-6503 都是这种现场）。
7. 可读面：`reqboard_status` / 诊断面能回答"它为什么没起轮"（等弹框 / 停手位 / 不可驱动三者可辨）。

## 关键决策与取舍

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 唤醒落点 | 恢复采集半投递（`wake()` 真投一条消息） | 保持"唤醒唯一经 round 半预留→投递→准入" | Dive 化的既定裁定：进会话只走 `createRoundMessage`（留痕与准入一体）；新开路径要重做两套纪律 |
| 触发信号 | 事件桥按 `requirement-updated` 全量读盘判定 | 清位成功即请求一次驱动 | 桥的 change 帧只有 `{kind, requirementId, revision, summary}`，**不含** `driverHealth` ⇒ 全量读盘=每次写都一次 IO；回调只在真清位时发生 |
| 过期阈值 | 单一 TTL（30 分钟套所有在途登记） | 按 `suspend` 分档（挂起 30 分钟 / 阻塞 宽限+余量） | 阻塞型弹框最长可等约 59 分钟；套 30 分钟会把「人还在看框」误判过期 ⇒ agent 抢跑 |
| 范围 | 只修时序（最小改动） | 时序 + 清位即驱动 + 在途过期对账 | 只修时序仍可能被其它清位路径丢触发；且"过期后自动恢复"是台账**已经写下**的承诺，现在兑现不了 |

## 技术方案与亮点

需求阶段已拍板的技术口径（细节进 `design/architecture.md`）：

- 改动点三处：确认收敛点**带 ref 且 await 清位**（前置于推进）；清位成功**回调一次驱动请求**（单点注入到 round 半 `requestDrive`）；在途登记**惰性分档过期**。
- 与常规做法的差异：**把"停手位被解除"本身当作驱动事件**，而不是再加一条"投递提醒消息"的旁路——
  所有触发最终收敛到 round 半同一条准入路径（可核验指向 `application/dive/round-driver.ts` 的 `requestDrive` 合并语义与 `tests/dive-wake-e2e.test.ts`）。
- 不变量：**"确认→被观察到的状态推进"与"确认→起轮"必须同时成立**；任一单独成立即为缺陷（本次事故正是前者成立、后者不成立）。

## 依赖与约束 <!-- serves: FR-1 -->

- **强依赖**：`ReqboardDiveManager` 的 round 驱动器（`requestDrive` / `onRequirementMoved`）、`agents.get`、store 订阅桥（`reqboard/requirement-moved`）——均为现有实现。
