# 用例与行为口径（REQ-261006170150-52cc）

> 本文回答：**谁在什么场景下、看到什么**；每条的"观测量"都指向一个可查的面（台账字段 / 回合 / 诊断日志）。

## 角色与关注点 `serves: FR-1`

| 角色 | 关注 | 本设计给的答案 |
|---|---|---|
| 会话里的用户（需求方） | 点了确认，流水线就继续 | 无需再手打「继续」；超宽限后作答同样续跑 |
| 窗口 agent | 提交产物后等确认 | 等待结束后被叫起来，且拿到的是**新阶段**的回合文 |
| 看板使用者 | 停摆要看得出来 | `[WAKE-SKIP]` 诊断留痕 + `[Dive 恢复]` 台账评论，能回答"为什么没起轮" |

## 关键序列 `serves: FR-1, FR-2`

**UC-1 逐拍（后台弹框超宽限 → 人晚答）**

1. `submit(kind=requirement)` 登记产物 → `triggerAutoConfirm` 后台弹框（宽限 2 秒）→ 写入停手位 `awaiting-confirm:<ticket>`。
2. 宽限到期 → 后台转挂起、submit 早已返回 → agent 回合正常结束（`agent/status=idle`）。
3. 人在弹框上点肯定 → 回答进入挂起续跑：
   ① 带 `ticket` 清位（await，`notify:false`）→ ② 落章 → ③ 过门 → ④ 推进（`status` 变，桥发 `requirement-moved`）
   → ⑤ `confirm-advance` 复位 → ⑥ `advanced===true`，**不**补发。
4. ④ 的事件在**停手位已清**的状态下到达驱动 ⇒ `isDrivableRequirement` 与 `dialogInFlight` 均通过
   ⇒ 预留 → 投递 → 准入 ⇒ agent 被叫起来（回合文按**新阶段**渲染）。

**UC-3 逐拍（否定作答）**

1. `settleAnswers` 判定非肯定 ⇒ `recordDeclinedConfirmation`（留痕，不改状态）。
2. 清位（带 ref，`notify` 缺省 true）⇒ 台账真的清了 ⇒ `onCleared` ⇒ 驱动请求。
3. 无状态迁移 ⇒ 没有 `requirement-moved` ⇒ 这一次请求**就是**唯一触发 ⇒ 起 1 轮。

**UC-4 逐拍（过期恢复）**

1. 心跳 tick → ① 停手对账：`isAwaitingConfirmStop(req)` 为真 → 问 `dialogInFlight(req)`。
2. 该登记已越过分档 TTL ⇒ `inFlightFor` 返回 false ⇒ 走既有 `exitAwaitingConfirm(reason='expired')`（带 `onCleared`）。
3. 清位成功 ⇒ 回调 ⇒ 驱动请求 ⇒ 起轮；心跳回执 `resumed[]` 点名，台账留 `[Dive 恢复]`。

## 反例与边界场景 `serves: FR-2, FR-3`

| 场景 | 期望行为 | 为什么 |
|---|---|---|
| 推进成功后又补发一次驱动 | **禁止**（INV-4）：会清掉已排队预留并再投一条回合文 | 同一确认只允许一个触发源 |
| 未 armed（人按过"暂停"） | 清位照做、驱动请求照发，但 `drive()` 照旧拒绝起轮 | 人的意图优先（既有纪律，本次不放宽） |
| `driverHealth=paused`（运行时故障） | 同上：请求不放大成"绕过停手位" | 停机位语义不变 |
| 清位时还有第二票在途 | 停手位保持，不请求驱动 | 确实还有人在被问（UC-6） |
| 过期判定早于真实等待上界 | **禁止**：阻塞型 TTL 必须 ≥ 宿主交互超时（60 分钟 ≥ 宽限 59 分钟） | 防"框还在、链已跑" |
| 台账写失败 | 拦截/清位语义按既有纪律（永不抛、告警）；不因本需求新增静默降级 | 失败要响亮 |
| 终态需求（done/archived/canceled） | 不因清位回调而起轮（`drive()` 既有终态收手） | 唤醒纪律不变 |
