# REQ-261001124111-5d36 面板不再要人手动刷新：DAG 层级与泳道卡片必须自己更新

> 档位：**轻档**（改动面 = 客户端面板的刷新与陈旧可见性；无新决策点）· 类型：feature
> 单向升级触发器见文末「档位依据」：若定案落在**主机侧跨进程缓存/架构**，立即升级重档。

## TL;DR

会话顶部需求面板（拆分节点的「📊 DAG 层级」、实施节点的「🔀 流程图 / 泳道」）会**停在落库前的旧快照**：
面板显示「暂无任务」、泳道一列空白，而服务端同一刻有 19→23 张任务卡——**手动刷新页面后立刻恢复正常**（用户实测确认）。

要做的事一句话：**让面板自己拿到最新数据**——展开期间自动刷新（≤5 秒）、数据时间可见、拿不到就响亮报错，
彻底消灭「看起来是空的、其实是旧的」这种静默假空态。

## 现状（实测，可复核）

### 事实一：服务端有数据，渲染器也能画出来（两处都已排除）

| 检查 | 命令 / 方式 | 结果 |
|---|---|---|

| 接口有卡 | `curl -s .../requirements/REQ-261001110934-3766/stages` → `stages[decomposing].body.tasks` | **19 张**（父卡 12 / 子卡 7） |
| 单节点接口有卡 | `curl -s .../requirements/REQ-261001110934-3766/stage/decomposing` → `body.tasks` | **19 张** |
| 渲染器能画 | 用上面真实 payload 调 `renderNodePanel({overview, stage:'decomposing'})`（`npx tsx`） | 输出**不含**「暂无任务」，含 `<canvas id="np-dag-canvas">`；`implementing` 节点输出 **36 个卡片元素** |

→ **病灶不在数据源、也不在渲染函数**，而在「客户端面板拿着的是什么时候的快照」。

| 时刻 | 事件 | 面板当时能看到什么 |
|---|---|---|
| 12:04:50 | 拆分计划 submitted | 0 张卡 |
| 12:06:00 | 计划 approved（**同一毫秒任务卡 createdAt 落库**） | 0 → 19 张卡 |
| 12:25:26 | 需求转入 implementing | 19 张卡 |
| 12:36:28 | 需求 updatedAt 最后变化 | 19 张卡 |
| **12:40:37** | **用户截图（附件落盘时间）** | 面板显示「36 分钟前」+「暂无任务」= **≈12:04–12:06 的快照** |

同一张截图里，**顶部流程图已显示「实施」为当前节点**（蓝色实心点）——即该组件的 `data`（15 秒轮询）
是新的，**只有面板的 `stageOverview` 停在 36 分钟前**。用户刷新页面后正常。

### 事实三：代码里有一条「静默陈旧」的结构性通道

`src/client/conversation-progress.ts`：

| 位置 | 现状 | 后果 |
|---|---|---|
| `:366-368` | 错误态只在 `stageOverview === null` 时显示：`else if (stageOverviewErr.length > 0 && stageOverview === null)` | **已有旧快照时，刷新失败被彻底吞掉**：面板继续渲染旧数据，无任何提示 |
| `:164-177` | 面板刷新只由 `[detailOpen, reqIdForStage, req.updatedAt]` 触发 | 任务增删/推进**不改** `req.updatedAt`（既有注释自认：`"任务状态变更时需求 updatedAt 不变导致泳道不更新"`）→ 任务级变化**只能靠 SSE 兜底** |
| `:180-196` | SSE 订阅仅在 `detailOpen` 时建立；断线/被代理缓冲时无兜底轮询 | SSE 一旦不生效，面板**可以无限期停在旧快照**（本次现象的形状） |
| `:164-168` | 只在 `!detailOpen || reqId === undefined` 时 `setStageOverview(null)` | 切换需求时**不重置**，新数据到达前会短暂显示**上一个需求**的卡片 |

## 业务流程图

```
         今天（要人手动刷新）                        本需求之后（面板自愈）
+--------------------------------------+   +--------------------------------------+
| 面板展开 ── 拉一次 /stages ── 快照X   |   | 面板展开 ── 拉一次 + 每 5s 轮询 + SSE  |
|        │                             |   |        │                             |
|        ├─ 任务落库（不改 updatedAt）  |   |        ├─ 任务落库 → <=5s 自动出现新卡 |
|        └─ SSE 没生效 ── 无兜底        |   |        ├─ 拿不到 → 红字「刷新失败」    |
|                 │                    |   |        └─ 面板头显示「数据时间 HH:MM:SS」|
|                 v                    |   |                 v                    |
|  永远「暂无任务」/ 泳道空列（假空态）  |   |  永远与 /stages 同源（或明确说旧了）  |
+--------------------------------------+   +--------------------------------------+
                    │
                    └── 用户手动刷新页面 ──▶ 立刻正常（这就是缺陷本身）
```

## 判定标准（可证伪）

1. **手工（主判据）**：面板展开在「拆分」节点 → 在另一个窗口对同一需求执行一次 `reqboard_task_move`
   （或新增一张卡）→ **≤5 秒**面板出现该变化（计数/DAG 节点/泳道卡片之一），**全程不刷新页面**。
2. **手工（陈旧可见）**：DevTools 断网 ≥30 秒 → 面板出现「刷新失败，显示的是 HH:MM:SS 的旧数据」；
   恢复网络 ≤10 秒 → 时间戳前进、提示消失。**不得**只留旧快照且无提示。
3. **手工（切换不串档）**：面板展开时切到另一需求 → 不得出现上一个需求的卡片（加载中就显示「加载中」）。
4. **自动（可跑锚点）**：`npx vitest run tests/client-panel-refresh.test.ts` 全绿，含
   - 用真实 `/stages` 形状 payload（19 张卡）断言 `renderNodePanel` 输出**不含**「暂无任务」且含 canvas 容器；
   - fake timers + stub `fetchStageOverview`：面板展开 20 秒内**至少 4 次**刷新调用；请求失败时渲染出错误条（即使已有旧数据）。
   - **自证有效**：把刷新调度注释掉后该用例必须转红。
5. **命令复核**：面板显示的卡片数 == `curl -s .../requirements/<REQ>/stages | python3 -c "..."` 的 `body.tasks` 长度
   （同一事实源，误差窗口 ≤ 一次刷新周期）。

## 产品定义

**一句话**：需求面板从「打开那一刻的快照」变成「**活的窗口**」——只要面板开着，它显示的就是服务端此刻的任务 DAG 与泳道，
拿不到就明说「这是旧数据」。

**核心价值**：把「看起来没东西」和「真的没东西」分开。当前缺陷的伤害不是少了几个像素，而是
**用户会据假空态做判断**（"这次拆分没落库？"），然后去手动刷新、去怀疑数据、去怀疑流程。
消除手动刷新 = 消除一整类误判与返工。

**与现状的区别**：不新增页面、不改面板结构；把刷新触发补齐（面板级轮询兜底）、把陈旧变成可见（时间戳 + 错误条）、
把切换重置补上（不串档）。

三要素检查：
- [x] 是什么：面板数据自刷新 + 陈旧可见（不是新的监控页面）
- [x] 核心价值：假空态 → 真实态或显式旧态
- [x] 与现状区别：现状只有「打开时拉一次 + SSE 兜底 + 失败静默」

## 用户与角色

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 需求提出者 / PM（人） | 看板或会话顶部展开面板，核对「拆分落库了吗 / 实施剩几张卡」 | 面板显示「暂无任务」而实际有 23 张卡，只能手动刷新页面才敢下结论 |
| 并行窗口的 Agent（写方） | 在另一个窗口落库任务、推进卡片状态 | 它的写入不会让已打开的面板动起来；人看到的是过期视图 |
| 维护本插件的 Agent | 改客户端刷新链路 | 失败被吞、无时间戳，线上现象无法从界面自证，只能靠翻代码猜 |

## 功能点

- **FR-1: 面板级自动刷新，无需刷新页面** —— 面板展开期间，任务落库 / 卡片推进 / 需求状态变化后 **≤5 秒**自动出现新数据；实现上以「面板自持的一次轻量 `/stages` 轮询」为兜底（SSE 保留为快速通道），使任务级变化**不依赖 SSE 是否活着**（现状：任务变化不改 `req.updatedAt`，SSE 是唯一通路）
- **FR-2: 数据时间可见（陈旧不再隐形）** —— 面板头部显示「数据时间 HH:MM:SS」，每次成功刷新前进；距上次成功刷新 >30 秒时该时间戳变为警示态（颜色/文案），让人一眼看出「这不是最新的」
- **FR-3: 刷新失败要响亮** —— 已有旧快照时刷新失败，**必须**显示错误条「刷新失败，显示的是 HH:MM:SS 的旧数据」（现状 `conversation-progress.ts:366-368` 把该错误吞掉）；恢复成功后错误条自动消失
- **FR-4: 需求切换与重开不残留** —— `requirementId` 变化时必须先把面板置为「加载中」再取新数据，**不得**在新数据到达前显示上一个需求的 DAG / 泳道 / 倒计时
- **FR-5: 客户端版本陈旧可见（P1）** —— 页面加载的插件 bundle 若落后于磁盘最新构建，面板显示「插件已更新，点此刷新」并提供一键 `location.reload()`；不做热替换、不静默跑旧逻辑（用户本次是靠手动刷新恢复的，本 FR 让这种情况**自己说出来**）

## 边界

**做**：
1. 面板刷新链路（轮询兜底 + SSE 保留 + 打开即拉）、陈旧可见（时间戳 + 失败错误条）、切换重置、客户端版本陈旧提示
2. 一条可跑的回归测试锚点（含"改坏必红"自证），进 `npx vitest run`

**不做**：
1. **不做 WebSocket / 毫秒级推送**：5 秒轮询足够（面板是核对用的辅助监控），代价是每页一个常驻双向连接与重连状态机
2. **不做跨标签页 / 跨窗口广播同步**：单页自愈即可；多页各自轮询，服务端 `Cache-Control: no-store` 已保证不吃 HTTP 缓存
3. **不做面板结构或视觉重设计**：只新增「数据时间 / 错误条 / 版本提示」三处可见元素，既有区块与类名不动（避免牵连 `node-panel` / `dag-view` 的既有验收）
4. **不改服务端数据契约**：`/stages` 返回体、`queue.json`、台账字段一律不动（本次已实测服务端数据正确）

## 非功能需求

- 性能：面板展开期间每 5 秒一次 `/stages`（本机实测该请求 <100ms / 87KB），仅在 `detailOpen` 时发起，关闭即停
- 兼容：不依赖 SSE 可用；SSE 正常时按事件即时刷新，异常时退化为 5 秒轮询，两种路径渲染结果一致
- 可观察：时间戳与错误条进 DOM（可被截图/单测断言），不依赖 console 日志

## 待定案（design 阶段前 20 分钟闭合，不留悬案）

本次现象已确认「刷新即恢复」，但**面板为什么一直不刷新**有三种候选，设计文档必须给出定案证据：

| 候选 | 判据 | 若成立，落在哪个 FR |
|---|---|---|
| A. SSE 未生效 + 任务变化不改 `updatedAt` → 无任何兜底触发 | 面板展开时 `/events` 无帧、`req.updatedAt` 长时间不变 | FR-1（补轮询兜底） |
| B. 页面跑的是旧 bundle（无刷新逻辑），只能靠刷新页面换新代码 | bundle 版本戳与磁盘不一致 | FR-5（版本可见 + 一键刷新） |
| C. 刷新曾失败且错误被吞（`:366-368`），旧快照被当成最新 | 面板有旧数据、无错误提示、network 有失败请求 | FR-3（失败响亮） |

> 定案方式：展开面板后观察 ①`/events` 是否有帧 ②`/stages` 请求周期 ③页面 bundle 版本戳；
> 三者取实测值写入设计文档 `design/architecture.md` 的「现状复核」节。
