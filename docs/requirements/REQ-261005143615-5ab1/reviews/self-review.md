# 自评审报告（REQ-261005143615-5ab1）

## 一、这次改了什么（一句话）

详情页判「登记文档在不在盘上」时不再看「谁在看」，而是按**这条需求自己声明的工作区**判——
命中哪个根就用哪个根的绝对路径；一个可用根都没有时说「未判定」，文件真不在时才说「缺失」。

## 二、逐条对照设计自评

| 设计要求 | 实现 | 结论 |
|---|---|---|
| 候选序 = 需求声明根 → 会话根 → cwd | `panels.ts` 的 `docRootsOf` 按此序构造并去空去重 | 一致 |
| 只留真实存在的根（"根不在"≠"文件不在"） | 用 `existsSync` 过滤（探测在 http 层，application 层不碰 fs） | 一致 |
| 命中即止、命中根决定 absPath | `hitOf` 逐根 `exists`，首个命中即返回；`absPathOf` 用该根的 `resolve` | 一致 |
| 候选非空而全不命中 → file-missing | `entriesOfArtifacts` 的三元分支 | 一致 |
| 候选为空 → unknown 且不注入 absPath | 同上；`wired` 标志区分"端口未装配" | 一致 |
| generated / 原型 INDEX / 未登记设计行同规则 | 三处都改为走读根表 | 一致 |
| 缺省 = 旧单根行为 | `resolveDocRepos` 两口任一缺省即单根，`wired=false` 抑制新语义 | 一致（有用例） |

## 三、我自己能挑出的问题（都已在本次处理或如实留档）

1. **`generatedOf` 在多根下会逐根枚举并按 path 去重**：同一份 `rtm-*.yml` 若在两个根都存在，
   取序首那个根的 `absPath`。这是刻意的（与文档行同口径），但设计文档里没有逐字写明"生成物也去重"——
   **如实记录为设计措辞的精度问题**，不是行为分歧。
2. **运行中的 GUI 不会自动生效**：插件在 DSH 启动时载入，用户当前页面仍是旧模块。已在验收材料"已知边界"里写明"需重启"，
   没有假装"刷新即生效"。
3. **全量测试有两处与基线不同的失败**（`apply-wiring` 工具计数、`move-rollback` 设计文档门禁）：
   逐条看过失败原因，都不是本需求所改模块（本需求不加工具、不碰设计门禁链），
   属同期其它窗口在飞的改动。**没有把它们算作"已知可接受"**，而是在证据附录里原样列出。
4. **`unknown` 与 `file-missing` 的样式差异只有虚线边框**：色值同为次级灰。
   这是刻意（两者都"不可点"），但如果将来有人只看颜色不看文案，可能仍会混。
   文案层已明确区分（「未判定 · 读根不可得」vs「文件缺失」），暂不加深色差以免与"缺失"抢注意力。

## 四、风险与回滚

- **风险**：多根命中顺序若与用户预期不同（例如同一相对路径在需求根与会话根都存在），
  页面会取**需求根**那份——这与"读与写同根"的既有口径一致，且页面同时显示台账相对路径供对账。
- **回滚**：不注入 `docRootsOf` / `docsAt` 两口即逐字段回到改造前（`tests/query-docs-compat.test.ts` 钉住）；
  台账零迁移，无需数据回填。

## 五、结论

实现与设计**无偏离**；范围未蔓延（未改打开通道协议、未改台账存储、未为既有缺失语义翻案）；
交付物齐（需求 / 设计 7 份 / 计划 / 任务卡汇报 / 测试证据 / 真机对账证据 / 本报告）。
