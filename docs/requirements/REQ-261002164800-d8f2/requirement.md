## TL;DR

「需求条款 ↔ 任务卡」这条追溯链，在**计划落库那一刻**就断了，而且是三处一起断：

- **批不了**：一张卡没有 FR 引用 → 批准路径把**整批**拒掉，落库 0 张卡（实测 REQ-261002161439-277d 16:30:40）。
- **接不上**：计划任务表里的 `requirement_refs` 在入参 schema、协议层两处被丢；文档「覆盖对照表」这条兜底**只挂在批准路径**，手动拆分不读它。
- **补不回**：卡一旦落库，**没有任何入口**能再给卡写 refs。

做完之后：三处落库入口走同一份取数与同一道门禁；卡上的 refs 与文档覆盖表只有一个来源；存量 531 张空 refs 有可 dry-run、幂等的回填路径。

## 产品定义

**一句话**：让「需求条款 ↔ 任务卡」这条追溯链在**计划落库那一刻**就闭合，并且**只有一个取数来源、一道门禁、三条入口**。

- **是什么**：reqboard 计划落库链路的取数与门禁收敛——新建卡时把 refs 写对；已落库的卡能补写；存量数据能一次性回填。
- **核心价值**：从"落库结果对不对靠运气"到"落库结果可预测、可复核、可修复"。RTM 的 `serves`、覆盖度读数、验收单的"未被接收（红）"才有同一个答案。
- **与现状的区别**：现状是**三种入口两套规则**——批准路径有卡级 refs 硬门禁（缺一即全拒），手动路径没有；文档兜底只挂一边；落库后无写入口。本次把它们收敛成一份实现。

## 用户与角色

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 窗口 agent（跑需求流水线） | 计划获批后落库任务卡 | 批准返回 0 卡却不知为何；报错让它"在计划 tasks 里给 requirement_refs"——这个动作**做不到**；手动补落后卡上 refs 全空，且无路可补 |

## 功能点

- **FR-1: 三条落库入口收敛为同一取数与同一门禁**——批准弹框、看板「批准计划」、`reqboard_decompose` 三处都经**同一个 refs 取数函数**与**同一个 `landPlanTasks` 落库编排**；看板批准不再是"只盖章不落库"的空操作
- **FR-2: 计划携带任务表的 refs 通道打通**——`reqboard_submit(kind=plan)` 入参 schema 接受 `requirement_refs`，`PlanTask` 增字段、`normalizePlanTasks` 保留并校验（编号形如 `FR-N`，去重、非法即拒并点名）
- **FR-3: 文档覆盖表兜底在三条入口一致生效**——「覆盖对照表」作为第二数据源进入**同一个** refs 取数函数（显式优先、文档兜底）；两处都取不到时**不拒整批**，改为落库 + 返回体点名
- **FR-4: 已落库卡的 refs 有唯一补写入口**——工具与看板路由共用同一实现：只改 refs、幂等、留痕 `reason`；写后同步 `rtm-implementing/<id>.yml` 的 `serves` 与覆盖表读数
- **FR-5: 存量空 refs 可一次性回填**——回填器支持 `--dry-run` / `--apply` / `--check`，逐需求按覆盖表回填、幂等、产出报告；**只动非归档需求**
- **FR-6: 落库失败要响亮，且恢复路径必须真的能走**——落库前的拒绝不得留下「计划已批准 + 0 卡 + 无指引」半态；错误文案只允许指向**当前确实可执行**的动作；文案不得声称某通道与另一通道等价而行为不同
- **FR-7: 落库返回体的覆盖度读数可信**——`task_coverage` / `covers_frs` 以**落库后的真实任务记录**计算，不再用缺字段的投影对象冒充（现状恒为空数组）

### 1. 三条入口收敛（FR-1）

- **使用场景**：任何一次"计划已获批准，该落库了"的时刻，无论由谁触发。
- **操作流程**：
  1. 人批准计划——会话弹框、或看板「批准计划」按钮；
  2. 或窗口 agent 手动调 `reqboard_decompose`；
  3. 三条路都调用同一个 `landPlanTasks`，落库成功后推进到 implementing。
- **预期结果**：同一份已批准计划，**换任何入口落出的卡集合、refs、依赖完全一致**（幂等，不重复造卡）。
- **边界条件**：计划未获批 → 三条路都拒；已有未取消任务 → 三条路都幂等跳过（不造幽灵卡）。

### 2. 计划携带任务表的 refs 通道（FR-2）

- **使用场景**：agent 写拆分计划时已知道"这张卡接哪几条 FR"。
- **操作流程**：
  1. `reqboard_submit(kind=plan, tasks=[{key:"t1", …, requirement_refs:["FR-1","FR-2"]}])`；
  2. 台账 `plan.tasks[].requirement_refs` 落库保留；
  3. 落库时写进 `TaskRecord.requirementRefs`。
- **预期结果**：卡上 refs 与计划里写的一致；非法编号在**提交计划那一刻**就被拒（而不是落库时才发现）。
- **边界条件**：旧台账/旧计划无该字段 → 视为空数组（不做迁移），由文档兜底（FR-3）。

### 3. 文档覆盖表兜底（FR-3）

- **使用场景**：计划文档的「条款覆盖对照表」写了 `FR-1 ↔ t2、t3、t4、t8`，但任务表里没写显式 refs。
- **操作流程**：
  1. 落库前，取数函数先读显式 refs；缺失的 key 用文档覆盖表补齐；
  2. 仍为空 → **不整批拒绝**，落库照常；
  3. 返回体 `unrefed_cards` 与需求评论列出这些卡，人可见。
- **预期结果**：不再出现"一张卡缺 refs ⇒ 0 张卡落库"；文档表存在时，卡上 refs 非空。
- **边界条件**：文档缺失 / 无覆盖表 → 退化为"全部卡无 refs + 警告"，仍可落库（不阻塞交付）。

### 4. 已落库卡的补写入口（FR-4）

- **使用场景**：发现某张已落库的卡 refs 为空或写错（本项目实测 531 张）。
- **操作流程**：
  1. 调补写入口（工具 / 看板路由），给 `task_id` + `requirement_refs` + `reason`；
  2. 系统只改这一个字段，写队列（经 `TaskStore`）后同步 RTM；
  3. 返回变更前后值与落盘态。
- **预期结果**：卡上 refs 更新；`rtm-implementing/<id>.yml` 的 `serves` 随之更新；台账留痕一条 `reason`。
- **边界条件**：值相同 → 幂等不写盘（mtime 不变）；`task_id` 不属于本窗口绑定需求 → 拒。

### 5. 存量回填（FR-5）

- **使用场景**：修好生成链后，把历史空 refs 补齐。
- **操作流程**：
  1. `--dry-run` 扫全部需求，输出"可回填卡数 / 无来源卡数 / 冲突卡数"；
  2. `--apply` 按需求逐个回填（每需求一份报告）；
  3. `--check` 复扫断言 `empty_with_doc_coverage: 0`。
- **预期结果**：非归档需求的空 refs 归零（或仅剩"文档表本身没写"的卡，且逐卡列出）。
- **边界条件**：归档需求**只报告不回填**；回填可重入（重复跑不产生二次变更）；不覆写已有非空 refs。

### 6. 失败响亮与恢复路径真实（FR-6）

- **使用场景**：落库被拒 / 中途失败。
- **操作流程**：
  1. 拒绝时返回结构化失败（错误码 + 缺口清单 + **可执行的**恢复动作）；
  2. 落库已生效但收尾失败 → 照常推进并留痕；
  3. 落库未生效 → 不推进，写系统评论 + `advance.pausedReason` + 告警。
- **预期结果**：任何一次落库失败，人都能在看板看到"哪一步失败、现在能做什么"。
- **边界条件**：恢复动作必须是**当前版本真的能调通**的入口（本次修的就是"指了做不到的动作"）。

### 7. 返回体读数可信（FR-7）

- **使用场景**：agent / 人据 `reqboard_decompose` 返回体判断覆盖情况。
- **操作流程**：落库后以真实任务记录计算 `task_coverage` 与覆盖率；`warning` 列出未被接收的 FR。
- **预期结果**：返回体的读数与磁盘上的 RTM 一致，不再恒为空。
- **边界条件**：任务数为 0（幂等跳过）时读数如实为空，不编造。

## 边界

- 不做**看板客户端 UI**：补写入口只到工具 + HTTP 路由（理由：本次先把数据链修对；UI 入口另立需求）。
- 不做**第二种 RTM 事实源**：只把"两套取数"收敛成一套，不新增 RTM 文件或字段语义（理由：两份真相正是本缺陷的成因）。
- 不动 **v10 分片迁移**（REQ-261002161439-277d 在进行中）：本需求只经 `TaskStore` 端口与 `landPlanTasks`，不直接读写队列文件（理由：避免与在途重构互相踩）。
- 不回填**归档需求**的卡 refs（理由：归档只读，且对交付无影响；需要时由后续需求单独处理）。
- 不改**需求文档格式门禁**（编号连续性 / 唯一性 / 必填节）规则本身（理由：本次是落库链缺陷，不是文档门禁问题）。

## 非功能需求

- 兼容：旧台账（`plan.tasks` 无 `requirement_refs`）与旧队列（卡无 `requirementRefs`）读取行为不变，一律视为空数组。
- 幂等：任何落库与补写入口重复调用，队列文件 mtime 不变（沿用既有幂等判据，t11）。
- 尺寸：宿主单文件 ≤400 行（C-02）——本次改动涉及 `confirm-settle.ts`（现 439 行，已超线），取数与门禁必须**抽出**而非就地加长。
- 观测：一次落库的"无落点卡"必须出现在返回体与需求评论两处，不允许只进日志。

## 验收标准（整体）

1. 起一个夹具需求（11 张卡，其中 1 张纯文档卡不含 FR）→ 计划提交时给其余卡写 `requirement_refs` → 走批准弹框路径；
2. 观察到：11 张卡全部落库（现状是 0 张），返回体列出那张无落点卡，需求推进到 implementing；
3. 换到看板「批准计划」路径重演同一个需求 → 行为一致（同样落库、同样推进、不重复造卡）；
4. 对一张已落库卡调补写入口 → 卡上 refs 与 `rtm-implementing/<id>.yml` 的 `serves` 同步更新，留痕可查；
5. 对全仓跑 `--dry-run` / `--apply` / `--check` → `empty_with_doc_coverage: 0`，报告逐需求可核；
6. 全量回归：`pnpm test` 失败 ≤106、`pnpm typecheck` ≤223、`pnpm build` 退出码 0。

## 依赖与约束

- 依赖（强）：`TaskStore` 端口语义不变——本需求全程经端口读写任务，迁移到分片存储后仍然成立。
- 依赖（强）：`rtm-yaml` / `rtm-integration` / `status-rtm-integration` 三个消费方字段语义不变（`serves ← requirementRefs`）。
- 依赖（弱）：`decomposition.md` 的「覆盖对照表」继续作为第二数据源（既有的 `taskRefsFromDecomposition` 解析器复用）。
- 约束：分层边界只许向内（C-01）；`tools/` 与 `http/` 内不写状态字面量。
- 约束：改动 `normalizePlanTasks`（新增必填校验）会影响既有用例，需与 HEAD 基线逐条比对（C-14/C-15）。
- 约束：协议文件 `src/shared/protocol.ts` 加字段必须可选，避免破坏存量台账的反序列化。
