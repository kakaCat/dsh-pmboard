# REQ-261001170807-06fd 节流不再惩罚正常收尾 + 子卡验收标准自带可跑命令

> 档位：**重档**（触及收尾门判定与子卡模板两处契约）· 类型：bug · 来源：REQ-261001154450-b918 实施实测

## TL;DR

流程有两条规则**惩罚了唯一正确的做法**：

- **收尾被节流**：子卡关闭豁免节流，但子卡关闭会**给父卡的节流上弦**——于是"关完 4 张子卡 → 关父卡"这个唯一正确的收尾顺序，**每张卡必然被拒一次**。
- **模板产出过不了门禁**：子卡模板给的验收话术是"改动已落盘，相关测试或命令跑通并附输出摘要"——是断言词，不是操作；而验收门禁要求"可执行操作"。结果只能**收尾时逐张回补**。

```
   今天（实测）                                    本需求之后
   +-------------------------------+      +--------------------------------+
   | 关 4 张子卡 ✅（豁免节流）     |      | 父子链收尾不再被节流惩罚        |
   |   ↓ 立刻关父卡                | -->  | （只拦"连关兄弟卡"那种滥用）    |
   | ❌ REQBOARD_BULK_CLOSE         |      |                                |
   | 8475 因此 sleep 62 ×32 = 33 分 |      | 子卡验收标准自带可跑命令        |
   | 验收门禁要"怎么验"，模板没给   |      | （模板与门禁同口径，收尾免回补）|
   | → 收尾回补 38 张卡             |      |                                |
   +-------------------------------+      +--------------------------------+
```

| 面 | 现状 | 本需求之后 |
|---|---|---|
| 父子链收尾 | 关子卡 → 关父卡必被节流拒 | 正常收尾零等待 |
| 兄弟卡滥用 | 一次调用连关 4 张卡被拦 | **仍然被拦**（不退让） |
| 子卡验收标准 | 模板生成断言词，验收门禁拒收 | 模板直接产出 `npx vitest run …` 之类操作句 |
| 收尾成本 | 人工回补 38 张卡的标准 | 落库即合规，无需回补 |

## 判定标准（可证伪）

| 断言 | 量法 | 通过条件 |
|---|---|---|
| A1 收尾不被惩罚 | 连续执行"关某卡全部子卡 → 关该父卡" | 父卡一次成功，无 `REQBOARD_BULK_CLOSE` |
| A2 滥用仍被拦 | 同一调用序列里连关**两张兄弟卡**（不同父卡） | 第二张仍被 `REQBOARD_BULK_CLOSE` 拒绝 |
| A3 边界不误伤 | 关 A 卡父卡后 60 秒内关 B 卡父卡 | 按设计被拦（跨卡的连环关闭仍受节流约束） |
| A4 模板自带命令 | 新需求落库后抽一张子卡看 acceptance | 含可执行命令（`npx vitest …` / `pnpm …`）与期望输出锚点 |
| A5 门禁不再回补 | 对一条新建需求直接跑到验收 | `reqboard_submit(kind=verification)` 不因"缺怎么验"拒收 |

## 产品定义

**节流的目的**是防"一次调用连关一叠卡"的滥用，不是给正常收尾设卡。判据要认得出"这是同一张卡自己的链在收尾"。

**模板与门禁必须同口径**：门禁要什么，模板就得产出什么；否则两者之间的矛盾会以"收尾时人工回补"的形式由 agent 买单。

## 用户与角色

| 角色 | 关心什么 | 本需求给他什么 |
|---|---|---|
| 实施 agent | 收尾不要白等 | 父子链收尾零等待；滥用仍被拦 |
| 收尾的 agent | 不要事后补 38 张卡 | 子卡落库即带可跑验收标准 |
| 维护者（人） | 流程不要自相矛盾 | 模板与门禁同口径，一处改处处一致 |

## 接口与数据契约

**节流判据（`findRecentAgentDoneTask`）**

| 项 | 契约 |
|---|---|
| 输入 | 现有 `tasks` 投影需带上 `parentId`（TaskRecord 已有该字段，TaskWithHistory 投影需补） |
| 判据 | 命中的"其他任务"若为**本卡自己的子卡**（`candidate.parentId === taskId`）→ 不计入节流 |
| 不变 | 兄弟卡、跨卡关关闭仍计入（A2/A3 必须仍被拦） |

**子卡模板（acceptance 生成）**

| 项 | 契约 |
|---|---|
| dev / integrate | `npx vitest run <对应测试文件> → 全绿` |
| review | `对照 docs/requirements/<REQ>/design/ 逐条核对；<同一命令> → 全绿` |
| test | `pnpm test → 失败数 ≤ <基线>；npx tsc --noEmit → 错误数 ≤ <基线>` |
| 兜底 | 无法确定测试文件时给出可跑命令占位（如 `npx vitest run <卡片实现涉及的测试文件>`），不得退回断言词 |

## 功能点

**FR-1: 父子链收尾不再被节流惩罚**

`findRecentAgentDoneTask` 的判据排除"本卡自己的子卡"，使"关完子卡 → 关父卡"一次通过；兄弟卡与跨卡连环关闭仍被 60s 节流拦住。

**FR-2: 子卡模板生成可执行的验收标准**

自动生成的子卡（研发/联调/复核/测试各阶段）其 acceptance 必须含可执行命令与期望锚点，使新建需求从落库起就满足"照着验"门禁，收尾无需人工回补。

## 边界

**做**

1. 上述两处判据/模板改造，及各自的可证伪用例。
2. 用一条新建需求做端到端验证（落库即合规、收尾零等待）。

**不做**

1. 不取消 60s 节流本身（防滥用是有效设计）。
2. 不改人工门、不改验收单结构。
3. 不动既有已落库卡片的 acceptance（存量不追溯）。

**红线**

- 除"父子链豁免"外，节流行为逐字不变（A2/A3 用例锁住）。
- 模板改动只影响**新落库**的子卡，存量卡读取路径不变。

## 复现步骤

```
① 建一条需求 → 批准计划 → 落库（1 张父卡 + 4 张子卡）
② 依次关闭 4 张子卡        → 每次都成功（子卡豁免节流）
③ 立刻关闭父卡             → 期望成功；实测 REQBOARD_BULK_CLOSE
                             「60 秒内刚关闭了任务 <刚才那张子卡>」
```

旁证（实测数字）：REQ-261001143526-8475 会话中 agent 为绕开它固定 `sleep 62`，
共 32 次 = **1984 秒（33.1 分钟，占该需求墙钟 65%）**；本会话 10 张卡每张各被拦一次。

## 根因

| 环节 | 事实 | 出处 |
|---|---|---|
| 子卡关闭 | 走 `checkSubtaskEvidence`，**豁免** 60s 节流 | [support.ts:255-285](src/application/internal/support.ts#L255-L285) |
| 父卡关闭 | 走 `checkDoneEvidence`，**过**节流 | [support.ts:287-304](src/application/internal/support.ts#L287-L304) |
| 节流判据 | `findRecentAgentDoneTask` 只排除 `t.id !== taskId`，**未按 `parentId` 归属排除本卡子卡** | [DoneEvidenceSpec.ts:42-46](src/domain/workflow/DoneEvidenceSpec.ts#L42-L46) |

**结论**：子卡的 done 事件必然给父卡"上弦"——同一张卡先亲子后父的收尾顺序天然踩中 60s 窗口。
节流的设计意图（[DoneEvidenceSpec.ts:32-33](src/domain/workflow/DoneEvidenceSpec.ts#L32-L33) "事故 C：一次调用关 4 个任务"）针对的是连关**兄弟卡**，与父子链收尾无关。

## 追加条款（2026-10-01 用户裁定并入；原话："这个交互和流程有问题" → "添加到本次需求里"）

### FR-3 · 验收弹框应把已有证据递到眼前，人只裁决

**现象**：7 个验收项一次性抛 14 个问题（每项"裁决 + 实际结果"两问）；点"通过"后**必须手输**实际结果，
而证据（命令输出/文件路径）系统里本来就有；证据只在第一问、且被截到 **40 字符**（LIMITS.popupEvidenceMax），
面对一条命令或路径等于没给。用户原话："应该自动给我回填信息的"。

**已做**：证据上限 40 → 160；"实际结果"问改为随问带上**判据 + 已有证据**，人只做裁决、不重抄。

### FR-4 · 弹框失败必须说真因，不得栽给用户

**现象**：实测调用 reqboard_accept_sheet 返回"用户未作答（取消/暂离）"，而用户什么都没点。

**根因**：AcceptSheet.ts:193-198 的 catch 把**除权限外的所有异常**统一写成"用户未作答（取消/暂离）"
——超时、中断、渲染故障全被归因给用户，真因被吞。

**已做**：区分"被中断（abort）"与"工具故障"，并把**原始错误文本**写进 note（不再出现"用户未作答"）。

### 回归

| 落点 | 断言 |
|---|---|
| tests/accept-sheet-tool.test.ts | 非权限异常 → note **不含**"用户未作答"、含真因与"工具故障" |
| 同上 | abort → note 含"弹框被中断"，不栽给用户 |

> 诚实说明：FR-3 的弹框内容改动**没有**配套自动化用例（试写的用例依赖弹框调用链、在本文件内不稳定，已移除）；
> 其证据为代码 diff 与下次验收时实际看到的弹框内容。这一点不隐瞒。

### FR-5 · 验证是 agent 的活，人只做裁决（2026-10-01 用户裁定："点击验收你应该验证对不对，不是用户去验证"）

**现象**：验收项已带 agent 记录的实际结果（任务的验收标准、验收材料里的证据），弹框仍要求**用户手填**
"实际结果"；不填就记「未复核」。信息本来就有，却逼人重抄一遍。

**已做**：AcceptSheet 的 resultOf 增加第三级来源——**验收项自带的 agent 证据**。
选"通过"时取结果顺序：第二问自填 → 第一问自填 → **该项已有的 agent 证据**。

**保留的底线**：完全没有任何结果的项，选通过仍记 **unverified**（不冒充通过）。

**这是一次有意的行为反转**（推翻 REQ-b918 FR-1 的"必须手填"）：原用例已按新口径改写并注明理由，
而不是删掉——反转必须留在案卷里。
