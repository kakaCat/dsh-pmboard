# 需求说明（REQ-261005165552-6783 capture 段改字面量：台账/用户文本里的花括号占位符不再打挂整轮）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。
> 追认事故：**REQ-261005105032-3b02 的窗口整轮卡死**（`session-5632659d`，2026-10-05T08:51:21Z）。
> 台账原文（`record.json` → `interruption.reason`）：
> `error:UNKNOWN:malformed prompt variable reference "{{NOPE}}" in section "reqboard:capture"`
> ——每一轮都在系统提示词装配处抛错，**模型根本没机会跑**。

## TL;DR <!-- serves: FR-1 -->

- **这是什么**：把 pmboard 唯一的系统提示词段（`reqboard:capture`）注册为**字面量段**——宿主不再把这一段的文本当模板做变量插值。
- **为什么现在做**：这一段会把**在制任务的说明/验收标准、用户消息节选、需求标题**原样拼进提示词；只要这些文本里出现一个完整的花括号变量（模板里到处是 `{{REQ_ID}}` 这类大写占位符），宿主就抛错 → **整轮运行失败、窗口永久卡死**，且报错文本自身带着占位符，贴到别的窗口会复现同一故障。
- **做完得到什么**：**这类整轮级故障归零**；被卡死的 `REQ-261005105032-3b02` 窗口重载后恢复；未来新增提示词段必须显式声明"要不要插值"。

## 业务流程图 <!-- serves: FR-1 -->

```
窗口每回合装配系统提示词
   │
   ├─ capture 段文本（三种来源）
   │     ├─ 静态立项引导（全字面量）
   │     ├─ 用户消息节选（原文引用）
   │     └─ 绑定推进纪律 + 在制任务的说明/验收标准 + 阶段提示词
   │
   ├─（改前）宿主 renderPrompt 把整段当模板插值
   │     └─ 文本里出现完整 {{name}}：名字非法（大写）⇒ malformed ／ 名字合法但未注册 ⇒ unknown
   │           ⇒ 抛错 ⇒ **本轮失败（模型没跑）** ⇒ 该窗口每轮必炸
   │
   └─（改后）段上声明 interpolate:false
         └─ 文本**原样**进提示词：出现什么都不抛
              │
              └─ 验证：反例回归 + pnpm build + 重载 ⇒ REQ-3b02 窗口解冻（可再跑一轮）
```

## 产品定义（serves: FR-1）

**提示词段的"字面量身份"**：pmboard 的捕获段是**纯自撰文案 + 原文引用**，从不使用宿主的提示词变量体系；
但宿主对每个段默认按模板插值，于是"我们引用了别人的原文"这件事变成了**整轮级炸弹**。

本需求给这一段补上它本来就该有的身份声明：**这一段是字面量，不要解析**。

**核心价值**：把「文本里恰好有个花括号」从**整轮失败**降级为**无害字符**。
**与现状的区别**：现状是"隐性依赖宿主默认行为"——注册处一个字都没写，默认却决定了整个窗口能不能跑。

## 用户与角色（serves: FR-1）

| 角色 | 什么场景用 | 痛点（现状） |
|---|---|---|
| 窗口 agent（已绑定需求、有在制卡） | 每回合装配系统提示词 | 本卡验收标准里引用了模板占位符 → **整轮抛错，连话都说不出** |
| 窗口 agent（未绑定需求） | 用户消息到达后注入立项引导 | 用户消息里带占位符 → 同样整轮失败；**越是想让人来报障，越容易把接手窗口也打死** |
| PM / 人 | 报障、排查、继续用那个窗口 | 报错只给段名，看不出是谁把什么喂进去的；窗口卡死后**只能重启** |
| 接手窗口（交棒/新窗口） | 上下文遗弃后续跑 | 接手时第一步就是装配提示词，遇到同一张卡 → 接手即卡死 |
| 维护者（改插件的人） | 新增/修改提示词段 | 段的"要不要插值"没有在注册处声明，隐性契约靠口口相传 |

### 功能点详细说明

- **FR-1: capture 段注册为字面量段（`interpolate: false`），文本逐字节不变**
  注册处（`src/gate-wiring.ts` 的 `systemPrompt.section({...})`）显式传 `interpolate: false`；
  段的三种文本（静态引导 / 用户消息节选 / 绑定推进纪律 + 在制任务说明与验收 + 阶段提示词）
  **内容逐字节不变**，只是不再经过宿主的变量插值。
  注释写清为什么（本段全部为自撰文案与原文引用，从不使用宿主变量），
  避免下一个人"看着多余"把它删掉。
  **不改文本语义**：不做转义、不做清洗、不把花括号替换成全角——原文引用（用户原话、卡上验收原文）必须保真。

- **FR-2: 注入面机械回归——三组花括号反例不再抛错，且文本字面保真**
  在接线冒烟（`tests/apply-wiring.test.ts`）里断言该段 `interpolate === false`；
  新增一份反例回归（`tests/capture-literal-section.test.ts`），构造三组输入并断言"段文本原样包含占位符、组装不抛"：
  1. 在制任务的 `acceptance` / `description` 含完整花括号变量（本案现场：`t-7e7da9` 的验收标准）；
  2. 用户消息节选含完整花括号变量（未绑定窗口的动态引导路径）；
  3. 需求标题含完整花括号变量（绑定段的清单行）。
  反例必须**先证明自己会炸**：测试内附一段与宿主同语义的插值判据（完整 `{{name}}` 组 + 名字非法/未注册 ⇒ 抛），
  在关掉开关的桩上断言"字节级原样保留、无异常"——避免写出恒真断言。

- **FR-3: 重建产物并重载，被卡窗口解冻（含证据留档）**
  `pnpm build` 出新产物（`dist/index.mjs`）→ 重载插件 → 被卡窗口 `session-5632659d`（`REQ-261005105032-3b02`）恢复；
  留两份证据：①该窗口诊断日志（`state/reqboard-capture-diag.log`）出现正常的 `NODE-4` / `NODE-5` 行；
  ②该需求台账不再新增 `malformed prompt variable reference` 记录。
  **说明为什么必须重载**：任务队列是**进程内缓存**（`QueueTaskStore`），只改盘上的 `queue.json` 不重启不生效——
  所以"手工热修数据"并不比"出修复产物"省事，本需求一次重载同时消雷与解冻。

- **FR-4: 本插件注册的每个提示词段必须显式声明插值开关**
  接线回归里断言：pmboard 注册的每个 section 都**显式**带 `interpolate` 字段（`true` / `false` 皆可，**缺省即红**）；
  未来新增段必须写下自己的选择，不允许"靠宿主默认"。

## 边界（不做什么）（serves: FR-1）

1. **不改宿主、不动 vendor**：不向 DSH 提"section 文本含未注册变量不应打挂整轮"的加固，也不改 `vendor/`。
   理由：段文本本来就是自撰字面量，宿主提供的开关正是为此而设；改宿主的升级风险与影响面远超本缺陷。
2. **不做全仓注入面大扫除**：只修本插件注册的这一个段；其它插件、其它宿主缝不在本次范围。
3. **不引入转义/清洗层**：不改注入文本内容——原文保真是本仓的既有语义（D-x 原话、验收原文、用户消息都要能逐字引用）。
4. **不改既有段文本与既有断言**：`tests/capture.test.ts` / `tests/stage-prompts.test.ts` 的断言语义不变，只有注册处多一个字段。
5. **不追溯历史记录**：已发生的 `interruption` 原样留在台账里当证据，不做数据订正。
6. **不改卡片状态机与拆分纪律**：本次不碰任何门禁判据、不碰任务状态机；被卡窗口解冻后按原流程继续。

## 非功能需求 <!-- serves: FR-1 -->

- **兼容**：段文本除插值开关外**逐字节不变**；`capture.test.ts` / `stage-prompts.test.ts` / `acceptance-criteria.test.ts` 的断言不变。

- **性能**：无新增 I/O；段组装多一次布尔判断。
- **安全**：无新增外部输入面；不改数据、不改网络路径。

## 关键决策与取舍 <!-- serves: FR-1 -->

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 修在哪一层 | 改宿主 `renderPrompt` 容忍非法变量 / vendor 改 DSH | 插件侧注册 `interpolate:false` | 段文本本就是自撰字面量，宿主开关为此而设；改宿主超出本仓边界（D-1、D-2） |
| 文本要不要转义 | 注入前把花括号替换成全角/加空格 | 不改文案一个字 | 转义破坏"原话进提示词"的保真语义（用户原话、卡上验收原文都要逐字引用） |
| 解冻方式 | 手工改 `queue.json` + 重启（热修数据） | 出修复产物再重载 | 任务是进程内缓存，热修同样要重启；一次重载同时消雷与解冻（FR-3） |
| 是否加写法纪律 | 规定全仓不得裸写花括号占位符 | 不加纪律，只加显式声明（FR-4） | 关掉插值后裸写已无害；纪律成本高、收益为零 |

## 技术方案与亮点 <!-- serves: FR-1 -->

- **单点改动**：注册处加一个布尔字段（`interpolate: false`），零运行时逻辑、零新依赖。
- **反例先行**：回归测试自带"与宿主同语义的插值判据"，先证伪"没有开关就会炸"，再证"有开关字节级保真"。
- **与常规做法的差异**：常规做法是**在文本侧转义**（把 `{` 换成别的字符）；本需求选择**在契约侧声明**——
  文本一个字节不改，故障归零（细节进 `design/architecture.md` 同名节）。

## 依赖与约束 <!-- serves: FR-1 -->

- **依赖（强）**：宿主 `PromptSection.interpolate`（装机版本实测支持）。
- **依赖（弱）**：被卡窗口 `REQ-261005105032-3b02` 仍在 `implementing` 且卡 `t-7e7da9` 在制——解冻证据取自它。
- **约束**：不改 `vendor/` 与宿主；不改段文本内容；改动只落在 `src/gate-wiring.ts` + 两个测试文件。
- **约束（实施期自证纪律）**：本需求自己的拆分计划里，凡是会进注入面的文本
  （任务 `acceptance` / `description` / `context`、需求标题）**不得裸写 ASCII 双花括号**——
  用全角写法或文字描述。否则本需求的卡会把自己窗口再打挂一次（这正是本案的教训）。
