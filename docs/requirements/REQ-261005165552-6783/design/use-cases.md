# 用户场景（REQ-261005165552-6783）

<!-- serves: FR-1, FR-2, FR-3, FR-4 -->

> 读者：维护者与验收人。四个场景全部来自**真实事故链路**（场景 1、2 是现场，场景 3 是根因形态，场景 4 是恢复动作）。
> 每个场景都写"改前看到什么 / 改后看到什么"，改前的描述均有台账或日志出处。

## 场景总览 `serves: FR-1, FR-2, FR-3, FR-4`

| 场景 | 谁 | 什么时候 | 改前 | 改后 |
|---|---|---|---|---|
| UC-1 | 窗口 agent（已领卡） | 每回合装配系统提示词 | **整轮失败**，模型没跑 | 正常开工，占位符当普通文字 |
| UC-2 | 窗口 agent（未绑定需求） | 用户消息到达、注入立项引导 | 消息里带占位符 → **整轮失败** | 正常回复，原文照引 |
| UC-3 | 维护者 | 新增/修改提示词段 | 隐性默认（靠宿主缺省） | 必须显式声明插值开关 |
| UC-4 | 人 / 接手窗口 | 事故后恢复 | 只能重启，重启后照旧 | 重载即解冻，有可复核证据 |

## UC-1: 领到"验收标准里引用了模板占位符"的卡 `serves: FR-1, FR-2`

**背景（现场）**：`REQ-261005105032-3b02` 的卡 `t-7e7da9`（加模板门禁探针）在制。
它的验收标准里写着"往模板塞未登记占位符（两个花括号 + `NOPE`）→ 退出码 1 且点名"——
这是**完全正当**的文档写法。

**改前**：
1. 窗口 `session-5632659d` 收到任何一条消息 → 宿主装配系统提示词；
2. 捕获段走"已绑定"分支，`boundSectionTextFrom` 把在制任务的验收标准原样拼进段文本；
3. 宿主按模板扫描这段文本 → 大写占位符名字非法 → **抛错，本轮结束**（模型一次都没跑）；
4. 卡的验收标准不会自己变 → **下一轮照旧**。窗口从此只能靠重启，而重启后同一张卡仍在制。

**改后**：
1. 段上声明了字面量身份 → 宿主**整段跳过变量扫描**；
2. 同一段文本原样进提示词，agent 看到的是卡的验收原文；
3. 窗口正常跑完这一轮，任务照常推进。

**边界**：本次**不改** `t-7e7da9` 的验收标准原文（不去适应门禁，而是让门禁不再误伤）。

## UC-2: 未绑定窗口收到一条含占位符的用户消息 `serves: FR-1, FR-2`

**背景**：捕获 hook 会把到达的用户消息登记为"待捕获候选"，下一回合由捕获段引用其**节选**（≤300 字）。

**改前**：
1. 用户在某个未绑定窗口贴一段含占位符的文本（例如**直接贴本次报错信息本身**——报错信息里就带着占位符）；
2. 捕获段返回动态引导（引用该消息节选）；
3. 宿主扫描 → 抛错 → **窗口整轮失败**；
4. 最讽刺的一点：**越是来报这个障，越容易把接手窗口也一起打死**（故障自我复制）。

**改后**：动态引导照常注入，节选原文照常引用；窗口正常回一句"这条不立项/这条值得立项"。

## UC-3: 维护者新增一个提示词段 `serves: FR-4`

**改前**：注册处只写 `name/order/text`，"要不要插值"由宿主缺省决定（缺省 = 插值）。
任何人新增段时都在**无意识地**继承一套模板语义，而自己的文本里可能全是外来原文。

**改后**：接线回归断言"本插件每个段都必须显式带 `interpolate` 布尔值"。
维护者新增段时必须回答"我这段的文本会不会扫描变量"——回答本身就是设计决策。

## UC-4: 事故恢复（重建 + 重载 + 证据） `serves: FR-3`

**改前**：窗口卡死后，人只能重启 DSH；重启后同一张卡仍在制 → **重启即复发**。
（顺带说明：手工改 `queue.json` 也不行——任务队列是**进程内缓存**，不重启不生效。）

**改后**：
1. `pnpm build` 出含开关的新产物；
2. 重载插件；
3. 在被卡窗口发一条消息 → 正常跑完一轮；
4. 复核三件证据：窗口回复、诊断日志 `NODE-4/NODE-5` 正常、台账 `interruption` 无新增。

## 关键决策与取舍 `serves: FR-1, FR-3`

| 取舍点 | 否掉的方案 | 选了 | 为什么 |
|---|---|---|---|
| 场景 1 的两条出路 | 改卡上验收标准的写法（去掉占位符） | 改段的渲染语义 | 卡上写法正当；改它等于"让人适应缺陷"，且下一次换个人写又会复现 |
| 场景 2 的两条出路 | 对用户消息节选做消毒（把花括号换成别的） | 段声明字面量 | 消毒会篡改用户原话，违背原文保真 |
| 场景 4 的恢复手段 | 等下次发版顺带修 | 本次重建 + 重载 | 卡死窗口是**生产中断**，不能等 |

## 技术方案与亮点 `serves: FR-2, FR-3`

- 四个场景构成一条完整闭环：**根因形态（UC-3）→ 两种入口（UC-1/UC-2）→ 恢复动作（UC-4）**，
  验收人可逐条对照台账与日志复核。
- 亮点同架构设计：**一个布尔字段消掉整类故障**，不改文案、不改数据、不改宿主。
