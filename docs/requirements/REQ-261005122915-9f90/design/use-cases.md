# 用例设计（REQ-261005122915-9f90）

> 全部用例都以「谁在什么时候点了什么、系统该怎样」叙述；技术落点见 `backend.md` / `frontend.md`。

## UC-1 回退后重新批准计划（本次现场，必须不再发生） `serves: FR-1, FR-2, FR-3`

**前置**：需求 `implementing`，13 张卡全 `todo`、未开工。
**动作**：agent 回退到 `decomposing`（物化 13 张占位卡）→ 重新提交 23 张计划 → 人批准。

**期望（修复后）**：

1. 落库前置步骤先把 13 张占位卡置 `canceled`（留痕「已被新计划取代」）；
2. 幂等判定看到「真卡 0 张」→ **真的落 23 张卡**；
3. 需求推进到 `implementing`，看板 DAG 上是 23 张新卡；
4. 台账评论写「已落库 23 张」，**不再**出现把占位卡算成已落库的假账。

**修复前的实际表现**（现场证据）：`createdCount=0`、评论写「已落库 13 张卡」、状态照样推进，
DAG 上跑的仍是旧计划范围的 13 张占位卡。

## UC-2 落库真的没发生（覆盖门禁拒绝等） `serves: FR-3`

**前置**：计划已批准，但某条 FR 没人接（覆盖硬门会抛）。
**动作**：批准计划（弹框或看板）。

**期望**：

1. 需求**留在 `decomposing`**（不推进）；
2. 台账写系统评论：失败原因 + 两条恢复路径（修文档后手动 `reqboard_decompose` / 看板拆分入口）；
3. `advance.pausedReason = 'auto_decompose_failed: …'` 且产生高优告警；
4. **判据不得被占位卡骗过**：队列里只剩占位卡时，「未取消任务数 > 0」不再被当作落库成功的证据。

## UC-3 人在看板清理误物化卡 `serves: FR-5`

**前置**：需求有回退记录（`rollback.seq = N`），队列里有该次回退物化的占位卡。
**动作**：人在需求详情点「清理误物化重做卡」。

**期望**：

1. 按钮**只在有回退记录时出现**（无记录 → 不渲染，不给假按钮）；
2. 点击前有 `confirm`，说明后果（按第 N 次回退的物化清单批量取消；不碰已完成卡）；
3. 成功后展示**可核对回执**：匹配方式（`lastMaterialized` / 兜底）、取消张数、父子还原条数、
   逐条 `skipped` 原因；无跳过时不显示跳过区；
4. 失败（如序号不存在）原样透出服务端文案与错误码，不静默；
5. 幂等：再点一次 → `canceled === 0`，队列无变化（回执如实说明）。

## UC-4 同一需求第二次回退 `serves: FR-4`

**前置**：需求已回退过一次且**没清理**（队列里还有占位卡 `todo`）。
**动作**：人/agent 再回退一次（`implementing → decomposing`）。

**期望**：

1. 上一轮的占位卡被 **`canceled`**（它们没有子卡身份，不能「原地复位」）；
2. 不产生「重做卡的重做卡」（既有性质，回归锁定）；
3. 真子卡（有 `parentId`）仍按既有规则复位为 `todo`；
4. 于是下一轮落库时幂等判定看到的是「真卡 0 张」，不会再被历史占位卡埋掉。

## UC-5 清场后重新落库（现场复演） `serves: FR-1, FR-5`

**前置**：REQ-261005105032-3b02 现状（`implementing`、已批准 23 卡、队列只有 13 张占位卡）。
**动作**：清场（第 1 次回退）→ 重新落库。

**期望**：队列活卡 = 该需求已批准的 23 卡计划；需求状态与落库结果一致；
台账同时留下「清场」与「落库」两条可复核评论。
