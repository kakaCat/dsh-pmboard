# REQ-261001184609-cecb 验收不再要人填结果：agent 跑完验证自己落章，人只点通过

> 类型：feature · 难度：expert · 来源：用户裁定（2026-10-01）“你都告诉用户验证内容，你跑一下自己填写就可以了，为何还要用户去填写”

## TL;DR

验收单把两件事混在一起了：谁去跑验证、谁做裁决。结果是 agent 明明跑过验证，
人还要在弹框里把命令输出重抄一遍（不抄就记「未复核」）。本需求把两者分开。

   今天                                     本需求之后
   +-----------------------------+          +---------------------------------+
   | agent 提交验收材料          |          | agent 提交材料时逐项给出        |
   |  ↓ 弹框逐项问“实际结果”     |   -->    |   “跑了什么 + 实际输出”         |
   | 人必须手打一遍（否则未复核）|          |  ↓ 工具写进该项的 result        |
   | 人再点通过                  |          | 人只看结论：通过 / 退回         |
   +-----------------------------+          +---------------------------------+

| 面 | 现状 | 本需求之后 |
|---|---|---|
| 谁跑验证 | 人要重抄 agent 已跑的命令输出 | agent 跑并落库 |
| 谁裁决 | 人 | 人（不变） |
| 手填场景 | 每一项都要求 | 仅「需人工确认」项（显式标注） |
| 无法自动验证 | 与普通项混在一起 | 单列一类，写明为什么必须人看 |

## 判定标准（可证伪）

| 断言 | 量法 | 通过条件 |
|---|---|---|
| A1 材料即结果 | 提交验收材料后查验收单 | 每个可自动验证项都带 result（命令 + 输出摘要） |
| A2 人零输入 | 走一次完整验收 | 不填任何文本即可完成全部可自动验证项的裁决 |
| A3 不可验证项显式 | 查验收单 | 需人工确认的项带标记与理由，不与普通项混淆 |
| A4 反例仍拦 | 对没有 agent 结果的项选「通过」 | 仍记 unverified（不冒充通过） |

## 产品定义

验证是执行方的活，裁决是人的活。执行方跑得出结果就必须自己落库；人只在“看结论、拍板”这一步出现。

把执行证据工作推给人，代价是双份：人花时间重抄，且抄来的内容未必比 agent 的原始输出更可信。

## 用户与角色

| 角色 | 关心什么 | 本需求给他什么 |
|---|---|---|
| 验收的人 | 不想当打字员 | 只看结论点通过/退回 |
| 实施 agent | 跑了就该算数 | 提交材料时落结果，不必求人代填 |
| 维护者 | 台账要可信 | 结果有来源（命令+输出），不是人手抄的转述 |

## 功能点

- **FR-1: 验收项的实际结果由 agent 落库**

  提交验收材料时，agent 逐项给出“跑了什么命令 + 实际输出摘要”，由工具写入该项 result；
  没有结果的项保持空（不伪造）。

- **FR-2: 验收弹框默认只问裁决**

  验收项已有 result 时，弹框只呈现结论与该项已有的结果，人点“通过 / 退回”；
  不再要求人输入任何文本。

- **FR-3: 不可自动验证项显式标注**

  需要人工看界面/数据的项，单列一类并写明为什么必须人看（如“界面视觉”“线下流程”），
  这类项才要求人填写实际结果。

## 边界

做：

1. 验收材料到验收单 result 的逐项落库通道。
2. 弹框与看板展示已落库结果，人只裁决。
3. 不可自动验证项的显式分类与理由字段。

不做：

1. 不取消人工裁决（人仍然必须点通过/退回）。
2. 不自动判定“验收通过”（闸门永远在人这边）。
3. 不改动任务卡验收标准的生成规则（那是 REQ-261001170807-06fd 的范围）。
