# REQ-261002110908-81d0 用例设计 · 三条主线与一条"不覆盖"的异常流 `serves: FR-1, FR-2, FR-3`

> 读者是"要照着写参数的人（agent）"与"要判断这条需求管不管用的人（维护者）"。
> 每条用例写清：谁在什么时机读到什么、因此少犯了哪个错。

## UC-1 模型写完工汇报（主线） `serves: FR-1`

**角色与时机**：实施 agent，一张卡干完之后、准备调 `reqboard_task_report` 的那一步。

**主流程**：

1. agent 读到工具描述与 `completed` 的参数说明（含"每条短句""要引号用「」""太长拆多次"）。
2. agent 把复核结论写成若干短句，引号改用「」。
3. 若内容多，agent 分两次调用（第二次幂等追加为"第 2 段"，不重复登记产物）。
4. 工具正常落盘，链继续往下走。

**后置条件**：任务卡文档出现汇报段；`lastReport` 写入（凭证门可过）。

**与原流程的差别**：只多了"读约定"这一步，**命令与返回值一模一样**。

## UC-2 模型提交验收材料 / 确认问题 / 断点原因（同类场景） `serves: FR-2`

**角色与时机**：任何要写一段中文进工具参数的时机（`reqboard_submit` 材料、`reqboard_ask_confirm` 问题、`reqboard_note_interruption` 原因…）。

**主流程**：

1. agent 读到该字段的参数说明——它引用的是**同一句**约定（不是各写各的）。
2. agent 按同一口径书写，长文本拆段。
3. 维护者新增一个同类工具时，清单未登记 → 用例红 → 被逼着登记，约定自动覆盖新工具。

**后置条件**：约定覆盖面可枚举、可被机器检查（`LONG_TEXT_FIELDS`）。

## UC-3 实施阶段自检（时机提醒） `serves: FR-3`

**角色与时机**：同一实施 agent，但发生在**动笔之前**——实施提示词片段里的一行。

**主流程**：

1. agent 按实施片段执行，读到"汇报自检"这一条。
2. 落 `reqboard_task_report` 前先自查引号形态与篇幅。
3. 发现太长 → 当场拆成多次调用。

**后置条件**：提醒发生在生成参数**之前**（描述在工具定义里，属于事后可见；两者互补）。

## UC-4 异常流：模型仍然写出非法 JSON（**本需求不覆盖**） `serves: FR-1, FR-2`

**触发**：约定读到了仍然漏转义（模型输出不确定，概率无法归零）。

**现状行为（如实记录，不做兜底）**：

1. DSH Messages 适配器在 `message_stop` 处 `JSON.parse` 失败 → `LlmError(MALFORMED_RESPONSE)`。
2. **整整一轮**判失败：本轮推理、文本、其它工具调用全部作废；上报 GUI「本轮运行失败」。
3. 任务卡 `lastReport` 不写 → 凭证门不放行 → 链停摆（这正是 `t-f81376` 的现场）。

**本需求的处置**：**不覆盖**。降低概率可以，消除失败粒度不行——那要改 DSH 核心适配器（跨仓、另有决策点，见 `requirement.md` 的「边界」）。
**为什么写出来**：这条异常流必须显式留在设计里，防止后人误以为"本需求已经根治了整轮失败"。
