## UC-1 新增错误码（前向兼容的关键场景） `serves: FR-1, FR-9`

**前置**：另一个窗口在 `src/` 新增了一个码（实测发生过两次：
`REQBOARD_OWNER_WINDOW_NOT_LIVE`、`REQBOARD_SKIP_INTEGRATION_REASON_REQUIRED`），
既没进清单也没写用例。

**主流程**：
1. 该窗口跑 `pnpm test`；
2. `tests/error-code-inventory.test.ts` **红**并点名：`REQBOARD_FOO_BAR`（`src/...:NN` 未进清单）；
3. 消息里给**可执行的自助命令**：`npx tsx tests/drill/refresh-error-code-inventory.mts`；
4. 他跑该命令 → 清单追加该码，`tier: "unclassified"`、`covered: false`；
5. 再跑测试 → **仍红**（`unclassified` 必须归零），消息要求分级并补一条矩阵用例，或进白名单并写 `reason` + `plan`；
6. 他分级 + 补 `TriggerSpec` → 绿。

**为什么这么设计**：既**不阻塞**别人加码（第 4 步让红变可解），又**不让他靠刷新洗绿**
（第 5 步把分级义务留下）。这是 FR-9③「前向兼容」与 FR-3「棘轮」的交点。

**异常分支**：直接改 `frozenCount` 放宽 → 棘轮红；把码写进 `excluded` 声称它不是码 →
排除项守卫红（恰 5 条固定项）。

## UC-2 复核基线为什么允许 68 条失败 `serves: FR-4`

**主流程**：打开 `docs/reviews/test-baseline.reverse.notes.md` → 逐条读「红因类别 / 红线内可达性 / 证据」
→ 看到 `src-debt` 类（如 `tests/layer-boundary.test.ts` 的 `domain/` 用 `Date.now()`）
即知**不是测试写错，是 src 债**；看到 `unknown` 条数即知还欠多少定位工作。

**判据**：notes 的条目集合与 `reverse.txt` **逐字相等**（守卫保证），故「有一条没写红因」不可能静默存在。

## UC-3 人验收：核对两个读数 `serves: FR-1, FR-2`

**主流程**：实施方给出改前/改后两行读数（反向占比 3.82%；零覆盖 25），
**都带工作树指纹**，口径为**双形态**并给出假阴性率（7/102 = 6.86%）；人可自行复跑判据命令核对。

**异常分支**：只给字面量口径 → 不合格（会把 7 条不存在的工作量记成缺口）；
读数没带指纹 → 不合格（多窗口共用工作树，无指纹的读数无法界定）。

## UC-4 某码测不了，登记豁免 `serves: FR-3`

**主流程**：在 `error-code-exempt.json` 追加 `code` + `tier` + `reason` + `evidence` + `blocker` + `plan`；
`reason`/`plan` 任一为空 → 红；该码必须同时在 inventory 里 `covered=false`（双向相等）；
**不得**上调 `frozenCount`。

**反模式（守卫会拦）**：把能测的码也塞进白名单；给在产码打 `blocker=no-production-point`。

## UC-5 怀疑守卫误报或失效 `serves: FR-2, FR-5`

**主流程**：先看失败消息是否给了 `<how>`（本需求要求每条红都给）；若怀疑「守卫自己坏了」，
跑守卫的**元测试**（矩阵三条自检、契约锚点的探针用例、权限模型的启动自检）。
设计上守卫自带自检，因为**守卫的守卫没有守卫**。

**异常分支**：`TEST_HERMETIC_ROOT_UNKNOWN`（无法确定仓库根）→ 拒绝放行，**不得**当作通过；
⑤-a 探测到权限模型未生效 → 响亮标注「未覆盖」，不得静默当通过。

## UC-6 反向演练 `serves: FR-8`

**主流程**：跑 `npx tsx tests/drill/reverse-drill-error-codes.mts` → 先做**范围自检**
（每条 `target` 必须真实存在，防「没跑也全绿」）→ 逐条：文件级备份 → 写坏 → 跑判据 →
断言**变红且输出点名** → 逐字节还原 → sha256 复核 → 退出码 0。

**并发安全分支（血的教训）**：跑判据期间若目标文件已被别的窗口改写 → **放弃还原并响亮报错**，
绝不回写覆盖别人的改动。**禁用**按路径检出还原。

## UC-7 多窗口并发跑测试 `serves: FR-5`

**改前（病的表现）**：`harness.ts` 的 `FakeDocs.workspaceRoot()` 返回 `'.'` → RTM 写入绕过 docs 端口
直接拼 `./docs/requirements/<REQ>/rtm-*.yml` → 合成 id `REQ-000001` 撞上真实跟踪目录 →
15 个 tracked 文件每次 `pnpm test` 被改写，别的窗口看到一堆不属于自己的脏改动。

**改后（期望）**：
1. ⑤-b 契约锚点钉住「替身根必须是绝对临时根」（改回 `'.'` 即红）；
2. `FakeDocs` 认绝对根（`keyOf` 归一 + 根自身存在），10 条立项回归清零（已实测）；
3. ⑤-a 权限模型从内核层拒绝任何仓内写入（即便将来又有人写出新的泄漏路径）。

**判据的诚实边界**：共享工作树里**无法**用「全树哈希前后不变」判（D-4 实测）；
归因一律用 A/B 对照（FR-10），整体验证放**隔离副本**里做（⑤-c）。

## UC-8 拆分/实施窗口接续使用本设计 `serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8, FR-9, FR-10`

## UC-9 接手一次「已回退重写」的需求 `serves: FR-10`

**前置**：本需求第一版走到 implementing（13 张卡、2 张完成）后按用户指令回退重写。
接手窗口要能从文档里看出**为什么回退**，而不是重蹈覆辙。

**可用信息**：
1. `requirement.md` 的**「实施期实证」节**列出四条只能靠实做才知道的事实；
2. **「已被证伪、不得再写进设计的机制」表**明确三种机制永久作废及其证据；
3. **FR-10** 要求机制先验证再写进设计、判据灵敏度必须用 A/B 反证；
4. 已完成的 t1/t2 代码保持现状，**去留由新版设计定稿后重新评估**（不得默认沿用）。

**异常分支**：若新版设计又要引入一个未验证的机制 → 按 FR-10 先做**最小验证**
（如本次用 5 行脚本证明权限模型真能拦），再写进设计。
