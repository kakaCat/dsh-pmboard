# 数据模型（REQ-261004121649-bfa7）

> serves: FR-1, FR-3

## 一、任务卡上新增的可追溯字段（serves: FR-1）

队列（`docs/requirements/<REQ>/queue.json`）的任务记录**已**有 `reworkOf`（指向被替代的原卡）。
本需求不再新增字段，只**规定它的填写口径**：

| 字段 | 现状 | 本需求规定的口径 |
|---|---|---|
| `reworkOf` | 已存在，指原卡 id | 只在「顶层父卡的重做卡」上填；子卡复位时**不填**（复位不等于重做） |
| `parentId` | 已存在 | 子卡复位后**必须保留**（这是 FR-1 的判据） |
| `stageKind` | 已存在（子卡阶段） | 同上，复位后必须保留 |
| `stages` | 已存在（可选） | 重做卡**显式置 `[]`**（= 不自动展开子链，FR-2） |

## 二、回退序号与幂等记录（serves: FR-3）

回退序号挂在需求记录上（不落队列文件，避免两个存储各存一份）：

```
requirement.rollback = {
  seq: number,                    // 该需求累计回退次数（FR-3 的幂等键组成部分）
  lastAt: number,                 // 最近一次回退时间（留痕/审计）
  lastMaterialized: string[],     // 最近一次物化出的卡 id（FR-4 批量清理的输入）
}
```

- **幂等**：物化前先查 `(requirementId, taskId, seq)` 是否已有重做卡；有则跳过；
- **批量清理**：直接消费 `lastMaterialized`（无需人提供卡列表），再按 `reworkOf` 反查还原父子关系。

## 三、兼容与迁移（serves: FR-3）

- **旧数据**：没有 `lastMaterialized` 记录的需求（存量 2 条的 `rollback` 只有 from/to/at/by）
  → 批量清理入口只能用兜底匹配；这条兜底**必须在回执里如实说明匹配方式**，不允许假装精确；
- **兜底的判据是两个条件同时成立**（实施校准 2026-10-04）：`reworkOf` 非空 **且** 标题带
  `[重做] ` 前缀。实测 0fbf 的 56 张里，只有 17 张两者齐备，另 39 张是**由子卡膨胀出来的**
  （有 `parentId` 但无 `reworkOf`）——它们早已是 `canceled`，清场不需要再动它们。
  单看前缀会多杀、单看 `reworkOf` 会漏杀，两个都要才对得上真实数据；判据宁可漏不可错杀；
- **序号校验只管记过序号的记录**：`rollback.seq` 缺省的存量记录没有「批次」可分（清单只有一份），
  若一律按序号拒绝，兜底路径就永远走不到、旧卡永远清不掉。故只在**记过序号**时校验相等；
- **迁移**：不新增必填字段、不改 `schemaVersion`、无需回填；
- **回滚**：删字段消费点即可，旧字段（`reworkOf` 等）行为退回现状。
