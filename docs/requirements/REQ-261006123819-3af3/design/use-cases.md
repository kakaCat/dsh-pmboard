## UC-1 新增工具后跑契约测试 <!-- serves: FR-1 -->

**角色**：后续需求的实施窗口。

**场景**：在 `src/tools/` 下新增一个 `defineFooTool` 工厂，并在 `src/index.ts` 里注册。

**操作流程**：

1. 实施者新建目录 `src/tools/FooTool/`，写 `FooTool.ts` 导出 `defineFooTool(deps)`。
2. 实施者在 `src/tools/index.ts` 导出它，在 `src/index.ts` 的 `apply()` 里注册为 `reqboard_foo`。
3. 实施者跑 `npx vitest run tests/output-contract.test.ts tests/tools-dispatch.test.ts tests/apply-wiring.test.ts`。
4. 若忘了在 `src/tools/registry.ts` 登记，三个文件同时点名（目录差集 / 注册名差集 / 工厂未登记）。
5. 实施者补 `TOOL_REGISTRY` 一条（含 `responseSources`），复跑 → 全绿。

**预期结果**：

- 结果 1：漏登记时**三个面各自点名**，消息里带工具名（不是只报"数量不符"）。
- 结果 2：补登记后三文件全绿；`registry` 一条即可，不需再改三处清单。

**边界条件**：

- 工厂带第二参数（如 `defineBindTool(deps, opts?)`）时同样能被安全网扫到（正则已放宽）。
- 工具不产生对象返回（全部返回模板字符串）时，`responseSources` 指向用例文件即可满足 I-5。

## UC-2 判定"有没有引入新失败" <!-- serves: FR-2, FR-6 -->

**角色**：任何实施窗口。

**操作流程**：

1. 实施者跑 `pnpm baseline:check`。
2. 脚本自己跑全量 vitest（JSON reporter）与 `tsc --noEmit`，并采集工作树指纹。
3. 与 `docs/reviews/test-baseline.failures.txt` 算集合差。
4. 差集为空 → exit 0，打印指纹与两栏计数（新增 0 / 消失 0）。
5. 差集非空 → exit 1，分两栏打印「新增失败」「不再失败」，并提示"确认非本次引入后再 `pnpm baseline:refresh`"。

**预期结果**：

- 结果 1：**判据是差集，不是计数**——因此在基线数字过期时依然正确（例如现在 70≤98、0≤197 的失效情形不再发生）。
- 结果 2：输出自带工作树指纹，读数在任何并发写入下都可界定（FR-6）。

**边界条件**：

- 基线文件缺失时：报"没有基线，先 `--refresh`"，exit 1，**不静默当作通过**。
- `--refresh` 是"承认现状"的动作：脚本会打印将被写入的新指纹与差集，要求人确认这是有意的。

## UC-3 打开已归档需求 <!-- serves: FR-3 -->

**角色**：人。

**操作流程**：

1. 人打开任意一条 `status=archived` 需求的详情页（本仓现有 87 条）。
2. 服务端 `buildGateVerdicts` 按 `status` 判定归档门，`at` 取 `statusHistory` 里 archived 事件的真实时刻。
3. 详情页「文档」Tab 的归档块与门禁区块显示「已归档 · <时刻>」。

**预期结果**：

- 结果 1：归档门 `verdict: 'passed'`（改动前恒为 `pending`）。
- 结果 2：归档块徽标为 `data-state="pass"`、`data-archived="yes"`（改动前恒为 pending/no）。

**边界条件**：

- 取不到 archived 事件时（理论上 0 条，实测 87/87 都有）**省略 `at` 键**，仍判 `passed`，徽标不带时刻。
- 载荷里取不到归档门读数（旧服务端/端点未接线）时，客户端按「材料已备」呈现，不断言已归档。

## UC-4 打开"已归档但没有归档清单"的需求 <!-- serves: FR-3 -->

**角色**：人。

**场景**：本仓现有 **22 条** `status=archived` 但没有归档清单的需求（如 `REQ-261002110908-81d0`、
`REQ-261002105242-a3fb`）。

**预期结果**：

- 结果 1：归档门显示「**尚未提交归档材料**」——与「材料已提交，待归档确认」是**两个不同的状态**，
  人要能分辨"没交"和"交了没人批"。
- 结果 2：文档面板不出现归档块（`d.archive === undefined` 时整块不渲染），不显示一个空的"归档"分区。

**边界条件**：这也是本需求**不**解决的已知缺口（归档补交通道缺失，O-6，另立需求）；
本条只保证"页面如实说出缺什么"。

## UC-5 改完知识层跑自检 <!-- serves: FR-4 -->

**角色**：任何实施窗口。

**操作流程**：

1. 实施者按 C-13 跑 `pnpm kb:check`（内含 kb-build --check + conventions-sync --check + kb-probe）。
2. 有生成物漂移 → 按提示跑 `pnpm kb:build` 重生成。
3. 复跑 `pnpm kb:check` → exit 0；`npx tsx scripts/kb-probe.mts` → `0 项失败`。

**预期结果**：

- 结果 1：11 项检查全过（现状 6 项失败）。
- 结果 2：`docs/knowledge/INDEX.md` 字符数 ≤8000（现状 10489）。
- 结果 3：C-22 与 kb-0043 / kb-0048 都有索引行；两份 entry 的 `one_liner` 合法。

**边界条件**：

- `kb-0003` / `kb-0004`（stale）与 `kb-0031`（superseded）**不进索引**——非 active 条目按设计不登记。
- 若 `design-tokens.md` 220 行 > 200 的处置选择"调预算"，必须在规范里写明理由（调预算＝软化门禁，须留痕）。

## UC-6 本需求收尾提交 <!-- serves: FR-5 -->

**角色**：本窗口 agent。

**操作流程**：

1. 六条 FR 的实施与验证完成后，本窗口按主题提交**本需求自己的文件**。
2. `git log --oneline --grep=REQ-261006123819-3af3` 能查到提交。
3. 收尾检查单/规范里出现「改动后必须提交」条目。
4. 其他窗口的 250 个在飞文件**不纳入**本次提交（D-1）。

**预期结果**：

- 结果 1：`git show --stat` 的文件集合 ⊆ 本需求改动清单，不含其他需求目录。
- 结果 2：存量悬空作为已知缺口写进验收材料。

**边界条件**：本仓多窗口共用工作树，提交时工作树可能正被其他窗口改写——
因此提交前必须先记指纹（FR-6），提交内容按"本需求改动清单"逐个 `git add`，
**不使用 `git add -A`**。

## 关键决策与取舍 <!-- serves: FR-1, FR-2, FR-3 -->

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| UC-2 的判据 | 计数比对（沿用 C-14 现状） | 集合差 | 计数口径在数字过期时静默失效（实测 70≤98 被允许），集合差不会 |
| UC-4 的状态区分 | 统一显示「待归档」 | 区分"没交"与"交了待批" | 22 条缺清单需求与 64 条已交材料需求，人的下一步动作完全不同 |
| UC-6 的提交方式 | `git add -A` 一次提交 | 按本需求清单逐个 add | 工作树上有别的窗口的在飞改动，`-A` 会把它们一起带上（D-1） |

## 技术方案与亮点 <!-- serves: FR-2, FR-6, FR-3 -->

- **UC-2 一条命令覆盖两条 FR**：`baseline:check` 的集合差判据（FR-2）与输出里的工作树指纹（FR-6）
  同源产出，不额外造机制。
- **UC-4 是"页面说实话"的具体化**：本需求不修归档补交通道，但让人能一眼看出"缺的是材料还是批准"。
- **UC-1 的失败信息带工具名**：三面各自点名差集，而不是"数量不符"——后者需要人去 diff 才知道缺谁。
