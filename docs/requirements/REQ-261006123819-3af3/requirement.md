## 产品定义 <!-- serves: FR-1 -->

**是什么**：一次"把审计发现的仓库级欠债按性价比清单还掉"的整治需求。

它修的不是某个功能，而是**判定的可信度**——仓库里那批"宣布通过/失败"的机械判据本身。

**核心价值**：把"门禁红着、基线过期、字段没人写"这三类**不会报错的退化**变成会响亮的失败。

现状是：门禁红着没人管，于是新增违规与存量噪声不可区分；基线写着三个不同的数，于是"没超基线"这句话没有意义。

**与现状的区别**：不是新增门禁，而是让**已存在的门禁重新可信**——先修判据，再谈用判据看代码。

**三要素检查清单**：

- [x] 说清楚"是什么"：仓库级判定口径与死代码的整治
- [x] 说清楚"核心价值"：让已有门禁恢复判别力，让基线成为单一事实源
- [x] 说清楚"与现状的区别"：不是加规则，是让规则自洽且可信

### FR-1: 补齐工具响应源映射并从注册面派生清单

**功能描述**：实施者新增一个工具后跑契约测试即红，漏登记当场被点名，不必再靠人记"要登记几处"。

**详细说明**：

- **使用场景**：任何窗口在 `src/tools/` 下新增一个 `define*Tool` 工厂后，跑契约测试时。
- **操作流程**：
  1. 实施者在 `src/tools/` 下新增工具工厂。
  2. 跑 `npx vitest run tests/output-contract.test.ts tests/tools-dispatch.test.ts tests/apply-wiring.test.ts`。
  3. 若漏登记，测试打印**缺哪个工具**；登记后三个文件全绿。
- **预期结果**：
  - 结果 1：`RESPONSE_SOURCES` 覆盖全部 25 个工具工厂（现状 21 个，缺 `TaskAdopt` / `Knowledge` / `Regenerate` / `SkillInstall`）。
  - 结果 2：`tools-dispatch` 与 `apply-wiring` 的期望清单不再手写，从注册面派生（现状三处清单三个数：25 / 18 / 26）。
- **边界条件**：
  - 边界 1：不新增工具、不改工具行为，只补登记与派生方式。
  - 边界 2：工厂扫描口径沿用既有正则 `export function define(\w+)Tool\(deps: UseCaseDeps)`；带第二参数（如 `defineBindTool` / `defineHandoffTool`）的工厂是否纳入，属设计决策。

**验收标准**：
1. `npx vitest run tests/output-contract.test.ts` → `Test Files 1 passed`，且 4 个缺失映射的用例由红转绿。
2. `npx vitest run tests/output-contract.test.ts tests/tools-dispatch.test.ts tests/apply-wiring.test.ts` → 全绿、exit 0。
3. 反向证伪：临时删除 `RESPONSE_SOURCES` 中任一键 → 该文件复红并点名缺失工具；还原后复绿。

  2. 按 C-14/C-15 新口径**与基线文件比对集合差**，而不是比一个写死的数。
  3. 基线过期时，用一条命令刷新基线文件，规范与其余文档无需改动。
- **预期结果**：

- **边界条件**：
  - 边界 1：不修任何存量失败用例（救绿属 O-4，另立需求）。

### FR-5: 提交纪律落地（本需求自提交）

### FR-6: 回归与审计证据必须带工作树指纹

**功能描述**：下一份回归或审计证据里带着"这份读数是在哪个工作树状态下采集的"，读数在并发写入下仍可界定。

**详细说明**：

- **使用场景**：任何窗口产出回归证据或审计报告时；人复核这些证据的时效性时。
- **操作流程**：
  1. 采集读数的窗口记录 `HEAD` 与 `git diff --stat` 指纹。
  2. 指纹与读数一起写进证据/审计文档。
  3. 复核者按指纹判断该读数是否还有效。
- **预期结果**：
  - 结果 1：本需求产出的证据与审计文档带「工作树指纹（HEAD + `git diff --stat` 摘要）」字段。
  - 结果 2：该字段要求进入证据文档模板或收尾检查单，不只落在本次两份文件里。
- **边界条件**：
  - 边界 1：不实现行校验、不动会话启动流程、不做 worktree 隔离（O-14 完整版另立需求）。
  - 边界 2：指纹只记录、不参与任何门禁放行判断（不做成新的假绿通道）。

**验收标准**：
1. 本需求的验收材料中含 `HEAD` 与 `git diff --stat` 摘要（可 grep 到提交短哈希）。
2. 证据文档模板或收尾检查单里能 grep 到"工作树指纹"要求。
3. 反向证伪：把该字段从模板中删除，检查单/模板自检必须报缺（若模板层无自检，则本 FR 降级为"仅落两份文件"并在验收材料里写明降级）。

## 边界（不做什么） <!-- serves: FR-1 -->

- **不做存量门禁救绿**（O-4：`layer-boundary` / `size-budget` / `message-hygiene` / `probe-hard-criteria` / `project-scope` / `skills-assets` / `template-address-injection` 等红灯）。
  理由：它们依赖 FR-2 的新基线口径；先救绿会被 70 例噪声重新污染。时机：FR-2 落地后另立需求。
- **不做归档材料补交通道**（O-6：22 条已归档需求无归档清单）。
  理由：那是产品行为改动，需要设计"不依赖绑定窗口的补交通道"并过人工门，范围超出本次 5 条机械修复。时机：紧随本需求另立。
- **不做 eval-suite 执行器**（O-8：36 条用例零自动化、从未执行）。
  理由：需求原边界即写明"另立需求"，属新建子系统。时机：独立需求。
- **不做 project-manual 拆分**（O-9：48 节机制备忘 / 1412 行）。
  理由：文档重组需要人裁决"哪些节外迁到 L2"，不是机械改动。时机：独立需求或人工整理。
- **不做多窗口 worktree 隔离**（O-14 完整版）。
  理由：影响所有窗口的开工方式，需改会话启动检查，成本与风险都超出本需求。本次只取其中"证据带工作树指纹"一条。
- **不提交其他窗口的在飞改动**（人已裁定）。
