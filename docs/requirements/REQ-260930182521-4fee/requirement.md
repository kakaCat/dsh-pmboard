# REQ-260930182521-4fee DAG 层级与泳道图卡片颜色未按阶段展示

> 一句话目标 + 可证伪判定标准 + 范围边界 + 档位依据

## TL;DR

同一张任务卡在「DAG 画布」和「泳道」两个视图里颜色对不上、且都不等于它所处阶段的应有颜色。根因有两条：① 六阶段色板存在两套硬编码（Canvas 一套、泳道 CSS 一套），同一阶段的色值语义相反地错位；② 卡片着色用任务原始 `status`，而泳道列归属用 `laneOf` 推导的「所处环节」——着色口径与分列口径不同源。修复 = 色板单一事实源 + 着色状态与列归属同源。

```
现状（以"链已走到测试"的父卡为例）：

  泳道视图                          DAG 画布
 ┌──────────────┐                 ┌──────────────┐
 │ 测试中 列     │ ← 列归属=laneOf │  节点卡片     │
 │ 列头色点=橙   │    =testing     │  底色=浅蓝    │ ← getStatusBackgroundColor
 │ ┌──────────┐ │                 │ (in_progress)│    (原始 status)
 │ │卡片=浅蓝  │ │ ← data-status=  └──────────────┘
 │ │in_progress│ │    原始 status        ↑ 色板还另一套：
 └──────────────┘                 integrating 橙/紫颠倒、
   ↑ 颜色 ≠ 所在列阶段色            testing 绿/橙颠倒（详见下表）
```

## 产品定义

看板实施节点提供 [DAG][泳道] 双视图（需求详情「执行」Tab 同一份 DAG 画布），卡片颜色是用户识别「这张卡走到哪个阶段」的核心视觉信号。现状是三处口径互相打架：泳道列归属用 `laneOf` 推导（卡片层契约 2026-09-28），泳道卡片 CSS 按 `data-status`（原始状态）着色，DAG 画布按原始状态 + 另一套色板着色。结果：父卡被子卡链推进到「测试中」时，泳道里它站在橙色列下却显示蓝色卡片，DAG 里又显示绿色——用户无法凭颜色判断阶段。本需求把「阶段 → 颜色」收敛为单一事实源、把「着色状态」与「列归属」收敛为同一推导口径。

## 用户与角色

- **看板用户（PM/需求方）**：扫一眼泳道/DAG 判断各卡所处阶段的人，需要颜色与阶段严格对应、两视图一致
- **实施 agent**：推进任务状态的一方，颜色错位会让其交付截图在验收时误导验收人
- **前端维护者**：改色值时只需要改一处（单一事实源），不再担心两处色板漂移

## 功能点

- **FR-1: 六阶段色板单一事实源**——todo/in_progress/integrating/testing/in_review/done 六阶段的卡片底色只在一处定义（以 2026-09-24 用户裁定的泳道六状态色为准：灰/蓝/紫/橙/粉/绿），DAG Canvas（card-renderer.ts）与泳道 CSS（styles/node-panel.ts）、列头色点全部从同一常量派生，删除 card-types.ts 中错位的 STATUS_BACKGROUND_COLORS 独立色板
- **FR-2: 卡片着色状态与列归属同源**——泳道卡片与 DAG 节点的着色状态一律使用 `laneOf(card, kids)` 推导的环节 key（与泳道列 key 同词汇），不再直接使用任务原始 `status`；无子卡/存量卡的回落行为由 laneOf 既有逻辑覆盖（非 in_progress 或无子卡 → 自身状态）
- **FR-3: 颜色一致性自动化断言**——新增测试固定「六阶段 → 色值」映射与「laneOf → 着色 key」口径：对链走到 testing 的父卡，断言泳道卡片 HTML 的着色属性与 DAG 数据产出的着色 key 均为 testing，且两处色值引用同一常量

## 边界

**做**：
1. 收敛六阶段色板到单一常量源（card-types.ts 或新建共享常量），Canvas 与 DOM/CSS 两侧同源引用
2. 泳道卡片与 DAG 节点的着色状态改用 laneOf 推导结果（含既有回落），消除「站在 A 列显示 B 色」
3. 新增颜色一致性测试（纯函数 + DOM 字符串断言）

**不做**：
1. 不改泳道列归属算法本身（laneOf 的推导口径 2026-09-28 已定，本需求只让着色跟上它）
2. 不改需求级泳道看板（views/board.ts）的阶段色 token（--pm-c-* 那套 8 色节点色，与任务六状态色是两个语义层）
3. 不动 DAG 的布局/连线/交互（传递归约、关键路径、悬停高亮等均不在本次范围）

## L1 一句话目标 + 可证伪判定标准

**目标**：让 DAG 画布与泳道两个视图里的任务卡颜色严格按「卡片所处阶段」展示，且两视图同一阶段同一颜色。

**可证伪判定标准**：
1. `pnpm vitest run` 中新增的颜色一致性测试通过：六阶段色值在两视图引用同一常量源；对一张子卡链走到 testing 的父卡，泳道卡片着色 key 与 DAG 着色 key 均为 `testing`
2. 看板实测（刷新 GUI 后）：一张父卡子卡链推进到「测试」阶段 → 泳道卡片显示浅橙、所在列列头色点为橙、DAG 画布节点同为浅橙系；链推进到「复核」→ 三处同为浅粉系（截图对比）
3. `grep` 断言：`src/client/` 下不存在第二套六阶段底色硬编码（STATUS_BACKGROUND_COLORS 的错位色值不再被任何渲染路径引用）

## L3 档位依据

**按 feature 走完整流程的依据**：
- 存在待裁决策：六阶段色板以哪套为准（本档建议以 2026-09-24 用户裁定的泳道色为准，Canvas 侧对齐；反向方案是把泳道 CSS 改成 Canvas 色板——需设计阶段定死）
- 改动面跨渲染后端：Canvas 2D（card-renderer.ts）+ DOM CSS（styles/node-panel.ts）+ 数据组装（dag-view.ts / node-panel.ts）+ 测试契约
- 触碰既有用户裁定（2026-09-23/24 两轮关于泳道卡片与 DAG 节点外观的裁定），修改需留痕可回溯

## 数据契约与兼容

- **无数据模型变更**：queue.json / 台账字段一律不动；laneOf 已是既有导出函数，本需求只新增消费方
- **接口变化**：card-types.ts 的 `getStatusBackgroundColor` 语义从「按原始状态取独立色板」改为「按阶段 key 取统一色板」（签名不变，色值来源变）；renderSwimlane 输出的卡片着色属性值从原始 status 变为 laneOf 结果（DOM 契约的 class/data-* 结构不变）
- **存量兼容**：纯展示层改动，无迁移；回滚 = 还原相关文件，无数据风险
