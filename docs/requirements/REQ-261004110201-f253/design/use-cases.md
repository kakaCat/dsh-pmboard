# 用例设计（REQ-261004110201-f253）

> 谁在什么场景下用、得到什么。每条用例标注它服务哪个功能点；不含实现细节（那些在 architecture/interfaces）。

## UC-1 按阶段换模型：省钱不降质量（人配置） `serves: FR-1`

**角色**：维护者（写配置的人）。

**场景**：人发现 review/test 段用强模型太贵，于是写路由表：

```yaml
stageRouting:
  dev:        { model: "strong-model" }
  review:     { model: "cheap-model" }
  test:       { model: "cheap-model" }
  "test@expert": { model: "strong-model" }   # 专家档的测试段例外，走强模型
```

**结果**：新开跑的父卡，其 review/test 子卡的脚本里带上便宜模型；
专家难度的 `test` 段因两级命中优先 `test@expert` 仍走强模型。
**没写路由表的窗口**：脚本与改造前逐字节一样（无感知）。

## UC-2 看清钱花在哪、哪段白跑（人查） `serves: FR-2, FR-3`

**角色**：人（看板使用者）。

**场景**：一条需求跑完后，人问「这次哪个阶段最费时间？有没有白跑的段？」

**结果**：调 `reqboard_status` 看到 `stage_telemetry`：
每段给出 `runs / avgDurationMs / outputCount / zeroOutputRuns`。
若某段连续零产出达阈值（默认 2），需求台账上已有一条 `[零产出告警]` 评论，
人据此决定「这段模板该不该留 / 该不该换提示词」——**系统不替人改模板**。

## UC-3 多需求并行：谁先跑、跑几条（系统闸 + 人调） `serves: FR-4`

**角色**：人（排优先级）+ 编排器（执行）。

**场景**：三条需求都 `autoRun`，人把最要紧那条设 `priority: 10`，另两条默认 0。

**结果**：
- 候选遍历按 priority 降序：10 那条先投递；两条 0 分的按创建时间先后。
- 若配置 `maxInFlightRequirements: 2` 且已有 2 条在跑（新鲜推进锁）：
  本轮**不投递**第三条，回执如实说 `stopped='wip_limit'`，点名在跑的是哪两条、上限多少。
- 上限默认 0 = 不限 → 行为与改造前一致。

## UC-4 失败/异常场景 `serves: FR-1, FR-2, FR-4`

| 场景 | 系统行为 | 人看到什么 |
|---|---|---|
| 路由表写了不存在的 stageKind | 装配期抛错，插件不启用 | 点名非法键（响亮失败，不半可用） |
| 历史执行没有产出计数 | 读侧记「未知」，不计入零产出 | 遥测里该段 `zeroOutputRuns` 不含旧数据（看板注明起点） |
| WIP 上限把人需要的那条挡住了 | 不投递、不静默 | 回执给出原因 + 两条解除方式（等结束 / 调大上限） |
| 遥测完全无数据（新需求还没跑过子卡） | 回执省略 `stage_telemetry` 键 | 不显示空表，也不显示 null |

## UC-5 边界：本需求不覆盖的场景 `serves: FR-1, FR-2, FR-3, FR-4`

- **不**自动挑模型（「哪个模型更划算」需要评测基线，另立需求）。
- **不**自动改阶段模板或提示词（零产出只告警，改由人裁决）。
- **不**做跨需求成本预算硬闸（只做 WIP 上限与可见性）。
- **不**回填历史遥测（重建近似值会让数据说谎）。
