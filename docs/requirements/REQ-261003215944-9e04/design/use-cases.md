# 用户场景 · 一个需求可以有多个窗口，一个窗口可以有多件事（REQ-261003215944-9e04）

> **TL;DR**：今天"一个窗口只装得下一件事、一件事只认一个窗口"。本需求把它换成
> **一个需求 = 一位主事人 + 若干帮手，窗口不够就 fork 一个新的**。
> 四类人各拿回一次选择权；**agent 只把文书备好，拍板永远是人**——这是本文所有场景的共同底线。

## 场景总览 `serves: FR-1, FR-2, FR-4, FR-5, FR-6, FR-8, FR-10, FR-11`

```
  一个窗口装了太多事                          一件事需要一个团队
  ─────────────────────                       ─────────────────────
  窗口A ── 需求一（主事人）                    需求一 ── 主事人（窗口A）
  窗口A ── 需求二（主事人）      ← 不再被拒     需求一 ── 帮手（窗口B）
  窗口A ──fork──▶ 窗口C ── 需求三              需求一 ── 旁观者（窗口C）
  （agent 提议，人拍板）                        （各推各的卡，推阶段仍归主事人）
```

## UC-1 窗口忙了，第二件事也能落地 `serves: FR-4, FR-1`

- **触发**：某人已在窗口 A 里推进"需求一"，现在又想在同一个窗口启动"需求二"。
- **agent 做什么**：不再直接拒绝，而是把**选择**交给用户——
  ① 就地在 A 里当"需求二"的主事人；② 由 agent 先 fork 出一个新窗口 C，"需求二"归 C 主事，A 只留一条指针。
- **人看到什么**：一句明确的二选一（各自说明后果：选①A 同时管两件事；选②A 从此不干预"需求二"）。选②时侧栏多一个会话。
- **人做什么决策**：挑一个分支；也可以说"先不开"。
- **异常流**：fork 建不出来（源会话还没跑过一个完整回合）→ agent 明说建不出来、建议用"全新空会话"，
  **不许**含糊地说"已经开好了"；这时人仍可以选择①。
- **完成标志**：`需求二` 出现在看板上，且它的主事人是谁一眼可查；A 的看板仍能看到"需求一"的全部动作。

## UC-2 长活儿不占当前窗口 `serves: FR-1, FR-7, FR-8`

- **触发**：人说"这个要跑很久，别占着我这个窗口"。
- **agent 做什么**：请 DSH 现成的会话能力分支出一个新窗口，把这件事的背景底稿投递过去；
  投递时**署自己的名**（不是冒充人说的一段话），冷掉的会话也能被叫醒。
- **人看到什么**：忠实的三句话——"会话已创建、请在左侧栏打开、本页可以切过去"；
  以及一句"底稿已投递"。**不会**看到"已为你打开新窗口"这种做不到的承诺。
- **人做什么决策**：去侧栏打开新窗口、看一眼底稿是否准确；不准就当场纠正，再决定是否让它继续。
- **异常流**：当前环境没有开窗能力 → agent 直接说明"这个环境开不了新窗口"，并给出替代（仍在本窗口做 / 人手开）。
- **完成标志**：侧栏里能打开那个新会话，底稿就在里面；新窗口在主需求上下文中显示为一个参与席位。

## UC-3 拉一个帮手进来 `serves: FR-2, FR-3`

- **触发**：一条需求同时在跑几张互不相干的卡，一个人（一个窗口）推不动；人让第二个窗口加入。
- **agent 做什么**：把第二个窗口登记为这条需求的"帮手"（可以领卡、汇报、推自己的卡）；
  需求的主事人身份不变，仍然是原来那个窗口。
- **人看到什么**：需求的参与窗口列表里多了一行，写明角色（主事人 / 帮手 / 只读跟随）；
  谁改了什么，留痕里能看出是哪个窗口做的。
- **人做什么决策**：决定帮手能做什么——默认只能推自己认领的卡；要不要把它升为主事人（换绑）由人定。
- **异常流**：帮手想替这条需求"推进阶段"或"解绑主事人"→ 被明确拒绝，并告诉它"这不是你的权限"；
  重复把同一个窗口加两次 → 幂等，不报错、不加两行。
- **完成标志**：帮手成功推完一张自己认领的卡；它尝试推阶段时拿到拒绝；主事人的窗口一切照旧。

## UC-4 只点一次确认就立项 `serves: FR-5, FR-8`

- **触发**：agent 判断一件事值得单独立项，但当前没有人在跟它对话（人只是离开了键盘）。
- **agent 做什么**：把立项要问的四件事**先替人填成草稿**（名称候选、类型、难度、文档位置），
  放到人的面前等人点；它**不能**替人按下确认。
- **人看到什么**：回到窗口时看到一份填好的立项草稿与一个确认框，以及"这是 agent 起草的"的标注。
- **人做什么决策**：点确认（立项成立）／改两个字段再确认／取消（明确不立项）。
- **异常流**：**没有人工回合时，agent 自己发起的立项一律被拒**（见 UC-8）；
  弹框通道不可用时，agent 只给文字草稿，绝不伪造一条已立项记录。
- **完成标志**：人点过确认后，需求出现在看板；未点之前，看板上**没有**这条需求。

## UC-5 新窗口里的计划一键批准 `serves: FR-6, FR-8`

- **触发**：设计写完后，agent 在新窗口把拆分计划与任务表写好并提交，等人批准。
- **agent 做什么**：提交计划、把"打算怎么做/分几张卡/哪张卡偏重"讲清楚；
  **不**自己批准、也**不**绕过批准去把任务卡落库。
- **人看到什么**：一份可读的计划与批准入口；偏重的卡会被点名（带建议拆法），不必翻返回体。
- **人做什么决策**：批准（任务卡才落地）／退回重写（需求停在拆分环节，不会偷偷开工）。
- **异常流**：人没批就催 agent 落库 → 被明确挡回，并提示"计划还没批"；批准动作本身留痕，可追溯是谁批的。
- **完成标志**：批准后任务卡出现在看板上；退回则看板上没有新卡。

## UC-6 确认了这道门，链自己接着跑 `serves: FR-9, FR-10`

- **触发**：需求在某个门禁上等人回应，或自动跑到本轮上限停下；人在推进弹框上确认。
- **agent 做什么**：确认后立刻把"继续跑"该做的复位一次做完（本轮的额度还回去、暂停标记清掉）；
  这件事**只有一处实现**，不再由七个地方各写一遍、各看一套规则。
- **人看到什么**：确认后链接着跑、不用再手动去点一次；看板上的状态与弹框上确认的是同一件事。
- **人做什么决策**：确认推进（"这道门的产物我认了"）。**注意**：这不等于"我同意全程自动跑"——
  要不要自动化是另一个开关，只有人能按。
- **异常流**：弹框还停在屏幕上时，链**不会**自己先跑起来；人主动按过"暂停自动化"的，确认推进不改这个决定。
- **完成标志**：确认后需求继续推进；若之前是人主动暂停的，确认后仍是暂停（要跑得人再按"继续"）。

## UC-7 点文档不再报「文件不存在」 `serves: FR-11`

- **触发**：人在看板上点"需求文档"，或点开工作区里的说明文档（首页说明、知识索引、交接稿）。
- **agent 做什么**：把"文档从哪个目录找"统一到**当前会话的工作目录**这一个源头；
  打开前的检查与真正打开用同一套判断，不再一个按东、一个按西。
- **人看到什么**：右侧栏渲染出文档正文，不再出现「文件不存在，可能已被移动或删除」。
- **人做什么决策**：照常阅读、按文档内容与人讨论。不需要"再刷新一次看板"这种绕路。
- **异常流**：真的找不到文档时，说明是"哪个目录下没找到"，而不是给一个必然不存在的路径让人困惑。
- **完成标志**：工作区里的说明文档与新建需求的需求文档，**第一次点击**就能看到正文。

## UC-8 反例场景：两件"顺手替人做主"的事都不成立 `serves: FR-5, FR-10`

- **用例角色**：① 想省事的 agent；② 已经明确说过"先别自动跑"的人。
- **触发**：① 没有人跟 agent 说话的那个回合，agent 想自己把需求立了；
  ② 人按过"暂停自动化"（解除锁定、改回手动）之后，又在一个推进弹框上点了确认。
- **agent 做什么**：① 尝试立项；② 借"人确认了推进"这个动作，顺手把自动化也打开。
- **人看到什么**：
  ① 立项被拒，理由写明"需要人的直接回合"，且看板上没有多出这条需求；
  ② 推进被认下（该走的路继续走），但"自动化"仍是关着的——弹框上根本没有"替我打开自动化"这个效果。
- **人做什么决策**：① 想立项就自己说一句话再让 agent 走一遍；② 想恢复自动跑，自己去看板按「继续」。
- **异常流**：agent 反复尝试（重弹确认框 / 重复投递）都不会把这两件事办成；
  两次动作的留痕分得清哪次是系统做的、哪次是人按的。
- **完成标志**：**G0（必须有人在场才能立项）与 G3（计划必须人批）两条门一行没松**；
  "要不要自动化"这个开关，从头到尾只在人手里。
