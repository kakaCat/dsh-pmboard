# 需求说明（REQ-261005105032-3b02 让原型进流水线：UI 需求在需求阶段必交原型，且原型可判定）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。
> 追认事故：REQ-261004222448-292a（纯 UI 需求）交付后被人眼判「**与原型差距巨大**」。
> 本窗口已定位根因并修掉两处可复现缺陷（sides 括号写法解析、会话 `reqboard_move` 丢失 G2 文档集门禁），
> 本需求在其之上做**制度与契约层**改造。

## TL;DR <!-- serves: FR-1 -->

- **这是什么**：把「UI 需求的原型」从**附件**升格为**需求阶段的必交产物**，并让原型**可判定、可追溯**——唯一权威版本 + FR 锚点 + 任务卡/RTM/提示词/验收全链带锚点。
- **为什么现在做**：REQ-292a 实测——需求声明了 frontend 端侧却被解析 bug 吞掉 → 设计阶段零前端设计文档 → 原型只登记为 `notes`、84 张卡 0 处引用、执行提示词不带原型 → 交付物与原型差一个数量级（文档 Tab 渲染 317 行 vs 原型 15 行），**靠人眼才发现**。
- **做完得到什么**：**UI 需求不交原型就出不了需求阶段**；原型只有一个权威版本；每张 UI 卡都能指到原型锚点；页面与原型的结构差异由探针判失败，而不是靠人眼。
- **同一根因的另一半（用户补充）**：需求阶段的**讨论内容在需求文档里被弱化**——口头说定的补充/裁定只留在会话里，实施时看不到，验收时人只能再说一遍。本需求一并解决：**讨论裁定必须逐条落账（D-x）并进追溯链**（见 FR-8 / FR-9）。
- **再加一半（用户补充）**：改了节、改了编号，就一定会碰到**校验器**——`D-x` 现在对校验器完全不可见、"贴个原型锚点"会被算成"已覆盖该 FR"、下游门红了没人管。故本需求把**文档校验同源**也列为必做（FR-11：校验器同步清单 + 禁假引用 + 阶段门时序 + 自检脚本）。

## 产品定义（serves: FR-1）

**原型进流水线机制**：本平台的「原型」目前是一份**没有身份的文件**——它不属任何必备产物、不受任何门禁、不进追溯链，
于是"照原型实现"只能靠人反复口头强调。本需求给它三重身份：

1. **产物身份**：`kind=prototype`，UI 需求在**需求阶段**必交，缺则出不了需求阶段。
2. **契约身份**：唯一权威版本（多版并存即拒），需求/设计/任务/RTM 引用的必须是它。
3. **判据身份**：原型自带机器可读锚点（`#FR-N` + 关键几何量），成为任务卡验收与端到端探针的判据来源。

**核心价值**：把「按原型做」从**口头纪律**变成**代码级门禁 + 可失败断言**。
**与现状的区别**：现状靠"需求文档里写一句『设计参照』"（REQ-292a 那句还指错了版本）；本需求之后同一个事实有唯一落点，且有人（门禁）在守。

### 功能点详细说明

- **FR-1: UI 需求在需求阶段必须交付原型产物，否则不得进入设计**
  分类为 feature / refactor 且 `requirement.md` front-matter `sides` 含 `frontend` 的需求，在
  `brainstorming → design` 转移时校验存在**已登记**的 `kind=prototype` 产物；缺失即拒绝，
  消息点名「缺什么、放哪、用什么命令补」（`reqboard_submit(kind=prototype)`）。
  非 UI 需求（`sides` 不含 frontend）不受此约束——避免给纯后端/文档需求加仪式。
  **豁免必须由人裁决**（用户裁定，见 D-13）：`prototype_exempt: <理由>` 只在**理由非空**
  且**随既有 G1 确认门一并被人确认**时生效；**agent 不能自己豁免自己**（不新增弹框，搭 G1 的车）。

- **FR-2: 原型成为一等产物（kind=prototype），落盘/登记/确认与既有产物同构**
  新增 `ArtifactKind='prototype'`；`kindForRelPath` 认 `prototypes/*.html`（旧目录 `prototype/*.html` 兼容识别并提示迁移）；
  进入 brainstorming 时按模板**幂等落盘**原型骨架（`templates/brainstorming/prototype.html`）；
  登记走 `reqboard_submit(kind=prototype)`，与 `requirement` 一样支持人工确认门（确认后才算"人看过原型"）。

- **FR-3: 原型必须有且只有一个权威版本**
  原型目录内必须存在唯一权威版本标记（清单文件或页内标记，二选一，设计阶段定死）；
  同时存在两个及以上未标 `superseded-by` 的版本 → 门禁拒绝并点名两份路径；
  `requirement.md` / `frontend.md` 引用的原型路径**必须等于**权威版本，指向被作废版本即拒绝
  （正对 REQ-292a 的"需求文档指出上一版"）。

- **FR-4: 原型必须可判定——自带 FR 锚点与关键几何量声明**
  原型每个功能点一个 `id="FR-N"` 区块（与需求条款同号）；原型内以机器可读形式声明本页关键几何量
  （如首屏关键栏 `top`、表格行数、字号令牌名）——**声明的是"可观测量的名字与实测值"，不是最终阈值**。
  登记原型产物时抽取锚点与几何量清单写进产物元数据，供下游门禁/探针/卡片直接引用。
  **阈值不在原型里自证**（用户裁定，见 D-10）：原型只提供观测口径，**阈值由设计阶段按真实页面数据定死**，
  再由 UI 卡的 acceptance 与探针引用——避免"自己声明自己过"。

- **FR-5: 追溯链带原型锚点（任务卡 / RTM / 覆盖门禁三处贯通）**
  拆分计划里每张 UI 卡的「设计落点」必填原型锚点（形如 `prototypes/detail.html#FR-4`）；
  RTM 四层追溯（FR → 设计 → 任务 → 测试）把原型作为**FR 与设计之间的可引用节点**；
  缺原型锚点的 UI 卡在拆分覆盖门（`reqboard_decompose` 前）被拒。RTM 具体改动见「RTM 影响面」节。

- **FR-6: 执行侧可见——子代理提示词带原型，UI 卡验收含原型对照判据**
  自动链子卡提示词（`buildSubtaskPrompt`）对 UI 卡带上原型路径 + 本卡锚点；
  拆分计划的 UI 卡 `acceptance` 模板必须含**至少一条可失败的原型对照判据**（结构断言 + 几何量硬判据）；
  端到端探针禁止"只打印不判失败"的诊断行——几何量一律硬判据（REQ-292a 的 Tab 栏 1118px > 713px 就是漏网项）。

- **FR-7: 验收侧制度化——验收单含「与原型对照截图」**
  UI 需求的验收单自动增加一项「与原型对照截图（含差异说明）」；提交验收材料时缺该项即拒。
  目的是把"人一眼看出"从偶发事件变成**每次必查的一项**。

- **FR-8: 讨论裁定必须逐条落账（D-x），禁止只留概括**
  需求阶段的人机讨论中产生的**裁定**必须在 `requirement.md` 的「讨论与裁定记录」节逐条落账，每条含：
  **编号 `D-N`** / **原话来源**（会话消息 id 或时间戳 + 引用原话）/ **裁定结论** / **影响哪条 FR** / **可验证判据**。

  **裁定边界（用户裁定，见 D-11）**：只有**祈使句**（"改成 X""加一条 Y"）、**纠正**（"不对，应该是 Z"）、
  **补充要求**（"还要考虑 W"）算裁定；**疑问句与事实确认不算**。讨论中确实没有裁定时，
  允许显式写「本节无裁定」作为**真空态**（不视为空节）——禁止为了过门禁硬凑条目。

  门禁：需求文档缺该节、或存在裁定留痕（会话里有人的补充/指正）而该节为空 → **拒绝进入设计**；
  同时机械反例：只有概括句、没有原话来源或没有影响 FR 的条目一律视为无效条目（点名哪条无效）。
  目的：把"讨论 → 文档"的**信息损耗**从不可见变成可核验——文档不再能靠一句"已按讨论调整"糊过去。

- **FR-9: 裁定编号进追溯链，并作为验收口径的一等公民**
  `D-x` 与 `FR-x` 同为可引用编号：设计章节、拆分计划的每张卡、任务卡「范围」、RTM 四层追溯
  都必须能引用它；实施子代理的提示词带上**本卡关联的 D-x 原话**（不只是 FR 标题）；
  验收单每一项可追到 `FR-x` / `D-x`。验收时若人发现"文档里没写"，返工顺序固定为
  **先补文档（D-x）再改代码**——避免同一个要求第二次口头重申。

- **FR-10: 契约同源——模板与四条注入面必须同改，并加防断点机械回归**
  产物/门禁改了而**模板与注入提示词没跟着改**，就是断链：agent 要么无法合规（卡死），
  要么看不到新要求（静默跳过）。本需求要求四处**同源**并机械守住：

## 边界（不做什么）（serves: FR-1）

1. **不追溯已归档需求**：存量 9 条受影响需求（8 条 archived + REQ-292a accepting）只享受"解析修好"的红利，不回填原型/frontend.md；已归档的一律不追。

3. **不改既有必填节名与产物语义**：只在 `sides` 特征清单上新增原型维度，不动 `requirement`/`design`/`decomposition` 的既有必填节与门禁语义。
4. **不给非 UI 需求加仪式**：`sides` 不含 frontend 的需求，不要求原型、不要求 frontend.md。
5. **不新增运行时依赖**：探针沿用现有 headless Chrome 调用方式，不引第三方视觉/截图库。
6. **只记裁定，不记闲聊**：讨论入账限于「裁定/结论/补充要求/被否方案」，闲聊与过程性寒暄不入账（避免文档变成会议纪要）。
7. **不追溯存量**：历史需求已完成讨论不再补录 D-x；新规则对新建与进行中的需求生效。
8. **不改上游 skill 原文**：注入片段的改动只落在本仓段（`common/iron-rules.md`、各 `<stage>/<category>.md`、`heavy/overrides.md`）——vendored 原文与 vendor 保持逐字节一致（既有漂移门禁的硬约束）。
9. **不重写提示词体系**：本次只在既有片段路由与四条注入通路上补内容，不重构注入架构、不新增第五条通路。

- **幂等**：原型骨架落盘"不存在才写"，永不覆盖已写内容（沿用模板落盘既有纪律）。
- **可回滚**：新增门禁可通过需求级豁免声明（`prototype_exempt: <理由>`）放行，理由必填——与 `design_exempt` 同款。
- **性能**：门禁只做目录级存在性 + 小文件解析（原型 HTML 只读锚点区块，不整体加载渲染），单次判定 < 100ms。
- **可测**：每条 FR 至少一个可失败用例；探针支持逆验证（人为改坏 → 必红）。
- **抗弱化（FR-8）**：需求文档不允许把讨论裁定概括为"已按讨论调整"这类不可核验表述；每条裁定必须可追到**原话来源**，机械判据是"能指回具体会话消息/时间"。
- **信息损耗可观测（FR-8）**：讨论轮次与裁定条目数不再脱钩——有裁定留痕而条目为零即失败，堵住"讨论了半天、文档只有一句话"。
- **同源（FR-10）**：门禁 / 模板 / 注入提示词（片段 + 回合指令 + 节点输入包 + 子卡提示词）四处引用**同一份事实源**；改任一处而不同步其余三处 = 缺陷，由 R1~R4 机械抓住。禁止"运行时不读盘导致改了片段没生效"这类静默漂移。
- **校验同源（FR-11）**：新增节 / 新增编号必须同步更新校验器清单；**不许假引用**（锚点不得刷覆盖度）；下游门必须写明转绿时点，逾期即红——不允许"红了也没人看"。
- **可自检**：`scripts/req-doc-validate.mts` 一条命令跑完全套文档校验（必填节 / front-matter / 格式门 / 编号链 / 追溯 / RTM 健康 / E2E 覆盖），纳入 R1。

## 风险评估 <!-- serves: FR-1 -->

| 风险 | 影响 | 缓解 |
|---|---|---|
| 门禁过严卡住正常 UI 需求 | 流程卡死，人被迫绕过 | 提供 `prototype_exempt`（理由必填、留痕）；非 UI 需求不适用 |
| 原型骨架变成"交差填空" | 有文件无判据，门禁形同虚设 | FR-4 要求锚点 + 几何量；FR-6 要求 acceptance 含对照判据（门禁机械核验） |
| RTM schema 变更影响存量读取 | StageOverview/看板读旧文件崩 | 新节全部可选 + 缺节视为 pending；`rtm_version` 升位可识别 |
| 几何量阈值写死导致环境相关假红 | 换机器/字号就红 | 阈值只声明**上限**且来自原型自身声明，不硬编码绝对像素；断点显式传窗口宽（REQ-292a 已踩过测量环境坑） |
| 客户端把原型误当"文档"渲染 | 文档 Tab 再次倾倒 | 原型单列分组 + 分组计数恒等式（`documents + discovered == 台账产物数`） |
| 裁定落账变成形式主义（抄一句交差） | 门禁形同虚设 | 每条 D-x 强制五要素（原话来源/裁定/影响 FR/判据/编号），缺一即点名；FR-9 再卡"必须被引用" |
| **只改门禁、模板与注入面没跟（断链）** | agent 看不到新要求（静默跳过）或无法合规（卡死） | FR-10 列全模板 6 份 + 注入 4 条通路，并由 R1~R4 机械守住；D-7 已定为必改面 |
| 片段产物未重生成（构建期内联） | 注入的仍是旧纪律，且**没有任何报错** | R4：把 `check-prompt-fragments` 接进 pnpm 与提交前清单；R3 顺手验证路径可达 |
| **假引用刷覆盖度**（贴原型锚点即算 serve） | 覆盖度虚高，链上看着全绿实际没做 | FR-11：锚点引用单列、不与编号引用混算；验收标准 20 逆验证 |
| **D-x 校验器不可见** | FR-9 的"必须被引用"落不了地，写了也没人核 | FR-11：扩编号白名单 + 定 D-x 定义链；验收标准 19 |
| 下游门逾期红无人处置 | 门禁红被淹没（REQ-292a 的门禁丢 9 天没人发现） | FR-11：写清各阶段必须转绿的门；自检脚本前置 |

## 迭代计划 <!-- serves: FR-1 -->

1. **第一批（P0 骨架）**：FR-2 产物身份 + FR-1 需求阶段门禁（含 D-13 豁免需人确认）+ FR-3 权威版本（最小闭环：不交原型出不了需求阶段）+ **FR-8 裁定落账门**（同一阶段同一道门，一次把"讨论内容"钉住）+ **FR-10 同源与 R1~R4** + **FR-11 校验器同步（含 `req-doc-validate.mts`）**——不同步改模板/注入面/校验器，第一批量产的产物根本没机会被合规产出与核验。**不拆分范围**（D-15）。
2. **第二批（P0 判据）**：FR-4 锚点与几何量 + FR-5 RTM/任务卡贯通 + FR-6 执行侧可见 + **FR-9 裁定进追溯链**。
3. **第三批（P1 收口）**：FR-7 验收单对照项（原型 + 裁定双追） + 客户端原型单列 + 存量兼容核对。

## 验收标准（整体，可跑） <!-- serves: FR-1 -->

> 分三组（用户裁定 D-14）：**A 原型门禁** / **B 裁定保真** / **C 同源与校验**。每条都必须是可执行断言。

### A 原型门禁（FR-1~FR-7）

1. **条件门禁**：构造 `sides: [frontend]` 且未登记 prototype 的标本 → `brainstorming → design` 被拒且消息含 `reqboard_submit(kind=prototype)`；交齐后放行；`sides: [backend]` 标本不受影响。
2. **豁免（D-13）**：`prototype_exempt` 理由为空 → 豁免无效仍拒；理由非空但**未经人确认** → 仍拒（agent 不能自豁免）；人确认后放行。
3. **产物识别**：`kindForRelPath('prototypes/x.html') === 'prototype'`；旧 `prototype/x.html` 被识别并提示迁移（用例断言）。
4. **权威版本**：两版并存 → 拒并点名两份；需求文档引用被作废版本 → 拒（正对 REQ-292a 事故形态）。
5. **锚点与几何量（D-10）**：原型缺 `id="FR-N"` 区块或几何量声明 → 拒并点名缺哪条；断言**阈值不出现在原型自证路径上**（阈值只能来自设计阶段产物）。
6. **追溯贯通**：UI 卡缺原型锚点 → 拆分覆盖门拒绝；RTM `rtm-brainstorming.yml` 含 `prototypes` 节且 `coverage` 多一维（用本需求自身标本断言）。
7. **执行可见**：`buildSubtaskPrompt` 对 UI 卡的产出含原型路径与锚点（字符串断言）；对非 UI 卡不追加。
8. **判据硬**：探针人为改坏一处几何量 → 退出码非 0（逆验证）；无"只打印不判失败"的诊断行（源码级断言）。
9. **兼容**：存量 66 条需求 RTM 旧文件读取不报错、不被判不健康；已归档需求不被追溯拒绝。
10. `pnpm typecheck` = 0；新增/相关用例全绿；`pnpm kb:build && pnpm kb:check` 全绿。

### B 裁定保真（FR-8 / FR-9）

11. **裁定落账（FR-8）**：构造"会话中有人补充/指正、需求文档无「讨论与裁定记录」节"的标本 → `brainstorming → design` 被拒并点名缺节；构造"有节但条目只有概括句/缺原话来源/缺影响 FR"的标本 → 逐条点名无效条目。
12. **裁定边界（D-11）**：构造只有疑问句的标本 → **不要求**裁定条目（显式「本节无裁定」应放行）；构造"祈使句被漏记"的标本 → 拒绝。
13. **裁定被引用（FR-9）**：构造"存在未被任何 FR 或任务卡引用的 D-x"标本 → 覆盖度点名该 D-x；子卡提示词对带 D-x 的卡产出含该裁定原话（字符串断言）。
14. **返工顺序（FR-9）**：构造"人指出文档没写"的返工标本 → 返工工单要求先补 D-x 条目再改代码（断言工单文案与顺序），不允许直接改代码结单。

### C 同源与校验（FR-10 / FR-11）

15. **同源-R1（FR-10）**：对 `templates/` 下每份需求/设计/拆分/任务卡/验收模板渲染占位符后跑门禁 → 0 缺口；人为把某模板的必填节标题改坏 → 该回归必红（逆验证）。
16. **同源-R2（FR-10）**：门禁必填节集合与模板声明节名集合双向比对；构造"模板多一节/门禁少一节"两个标本 → 均失败（**该节仅 feature**，D-12 口径要体现在比对里）。
17. **同源-R3（FR-10）**：解析片段与回合指令中的路径指针，全部必须可达；构造一个指向不存在文件的指针 → 失败并点名。
18. **同源-R4（FR-10）**：`node scripts/check-prompt-fragments.mjs` 已接进 `pnpm` scripts 并出现在提交前清单；构造"改了片段不重生成"标本 → 该命令 exit 非 0。
19. **校验-编号白名单（FR-11 / D-9）**：扩白名单后 `collectIds('D-1') === ['D-1']` 且 `D-x` 有定义链规则；未定义却被引用 → 判 dangling。
20. **校验-禁假引用（FR-11 / D-9）**：`collectIds('prototypes/x.html#FR-4')` 不得让 FR-4 在覆盖度里被算作"已 serve"（锚点引用单列）；构造"只贴锚点不写实现"的标本 → 覆盖度**不上升**。
21. **校验-阶段门时序（FR-11）**：编号链 orphan / E2E 覆盖 / 三级追溯三门在各自阶段（设计交完 / 拆分落库 / 实施收尾）必须转绿；构造"逾期仍红"的标本 → 该阶段门禁拒绝并点名。
22. **自检前置（FR-11）**：`scripts/req-doc-validate.mts` 存在且已并入 R1；对它自身跑逆验证（人为改坏必填节 → 非 0 退出）。

## 关键决策与取舍 <!-- serves: FR-1 -->

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 原型放哪个阶段 | 留在设计阶段做（现状） | **需求阶段必交** | 用户裁定；且原型是"要做什么"的载体，晚于需求阶段就无法约束需求与拆分 |
| 原型的判据强度 | 像素/视觉相似度 | **结构 + 几何量 + 令牌** | 渲染差异（字体/窗口宽）会制造长期假红；REQ-292a 实测"漏传窗口宽导致量错"已有前车之鉴 |
| 是否新增独立 kind | 复用 `design`（与 frontend.md 合并） | **独立 `kind=prototype`** | 两者生命周期不同（原型在需求阶段、设计文档在设计阶段）；合并会让"缺原型"和"缺设计"同一条消息，人分不清补什么 |
| 存量处理 | 全量追溯回填 | **只修解析、不追溯** | 8 条已归档，回填是无收益的翻旧账；REQ-292a 另行收尾 |
| RTM 是否插新层 | 只在任务卡上带锚点 | **RTM 也插原型节点** | 用户明确问 RTM；且 RTM 是覆盖度与验收的材料源，链上断一层就查不到"哪个 FR 没原型承接" |
| 讨论内容怎么保真 | 把 FR 描述写得更详细 | **编号化裁定（D-x）+ 强制五要素 + 下游必须引用** | 描述再详细也是概括，无法证伪"少了哪句"；编号 + 引用才可机械核验，也才能定位到原话 |
| 裁定门放在哪一步 | 只在验收时检查 | **brainstorming → design 就卡** | 验收才发现 = 已经白干一轮（用户原话：验收阶段还需要重新说一遍） |
| 是否要机器抽取会话裁定 | 纯手工自觉落账 | 机器只判"存在裁定留痕/条目无效"，抽取仍由 agent 做 | 抽取口径要判断力（哪句是裁定），交给模型；门禁只做可机械核验的那半 |
| 改造范围 | 只改门禁（最小改动） | **门禁 + 模板 + 四条注入面同改** | 改门禁不改产出面 = 断链：agent 看不到要求就静默跳过，或看到要求但模板不产该节而卡死（用户裁定 D-7） |
| 同源怎么守 | 靠评审与自觉 | **R1~R4 机械回归** | D-5 已经证明"靠自觉"会分叉：模板与门禁口径不一致，且**双方都没报错** |
| 上游 skill 片段怎么改 | 直接改 vendored 原文 | **只改本仓段**（`common/iron-rules.md` / `<stage>/<category>.md` / `heavy/overrides.md`） | `check-prompt-fragments` 断言上游片段与其 vendor 逐字节一致；改原文会被漂移门禁打回，且下次同步即丢 |
| 几何量阈值从哪来（D-10） | 原型里写阈值、自己声明自己过 | **原型只声明观测量名与实测值**，阈值由设计阶段按真实数据定死 | 自证不可信；阈值属设计决策，且需要看到真实页面数据才能定 |
| 锚点算不算 FR 引用（D-9-2） | 锚点即引用（省事） | **锚点引用单列**，不与编号引用混算 | 实测 `collectIds('prototypes/x.html#FR-4')` 返回 `['FR-4']`——混算会让"贴锚点"刷出漂亮的覆盖度 |
| 是否扩编号白名单（D-9-1） | 让 D-x 保持不可见、FR-9 降级为文本检查 | **扩白名单 + 定 D-x 定义链** | 不可见 = 无法核验"必须被引用"；扩了才谈得上覆盖度与 dangling |
| 模板改几份（D-12） | 六份需求模板同改（通用区一致约束） | **仅 feature**，其余按需 | 省 5 份不相关模板的改动；代价是类型间不完全对齐（如实记在边界里） |
| 范围是否拆两批（D-15） | 拆成两个需求（先最小闭环） | **一次做完**，第一批落最小闭环 | 用户明确"我们立项来解决"；拆开会让"同源/校验"与产物门不同期生效，反而制造断点 |

## 技术方案与亮点 <!-- serves: FR-1 -->

- **技术栈与关键依赖**：TypeScript + vitest；探针沿用仓库现有 headless Chrome 方式（无新增依赖）。
- **模块划分**：产物规约（domain）→ 条件必交判定（application/internal/category-doc-sets）→ 门禁组装（artifact-gates/design-gates 同族新建 prototype-gates）→ RTM 生成（vendor/reqboard/rtm）→ 执行提示词（use-cases/ExecuteTask）→ 客户端展示（client/views/panels）。
- **设计模式**：条件必交策略（复用 `sides` 驱动的策略解析）、门禁单点（四条转移路径统一调用，避免 REQ-292a 那种"某条路径漏门"）。
- **与常规做法的差异**：常规"设计稿驱动开发"靠评审会；本方案把原型**变成产物 + 判据**，让门禁与探针代替人做第一轮比对。
- **可核验指向**：本需求的每条 FR 都必须落到「可失败用例」——见验收标准 1~8。
