# 需求说明（REQ-261006164732-6503 确认门重复弹出与审批台账被覆写：门的生命周期收敛为单一事实源）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。

## TL;DR

- **是什么**：同一道人工确认门会被弹**两次**——`reqboard_submit` 自动弹一次、阶段指南又要求 agent 显式再弹一次；
  第二次的作答还会把**已落章的审批时间与证据原文覆写**掉。
- **为什么**：门的生命周期**没有单一事实源**——防重弹判据挂在**结果态**（已落章）而不是**过程态**（已有门在等）；
  指南又把"要不要弹框"交给 agent 判断，机制与文案**双写**，必然漂移。
- **得到什么**：同一道门**至多一个在等的框**（注册层强制的结构性不变量）；指南只教"读门状态 + 取回执"；
  落章**条件写且首写不可变**；被取代的门迟到作答只留痕、不改台账。

## 业务流程图

```
修前：同一道门，两个触发源，判据只看"已落章"
  submit(kind=plan) ──自动弹──▶ 门A(pc-89b19a, 等 2 秒) ┐
                                                       ├─▶ 两个框同时在屏幕上
  指南："提交后调 ask_confirm" ──▶ agent 再弹──▶ 门B ───┘
                                    │
                                    └─ 判据问的是"plan.approvedAt 有值吗"（结果态）→ 空 → 放行新门

  人答门B ──▶ 落章 + 推进 implementing（正确的那次）
  人答门A ──▶ 迟到作答仍走完整落章路径 → approvedAt 被覆写、证据原文被换 ← 台账失真

修后：门只有一处建、一处落章，过程态就是判据
  任意触发通道 ──▶ requestGate(需求, 门)
                     ├─ 已有 open 门 ──▶ 复用：返回原 ref，不再弹第二个
                     ├─ 已落章        ──▶ 早退：不弹
                     └─ 都没有        ──▶ 建门(open) → 交付给一个通道

  人作答 ──▶ settleGate(ref, 答案)
              └─ 条件写：门仍 open ∧ 需求仍在该阶段；approvedAt / 证据 首写不可变
```

## 产品定义

**门（人工确认）本身是好东西**：推进前必须有人点头，这条不动。本需求不改任何一道门的**内容**判据。

错的是门的**生命周期管理**：今天"这道门现在有人在等吗"没有一个权威答案，于是四个触发通道各自判断、
防重弹只能退化成问台账"落章了吗"。**门的触发不该由 LLM 决定，也不该由每个入口自己决定。**

**核心价值**：把门从"散落在各入口的 if"变成一个**有状态的对象**——只在一处建、只在一处落章、
状态可读。做完之后，防重弹不是"多加一个判据"，而是**结构性事实**：新入口天然受约束。

**三要素检查清单**：

- [x] 是什么：确认门生命周期的单一事实源（建门唯一入口 + 同门唯一在途 + 落章条件写 + 状态可读）。
- [x] 核心价值：从"每个入口自觉防重弹"到"同门只可能有一个框"；从"台账可被后到作答覆写"到"首写即事实"。
- [x] 与现状的区别：判据从**结果态**（已落章）下移到**过程态**（门在等）；指南从"教 agent 弹框"改为"教 agent 读状态 + 取回执"。

## 用户与角色

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 人（看板 / 会话） | 被请去批准需求、设计、拆分计划、验收 | 同一件事被问两次，两次题干还不一样；第二次点下去把第一次的批准记录改写了，事后看不出"谁在什么时候批的什么" |
| 窗口 agent | 提交产物后等批准 | 指南让它"去弹框"，但机制已经弹过了；它无从知道"这道门有人在等吗"，只能照做，于是亲手制造第二个框 |
| 维护者 | 加减门 / 加减交付物种类 / 加新确认通道 | 新增一个触发通道就多一个"忘记防重弹"的面；判据散在各入口，回归面靠人记 |

## 功能点（需求条款）

| 编号 | 名称 | 一句话 |
|---|---|---|
| FR-1 | 建门唯一入口 + 同门唯一在途 | 任何通道请求同一道门时，至多一个未作答的门；命中即复用，不新开框、不新登记票 |
| FR-2 | 门状态可读（三面同源） | `reqboard_status` / 回执 / 看板「待确认」投影同一份门状态，能回答"现在谁在等、等的是哪道门" |
| FR-3 | 指南去机制化 | 阶段指南与回执不再指令 agent 去弹框；改为"读门状态 + 取回执（`reqboard_confirm_receipt`）" |
| FR-4 | 落章条件写 + 首写不可变 | 只有"门仍 open 且需求仍在该阶段"的作答才落章；`approvedAt` / `confirmedAt` / 证据原文一经写入不可覆写 |
| FR-5 | 失效门的迟到作答中性化 | 被取代 / 已推进 / 已过期的门，作答只留痕 + 中性回执（写明已失效与当前状态），不落章、不推进 |
| FR-6 | 不变量探针与回归锁 | 一条命令可断言上面五条，并锁"真门首次照旧弹、照旧落章推进"零回归（覆盖 G1~G4） |

**FR-1: 建门唯一入口，且同一道门至多一个在等的框**

所有触发通道（submit 自动弹、agent 请求、看板确认、evidence 文字路径、回执续跑）一律经**同一个建门入口**；
该入口按 `(requirementId, target, kind)` 做**唯一性判定**：

- 已有 **open** 门 ⇒ **复用**：不弹新框、不登记新票，返回**原 ref**，回执写明「该门已有一个在等的框」；
- 已落章 ⇒ 早退（沿用既有「已确认，未重复弹框」语义）；
- 两者皆无 ⇒ 建门（open）并交付给**一个**通道。

判据：同一需求连调两次 `reqboard_ask_confirm(target=plan)` ⇒ 第二次**不**新增票（票表计数不变）、
返回的 ref 与第一次相同；弹框端口被调用**恰好 1 次**。

**FR-2: 门状态三面同源可读**

`reqboard_status.pending_confirms[]`、`reqboard_confirm_receipt` 回执、看板「待确认」投影**读同一份门状态**，
且至少能回答：这道门属于哪条需求、目标（`target`/`kind`）、ref、何时建立、**谁能答**（会话弹框 / 看板 / 两者）。

判据：建门后 `reqboard_status` 能列出该门（含 ref 与创建时刻）；复用路径下该清单仍**恰好一条**；
人作答后清单清空且回执 `confirmed=true`。

**FR-3: 阶段指南与回执不再指令 agent 去弹框**

两处文案副本（含片段源与生成物）改为**条件式**：

- `reqboard_submit` 回执在 `auto_confirm.triggered=true` 时**不得**再出现「下一步：调 `reqboard_ask_confirm`…」，
  改为「已有一道门在等：调 `reqboard_confirm_receipt`/`reqboard_status` 读确认态，**不要再发起确认**」；
- 阶段指南（拆分阶段两处副本 + 需求阶段交棒处）改为「**若回执已说明有门在等，就不要重复发起**；否则发起一次」；
- **恢复指引**（`pending_confirms[].recovery`）不得再写「重新发起 `reqboard_ask_confirm` 覆盖旧记录」——
  改为「已有一道门在等：① 取回执 ② 到看板作答」，因为"覆盖"的真实行为是再开一个框。

判据：文案断言——`triggered=true` 分支的 note 不含「下一步：调 `reqboard_ask_confirm`」、
`recovery` 不含「重新发起…覆盖」；片段改动后 `node scripts/check-prompt-fragments.mjs`（对应 C-16/C-17）退出码 0。

**FR-4: 落章条件写，且首写不可变**

落章（`approvedAt` / `confirmedAt` / `approvedEvidence` / `confirmedEvidence`）必须满足**两个条件**：
① 门仍处于 open；② 需求仍停留在该门对应的阶段。
任一不满足 ⇒ 不落章。且台账字段**首写即事实**：任何后到路径（迟到作答、回执续跑、看板重试）都不得覆写。

判据：对已批准的计划再走一次落章路径 ⇒ `plan.approvedAt` 与 `approvedEvidence` **逐字节不变**；
构造「需求已离开该阶段 + 门被取代」后作答 ⇒ 台账时间戳与证据不变化，仅多一条留痕。

**FR-5: 失效门的迟到作答只留痕**

被取代 / 已推进 / 已过期的门，其对话框作答走**中性通道**：返回 `confirmed=false` + 明确说明
（「该确认已被取代 / 需求已推进到 X，本次作答不改变状态」），并留一条评论；**不得**调用落章与推进实现。

判据：构造「票已被取代 + 需求已推进」的场景 ⇒ 作答后回执 `confirmed=false`、`advanced=false`、
台账无新时间戳、评论 +1。

**FR-6: 不变量探针与回归锁**

- 探针：一条命令输出「当前几道门在等、各自 ref / 目标 / 谁能答」，并断言「同门唯一在途」；
- 回归锁：锁死 FR-1~FR-5 的判据，并锁**真门正常路径零回归**（首次请求照旧弹框、肯定答复照旧落章并推进、
  否定答复照旧只留痕、看板确认通道照旧可用）；
- 覆盖 **G1 需求 / G2 设计 / G3 拆分 / G4 验收** 四道门各至少一例。

判据：见「验收标准（整体）」。

## 边界（不做什么）

- **不放宽任何门的内容判据**：裁定门 / 设计完整性门 / 拆分覆盖门 / 验收单的判据逐字不变；本需求只管门的**生命周期**。
- **不改门的种类与值域**：不新增门、不改 `ARTIFACT_CONFIRM_GATES` 的值域、不给原型补门（原型不是门，见 D-1）。
- **不做新界面**：门状态沿用既有 `pending_confirms` 投影与看板「待确认」入口，不新增控件、不新增页面。
  若设计阶段确认必须动客户端渲染 ⇒ 按 UI 需求重开原型门（`sides` 升级 + 交 `prototypes/<name>.html`），不在本需求偷偷夹带。
- **不改 TTL 与宽限口径**：30 分钟 TTL、2 秒自动弹宽限、缺省宽限三档语义原样保留。
- **不给 agent 新增"作废门"的入口**：agent 不得取消任何一道真门；复用不等于作废。
- 不做 A（取消自动弹，只留 agent 显式弹）：自动弹是人类"被问到"的主通道，取消它等于退回"agent 记得才问"。
- 不做 B（取消 agent 侧 `reqboard_ask_confirm`）：看板、evidence、回执续跑都依赖这一入口；要改的是**建门唯一性**，不是砍入口。

## 非功能需求

- **兼容（零迁移）**：门状态为运行时结构，不新增持久字段；存量台账字段不改写、不回填；
  "同门唯一在途"对**新建立**的门生效，存量未作答票按新判据即时可用。
- **性能**：唯一性判定为内存判定（复用已有的票表与已读的 `RequirementRecord`），不新增 I/O。
- **可观测**：复用 / 早退 / 建门 / 建门被拒四条路径都要在回执与 `reqboard_status` 里能看出**为什么**。
- **安全**：不改人工门的推进白名单；任何新路径不得绕过"产物已确认"的代码级拦截。

## 验收标准（整体）

1. 同一需求连调两次 `reqboard_ask_confirm(target=plan)`：弹框端口**恰好 1 次**、票表计数不变、第二次返回原 ref（FR-1）。
2. 建门后 `reqboard_status` 列出该门（ref / target / createdAt / 谁能答）；作答后清空（FR-2）。
3. `reqboard_submit(kind=plan)` 的 `triggered=true` 回执 note **不含**「下一步：调 `reqboard_ask_confirm`」（FR-3）。
4. 对已批准计划再走一次落章 ⇒ `approvedAt` 与 `approvedEvidence` 逐字节不变；失效门作答 ⇒ 台账无新时间戳（FR-4 / FR-5）。
5. 四道门（G1/G2/G3/G4）各至少一例：首次请求照旧弹、肯定答复照旧落章并推进、否定答复照旧只留痕（FR-6）。
6. `npx vitest run tests/ask-confirm-pending.test.ts tests/pending-guard.test.ts tests/pending-guard-integration.test.ts tests/confirm-advance-deadlock.test.ts` → 退出码 0。
7. `npx tsc --noEmit -p tsconfig.json` → 退出码 0（C-15）。
8. `pnpm baseline:check` → 退出码 0（失败用例集合差为空，C-14）；若改了提示词片段：`node scripts/check-prompt-fragments.mjs` 退出码 0（C-17）。

## 关键决策与取舍

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 判据放哪一层 | 在各入口各加一次"同门去重" | 下沉到**唯一建门入口**（注册层不变量） | 三次同类事故都栽在"判据加在消费端、新入口绕过去"；结构性约束才挡得住下一个入口（D-3） |
| 指南怎么写 | 继续写"提交后调 ask_confirm 弹框"（现状） | 只写"读门状态 + 取回执"，不再指令弹框 | 机制已自动弹；指南再写一遍就是双写，今天 4 道门全部出现补弹即证据（D-1） |
| 重复调用返回什么 | 结构化拒绝（`REQBOARD_CONFIRM_IN_FLIGHT`） | 复用原票 + 返回原 ref | 拒绝会让 agent 打回重试、增加噪音；复用既保唯一性又给人一个框（D-2） |
| 迟到作答怎么算 | 允许补章（"有效但不覆写"）/ 完全不管 | **依 D-3 落定**：失效——只留痕 + 中性回执，不落章、不覆写 | 根治形态要求"台账首写即事实"（事实依据：本次迟到作答把 `approvedAt` 覆写、证据原文被换）；若人另裁为"允许补章但不覆写"，只改 FR-4/FR-5 两处即可 |

## 技术方案与亮点

- **建门唯一入口**：`requestGate(requirementId, target, kind)` 收敛四个触发通道；唯一性判定与复用语义集中在此，
  调用方只拿到"ref + 是新建还是复用"。落地形态在 `design/` 阶段定稿（候选：强化 `PendingConfirmRegistry.register` 为幂等注册）。
- **过程态即判据**：防重弹不再问"已落章吗"，而是问"这道门 open 吗"——判据从结果态下移到过程态，
  这正是三次事故的共同缺口。
- **指南去机制化**：把"要不要弹框"从 LLM 的判断里移除；LLM 只负责"读状态、取回执、按意见处理"。
  这样提示词与机制不再有第二份事实源，双写漂移从根上消失。
- **与常规做法的差异**：不加"agent 侧作废门"这类方便后门（会削弱真门），而是让**同一道门不可能存在第二个框**。

## 依赖与约束

- 依赖（强）：`AskConfirm` / `confirm-settle` / `PendingConfirmRegistry` 的既有分工（建门、落章、清票三处）。
- 依赖（强）：`SubmitArtifact`（G1/G3 自动弹）与 `SubmitVerification`（G4 在 submit 内 `await` 弹）的现实差异——
  统一两条路径属于本需求的**可选**部分，若设计阶段判定风险过高则只在文档登记为已知不一致。
- 依赖（强）：阶段指南片段与生成物（`fragments/*` → `generated/fragments.ts`）与 `stage-prompts` 基线。
- 约束：不改 `PENDING_CONFIRM_BLOCKED_TOOLS` 名单（四条写路径）与 `targetConfirmedInLedger` 落章判定。
- 约束：不改门值域 `ARTIFACT_CONFIRM_GATES`（requirement / design / decomposition / verification）。
