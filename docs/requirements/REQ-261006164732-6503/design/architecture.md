# 架构设计 · REQ-261006164732-6503 <!-- serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6 -->

> 关注点：把「人工确认门」的生命周期收敛成**单一事实源**。
> 不动任何一道门的**内容判据**、不新增门、不改门值域；卡片与批次划分属拆分阶段（W7 边界）。

## A-1 现状：四个通道各自决定"要不要弹" <!-- serves: FR-1, FR-4 -->

```
建门通道（各自判断）                          作答通道（各自判断）
  submit(G1/G3) ──triggerAutoConfirm──▶ 弹框A    会话弹框作答 ─┐
  SubmitVerification ──await askConfirm─▶ 弹框   看板 ConfirmArtifact ─┤─▶ 落章
  agent ──reqboard_ask_confirm──────────▶ 弹框B  evidence 文字路径 ────┤   applyConfirmDecision
                                                 回执续跑（suspend）────┘
```

- 防重弹的唯一判据在**结果态**：`plan.approvedAt !== undefined` / 产物 `confirmedAt !== undefined`
  （`AskConfirm.ts:97`）——它回答的是"已经批过了吗"，不是"这道门现在有人在等吗"。
- 实证后果：同门两个框并存（G3），且**迟到作答仍走完整落章路径**，把 `approvedAt` 与审批证据原文覆写。

结论：**"这道门有人在等吗"没有权威答案**，判据只能退化成问台账。

## A-2 目标形态：建门唯一入口 + 唯一性不变量 <!-- serves: FR-1, FR-2 -->

```
任意建门通道 ──▶ requestGate(deps, {requirementId, target, kind, question, …}, exec)
                   ├─ 命中「未作答且未过期」的门（同需求 + 同 target + 同 kind）──▶ 复用：返回原 ticket，不弹框
                   ├─ 命中「已落章」──────────────────────────────────────▶ 早退：不弹框，返回既有确认态
                   └─ 都没有 ─────────────────────────────────────────────▶ 新建：登记门 + 交付给该通道弹框
```

| 不变量 | 口径 | 唯一消费点 |
|---|---|---|
| **I1 同门唯一在途** | 同一 `(requirementId, target, kind)` 至多一条「未作答且未过期」的门 | `requestGate` |
| **I2 建门不由 LLM 决定** | agent 只"请求门"；弹 / 复用 / 早退由 `requestGate` 决定；指南不描述机制 | `requestGate` + 文案契约（I-7） |
| **I3 落章条件写** | 只有「门仍 open ∧ 需求仍在该门的来源阶段」的作答才落章；台账字段**首写不变** | `confirm-settle` |

**为什么这样才算根治**：判据从各入口**下沉到唯一的建门/落章点**。新加一个触发通道（看板 / evidence / 新 kind）
天然落在同一条判定里，不需要"记得也加一次去重"——这正是本仓同类事故连出三次的缺口。

## A-3 判定顺序：复用 → 早退 → 新建（不可换序） <!-- serves: FR-1, FR-3 -->

1. **先查在途**：只有先问"有门在等吗"，才能保证人在宽限内没答时不会被问第二次。
   若反过来先看已落章，会出现"门还在等 + 另一次提交已把它落章"时**再弹一个框**。
2. **复用不新建**：复用**不写台账、不产生第二条记录、不弹框**，因此不会与守卫 / 回执产生歧义（一个门一条记录）。
3. **新建是唯一会弹框的分支**：把"弹框"这个副作用收敛到一条路径上，可测（弹框端口调用次数）。

前置失败才抛错（无绑定需求 / 需求不在册 / 入参非法）；判定阶段**不抛**——它是纯读。

## A-4 落章：条件写 + 首写不变 <!-- serves: FR-4, FR-5 -->

两个前提（任一不满足即不落章，返回中性回执 + 留痕）：

| 前提 | 判定 | 不满足时 |
|---|---|---|
| 门仍 open | 该 ref 的运行记录 `outcome === undefined` | 走 `recordStaleAnswer`（只留痕） |
| 需求仍在该门的来源阶段 | `req.status === sourceStageOf(target, kind)`（来源阶段由 `ARTIFACT_CONFIRM_GATES` 反查，不另写映射表） | 同上 |

兜底幂等（防任何未预见路径覆写）：`approvedAt` / `confirmedAt` / `approvedEvidence` / `confirmedEvidence`
**只在为空时写入**。两条防线的分工：前提检查回答"这次作答还算不算数"，首写不变回答"就算算数也不许改写历史"。

## A-5 过程态可见 <!-- serves: FR-2, FR-6 -->

- 门的唯一事实源是运行记录表（`PendingConfirmRegistry`）；三面读同一份：
  `reqboard_status.pending_confirms[]` / `reqboard_confirm_receipt` / 看板「待确认」。
- 四条路径都要能读出"为什么"：**新建**（正常等待）、**复用**（已有一道门在等 + 原 ticket）、
  **早退**（已确认，沿用既有措辞）、**迟到**（已被取代 / 需求已推进）。
- 探针（FR-6）：一条命令列出"当前几道门在等、各自 ref / target / 谁能答"，并断言同门唯一。

## A-6 不做 <!-- serves: FR-1, FR-6 -->

- 不放宽也不收紧任何门的内容判据（裁定门 / 设计完整性门 / 拆分覆盖门 / 验收单）——本需求只管生命周期。
- 不改门值域 `ARTIFACT_CONFIRM_GATES`、不改 `PENDING_CONFIRM_BLOCKED_TOOLS`（四条写路径）、不改 TTL 与宽限数值。
- **不做新界面**：不新增控件 / 页面；门状态沿用既有投影。若必须变更客户端渲染 ⇒ 按 UI 需求重开原型门，不在本需求夹带。
- 不给 agent 新增"作废门"的入口（复用 ≠ 作废）；不引入配置开关（判据幂等，回滚即还原代码）。
- 不统一 G4 的 `await` 阻塞形态（与本需求判据正交，且会动验收提交流程时序，见 B-7）。
