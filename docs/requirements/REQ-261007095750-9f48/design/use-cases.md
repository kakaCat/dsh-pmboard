# 用例设计（REQ-261007095750-9f48）<!-- serves: FR-1, FR-2, FR-3, FR-4 -->

> 本文写"**谁在什么场景下用这条判据、期望看到什么**"。判据的实现口径在 `design/interfaces.md`，
> 用例与读数口径在 `design/test-cases.md`；本文不重复它们，只回答"对使用者的行为"。

## 1. 角色与场景 <!-- serves: FR-1 -->

| 角色 | 场景 | 改前（判据瞎着） | 改后（判据看得见 `src`） |
|---|---|---|---|
| 拆分者 | 给两张都改 `src/application/internal/*.ts` 的卡定 `depends_on` | 判据抽不到 `src` 路径 ⇒ 冲突门静默通过；零交集建议也不吭声 | 真共享文件 → 提交被拒并点名叫你加依赖或拆卡；伪依赖边 → 提示给语义理由 |
| 实施窗口 | 按计划并行开工 | 两卡互相覆盖，运行期才发现（mtime 兜底） | 拆分阶段就挡住，不必等到覆盖 |
| 验收人 | 核验"判据是不是真的在判" | 只能看单测绿（假绿） | 看**真实数据**：含 `src/` 行的可抽取比例 + 零交集命中数（改前基线对照） |

## 2. 主成功路径（拆分者视角） <!-- serves: FR-1, FR-2 -->

1. 拆分者写计划：卡 A 改 `src/application/internal/conflict-check.ts`，卡 B 改同一个文件，
   两张卡 `depends_on` 互不包含（没有任何理由）。
2. 提交计划 → 路径抽取给出两端都含 `src/application/internal/conflict-check.ts` →
   冲突门判定"互无依赖 + 共享同一文件" → **拒绝**，错误里点名该文件与两张卡（`REQBOARD_FILE_CONFLICT`）。
3. 拆分者二选一：给 B 加 `depends_on: [A]`（天然串行），或把两张卡改成改不同文件。
4. 重新提交 → 冲突消失（同一依赖链上的卡不算冲突）→ 计划进入下一步。

**另一条主路径（软提示不拦人）**：两张卡改不同 `src` 文件、互无依赖、也没写理由 →
出现 `dependency_warnings`（建议给语义理由：比如"B 只读 A 的导出类型，可并行"）——
**不阻断提交**，但让人有机会把"伪依赖/真并行"这件事想清楚。

## 3. 失败与并发路径 <!-- serves: FR-2, FR-3 -->

| 情形 | 发生什么 | 看到什么 |
|---|---|---|
| 扩根后冲突门在真实计划上出现新命中 | 判据第一次"看见"了 `src` 共享 | 逐条判真伪：真冲突 → 门之前是瞎的（正是本需求要修的）；误报 → 写进边界说明理由，**不放宽口径** |
| 误报真的存在（如只读引用被当成写） | 抽取器无法区分读写 | 如实登记为**已知边界**（`docs/architecture/doc-quality-gates.md` 的「已知边界」表），不偷偷改回去 |
| `implementation` 为空 / 没写文件路径 | 没依据 | 两处判据都**不判**（不误报、不放宽）；人工 review 补位 |
| 同一计划重复提交（已被拒） | 拒绝幂等 | 仍拒，台账零改动；处置只有改计划或拆卡 |
| 同工作树并发窗口正在改 `conflict-check.ts` | 可能把别人的在制改动卷进 diff | 改动前确认文件 mtime 与编译通过；提交前用 `git diff --stat` 确认改动面只有本需求的文件 |

## 4. 验收人视角：怎么确认判据真在判（而不是假绿） <!-- serves: FR-3 -->

1. **口径自证**（一行式，仓库外）：`declaredFiles('改 src/.../conflict-check.ts')` 返回非空
   ——若返回 `[]`，说明扩根没生效，后面一切读数不必看。
2. **可证伪的用例**：TC-6（两卡共享 `src/.../a.ts` + 互无依赖）必须**红**；
   把依赖补上后必须**绿** ——一红一绿才是判据，常年绿是装饰。
3. **真实数据对照**：含 `src/` 行的可抽取比例（改前 ≈19% / 改后 ≥90%）、零交集命中数（改前 ≈0 / 改后正数）、
   冲突门新命中逐条真伪判定。
4. **文档对齐**：领域篇「已知边界」表里本条不再是"未修"（TC-9）。
