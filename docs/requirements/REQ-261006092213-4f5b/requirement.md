# REQ-261006092213-4f5b 验收项由 agent 实测完成：人只做审核员

> 类型：feature · 难度：expert · 来源：用户裁定（本窗口）「我希望是验收项让agent来完成，人就是审核员」

## TL;DR <!-- serves: FR-1 -->

- 验收单**每一项**都由 agent 实测并落结果（命令 + 输出摘要），人只做审核员——看结论点「通过 / 退回」。
- 现在做，是因为 `result` 这套字段本来就是为这个目标设计的（两条既有需求已立过同样的话），但**没有兑现**：
  逐项绑不上（引用键在提交后才存在）、看板不预填、未复核底线不可达。
- 做完之后：人打开验收单只看到「结论 + agent 实测结果」，通过**不需要打一个字**；唯一要人动手的，
  是显式标注「无法自动验证」的项（界面视觉、线下流程），且必须写明为什么。

## 业务流程图 <!-- serves: FR-1 -->

```
agent 实施完
   │  逐项跑（依据 = 任务卡 acceptance 里已经写着的那条命令）
   ▼
reqboard_submit(kind=verification, summary, evidence, results=[{ref, result}])
   │  硬门：可预见项逐项交代；漏项 / 坏 ref / 空结果 → 拒绝并点名
   ▼
系统组装验收单：每项已带 result（resultSource=agent）
   │
   ├─▶ 会话弹框：有结果的项只问 1 问（通过 / 改进 / 其他）→ 人零输入裁决
   ├─▶ 看板逐项行：显示「实际结果（agent 实测）」并预填输入框 → 通过不再强制手打
   └─▶ 例外：needsHuman 项才要人填，且题干里写明「为什么必须人看」
        │
        ▼
   人裁决：全通过 → 归档；有未过项 → 逐项生成返工卡
```

## 产品定义 <!-- serves: FR-1 -->

验收单把「谁跑验证」和「谁裁决」混在了一起：agent 明明跑过验证，人还要把命令输出重抄一遍（不抄就记「未复核」）。
本需求把两件事彻底分开——**执行方给结果，裁决方给结论**。

**三要素检查清单**：

- 说清楚「是什么」：验收单的每项结果由 agent 落库，人的动作只剩「通过 / 退回」。
- 说清楚「核心价值」：人不再当打字员；台账里的结果是 agent 的原始命令与输出，而不是人手抄的转述。
- 说清楚「与现状的区别」：现状是「字段有了、链路没通」（绑不上、不预填、底线失效），本需求把链路打通并配上硬门。

## 用户与角色 <!-- serves: FR-1 -->

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 验收的人（PM / 需求方） | 需求进验收态，逐项看结论拍板 | 现在要手抄一遍命令输出，不抄就记「未复核」；看板连 agent 的结果都不显示 |
| 实施 agent | 实施完提交验收材料 | 明明跑过，结果却没地方落；写进 evidence 也绑不到项上（键在提交后才生成） |
| 维护者 | 事后查台账 / 复盘 | 只看得到人手抄的转述，分不清哪条结果是 agent 实测、哪条是人写的 |

### 条款

- **FR-1: agent 提交验收材料时逐项给出实测结果**

  - **谁**：实施 agent。**什么场景**：实施完成、调 `reqboard_submit(kind=verification)` 时。
  - **做什么**：按项提交 `results=[{ref, result}]`；`ref` 与验收项来源同构，不发明第二套键。
  - **看到什么**：验收单每个可预见项生成时即带 `result` 与 `resultSource='agent'`。
  - **接口（工具参数）**：`results[].ref` = `{kind:'task',taskId}` / `{kind:'requirement'}` /
    `{kind:'prototype-compare',path}` / `{kind:'decision-compare',ids}`；`results[].result` = 命令 + 输出摘要（≤500 字符）；
    `results[].needsHuman` + `results[].humanReason` 用于「我跑不了、必须人看」的项。
  - **数据契约**：台账字段**零新增**，沿用 `result` / `resultSource` / `needsHuman` / `humanReason`（三处契约已存在）。
  - **锚点**：A1。

- **FR-2: 逐项交代做硬门（漏项即拒）**

  - **谁**：提交方被门禁拦。**什么场景**：提交验收材料时。
  - **做什么**：校验「可预见项」集合 = 顶层父卡任务项 + 需求级项 + 对照项（原型 / 裁定）。
  - **看到什么**：任一项既没给 `result`、也没声明 `needsHuman` + 理由 → 提交被拒并**点名到项**；坏 ref（不存在、非活卡、
    重复、空 result）同样被拒。**系统项豁免**（孤儿用例 / E2E 缺口 / 三方一致性 / 锚点失效 / 追溯断链）——
    它们提交时才由代码算出，agent 无从预见，仍由人写处置意见。
  - **锚点**：A3、A6。

- **FR-3: 已有结果的项，弹框只问裁决**

  - **谁**：验收的人。**什么场景**：`reqboard_accept_sheet` 逐项弹框。
  - **做什么**：只回答「通过 / 改进 / 其他」，不打字。
  - **看到什么**：有结果的项只出现 1 问（不再出现「实际结果」第 2 问）；`needsHuman` 项才保留第 2 问，且题干带理由。
  - **锚点**：A2。

- **FR-4: 看板逐项行与详情页核验表展示实测结果并预填**

  - **谁**：验收的人。**什么场景**：看板验收面板逐项勾选、详情页核验表查看。
  - **做什么**：看板逐项行显示「实际结果（agent 实测）」并把该结果预填进输入框（可选填，人改了才记 `resultSource='human'`）；
    详情页核验表显示实际结果与来源（agent 实测 / 人工填写）。
  - **看到什么**：勾「通过」时留空不再被拦；服务端 `passed` 且 opinion 为空时取该项 `result`。
  - **锚点**：A2、A5。

- **FR-5: 无法自动验证的项显式单列 + 写明理由**

  - **谁**：验收的人（唯一要动手的场景）。**什么场景**：界面视觉、线下流程这类项。
  - **做什么**：提交方在 `results` 里显式声明 `needsHuman: true` 并写 `humanReason`；原型对照项由代码自动标注。
  - **看到什么**：这类项在看板与详情页有显式旗标与理由；弹框第 2 问的题干里写明「为什么必须人看」。
  - **锚点**：A4。

- **FR-6: 底线与放行判据修正**

  - **谁**：系统（代码级底线）。**什么场景**：裁决落库与归档放行。
  - **做什么**：`passed` 必须有结果（agent 落或人填）；两者皆空 → `unverified`（不计入通过）；
    「全部通过 → 归档」的放行判据从「只查 pending」改为「pending 与 unverified 都不许存在」。
  - **看到什么**：没有结果的项点通过不再冒充通过；有未复核项时不会弹出「全部 N 项通过 → 归档」。
  - **锚点**：A5。

- **FR-7: 留痕与文档**

  - **谁**：维护者 / 后续验收。**什么场景**：读 `docs/requirements/<REQ>/verification.md`。
  - **做什么**：验收结果表的「实际结果」列改用 `item.result`（并标来源），人的裁决意见仍单独可见。
  - **看到什么**：文档里的结果是 agent 实测原文，不再是「opinion 或待填写」。
  - **锚点**：A7（`pnpm test` 下的文档渲染用例）。

- **FR-8: 提示词与兼容回滚**

  - **谁**：agent（被提示词引导）与维护者（要回退时）。
  - **做什么**：accepting 阶段提示词写清「怎么逐项交结果」；`evidence` 老写法保留（整单证据，照旧进验收文档）；
    `DSH_REQBOARD_NO_ITEM_RESULT=1` 保留为一行回滚开关（关闭逐项绑定，退回「问第 2 问」旧口径）；
    存量在册验收单不回写。
  - **看到什么**：不带 `results` 的提交仍能成功（行为同今天）；置开关即回退，无需改代码。
  - **锚点**：A7、A8。

## 边界（不做） <!-- serves: FR-1 -->

1. **不新增命令执行引擎 / runner**：agent 就是执行者，跑什么由它按验收依据决定；宿主不跑命令、不维护白名单。
2. **不取消人工裁决**，不允许 agent 自判通过——它只给结果，不给裁决。
3. **系统项不由 agent 落结果**：提交时才算出，仍由人写处置意见。
4. **不改任务卡验收标准的生成规则与拆分模板**（属既有需求范围）。
5. **不重写存量验收单**。
6. **不把 `needsHuman` 的判定权完全交给 agent**：原型对照由代码自动标；其余必须显式写理由，无理由即拒。
