# 数据模型 · REQ-261001203710-0fbf <!-- serves: FR-1 -->

> 一句话：**不新增字段、不换存储**——分区键就用记录里已有的 `workspaceRoot`，本需求补的是「查询与解析真的按它分区」。

## 结论 <!-- serves: FR-1 -->

**无字段变更、无文件格式变更、无数据迁移。** 台账仍是 `~/.dsh/dsh-reqboard.json`（`schemaVersion` 不变），
每条需求仍带 `workspaceRoot`；变化只发生在**读取与解析时如何使用它**。

## 逐面核对 <!-- serves: FR-1 -->

| 契约面 | 现状 | 本需求 | 依据 |
|---|---|---|---|
| `RequirementRecord.workspaceRoot` | 已存在（REQ-260929210741-30ae FR-6），非必填 | **语义升级为分区键**：遍历与取路径都必须用它；不改类型、不改必填性 | 本机台账 25 条中 22 条有值、3 条为空 |
| 台账文件顶层结构 | `{schemaVersion, revision, requirements[], triages[]}` | **不变**（仍是 profile 级一份文件） | 拆文件属存储重设计，已列入「边界」不做 |
| `queue.json` | 每需求一份，位于该需求的目录下 | **不变**；只改「按哪个根去定位它」 | 见 interfaces.md 的逐记录解析 |
| RTM `rtm-*.yml` | 每需求一份，位于该需求目录 | **不变**；同上 | 同上 |
| HTTP state 响应 | 现有字段 | **只增** `usedProjectRoot`（可选字段），不删不改既有字段 | 可观测性契约 |
| docs 端口/适配器形状 | `DocRepository` / `QueueRepository` | **不变**（不引入每项目一个实例） | 边界 |

## `workspaceRoot` 的口径（本需求要定死的三条） <!-- serves: FR-1 -->

| # | 规则 | 理由 |
|---|---|---|
| 1 | 有值 → **它就是说一不二的项目根**；任何与之不符的解析结果都要拒绝，不得"就近处理" | 现状是"事后掰正"，掰不过来就静默写错地方 |
| 2 | 空/缺失 → 按调用方 `fallback` 处理，且**必须标注** `attributed:false` | 本机 3 条老记录属此类；不能静默当成当前项目（那正是跨项目污染的来源） |
| 3 | 不允许"写入时改用别的根" | 一旦允许，跨项目污染就有了合法出口；要么按记录根写，要么响亮失败 |

## 为什么不新增字段（例如 `projectId`） <!-- serves: FR-1 -->

- `workspaceRoot` 已经**唯一确定一个项目**（绝对路径），再加 `projectId` 会形成两份真相，且需要回填与同步。
- 若将来真要做"一个项目多工作区"，再引入显式 `projectId` 并做迁移——那时属**数据模型变更**，按 L3 信号升重档处理，不在本需求。
