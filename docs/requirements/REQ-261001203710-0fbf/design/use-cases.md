# 用户场景 · REQ-261001203710-0fbf <!-- serves: FR-1, FR-2 -->

> 一句话：四个主场景都围绕同一件事——**同一宿主进程里住着多个项目，而操作必须只动自己那一个**。

## 场景 1：多项目并行（本机实录） <!-- serves: FR-1 -->

**谁**：同时开着多个工作区会话的维护者。

**何时**：本机台账此刻的真实分布——`dsh-pmboard` 16 条、`dsh-notice-webhook` 5 条、`pi-investment/quantsys-v2` 1 条、无工作区 3 条，共 25 条；其中三个工作区**都有在途需求**。

```
   看 A 项目的看板
        │
        ├─ 现状：取【全部 25 条】的 id，用 A 的 cwd 逐条扫描
        │        └─► 也去扫 B / C 项目的需求 → 读空（静默）或读错
        │
        └─ 改后：只处理 workspaceRoot = A 的记录
                 └─► B / C 的目录【零访问】，跳过数如实回报
```

## 场景 2：立项建档必须落在自己项目里 <!-- serves: FR-2 -->

**谁**：需求方。

**何时**：本会话实测——立项时把新需求目录建到了 **dsh-notice-webhook**（含 `rtm-lifecycle.yml`），而台账 `workspaceRoot` 写的是 dsh-pmboard，**正确工作区连目录都没有**。

**改后**：建档按记录的项目根写；返回体带 `usedProjectRoot`，人一眼能看出"写哪了"。若解析结果与记录根不符 → 当场拒绝，而不是写完再让人去搬目录。

## 场景 3：计划落库 + 错配响亮失败 <!-- serves: FR-2 -->

**谁**：实施 agent。

**何时**：批准拆分计划后自动落库（本会话实测把 `queue.json` + 4 张任务卡写进了另一个项目，还报「落库成功」）。

```
   批准计划 → 落库任务卡 / queue.json / RTM
        │
        ├─ 校验：解析根 == 记录声明的 workspaceRoot ？
        │        ├─ 是 → 写入，并在评论留痕「本次写入根=<abs>」
        │        └─ 否 → 抛 REQBOARD_PROJECT_ROOT_MISMATCH
        │                 文案同时给出【两个绝对路径】+ 修复建议
        └─► 绝不出现"报成功但写别处"
```

## 场景 4：查规范时不再被「未初始化」误导 <!-- serves: FR-2 -->

**谁**：新窗口的 agent（按纪律开工先查 `reqboard_kb(kind='standard')`）。

**何时**：本项目磁盘上索引存在、`kb-build --check` 通过，检索却报「知识层未初始化」（本会话实测 2 次）。

**改后**：检索按**当前项目根**解析，并把两种病因分开报：

| 病因 | 该报什么 |
|---|---|
| 本项目确实没生成索引 | 「本项目知识层未生成」+ 解析出的项目根 + `npx tsx scripts/kb-build.mts --write` |
| 空间错配（根不对） | 「项目根与索引位置不一致」+ 两个路径 |

**为什么重要**：现状把这两种病统一报成「未初始化」，会把排查方向直接带偏（去重新生成索引，而索引本来就在）。

## 场景 5：未归属的老记录（兜底不静默） <!-- serves: FR-1 -->

**谁**：维护者。

**何时**：台账里有 3 条**没有** `workspaceRoot` 的老记录。

**改后**：按调用方的兜底根处理，但**标注** `attributed:false` + 「该记录无 workspaceRoot，按 <fallback> 处理」——仍可处理，但不再"看起来像本项目的"。

## 边界场景 <!-- serves: FR-2 -->

| 场景 | 预期行为 |
|---|---|
| 记录声明了项目根，但该根不可写 | 报错并指名路径；**不得**回落到调用方 cwd 静默写入 |
| 同一项目下多个需求 | 互不影响（按记录解析，同一项目根） |
| 看板的**全局列表**（纯展示） | 可继续展示跨项目条目——本需求限制的是**取路径**的操作，不是展示（展示不带路径语义） |
| 项目根是软链 | 比较时用 realpath 归一，避免 `A` 与 `A/` 或软链路径被判成"错配" |
