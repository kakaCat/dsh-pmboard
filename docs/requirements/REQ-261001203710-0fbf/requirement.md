## TL;DR

PM 插件把**所有项目**的数据装在同**一份内存/台账**里，却不按项目分区：查询、枚举、扫描都把"全部项目"当成一个项目处理，路径又按单一 `cwd` 解析。
于是不同项目**互相干扰**——产物被写进别的项目、扫描扫到别人家、检索读空。本需求给数据加上**项目维度**，并让每条取路径的操作按**该条记录自己的项目**解析。

## 根因（按你的假设核实 · 结论：**成立，且比路径问题更根本**）

**你的两次说明**（需求文档确认弹框作答原文）：

> 应该是 pm 每个立项没有自己的空间，导致 pm 插件中的不同项目产生了相互干扰，你看看是不是这个原因

> 我的意思的内存里的数据没有区分，不同项目

**核实结论：成立。** 真正的根因是**数据层没有「项目」这个维度**——路径错乱只是它的症状。

| 事实 | 证据（可复核） |
|---|---|
| 台账是**一份平铺文件**，无项目维度 | `~/.dsh/dsh-reqboard.json` 顶层只有 `{schemaVersion, revision, requirements[], triages[]}`；**25 条需求来自 4 个工作区混在一个数组**：dsh-pmboard 16、dsh-notice-webhook 5、pi-investment/quantsys-v2 1、无工作区 3 |
| 内存快照被**当成一个项目**遍历 | `src/adapters/ArtifactSync.ts` 的 `syncAllReqArtifacts(store, cwd)`：`store.snapshot().requirements.map(r => r.id)` 取**全部项目**的 id，再**用同一个 `cwd`** 逐个扫描；看板状态端点正是这样调用它（`stages.ts`） |
| 记录**有** `workspaceRoot`，但**查询不用它做分区键** | 与路径那条同构：字段声明了、枚举与解析却不按它分区 |
| 同一宿主进程里**确实同时住着多个项目** | 台账按 `workspaceRoot` 分组：三个工作区**此刻都有在途需求**（implementing / decomposing / brainstorming） |

**对修法的影响（我前两稿的偏差已按此修正）**：
第一稿写「在漏掉的路径上补校正」（补漏式），第二稿写「按需求解析路径」（仍是路径视角）——**都只治症状**。
按核实结论，主修法是：**先让数据带上项目维度，再让每条操作按"该条记录自己的项目"解析路径**（共享的 `cwd` / 根指针只可作兜底，不得作为唯一依据）。

## 本需求要修的条款

- **FR-1: 数据层带项目维度，查询与枚举按项目分区**——每条需求记录归属其工作区（记录已有 `workspaceRoot`，本需求让**查询/枚举/扫描真正按它分区**）：处理某项目时只遍历属于该项目的记录，不再「取全部 id 用同一个 cwd 扫」。台账可仍是一份文件，但**不得再把所有项目当一个项目处理**。
- **FR-2: 每条取路径的操作按该条记录自己的项目解析**——扫描产物、落盘任务卡与 `queue.json`、写 RTM、读项目级文件（如知识层检索）一律以**该记录声明的 `workspaceRoot`** 为根；落在别处或读不到时必须**响亮失败**并给出两个路径，**不得**报「成功」、也不得把项目错配谎报成「文件不存在 / 未初始化」。

## 产品定义

**是什么**：PM 插件的**数据与路径都带项目维度**——数据仍可集中存放，但每一处读写都知道「这条记录属于哪个项目」，并只在该项目里动作。

**核心价值**：让「报成功」等于「东西真的落在那个项目里」。现状最坏的一面不是报错，而是**报成功却动错项目**：产物跑进别的项目、扫描扫到别人家，两边都找不到责任人。

**与现状的区别**：现状是「一份数据 + 一个共享当前根 + 部分路径事后掰正」；修复后是「数据带项目维度 + 每条操作按记录自己的项目解析」，事后掰正从主修法降级为兜底。

**三要素检查**：

- [x] 说清"是什么"——数据与路径都带项目维度
- [x] 说清"核心价值"——真相与回执一致，项目之间不互相污染
- [x] 说清"与现状的区别"——从"共享当前根 + 事后校正"到"按记录的项目解析"

### 功能点详细说明

**详细说明 · FR-1**

- **使用场景**：同一宿主进程里同时有多个项目的需求（本机实测三个工作区都有在途需求）。
- **操作流程**：
  1. 人打开某项目的看板（或该项目的窗口发起操作）。
  2. 系统载入数据，按**项目**过滤出属于该项目的记录。
  3. 只对这些记录做扫描/统计/落库。
  4. 出现「记录的项目 ≠ 当前处理的项目」时，**跳过并留痕**，不得用当前项目的根去处理它。
- **预期结果**：
  - 结果 1：看板扫描只扫本项目目录；别的项目的目录**不被访问**。
  - 结果 2：本项目缺产物时如实报缺，不因别的项目有同名目录而误判。
- **边界条件**：
  - 边界 1：记录无 `workspaceRoot`（存量 3 条）→ 按既有兜底口径处理并标注，不得静默当成当前项目。
  - 边界 2：同一项目下有多个需求 → 互不影响。

**验收标准 · FR-1**：

1. 造 项目 A、项目 B 各一条需求（B 的记录含 `workspaceRoot=B`，A 的含 `A`）→ 以 A 为 cwd 调用看板扫描 → **断言 B 的目录未被访问**（可用探针计数或断言 B 的产物登记数不变）。
2. 反向：只留 B 的记录、以 A 为 cwd 扫描 → 断言不产生「B 的产物落在 A」的条目。

**详细说明 · FR-2**

- **使用场景**：立项建档、计划落库、写 RTM、读项目级文件。
- **操作流程**：
  1. 操作拿到目标记录。
  2. 以**该记录声明的 `workspaceRoot`** 解析所有路径。
  3. 解析结果与预期项目不一致 → 响亮失败（同时打印两个绝对路径）。
- **预期结果**：
  - 结果 1：产物只出现在该记录的项目里（`docs/requirements/<REQ>/` 齐全）。
  - 结果 2：其它项目目录**不被写入**（可断言不存在）。
- **边界条件**：
  - 边界 1：需求无 `workspaceRoot` → 沿用会话根，行为与修复前一致。
  - 边界 2：目标根不可写 → 报错并指名路径，不静默降级到别处。

**验收标准 · FR-2**：

1. 构造 会话根 A ≠ 记录的项目根 B → 立项/计划落库后：`B/docs/requirements/<REQ>/` 有产物，且 `A/docs/requirements/<REQ>/` **不存在**。
2. 人为让解析结果指向 A → 命令输出含「解析根 ≠ 记录的项目根」且非零退出，不得报成功。

## 边界（不做什么）

- **做 / 不做（同一条的两面）**：**做**「数据带项目维度 + 每条操作按记录自己的项目解析路径」（主修法）；**不做**把台账拆成「每项目一份文件」、改成「每项目一个仓储实例」或动组合根（那是存储与装配的重设计，出现即按 L3 单向升级信号停手并另立重档）。
- **不做**：不改知识层内容、生成器与索引格式；不改闸门判定规则与文案结构；不改状态机与前端渲染。
- **不做**：不做存量数据的批量搬迁与清洗（已错放的按需人工搬，本次已搬回 1 处），不写全量迁移脚本。

## 验收标准（整体）

1. 造两个项目的记录与目录：以 A 为当前项目处理时，**B 的目录零访问、零写入**；以 B 处理时同理。
2. 立项与计划落库：产物只出现在记录所属项目下；错配时响亮失败并给出两个路径。
3. 读侧：磁盘有知识层索引时检索命中；索引缺失时报「未生成」并给生成命令；**根错配**与**文件缺失**必须能区分。
4. `npx vitest run` 失败数与开工前基线持平；`npx tsc --noEmit` 无新增错误。
