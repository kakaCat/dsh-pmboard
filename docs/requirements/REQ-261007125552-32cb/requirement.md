# 需求说明（REQ-261007125552-32cb）

> 状态：需求分析（brainstorming） · 立据：2026-10-07
> 宣布路径：**Bounded**——本仓已有完整的拆分链路（decomposing 提示词档 + normalizePlanTasks 校验 + decompose 落库闸门 + RTM），本次是在既有链路上补粒度约束与拆分输入，不新建子系统。

## TL;DR <!-- serves: FR-1 -->

拆分阶段的任务卡太粗：一张功能卡常覆盖多个接口、一张页面卡覆盖整个页面，且拆分缺少设计依据。本需求把拆分输入（接口清单/组件树）前置到设计阶段，把粒度规则写进拆分档，并用代码门禁锁死执行。做完后：拆分产物落到接口级/组件级，RTM 追溯更准。

## 业务流程图 <!-- serves: FR-1 -->

```
现状：  设计文档（无接口/组件清单）──▶ 拆分凭经验 ──▶ 粗粒度大卡（一卡多功能/整页）
                              │
目标：  设计文档【+接口清单 +组件树】──▶ 拆分逐条对照 ──▶ 接口级/组件级卡 ──▶ 门禁校验【+接口数 +对照表】──▶ 落库
```

## 背景与动机

> 用户原话（2026-10-07，本窗口）：「我现在发现的问题是拆分太粗，一个功能可能需要几个接口来实现，一个页面可以分成结果组件来实现，拆分的时候应该没有设计」

现状证据（代码）：

- decomposing 档（[decomposing/heavy.md](../../../src/domain/prompt/fragments/decomposing/heavy.md)）只要求「对照设计盘点改动」，粒度约束仅有容量**上限**（16 DU，[limits.ts](../../../src/domain/limits.ts)），无下限与形态约束；
- feature 拆分类型档（[feature.md](../../../src/domain/prompt/fragments/decomposing/feature.md)）有「契约卡先行」「卡不跨层」，但无「一功能多接口须按接口拆」「页面按组件拆」的粒度规则；
- 门禁侧（[normalizePlanTasks](../../../src/shared/protocol.ts) / [Decompose.ts](../../../src/application/use-cases/Decompose.ts)）只查 key 唯一、依赖合法、文件冲突、FR 覆盖、footprint 下限——**不查一卡声明了几个接口、一张卡挂几个组件锚点**。

后果：粗卡在实施期才暴露「一卡装不下 / 并行互相覆盖 / 验收锚点含糊」，返工成本高。

## 产品定义 <!-- serves: FR-1 -->

拆分粒度约束系统：在需求拆分阶段，以设计文档产出的接口清单与页面组件树为拆分依据，把任务卡粒度锁到「接口级 / 组件级」，并用代码门禁强制执行。核心价值：从「凭经验拆出大卡、实施期返工」到「按清单拆出小卡、提交期即拦」，粒度错误左移到拆分提交时发现。

**三要素检查清单**：

- [x] 是什么：拆分粒度规则 + 门禁（作用于 decomposing 阶段）
- [x] 核心价值：接口级/组件级拆卡，粒度问题提交期即拦
- [x] 与现状的区别：现状只有容量上限与 FR 覆盖门，无粒度形态约束、无拆分输入（接口清单/组件树）

### FR-1：设计先行——接口清单与组件树进设计文档

**功能描述**：feature 需求的设计文档必须产出「接口清单」节（每个接口一行：方法+路径+职责）；需求含 UI 时另必备「页面组件树」节（页面 → 组件 → 叶子组件），作为拆分阶段的输入。

**详细说明**：

- **使用场景**：agent 在 design 阶段写设计文档；decomposing 阶段拆分时对照。
- **操作流程**：
  1. design 档（design 提示词片段）与设计文档模板（templates/design/）补「接口清单」「页面组件树」两节为必备；
  2. agent 写设计文档时逐条列出接口与组件；
  3. design 登记/确认时缺失该节即提示（只提示或硬拒在设计阶段定）。
- **预期结果**：进入 decomposing 的需求，其设计文档含机器可扫的接口清单与组件树。
- **边界条件**：无 UI 的需求（sides 不含 frontend）豁免组件树节；纯内部函数无 HTTP 边界的卡不受接口清单约束（在设计文档里声明即可）。

**验收标准**：

1. `npx vitest run <新增测试>`：feature 需求设计文档缺「接口清单」节 → 校验报缺失；含节 → 通过。
2. 模板落盘检查：`templates/design/` 对应模板含两节骨架（`grep -n "接口清单" templates/design/*.md` 命中）。

### FR-2：拆分对照——清单条目必须有卡接

**功能描述**：decomposition.md 增加「接口清单 ↔ 卡 key」「组件树 ↔ 卡 key」两段对照表；提交拆分计划时，清单条目没有卡接收（或卡未出现在对照表）即硬拒并点名，复用「文档所见 = 批准所见」校验模式。

**详细说明**：

- **使用场景**：agent 提交 `reqboard_submit(kind=plan)` / `reqboard_decompose(tasks=…)`。
- **操作流程**：
  1. agent 在 decomposition.md 写对照表（每个接口/组件一行 ↔ 计划 key）；
  2. 提交时门禁扫描：清单条目未出现在对照表 → 拒并点名；对照表行指向不存在的 key → 拒；
  3. 批准后落库照常。
- **预期结果**：拆分提交期即暴露「设计了但没拆」「拆了但设计里没有」两类静默缺口。
- **边界条件**：设计文档未产出清单（FR-1 豁免场景）时对照表门降级为提示，不硬拒（防锁死存量流程）。

**验收标准**：

1. `npx vitest run <新增测试>`：清单 3 个接口、对照表只覆盖 2 个 → 拒，报错点名缺的那个；全覆盖 → 通过。
2. 报错形态与现有 FR 覆盖门禁一致（结构化 code + 修复指引）。

### FR-3：粒度规则入档——功能卡接口级、页面卡组件级

**功能描述**：decomposing 提示词档（light/heavy）与 feature 类型档补三条粒度规则：① 功能卡=接口级，多接口功能拆 N 张接口卡、契约卡先行；② 页面卡=组件级，按组件树叶子拆，页面只留一张接线/组装卡；③ UI 卡一卡一原型锚点，一卡多锚点=太粗信号。

**详细说明**：

- **使用场景**：agent 在 decomposing 阶段起草任务表时遵循。
- **操作流程**：规则写进 `src/domain/prompt/fragments/decomposing/light.md`、`heavy.md`、`feature.md`（其余类型档按需补一句）。
- **预期结果**：注入的拆分档包含三条规则原文，agent 拆分输出粒度变细。
- **边界条件**：本 FR 是提示词层软规则，硬约束由 FR-2/FR-4/FR-5 兜底；不要求改 superpowers vendor 原文（本仓自写档）。

**验收标准**：

1. `grep -n "接口级" src/domain/prompt/fragments/decomposing/heavy.md` 命中；`grep -n "组件级" src/domain/prompt/fragments/decomposing/feature.md` 命中。
2. `npx vitest run tests/stage-prompts.test.ts`（或对应快照/装配测试）→ 全绿。

### FR-4：接口数门禁——一卡多接口即拦

**功能描述**：提交/落库时检测 feature 类任务卡 `implementation` 中声明的接口/路由数量，>1 即拒绝并点名「请按接口拆分成 N 张卡」（检测口径与 footprint.files 校验同构，单点实现）。

**详细说明**：

- **使用场景**：`reqboard_submit(kind=plan)` 与 `reqboard_decompose(tasks=…)` 两条入口都要拦（与现有门禁挂载点一致）。
- **操作流程**：
  1. agent 提交任务表；
  2. 门禁逐卡扫描 implementation 里的接口/路由声明（形态在设计阶段定：如 `POST /api/x`、`route(...)` 等可机器识别的写法）；
  3. 单卡 >1 个接口 → 拒，报错列出接口清单与建议拆法。
- **预期结果**：一卡多接口的粗卡无法落库。
- **边界条件**：契约卡（只定契约不实现接口）与组装卡豁免，由 `side`/`phase` 或显式标记区分（设计阶段定口径）；检测误报时的豁免出口 = 显式声明理由（参照 skipIntegrationReason 模式）。

**验收标准**：

1. `npx vitest run <新增测试>`：implementation 声明 2 个接口的卡 → 拒，错误码结构化且点名；声明 1 个 → 通过。
2. 豁免声明路径有测试：契约卡标记后 >1 接口不拦。

### FR-5：形态下限——footprint.files 超阈值提示切小

**功能描述**：单卡 `footprint.files` 超过阈值（初值设计阶段定，如 5）时触发「按接口/组件切小」的拒绝或标红，与既有 16 DU 容量上限互补（上限管装不装得下，下限管拆得够不够细）。

**详细说明**：

- **使用场景**：同 FR-4，提交/落库入口。
- **操作流程**：门禁读 footprint.files → 超阈值 → 拒并建议切分批数；确需保留则走超容量标红同款通道（`⚠️超容量(建议N批)` 模式的形态版）。
- **预期结果**：文件面过宽的粗卡提交期被点名。
- **边界条件**：阈值只作形态信号，不替代容量计算；迁移类/批量脚本类卡的豁免口径在设计阶段定。

**验收标准**：

1. `npx vitest run <新增测试>`：footprint.files=6（超阈值）→ 点名提示切小；=5 → 通过。
2. 阈值单一源在 `src/domain/limits.ts`（与 16 DU 同文件），`grep -n "files" src/domain/limits.ts` 可见。

### FR-6：RTM 兼容回归——拆细不断链

**功能描述**：粒度细化后 RTM 追溯不退化：一条 FR 被多张卡接收（一对多）正常计算覆盖；「每卡必带 requirement_refs」不变量不松；已批准计划与已落库存量卡不追溯、不迁移。

**详细说明**：

- **使用场景**：本需求全部 FR 落地后的回归验证；以及任何细化后需求的正常流转。
- **操作流程**：
  1. 构造一条 FR 被 3 张接口卡接收的计划 → 落库 → RTM `covers_frs`/`serves` 显示一对三；
  2. 漏写 refs 的卡 → FR 覆盖门禁仍拒 / 进 unrefed_cards 警告；
  3. 用存量（本需求落地前）已批准计划走 decompose → 不因新门禁追溯拒掉。
- **预期结果**：RTM 边数变多变准、无断链；存量流程不被新门禁锁死。
- **边界条件**：存量不追溯 = 新门禁只在提交/落库路径生效；确需给旧卡补 refs 走既有 `reqboard_task_refs` 通道。

**验收标准**：

1. `npx vitest run tests/decompose-rtm-integration.test.ts`（及新增一对多用例）→ 全绿。
2. 存量计划落库用例：旧形态计划（无对照表）在 FR-2 降级路径下可落库并有提示。

## 失败与并发路径 <!-- serves: FR-4 -->

- **检测误报**：接口数检测把注释/文档字符串误识别为接口声明 → 误拒合法卡。收敛：识别口径只允许**声明式写法**（设计阶段定死形态），误报时用户可走显式豁免声明（参照 `skipIntegrationReason` 模式，写理由放行）。
- **存量锁死**：新门禁上线后旧形态计划（无对照表/无清单）提交被拒 → 收敛：FR-2 在设计文档无清单时降级为提示；FR-6 回归用例覆盖「旧计划可落库」。
- **重复提交**：同一计划被拒后 agent 改完重交 → 走既有 plan 重交通道（旧批准作废、重新批准），本需求不改该状态机。
- **并发**：两窗口同需求提交计划 → 既有 `REQBOARD_CONFIRM_PENDING` 门兜底，本需求不新增写路径。

## 边界（不做什么） <!-- serves: FR-1 -->

- **不改 RTM 取数模型**：serves/covers_frs 仍从卡上 requirement_refs 现算，一对多是原生能力，不建第二套追溯键——理由：用户已确认「拆细只让 RTM 边变多变准」，改模型是无谓风险。
- **不追溯存量**：已批准计划、已落库卡不被新门禁回扫——理由：门禁只在提交/落库路径生效，回扫存量会锁死进行中需求。
- **不改子卡链模板**：dev/integrate/review/test 等 stage 模板不动——理由：本问题在父卡粒度，子卡链是卡内工序，两回事；确有联动需求另行立项。
- **不做粒度自动拆分**（agent 交一份粗计划、系统自动切成接口卡）：本期只拦不替拆——理由：自动拆分涉及依赖推断，风险大，先把「拦+给拆法建议」做扎实。

## 关键决策与取舍

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 粒度约束落在哪一层 | 只写提示词档（软规则） | 提示词档 + 代码门禁双层 | 实测教训：薄卡/伪依赖/跳联调只靠提示词时遵守率低（本仓 heavy.md 已记录 78/107、20/99 两组实测），门禁才锁得住 |
| 粗卡怎么处理 | 系统自动把粗卡切成接口卡 | 只拦 + 给拆法建议，不替拆 | 自动拆分要推断依赖与边界，误切比粗卡更难收拾；D-1 口径是「拆的时候有依据」，不是「机器替人拆」 |
| RTM 配套 | 为一对多改建模 | 不改模型，只加回归 | 一对多是现有取数原生支持（plan-refs 并集口径），改动=无谓风险 |

## 技术方案与亮点

- **复用既有门禁挂载点**：新校验挂在 `normalizePlanTasks`（提交期）与 decompose/plan 落库路径，不新增写路径；
- **阈值单一源**：files 阈值与 16 DU 同在 `src/domain/limits.ts`；
- **豁免一律显式声明理由**（skipIntegrationReason 同款模式），不给静默出口。

## 依赖与约束 <!-- serves: FR-1 -->

- 依赖：现有 FR 覆盖门禁（`assertClauseCoverageGate`）、footprint 校验（`normalizeFootprint`/`assertFootprintFloor`）、「文档所见=批准所见」对照表校验模式（强依赖，新门禁复用其形态）；
- 约束：提示词档改动必须同步 light/heavy 两档与类型档，生成物（generated/fragments.ts）由构建脚本再生成，不手改；
