## TL;DR <!-- serves: FR-1 -->

本插件对外暴露 27~28 个 reqboard_* 工具，是 agent 每天操作的唯一界面。
工具体越大、描述越长、职责越重叠，agent 选错工具、漏看副作用、被过时文案误导的概率越高。

本需求不改任何行为，只做一次**有代码证据的横向体检**：
工具面重叠、状态机/幂等/并发潜在 bug、文案与契约不一致，三份清单 + 一份精简优化方案。

## 产品定义 <!-- serves: FR-1 -->

**是什么**：一次对 reqboard 插件工具面与内部实现的**只读横向调研**，产出证据化问题清单与优化方案。

**核心价值**：把「感觉工具太多、描述太长」变成「哪几个工具该合并、哪几处文案在说谎、哪几个状态边界会出错」的可裁决清单。

**与现状的区别**：现状问题散落在代码与变更记录里，没有一份集中视图；本次调研不改行为，只产出认知。

**三要素检查清单**：

- [x] 说清楚"是什么"：工具面 + 实现的证据化体检报告
- [x] 说清楚"核心价值"：问题从「体感」变「可裁决清单」
- [x] 说清楚"与现状的区别"：集中视图，不改行为

### FR-1: 工具面重复/职责重叠清单

**功能描述**：拿到一张「工具职责总表 + 重叠对清单」，每个重叠结论都能在代码里复核。

**详细说明**：

- **使用场景**：维护者决定下版本工具面时，逐对核对。
- **操作流程**：
  1. 打开调研报告的 FR-1 章节。
  2. 对每个重叠对，按报告给的 `文件:行号` 复核证据。
  3. 对每条合并建议裁决采纳/不采纳。
- **预期结果**：
  - 结果 1：覆盖全部已注册工具（以 `src/tools/registry.ts` 实际注册数为准）。
  - 结果 2：至少覆盖已知疑似重叠对：task_execute vs task_run、create vs capture、status/task_tree/run_status/task_status 四查询面、open_window vs handoff、submit(archive) vs archive_amend、ask_confirm 双路径与 confirm_receipt。
  - 结果 3：双字段兼容（dep_reasons/depReasons 等 camel/snake 并存）有逐处统计。
- **边界条件**：
  - 边界 1：只读分析，不修改任何源码。
  - 边界 2：client 端 GUI 不在本次范围，只看 host 工具面。

**验收标准**：
1. `grep -c "define.*Tool" src/tools/registry.ts` 得到的注册数与报告总表行数一致。
2. 报告 FR-1 章节中每个重叠对至少含一处 `路径:行号` 引用，且抽检 3 处引用真实存在（用 grep 复核）。

---

### FR-2: 状态机/幂等/并发/降级路径潜在问题清单

**功能描述**：拿到一份按严重性分级的问题台账，每条可在代码中定位。

**详细说明**：

- **使用场景**：维护者评估哪些问题需要立后续 bug/refactor 需求。
- **操作流程**：
  1. 打开报告 FR-2 章节，按高→中→低阅读。
  2. 每条核对证据行号与问题描述。
- **预期结果**：
  - 结果 1：覆盖以下排查面：需求/任务状态机迁移表完整性、声明幂等操作的实现核验、批量操作部分失败的补偿、多窗口席位并发写台账的竞态、自动实施链（dive/run）状态快照契约、human_gate 是否有间接绕过路径、60 秒节流与预算放行的边界条件。
  - 结果 2：每条标严重性（高/中/低）与修复建议。
- **边界条件**：
  - 边界 1：不要求写复现测试，证据到「代码路径 + 逻辑推演」级别即可。
  - 边界 2：已修复的历史问题（如 RunStatusTool null 透传）只在「类似风险模式」层面引用，不重复报。

**验收标准**：
1. 报告 FR-2 章节每条问题含 `路径:行号` 证据，抽检 3 处真实存在。
2. 高危问题逐条含「触发条件 + 后果 + 修复方向」三要素。

---

### FR-3: 文案与契约一致性清单

**功能描述**：拿到工具描述（prompt.ts）与实现/schema 偏差的清单，以及描述体质量的量化数据。

**详细说明**：

- **使用场景**：精简工具描述、统一错误码定义时作为底稿。
- **操作流程**：打开报告 FR-3 章节，按清单逐项核对。
- **预期结果**：
  - 结果 1：全量 REQBOARD_* 错误码统计（总数、是否有集中定义、分布文件数）。
  - 结果 2：各工具 prompt.ts 字符数排名（前 10），标出明显超长项。
  - 结果 3：prompt 中内嵌历史叙事（日期裁定、历史 REQ 编号引用）逐处列出。
  - 结果 4：package.json 声称工具数（27）与 registry 实际注册数（28 个目录）的差异原因查明（如 AdvanceTool 是否注册）。
- **边界条件**：只统计与列出，不改文案。

**验收标准**：
1. `grep -rho "REQBOARD_[A-Z_]*" src | sort -u | wc -l` 的读数与报告统计一致（允许 ±2 的口径差异并注明口径）。
2. prompt 字符数排名可用 `wc -m src/tools/*/prompt.ts` 复核。

### FR-4: 优化方案

**功能描述**：基于 FR-1~FR-3 的证据，给出工具面精简与治理的可执行方案。

**详细说明**：

- **使用场景**：人裁决「下一步立哪些整治需求」。
- **预期结果**：
  - 结果 1：工具合并/废弃/下沉清单，每项标注对存量 agent 提示词与看板 UI 的影响。
  - 结果 2：目标工具数与达成路径（哪些先砍、哪些只改描述）。
  - 结果 3：治理建议（如错误码集中定义、prompt 长度上限、历史叙事外移到 CHANGELOG）。
- **边界条件**：方案只到「建议 + 影响评估」，不含实施。

**验收标准**：
1. 每条优化建议能回溯到 FR-1/FR-2/FR-3 的至少一条证据编号。
2. 目标工具数 ≤ 当前注册数，且给出每个被合并工具的去向。

## 边界 <!-- serves: FR-1 -->

**做**：host 端 27 个已注册工具的工具面（prompt/schema/实现）；domain / application / repositories / http 层的
状态机、幂等、并发、降级路径；agent 可见文案与契约一致性；基于证据的精简与治理方案。

**不做**：
- 不修改任何源码、配置、文档（除本需求目录下的产物）——本 spike 全程只读；
- 不覆盖 client 端 GUI 视图实现本身（仅在工具面一致性层面核对 host/client 契约）；
- 不评估宿主 DSH 平台（dsh-tools / 宿主弹框通道）内部，只在本插件与宿主的交界面上取证；
- 不含性能压测与负载测试；并发问题取证到「代码路径 + 逻辑推演」级别。

## 结论 <!-- serves: FR-4 -->

调研完成，报告全文：[design/research-report.md](design/research-report.md)（三路并行只读审查，证据均附文件:行号，关键证据经抽检复核）。

**一句话**：插件主流程健康（状态机主表无缺边、幂等扎实、失败隔离到位），问题集中在**边界路径与工具面治理**——
3 个高危实现 bug、27 个工具可精简至 21（保守）/19（激进）、136 个错误码无事实源、agent 可见文案六处口径漂移。

**请求人裁决**（对应「待答问题」）：

1. 是否为本报告的修复项立后续需求（建议按 FR-4 §4.0 优先级：H1 一行修先行）；
2. 工具面精简走保守档还是激进档；
3. 部署拓扑是否为单进程假设（决定 H3 是否立项）。

## 失败与并发路径 <!-- serves: FR-2 -->

- **失败路径**：三路并行审查中任一路因子代理失败而缺失 → 报告对应章节标注「该路未完成 + 原因」，不伪造结论；补救 = 补跑一次该路。
- **并发重复**：本调研全程只读，不写台账、不改源码，与其他进行中的需求并发执行无写入冲突；唯一写操作是本需求目录下的文档，单窗口独占。
- **状态机非法迁移**：本需求为 spike，产物是报告；若人裁决「不值得整治」，直接走取消/归档，不进入 design 拆分——不存在中间态悬挂（报告本身就是终态产物）。
