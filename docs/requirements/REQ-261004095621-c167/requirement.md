# REQ-261004095621-c167 · 定位并修复：模型选择器点击后消失（DSH 席位崩溃取证）

## TL;DR

- **是什么**：把「点模型选择器就消失」从"说不清的现象"变成**可取证、可定责、可验证**的闭环。
- **为什么现在做**：同一现象已跨三个回合、一次修复动作仍在；当前卡点不是猜测，而是**取不到崩溃原文**（桌面端 build 在 macOS 隐藏了 DevTools 菜单项且无快捷键）。
- **得到什么**：席位崩溃的原文+堆栈落到本机文件；归属判定（pm 修 / DSH 上报）；以及"点一次不再退役"的验证证据。

## 一句话目标 + 可证伪判定标准

**目标**：任何一次**客户端席位渲染崩溃**都在本机留下原文与堆栈（不再静默退役），并用这份证据判定
`conversation.input.model` 的崩溃归属；pm 有责则修 pm，无责则产出面向 DSH 的缺陷报告。

**判定标准（跑什么、看到什么算完成）**：

1. 席位健康度（现状即红）：`cordis_inspect_query(platform=client, provider=Slots, method=listSubTree,
   input={root:"conversation.input.model"})` → `selected.occupants[0].active === true`；
   连续 3 次"点击模型控件"后复查仍为 `true`。**开工实测：`active:false`**（本文件写作时）。
2. 取证通道自检：`curl -s -XPOST localhost:19387/dashboard/api/reqboard/client-error -d '{"slot":"x","message":"probe"}'`
   → `200 {ok:true}`，且 `~/.dsh/state/pm-client-render-errors.jsonl` 尾部出现同一条 probe（字段齐全）。
3. 通道反向演练：临时摘掉客户端 tee → `pnpm vitest run tests/<新增用例>` 必红（口径同
   `tests/binding-trace.test.ts` 的反向演练）。
4. 构建与回归：`pnpm build:client` → `[verify-client] OK … 关键符号齐全, 样式归属章在场, CSS 分片完整`；
   `pnpm vitest run <新增用例>` 全绿；`npx tsc --noEmit 2>&1 | grep -c 'error TS'` ≤ 144（2026-10-04 基线），改动文件零新增。
5. 归属结论落盘：`docs/requirements/REQ-261004095621-c167/evidence/` 下有①崩溃原文与堆栈
   ②归属判定（pm 侧 / DSH 侧）③若判 DSH：缺陷报告（现象/复现/证据/期望 vs 实际）。

## 产品定义（电梯演讲） <!-- serves: FR-1 -->

**是什么**：一条"客户端渲染异常可取证"的通道 + 一次针对模型选择器崩溃的归属闭环。

**核心价值**：DSH 的插槽机制对非 chain 条目「渲染抛一次异常即退役（abdicate）」，
席位从此渲染空白且**不向用户报错**——坏掉的东西看起来只是"不见了"。今天拿不到崩溃原文，
于是既修不了也定不了责。本需求让"不见了"变成"有原文、有堆栈、有归属"。

**与现状的区别**：现状靠人眼截图 + 猜；本需求靠本机落盘证据 + 可跑断言。
（不是造监控系统：只做一次本地取证通道，够定责即止。）

|---|---|---|

### FR-1: 现象复核与归属判定

- **FR-1: 现象复核与归属判定**

**功能描述**：维护者把"点击就消失"钉成可复核的事实——先与用户对齐消失的确切对象（模型控件本身 / 菜单 / 其它），再抓 3 次席位快照。

**详细说明**：
- **使用场景**：用户报"某控件点一下就消失"，现象与归属都不明时。
- **操作流程**：
  1. 向用户确认：消失的是哪个控件、点之前它在不在、点的是控件本身还是菜单里的条目。
  2. 每次复现后调 `Slots.listSubTree(root='conversation.input.model')`，记录 `occupants[0].active` 与 `registrant`。
  3. 结论写进 `evidence/` ：`active:false` + registrant 不是本仓 = 席位被退役；registrant 是本仓 = pm 顶替或崩溃。
- **预期结果**：
  - 结果 1：现象被钉成"点前 active / 点后 active"的对照，不再靠描述。
  - 结果 2：归属判定有唯一依据（谁注册的席位 + 是否退役）。
- **边界条件**：
  - 边界 1：用户无法复现时，以最近一次快照 + 现象描述为准，并在证据里标注"未能现场复现"。
  - 边界 2：`active:true` 但用户仍看不到控件（样式/布局问题）→ 转 FR-3 的另一条分支（非退役类），本需求只保证不误判。

**验收标准**：
1. 证据文件里出现 ≥3 条带时间戳的 `active` 快照 → 观察到 `点前 true / 点后 false` 的对照（或明确记录为未复现）。
2. 归属结论一行写清：席位 registrant = `mf`（DSH 自带）/ 本仓 → 由此决定走 pm 修复还是 DSH 上报。

### FR-2: 客户端渲染异常取证通道

- **FR-2: 客户端渲染异常取证通道**

- **本轮不做（2026-10-04 裁定，理由）**：该条款的前置假设是"桌面端取不到控制台（DevTools 不可得）"，
  已被本回合事实推翻——用户直接取到崩溃原文（`slot entry crashed in 'conversation.input.model': … React #130`），
  且现有三步取证法（inspect 看 `active` → 控制台取原文 → `npm pack` 对标安装一致性）已足够定位。
  故本期不新增客户端 tee / 宿主路由 / 落盘文件；**重开条件**（任一成立即按 `design/interfaces.md`
  附录契约实施）：a) 出现确实拿不到控制台的环境；b) 三步法判不动的静默退役；c) 同类事故每月 ≥2 次。

**功能描述**：pm 客户端在页面内 tee 掉 `console.error`（席位崩溃时框架会打印 `slot entry crashed in '<slot>': <error>`），把命中行经宿主路由落盘成本机 JSONL。

**详细说明**：
- **使用场景**：需要拿到"哪个席位、什么错、堆栈在哪"的原文，而运行环境取不到控制台（本机桌面端 macOS 实测无 DevTools 入口）。
- **操作流程**：
  1. 客户端在 `apply()` 时安装 tee（幂等）：命中 `slot entry crashed` / `Objects are not valid as a React child` 等特征串才上报，其余原样透传。
  2. `POST /dashboard/api/reqboard/client-error`，宿主 append 一行 JSON 到 `~/.dsh/state/pm-client-render-errors.jsonl`。
  3. 维护者读该文件得到原文与堆栈；取证完成后通道保留（默认开，可关）。
- **预期结果**：
  - 结果 1：一次崩溃 = 一行 JSONL，含 `ts/slot/message/stack/url`。
  - 结果 2：通道任何环节失败（网络、路由、权限）都不影响 UI，只在控制台留一条 warn 并计数。
- **边界条件**：
  - 边界 1：单条超 16KB → 截断并标 `truncated:true`（不许把宿主写爆）。
  - 边界 2：日志**不含**用户消息正文/文件内容，只留 slot、错误原文、堆栈、URL。
  - 边界 3：新增宿主路由需重启宿主才生效——与用户约定一次重启。

**验收标准**：
1. 手工 POST 样例 → 文件尾部出现同一条 JSONL（字段齐全，命令见判定标准 2）。
2. 触发一次已知崩溃（可注入一个必崩的探针组件）→ 文件里出现带堆栈的那一行，且 UI 无异常表现。
3. 反向演练：摘掉 tee → 用例必红。

### FR-3: 按归属修复或上报

- **FR-3: 按归属修复或上报**

**功能描述**：拿到证据后二选一——pm 侧有责就修本仓并回归；DSH 侧有责就产出可提交的缺陷报告，不改 DSH 源码。

**详细说明**：
- **使用场景**：证据已到手（FR-2 完成）且归属已判定（FR-1 完成）。
- **操作流程**：
  1. 若 `slot` 属本仓注册 → 修本仓代码 + 加回归测试（口径同知识库图标：裸对象/非法元素必须被断言拦住）。
  2. 若 `slot` 属 DSH 自带（如 `conversation.input.model`，registrant `mf`）→ 写报告：现象、最小复现、证据（JSONL 原文+堆栈）、期望 vs 实际、影响面。
  3. 报告落到 `evidence/dsh-model-seat-crash.md`，并在交付说明里给出"用户可自行验证"的步骤。
- **预期结果**：
  - 结果 1：pm 有责 → 修复后判定标准 1 变绿（`active:true` 且连点 3 次不退化）。
  - 结果 2：DSH 有责 → 交付物是报告 + 规避建议（如换模型走 `/model` 命令），并明确"本仓不改 DSH"。
- **边界条件**：
  - 边界 1：禁止用 pm 注册项顶替 DSH 席位来"修好外观"——那是遮蔽，不是修复（见边界节）。
  - 边界 2：报告不夹带推测性结论；拿不到堆栈就走 FR-1 的"未复现"分支，不硬写根因。

**验收标准**：
1. 判定标准 1 的断言在修复后为真；或报告里给出的"规避路径"经用户实测可用。
2. 交付说明里给出证据文件路径 + 用户可自查命令（inspect 查询语句原样可贴）。

### FR-4: pm 客户端"异常即退役"写法审计与防呆

- **FR-4: pm 客户端"异常即退役"写法审计与防呆**

**功能描述**：维护者把 pm 客户端里"渲染抛异常就会被席位退役"的高危写法审计一遍，并把已知那一类（裸对象元素）变成测试断言。

**详细说明**：
- **使用场景**：本需求起因之一就是同款缺陷（知识库侧栏图标返回裸对象 → 条目退役 → 图标静默消失）。
- **操作流程**：
  1. 审计：`grep -rn "props: {" src/client` 类写法的元素构造；确认全部走 `createElement`。
  2. 断言：组件返回值的 `$$typeof` 必须等于 `Symbol.for('react.element')`（已具备先例，见 `tests/kb-client-page.test.ts`）。
  3. 结论写进交付说明（审计了哪些文件、是否有新发现）。
- **预期结果**：
  - 结果 1：审计清单落盘，无新增高危写法；有则当次一并修。
  - 结果 2：同类回归由测试拦住，不再靠人眼。
- **边界条件**：
  - 边界 1：不含 DSH 自带组件的审计（不在本仓范围）。
  - 边界 2：不为通过审计而改写无关模块。

**验收标准**：
1. 审计命令与结论写进交付说明；`pnpm vitest run tests/kb-client-page.test.ts` 等现存断言仍全绿。
2. 若发现新高危写法 → 当次修复并补断言（否则写"未发现"）。

## 边界（不做什么） <!-- serves: FR-1 -->

- **不做 A：不用 pm 的注册项顶替 `conversation.input.model` 席位。**
  理由：该席位 `replaceRisk = shadows-shipped-ui`，顶替等于把 DSH 的控件换成 pm 的，真因被掩盖且责任转移到本仓；
  改走 FR-2/FR-3 的取证与上报。
- **不做 B：不在本仓修改 DSH 自带包（`app.asar` 内的 `ui-model-selection` 等）的源码。**
  理由：那是打包产物，改了不随版本存活；DSH 侧问题以报告交付（本仓 `src/` 是唯一可改面）。
- **不做 C：本期不引入 GUI 自动化测试框架（playwright / CDP 驱动）。**
  理由：取证目标是"拿到崩溃原文"，运行时 tee 成本更低；自动化留待确有需要时单独立项。

## 非功能需求 <!-- serves: FR-1 -->

- **开销**：tee 命中判断为同步字符串匹配，非命中路径零分配；单条上报异步发出，不阻塞渲染（判定：连点 10 次控件无可感卡顿）。
- **隐私**：落盘内容不含用户消息正文、文件内容、密钥；只留 slot 名、错误原文、堆栈、页面 URL。
- **容量**：JSONL 单文件 ≤1MB，超出滚动保留 3 份（`pm-client-render-errors.jsonl.1/.2`），不许无限增长。
- **兼容**：通道默认开启但只写本机文件；关闭后（配置或环境变量）行为与现状完全一致。

## 验收标准（整体） <!-- serves: FR-1 -->

1. 用户点模型控件 → 维护者用 inspect 拿到"点前 `active:true` / 点后 `active:false`"的对照证据。
2. `~/.dsh/state/pm-client-render-errors.jsonl` 出现该次崩溃的原文与堆栈。
3. 证据判定归属：本仓注册的席位 → 修本仓；DSH 自带席位 → 产报告。
4. 修复/上报后，判定标准 1 的断言为真（或报告中的规避路径经用户实测可用）。
5. `pnpm build:client`、新增用例、`tsc` 基线三项全过，交付说明里逐条给出命令与输出摘要。
6. 交付说明含 FR-4 的审计结论与"用户可自查命令"。

## 依赖与约束 <!-- serves: FR-1 -->

- **依赖（强）**：reqboard 宿主 HTTP 路由机制（与既有 `/dashboard/api/reqboard/*` 同款）；
  客户端 `apply()` 时机的插桩点（本仓 `src/client/index.ts`）。
- **依赖（弱）**：用户配合一次复现与一次宿主重启（新路由需重启生效）。
- **约束**：DSH 桌面端 macOS **无 DevTools 入口**（实测 `app.asar`：`devToolsItems` 为 `visible:false` 且 darwin 无 accelerator）
  → 取证方案**不得**依赖 DevTools。
- **约束**：席位退役是 DSH 插槽机制行为（非 chain 条目渲染抛异常即 `abdicate`），本需求不改变该机制。
