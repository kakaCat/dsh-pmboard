# 用户场景（REQ-261002175818-80a8）

> **TL;DR**：本需求的场景只有一个主轴——**超容量卡从「实施中途暴露」变成「批准之前可见」**。
> 三个角色（拆分节点 / 批准人 / 实施节点）在四个场景里各拿一次判断权，外加一条蒙门禁的异常流。

## 场景总览 `serves: FR-1, FR-3, FR-4, FR-6`

| 场景 | 角色 | 触发 | 完成标志 | serves |
|---|---|---|---|---|
| UC-1 拆分节点按容量切卡 | 拆分节点（agent） | 写拆分计划 | 每张卡带 footprint，超容量的卡已按建议批数切开 | FR-1, FR-3 |
| UC-2 批准人看到超容量并裁决 | 批准人（人） | 计划提交后批准闸门 | 或要求再拆、或知情放行；两者都留痕 | FR-4, FR-5, FR-6 |
| UC-3 蒙门禁被拦下 | 拆分节点（agent） | 声明 `files` 小于 implementation 点到的路径数 | 收到 `REQBOARD_BAD_FOOTPRINT` + 实际计数，改成真实值后通过 | FR-2, FR-7 |
| UC-4 旧计划与旧台账照旧 | 任意 | 提交/读取没有 footprint 的旧数据 | 不报错、不判定、回显「未声明」 | FR-8, FR-9 |

## UC-1 拆分节点按容量切卡 `serves: FR-1, FR-3`

- **用例角色**：拆分节点（agent），正在把设计落成拆分计划。
- **前置条件**：设计文档已确认；需求处于 `decomposing`。
- **交互流程**：
  1. 节点输入包里读到「一轮容量」纪律段：容量常量、权重口径、必须声明 footprint；
  2. 对每张卡算三个量：要碰的文件数、验收锚点数、实施描述字符数；
  3. 发现某张卡 `detailUnits` 超过容量 → **自己**按目录/接口边界切开（不等人催）；
  4. 在计划文档该卡行写「⚠️超容量(建议N批)」标记，并写进批准文本。
- **异常流**：算不准文件数 → 声明**留余量**（允许大于路径计数），不得缩水（缩水会在 UC-3 被拦）。
- **后置条件**：计划里每张卡的体量已知；超容量的卡要么被切开、要么带着标记进入批准。
- **完成标志**：`reqboard_submit(kind=plan)` 返回的 `overCapacity` 为空，或非空但每张卡都带标记与建议批数。

## UC-2 批准人看到超容量并裁决 `serves: FR-4, FR-5, FR-6`

- **用例角色**：批准人（人）。
- **前置条件**：拆分计划已提交；存在一张或多张超容量卡。
- **交互流程**：
  1. 批准闸门的问题文本里直接看到超容量卡清单（key + 建议批数）**，不必翻返回体**；
  2. 打开 `decomposition.md`，该卡行带「⚠️超容量(建议8批)」标记；
  3. 裁决：要求再拆（退回拆分）或在知情下放行（批准）。
- **异常流**：标记没写 / 文本没带 → 提交时被内容门禁拦下（`plan_overcapacity_marker_missing`），不会出现「标红静默失效」。
- **后置条件**：批准或退回，两条路径都进台账留痕。
- **完成标志**：批准动作完成后，落库卡上带着 footprint 与超容量标记；退回则需求留在拆分态。

## UC-3 蒙门禁被拦下 `serves: FR-2, FR-7`

- **用例角色**：拆分节点（agent），想用一个小数字让超容量卡看起来合规。
- **前置条件**：`implementation` 正文里点到 3 个路径（如 `src/a.ts`、`src/b.ts`、`tests/c.test.ts`）。
- **交互流程**：
  1. 声明 `footprint.files = 1`；
  2. 提交 → `REQBOARD_BAD_FOOTPRINT`，消息点明「声明小于证据」与实际路径计数与修复指引；
  3. 改成 `files = 3`（或把漏列的文件补进 implementation）→ 通过。
- **异常流**：把路径写成散文（不出现 `src/` 这类前缀）→ 不计入下限；这是**有意的**：下限是防缩水的下界，不是完整性审计。
- **后置条件**：声明单调可信——只能比证据大，不能比证据小。
- **完成标志**：`files < 路径计数` 恒被拒；`files ≥ 路径计数` 恒通过（无论超容量与否）。

## UC-4 旧计划与旧台账照旧 `serves: FR-8, FR-9`

- **用例角色**：任何读到存量数据的调用方（工具、看板、旧窗口）。
- **前置条件**：计划或台账里没有 `footprint` 字段（存量数据、或压根没声明）。
- **交互流程**：
  1. 提交一份无 footprint 的计划 → 照旧通过，返回 `overCapacity=[]`；
  2. 对旧台账任务卡调任务树 → 该卡回显「未声明」；
  3. 看板展示当轮余量参考 → 那个值来自运行时投影，旁边写着「参考值，非门禁判据」。
- **异常流**：运行时投影不可得（服务未装配 / 无会话）→ 余量参考**不显示**，不猜 0、不报错。
- **后置条件**：`REQBOARD_SCHEMA_VERSION` 仍为 9，无迁移、无回填。
- **完成标志**：UC-4 全程零错误、零台账变更。
