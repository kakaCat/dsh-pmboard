# 需求说明（REQ-261006201508-5cb6 pm 插件工具面梳理与文档计数校准）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。
> 本需求不产界面：`sides` 为空（无前端/后端产品侧改动），故无原型产物。

## TL;DR <!-- serves: FR-1 -->

- **这是什么**：把 pm（reqboard）插件的 agent 工具面梳理成一份可信清单，并把全仓对不上号的计数与名单一次校准。
- **为什么现在做**：登记面 27 条，README 却说「13 个」「21 个」、表内实际 23 行、缺 4 个已注册工具，还多一个源码里不存在的 `reqboard_advance`；注册日志写 `(13)` 却只列 19 个。
- **做完得到什么**：一处事实源（`src/tools/registry.ts`）+ 一张逐条对齐的 README 工具表 + 一条机器校验——以后改工具忘了同步文档，测试会红并点名。

## 业务流程图 <!-- serves: FR-1 -->

```
窗口 agent / 人
   |
   +-- 读 README 工具表 ──▶ 「27 个工具，分 6 组」──▶ 知道该用哪个
   |                     （今天读到的是 13 / 21 / 23 三套互相矛盾的数）
   |
   +-- 新增一个工具 ──▶ src/tools/<X>Tool/ ──▶ registry.ts 补一条
                                                   |
                                                   +-- pnpm vitest run tests/readme-tool-face.test.ts
                                                         ├─ 表名集合 == 登记面 → 绿
                                                         └─ 差集非空 → 红，点名「缺哪个 / 多哪个」
```

## 产品定义 <!-- serves: FR-1 -->

pm 插件的**工具面说明书**：一页说清「这个插件给 agent 提供了哪些工具、每个工具干什么用、
什么时候能用、谁说了算」，且每个数字都能被一条命令复查。

**三要素检查清单**：

- [x] 说清楚"是什么"：README 工具表 + 源码计数口径，即插件对 agent 的契约面。
- [x] 说清楚"核心价值"：把散落多处、互相矛盾的旧数收敛为一处可机器校验的清单——省掉「照文档找工具却扑空」。
- [x] 说清楚"与现状的区别"：现状是 4 处计数各写各的（README 正文 / README 标题 / package.json / 源码日志），漏改不报错、门禁照样绿。

## 用户与角色 <!-- serves: FR-1 -->

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 窗口 agent（含新窗口接管者） | 接手一条需求，读 README / 提示词决定该调哪个 `reqboard_*` 工具 | README 少列 4 个已注册工具、多列 1 个不存在的 `reqboard_advance`，照它找工具会扑空 |
| 插件维护者（人） | 新增 / 删除工具后同步文档、注释与日志 | 同一份清单手写在多处，漏改不报错，只会让门禁「看着绿」 |
| 评审者 / 验收人 | 复核「工具面到底几个、哪几个」 | 三套数并存，无法一眼确认哪个是真的 |

### FR-1: README 工具表与登记面逐条对齐

**功能描述**：人打开 README 看到的工具表，与 `src/tools/registry.ts` 的 27 条登记**一一对应**，
并按用途分组，表头数字等于表内实际行数。

**详细说明**：

- **使用场景**：窗口 agent 或人需要「这个插件有哪些工具」的权威答案时，读 README 即可，不必翻源码。
- **操作流程**：
  1. 人打开 `README.md` 的「提供的工具」一节。
  2. 看到表头计数（27）与表内行数一致、且按 6 组分类：立项与自查 / 阶段推进与人工门 / 拆分与任务 / 自动实施链 / 归档 / 协作与环境。
  3. 每组的每条给：工具名 + 一句话作用；能一眼判断该用哪个。
- **预期结果**：
  - 表内出现 `reqboard_archive_amend` / `reqboard_handoff` / `reqboard_skill_install` / `reqboard_task_refs` 四个**今天缺的**已注册工具。
  - 表内**不再出现** `reqboard_advance`（源码无此工具名；实际入口是 `reqboard_task_run`，别名是 `reqboard_task_execute`）。
  - 表头计数 = 表内 `reqboard_` 行数 = 27。
- **边界条件**：
  - 表可以加列（如「合法阶段」「是否人工门」），**校验只认工具名集合与计数**，不锁排版。
  - 别名工具（`reqboard_task_execute`）保留在表中并标注「已弃用别名」，不算多列。

**验收标准**：

1. 执行 `grep -c '^| \`reqboard_' README.md` → 输出 27。
2. 执行差集命令 `comm -13 <(grep -o 'reqboard_[a-z_]*' README.md | sort -u) <(grep -o "toolName: 'reqboard_[a-z_]*'" src/tools/registry.ts | grep -o 'reqboard_[a-z_]*' | sort -u)` → **无输出**（登记面无缺项）。
3. 执行 `grep -c 'reqboard_advance' README.md` → 输出 0。

### FR-2: README 其余计数与 package.json 描述改为真实口径

**功能描述**：README 正文（第 13 行「13 个 pm 工具」）、目录树注释（第 107 行「13 个 Agent 工具定义」）
与 `package.json` 的 description（「13 个立项/拆分/验收工具」）统一改为与登记面一致的 27。

**详细说明**：

- **使用场景**：人从 README 开头或 npm 元信息快速了解插件规模时。
- **操作流程**：
  1. 人读 README 开头介绍，看到「27 个 pm 工具」。
  2. 人读 `package.json` description，看到同一个数。
  3. 与 FR-1 的表头、FR-3 的日志读数三处一致。
- **预期结果**：四处读数（README 正文 / README 表头 / README 目录树注释 / package.json）全部为 27，无一处残留 13 或 21。
- **边界条件**：只改数字与措辞，不改 description 的其余语义；不引入新字段。

**验收标准**：

1. 执行 `grep -n '13 个\|21 个' README.md package.json` → **无输出**。
2. 执行 `grep -n '27 个' README.md package.json` → 至少 3 处命中（README 正文 / 表头或目录树 / package.json）。

### FR-3: 源码内日志与注释的计数、名单对齐

**功能描述**：注册日志字符串与工具面出口文件头注释里的计数、名单，与 `apply()` 后真实注册的
27 个工具名一致。

**详细说明**：

- **使用场景**：插件装配期或排查「工具到底注册上没」时，看启动日志。
- **操作流程**：
  1. 人跑插件启动，读日志行 `agent tools registered (N): ...`。
  2. 日志里的 N 与后面列出的工具名个数一致，且都等于 27。
  3. 读 `src/tools/index.ts` 文件头注释，不再出现「13 → 9 收敛后的 9 个工具壳」这类过期表述。
- **预期结果**：
  - `src/index.ts` 的日志计数为 27，且紧跟的名单**列全** 27 个工具名（今天写 13、只列 19 个）。
  - `src/tools/index.ts` 文件头不再声明与导出数矛盾的旧计数。
- **边界条件**：日志仍为单行字符串、仍走 `logger.info`；不改日志级别与时机；不因刷长度而拆成多行（拆行可以，但不得漏名）。

**验收标准**：

1. 执行注册名单解析断言：日志中 `(N)` 的 N == 名单里 `reqboard_` 名字个数 == 27（用例内断言，见 FR-4）。
2. 执行 `grep -n '13 → 9' src/tools/index.ts` → **无输出**。

### FR-4: 机器校验（README 表 ↔ 登记面）

**功能描述**：新增一条可跑用例，从 `TOOL_REGISTRY` 派生期望值，断言 README 工具表与源码计数
不漂移；漂移时报错点名「缺哪个 / 多哪个」。

**详细说明**：

- **使用场景**：维护者改完工具或文档后跑测试；CI / 本地门禁。
- **操作流程**：
  1. 维护者执行 `pnpm vitest run tests/readme-tool-face.test.ts`。
  2. 用例读 `README.md` 文本，抽出 `reqboard_*` 工具名集合与表内行数。
  3. 与 `TOOL_REGISTRY.map(e => e.toolName)` 比较。
  4. 集合或计数不一致 → 失败信息直接列出差集与「登记面 N 条 / README M 条」。
- **预期结果**：
  - 正常状态：绿。
  - 人为删掉 README 里一行工具 → 红，消息含被删工具名。
  - 人为在 README 加一个未注册名 → 红，消息含该名字。
- **边界条件**：
  - **数字不得写死**：断言随 `TOOL_REGISTRY.length` 走（与 `tests/apply-wiring.test.ts`、`tests/tools-dispatch.test.ts` 同纪律）。
  - 只校验**集合与计数**，不校验表格排版、列顺序、分组归属。
  - 不联网、不写盘。

**验收标准**：

1. 执行 `pnpm vitest run tests/readme-tool-face.test.ts` → 全绿。
2. 临时删 README 一行 `reqboard_` → 重跑该用例 → 失败且消息点名该工具；还原后复绿。
3. 用例源码中 `grep -c '27' tests/readme-tool-face.test.ts` 不作为断言常量出现（计数从登记面派生）。

## 失败与并发路径 <!-- serves: FR-1 -->

本需求是**只读校验 + 文本校准**：没有写路径、没有状态机变更、没有产物落库。逐项如实交代。

| 路径 | 触发条件 | 系统行为 | 人看到什么 |
|---|---|---|---|
| 校验读不到文件 | `README.md` / `package.json` 缺失或被挪走 | 用例抛 `ENOENT`，判定**红**（不静默跳过） | 失败信息含具体路径 |
| 校验抽不到节标题 | README 的「提供的工具（N 个）」标题被改写 | 断言失败并提示契约形态 | 提示应有的节标题写法 |
| 校验发现漂移 | README 与登记面工具名集合不相等 | 失败并**逐条点名** | `README 缺：…` / `README 多：…` / 计数差 |
| 表内行数与计数不符 | 删了一行但没改表头 | 失败并同时报行数与计数 | `表内 26 行 / 登记面 27 条` |
| 注册日志未打印 | 装配没走到工具注册段 | 用例失败并提示「注册日志未打印」 | 不误判成「名单为空」 |
| 并发：同一窗口重复跑校验 | 连续执行 `pnpm test` | 幂等：只读、无状态、不写盘 | 读数逐次相同 |
| 并发：两个窗口同时改 README | 人 / agent 并行编辑同一文件 | 无锁；由 git 层合并，漂移由下一次校验判出 | 要么合并冲突，要么校验红——二者必有其一 |
| 状态机非法迁移 | —— | **不适用**：本需求不新增状态、不改状态机，也不触碰任何工具的入参与返回 | —— |
| 写入失败 / 半份产物 | —— | **不适用**：本需求不改任何工具的行为，也不写台账；除 README / package.json / 注释 / 日志字符串外无持久化写入 | —— |

## 边界（不做什么） <!-- serves: FR-1 -->

- **不改任何工具的行为**：入参 schema、返回体、错误码、副作用一律不动。
  理由：本需求只动文档与注释/日志字符串；行为变更需另立需求，混做会让「验收判什么」失效。
- **不新增 / 不删除 / 不改名任何工具**：27 个的集合保持不变（含保留已弃用别名 `reqboard_task_execute`）。
- **不动客户端看板视图与 HTTP 端点**：`src/client/**`、`src/http/**` 不在本次范围。
- **不做界面原型**：`sides` 为空（无端侧改动）；立项时自动物化的 `prototypes/` 骨架不作为产物登记，也不改写为正式原型。
- **不新造第二套事实源**：`registry.ts` 已是唯一手写登记面并有三条不变量测试，本次只**补校验**，不引入 YAML/JSON 清单或生成器。
- **不顺手做无关注释清理**：只改与工具计数、名单直接相关的四处。
