## T-1 README 工具名集合与登记面对齐 `serves: FR-1, FR-4`

- **测试目标**：文档里出现的每个 `reqboard_*` 名字都在登记面，登记面每个工具都在文档里。

- **测试步骤**：
  1. 读 `README.md` 全文，用 `` /`(reqboard_[a-z_]+)`/g `` 抽名字集合（**全文扫**，能抓到"多写的幽灵名"）。

  - 失败时消息逐条点名，而不是只报"长度不等"。
- **测试数据**：现行 README + 现行登记面（无需夹具文件）。

## 关键决策与取舍 `serves: FR-1, FR-4`

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 逆验证要不要留成自动化用例 | 把"删一行 → 红"写成自动化用例（临时改文件再改回） | 留成**人工逆验证步骤**（T-4/T-5/T-6） | 自动化用例需在测试里改写仓内文件，并发/失败中断会留下脏文件；逆验证的价值是"证明用例不是恒绿"，人工跑一次即可 |
| 日志断言方式 | 静态扫源码字符串（`grep TOOL_REGISTRY.length`） | 装配后**捕获真实日志行**（T-7） | 静态扫证明的是"代码长这样"，捕获日志证明的是"跑起来确实一致"；后者才是事实 |
| 测试文件拆分 | 全部塞进一个文件 | 校验用例（`readme-tool-face`）与日志用例（`registry-log`）分开 | 两者失败原因不同（文档漂移 vs 装配漂移），分开后失败信息定位更快 |

## 技术方案与亮点 `serves: FR-3, FR-4`

**本份相关的差异**：

| 差异 | 常规做法 | 本方案 | 为什么 | 可核验指向（文件 / 测试 / 评审） |
|---|---|---|---|---|
| 文档类需求的测试 | 「文档改完了，人看一眼就行」 | 给文档配**可跑的**判定（集合 + 计数 + 逆验证） | 文档漂移不报错正是本需求的起因；不配判定就等于没修 | `tests/readme-tool-face.test.ts` T-1/T-2 |
| 日志的测试 | 静态扫源码 | 装配后捕获日志行断言 | 只有跑起来才能证明"数字与名单同源" | `tests/registry-log.test.ts` T-7 |
| 防"恒绿" | 只写正向断言 | 每个关键断言配一条逆验证 | 正向断言无法区分"真的对"与"断言写空" | T-4 / T-5 / T-6 |

**技术栈与关键依赖**：vitest ^2.0.0（既有）+ `node:fs` / `node:url`（既有）；无新增依赖。
