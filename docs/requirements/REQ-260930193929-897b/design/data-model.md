# 数据模型 · REQ-260930193929-897b <!-- serves: FR-2 -->

> 一句话：本需求**不改任何数据模型**——它是纯读路径的根解析修正，不新增/不修改任何持久化结构。
> 本文档用「负空间声明」代替空壳：逐面列出被核对过的契约面与结论，便于复核者反证。

## 结论 <!-- serves: FR-2 -->

**无数据模型变更、无数据迁移、无回填。**

修复动作是「读文档之前把读取器的根校正到需求工作区」——只改变**去哪个目录读**，不改变**读到的结构**，也不写任何持久化状态。

## 逐面核对 <!-- serves: FR-2 -->

| 契约面 | 现状 | 本需求 | 依据 |
|---|---|---|---|
| `RequirementRecord.workspaceRoot` | 已存在，立项时选定（REQ-260929210741-30ae FR-6） | **不变**，仅新增读侧消费方 | 字段定义与默认值（含缺省回落）由 FR-6 定死，本次不碰 |
| 台账文件 `dsh-reqboard.json` | 既有 schema | **不变** | 不新增字段、不改字段语义、不写新记录 |
| `queue.json` | 既有结构 | **不变** | 根校正同时作用于 `queueRepo`，但只是让它指向需求工作区下同名文件，结构与文件名不动 |
| `docs/requirements/<REQ>/` 目录约定 | 既有 | **不变** | 不新增子目录、不改文件命名 |
| RTM yaml（`rtm-*.yml`） | 跟随 `docs.workspaceRoot()` 落盘 | **不变** | 本次不改落盘逻辑；读侧根修好后，RTM 与会话根的错位现象会一并消失 |
| HTTP state 响应字段 | 既有 | **不变** | 对外协议零变更（见 interfaces.md） |

## 为什么不需要迁移 <!-- serves: FR-2 -->

- **没有新增字段** → 无回填对象。
- **没有改变字段含义** → 存量数据无需重解释。
- **没有改变文件布局** → 存量需求的文档位置不变。

反过来说：如果本需求被实施成"新增一个字段来记录读侧根"或"搬迁文档目录"，那说明设计跑偏了——正确做法是**读取时解析**，而不是**持久化第二份真相**（本仓「两份真相必然漂移」的既有教训）。

## 存量数据的行为 <!-- serves: FR-2 -->

| 存量形态 | 预期行为 |
|---|---|
| 需求有 `workspaceRoot` | 读侧按该根解析（本需求修复目标） |
| 需求无 `workspaceRoot`（旧需求/默认） | 校正函数 no-op，沿用会话 cwd 口径——与修复前逐字一致 |
