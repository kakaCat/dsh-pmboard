# 用户场景 · REQ-260930193929-897b <!-- serves: FR-1, FR-2 -->

> 一句话：主场景是「跨工作区立项的需求，设计确认后自动推进」；另有两个场景专门用来证明**没有把闸门改松**。

## 场景 1：跨工作区立项的设计确认（主场景 · 修复目标） <!-- serves: FR-1 -->

**谁**：实施 agent（推进需求的人/agent）＋ 需求方（立项时把工作区选成非当前会话目录的人）。

**何时**：需求立项时 `workspaceRoot = B`，而当前会话工作区 `A ≠ B`；设计文档已落盘在 B、已登记、已落章。

```
   人点确认设计文档
          │
          ▼
   落章（确认动作本身一直有效）
          │
          ▼
   自动推进 设计 → 拆分：先核验文档集完整性
          │
   ┌──────┴───────┐
   │ 修复前        │ 修复后
   │ 按 A 读        │ 按 B 读
   │ ✗ 找不到       │ ✓ 找到 requirement.md + design/*.md
   │ 报「不存在」    │
   │ 推进被拦       │ 推进成功
   │ 需求卡在设计    │ 需求进入拆分
   └───────────────┘
```

**修复前**：返回体带 `gate_failure`，缺口写着「requirement.md 不存在（无法核验文档集策略与端侧/豁免声明）」；需求停在设计节点，只能人工调 `reqboard_move` 绕过人工门。

**修复后**：返回体无 `gate_failure`，需求自动进入 `decomposing`，无需任何人工绕过。

**为什么值得修**：报错文案与磁盘事实相反，会把人/agent 引向「去补写文档」——而那份文档其实已经确认过了，补写有**覆盖已确认产物**的风险。

## 场景 2：文档真的缺失（防放宽对照 · 不可删） <!-- serves: FR-2 -->

**谁**：复核者 / 维护者。

**何时**：担心「为了消除误拦，把闸门改成了永远放行」。

```
   同样 A ≠ B，但 B 下确实没有 requirement.md
          │
          ▼
   核验必须仍然失败
          │
          ▼
   gate_failure.code = design_doc_incomplete
   gaps 含「requirement.md 不存在」
```

**这一条为什么必须存在**：它是「修复没有退化成绕过」的唯一证据。
少了它，一个把 `docs.exists` 直接短路成 `true` 的假修复也能让场景 1 通过。

## 场景 3：拆分内容硬门不再静默放行（同根因的第二后果） <!-- serves: FR-1 -->

**谁**：复核者。

**何时**：设计文档里混进了任务表（本应在拆分阶段的产物）。

- **修复前**：硬门按会话根 `list(design/)` → 返回空数组 → **扫描不到任何文档** → 无声通过，混入内容溜进设计产物。
- **修复后**：按需求根扫描 → 命中任务表特征 → 被 `design_contains_decomposition` 拒。

注意这是与场景 1 **方向相反**的后果（一个误拦、一个漏放），同一行修法同时解决两者。

## 边界场景 <!-- serves: FR-2 -->

| 场景 | 预期行为 |
|---|---|
| 需求无 `workspaceRoot`（存量/默认） | 校正函数 no-op，沿用会话 cwd 口径，与修复前逐字一致 |
| 看板路由（无会话上下文） | 按需求记录解析根，不再依赖「最后一次会话残留的根」——此前该路径的根是不确定的 |
| 需求 `artifacts` 为空/未定义 | 闸门直接放行（`isLegacy`），不进入读盘分支 |
| 同一进程多需求并发交替 | 根为全局可变，可能互相覆盖——**已知限制，明确不在本需求**（见 architecture.md） |
