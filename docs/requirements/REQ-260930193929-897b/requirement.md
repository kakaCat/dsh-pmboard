## TL;DR

设计文档确认之后，看板本该自动把需求从「设计」推进到「拆分」，却被自己的完整性闸门拦住，报「requirement.md 不存在」。
真相是文件**好好地在盘上**且已确认——闸门跑去**会话工作区**找文档，而文档在**需求工作区**里；两个目录不是同一个时必然误报。
本需求让闸门按需求自己的工作区读文档：该放行的放行，真缺的照拦。

## 产品定义

**是什么**：需求看板的「文档集完整性闸门」在核验文档时，读盘根必须与被核验需求自己的工作区一致。

**核心价值**：让人工门只拦真正该拦的东西。闸门误报不只是"多提示一句"——它会把需求卡死在设计节点，并给出**方向错误的补救指引**（"requirement.md 不存在"会诱导 agent 去补写文档，有覆盖已确认产物的风险）。

**与现状的区别**：现状是「写入按需求工作区、读取按会话工作区」——同一条需求的两类操作不同根，属于口径不一致；修复后读写同根，且复用仓内**已经存在**的根解析收敛点，不新造第二套解析。

**三要素检查**：

- [x] 说清"是什么"——闸门读盘根按需求工作区解析
- [x] 说清"核心价值"——消除误拦与误导性报错，人工门不被误阻断
- [x] 说清"与现状的区别"——从"读写不同根"改为"读写同根 + 单一收敛点"

## 功能点（需求条款）

### 功能点清单

| 编号 | 功能（一句话概述） | 优先级 |
|------|------------------|--------|
| FR-1 | 设计确认后的自动推进按需求工作区核验文档集：需求方立项时选了工作区 B 后，确认设计即自动进入拆分，不再误报文件不存在 | P0 |
| FR-2 | 核验结论可自证：文档确实在需求工作区就放行、确实缺失仍照拦，读侧根解析统一走既有收敛点 | P0 |

### 功能点详细说明

- **FR-1: 自动推进按需求工作区核验文档集**——G2 文档集完整性闸门的四个读侧调用点在读盘前，先把文档读取器的根校正到 `requirement.workspaceRoot`，再核验文档集；根未校正时不得读盘并据此判「文件不存在」。
- **FR-2: 核验结论可自证（正反双向）**——需求工作区与会话工作区不同根时，文档落在需求工作区即通过、确实缺失仍被拦；读侧根解析复用仓内既有收敛点（`resolveWorkspaceRoot` / `syncWorkspaceRootForRequirement`），不新造第二套解析；报错文案结构不变。

**详细说明 · FR-1**

- **使用场景**：需求立项时工作区选成非当前会话目录（跨仓/多工作区），设计文档已落盘、已登记、已确认。
- **操作流程**：
  1. 人确认设计文档 → 系统落章。
  2. 系统自动推进「设计 → 拆分」，先核验文档集完整性。
  3. 核验按**需求工作区**读取 `requirement.md` 与 `design/` 目录。
  4. 文档在盘上 → 核验通过 → 需求进入拆分节点。
- **预期结果**：
  - 结果 1：返回体不再携带 `gate_failure`。
  - 结果 2：需求状态自动变为 `decomposing`，无需人工调用 `reqboard_move`。
- **边界条件**：
  - 边界 1：需求没有自己的 workspaceRoot（存量/默认）→ 沿用会话工作区口径，行为与现状一致。
  - 边界 2：无会话上下文（看板路由）→ 按需求记录解析，不依赖"最后一次会话"残留的根。

**验收标准 · FR-1**：

1. 构造 会话工作区 A ≠ 需求工作区 B，文档只落在 B → 发起设计确认 → 见到需求自动进入 `decomposing`。
2. 台账中该需求的设计产物 `confirmedAt` 齐全 → 见到不再出现「requirement.md 不存在」。
3. 需求无 workspaceRoot → 见到行为与修复前一致。

**详细说明 · FR-2**

- **使用场景**：维护者担心"为了消除误拦而把闸门放松成永远放行"。
- **操作流程**：
  1. 跑新增的回归测试（含正向与反向用例）。
  2. 正向：文档在需求工作区 → 放行。
  3. 反向：把需求工作区下的 `requirement.md` 删掉 → 仍报 `design_doc_incomplete`。
- **预期结果**：
  - 结果 1：两条断言同时存在、同时通过。
  - 结果 2：覆盖四条读侧路径各一次，口径一致。
- **边界条件**：
  - 边界 1：存量需求（产物记录为空）仍直接放行，不新增拦截。
  - 边界 2：反向用例不得被跳过——它是"没有修成绕过口"的唯一证据。

**验收标准 · FR-2**：

1. 跑回归测试 → 正向与反向用例均通过。
2. 反向用例中断言 `gate_failure.code = design_doc_incomplete` 且 `gaps` 含「requirement.md 不存在」。
3. 四条读侧路径各有用例覆盖。

## 边界（不做什么）

- **不做**：不改 G2 闸门的缺口判定规则与报错文案结构——本缺陷只错在**取数根**，判定逻辑本身正确；改判定会引入新的误判面。
- **不做**：不把 `reqboard_move` 纳入 G2 完整性门——它是**方向相反**的邻接缺陷（该拦却没拦），已单列于文末「邻接发现」，另行立项；同一需求里同时改"误拦"与"可绕过"会让验收无法判定。
- **不做**：不重构 `deps.docs` 共享单例模型，不改状态机、闸门目录（`GateCatalog`）、台账协议、`queue.json` 格式与前端渲染。

## 非功能需求

- **兼容性**：无会话上下文（看板路由、启动恢复、测试）时根解析行为不变；存量需求（`artifacts` 为空/未定义）仍直接放行。
- **可回滚**：纯读路径校正，无数据迁移；回滚 = 还原相关源文件，无数据风险。
- **可测性**：新增用例必须能在不启动 Web 的情况下跑通（构造 A ≠ B 两个临时目录即可）。
- **范围**：不新增网络请求、不新增依赖、不改 HTTP 协议形状。

## 验收标准（整体）

1. 构造 会话工作区 A ≠ 需求工作区 B，在 B 下落盘 `requirement.md` + `design/*.md`。
2. `reqboard_submit(kind=design)` 登记 → 人工确认设计文档（落章）。
3. 系统自动推进 → **不再出现** `gate_failure`，需求自动进入 `decomposing`（无需人工 `reqboard_move`）。
4. 把 B 下的 `requirement.md` 删掉，重复第 2–3 步 → 仍被 `design_doc_incomplete` 拦下，报错点名「requirement.md 不存在」。
5. `pnpm vitest run` 与基线对比无新增失败；`pnpm typecheck` 无新增错误。
6. 全仓 grep：G2 闸门读侧调用点在读盘前均经需求级根校正（防新增旁路）。

- **强依赖**：写侧已有正确先例 `SubmitArtifact` / `SubmitDesignArtifacts`（它们已做需求级二次校正），读侧对齐同一口径。
- **约束**：不改 `checkDesignCompletenessGate` 的判定规则与文案结构。
- **约束**：不改状态机、闸门目录、台账协议与前端。
- **约束**：报错文案的 `what / why / how` 三件套保留——它是本次事故的补救通道，属于优点。

## 档位依据

**L1 一句话目标 + 可证伪判定标准**

- **目标**：让 G2 文档集完整性闸门按被核验需求自己的工作区读盘，消除「文件在盘上却报不存在」的误拦。
- **可证伪判定**：构造 A ≠ B 两个工作区，文档只放 B；确认设计后若无 `gate_failure` 且状态自动变为 `decomposing` 即达标；把 B 下的 `requirement.md` 删掉后仍被拦，则证明**没有**被放松成永久放行。

**L3 轻路径依据 + 单向升级**

- **为什么可以走轻档**：
  - 改动面小——四个读侧调用点接线到既有收敛点，无新组件、无新依赖、无新接口。
  - 无新决策点——修复方向由现状唯一确定（写侧已给出正确先例，读侧照抄同口径）。
  - 不动架构、不动数据模型——`deps.docs` 单例模型与 `queue.json` 均不改。
- **单向升级信号（出现任一即停手并升级重档，不许反向降级）**：
  - 若要一并处理 `reqboard_move` 不读盘的邻接缺陷（那是第二个决策点 + 会改变闸门强度）；
  - 若要引入"多需求并发时单例根安全切换"，即动架构。

**L4 批准闸门 + 下一步**

下一步：design —— 用 `reqboard_ask_confirm(target=artifact, kind=requirement)` 交棒；未获批准不得进入。

**L5 轻档 ≠ 无产物**：本 `requirement.md` 已落盘，将用 `reqboard_submit(kind=requirement)` 登记后请人确认。

## 邻接发现（本需求不含，建议另立）

**`reqboard_move` 完全不读盘，因此可以绕过 G2 完整性门。**

- `MoveRequirement` 只调用 `assertArtifactGates`（纯台账态判定，不读任何文件），从不调用 `checkDesignCompletenessGate`。
- 因此代码注释所称「design→decomposing 四条转移路径统一调用 G2 完整性门」**目前不成立**。
- 这解释了本次事故为何能靠 `reqboard_move` 绕过：**不是它校正对了，是它根本没取数**。
- 它与本缺陷方向相反（本需求修"不该拦却拦了"，它属于"该拦却没拦"），故**不在本需求范围**。
- 建议：另立 bug，或在 design 阶段裁定后纳入后续需求；无论哪种，都不应静默略过。
