## TL;DR

让「读文档的闸门」按需求自己声明的工作区读盘：新增**一个**统一入口做需求级根校正，把两个读盘闸门共 **7 处**调用点全部接上去，再用**正反双向**测试锁住——该放行的放行、该拦的照拦。

```
改动后数据流：

   会话入口 / 看板入口
        │   不再依赖「最后一次会话残留的根」
        ▼
   applyRequirementWorkspaceRoot(deps, req)      ← 新增：唯一入口
        │   req.workspaceRoot 非空 → docs / queueRepo 同时校正
        ▼
   读盘闸门（完整性门 4 处 + 拆分内容硬门 3 处）
        │
        ├── 文档在需求工作区 ──► 通过 ──► 自动推进
        └── 文档确实缺失     ──► 仍被拦（强度不放松）
```

## 本需求自身的现场复现（立据补充）

19:45 在本需求上**真实复现**：设计确认落章成功（5 份设计产物 `confirmedAt` 齐全），自动推进却被拦，报「requirement.md 不存在」——而该文件就在盘上（13283 bytes），且落在需求自己声明的 `workspaceRoot` 下。

**新证据（修正原描述）**：本次 会话 cwd == 需求 workspaceRoot（都是本仓）。所以触发条件**不止**「跨工作区立项」；真正条件是**宿主级 `deps.docs` 单例的根被别的窗口改过**（本机同时存在 `dsh-pmboard` 与 `dsh-notice-webhook` 两个工作区的会话）。

**同根因的更大面**：根不对时，**所有**读盘类门禁都会退化，而且方向不一致：

| 门禁 | 根错误时的行为 | 性质 |
|---|---|---|
| 完整性门（4 处） | 报「文件不存在」 | 误拦（fail-closed） |
| 拆分内容硬门（3 处） | `list(design/)` 返回空数组 → 扫描不到任何文档 | **静默放行**（fail-open） |
| FR 覆盖门（提交计划时） | 读不到 `requirement.md` → 提前 `return undefined` | **静默放行**（fail-open） |
| 需求文档格式门 | 同上，提前放行 | **静默放行**（fail-open） |

本需求只修**取数根**（一处根因），四个门禁的正确性同时恢复：**不新增判定、不放宽强度**。

## 任务明细

### t1 · 把「按哪个工作区读文档」收敛成一个统一入口

- **在做什么**：新增一个函数作为「需求级根校正」的唯一实现，并让既有写侧函数改为委托它。
- **解决什么问题**：现在只有写入侧会按需求工作区校正根，读取侧各写各的——根的口径没有单一事实源，新增读盘闸门必然再漏。
- **得到什么结果**：读写两侧共用一个入口；写侧行为与改造前逐字一致（不引入任何行为变化）。
- **验收**：既有 workspace-root 相关用例全绿；`rg` 确认新函数已导出且写侧走委托；`pnpm typecheck` 无新增错误。

### t2 · 让七个读文档的闸门都走这个统一入口

- **在做什么**：在两个读盘闸门的 7 处调用点，读盘之前先调用 t1 的入口。
- **解决什么问题**：根不对时，完整性门误拦、拆分内容硬门静默放行——同一个根因，两个相反方向的坏结果。
- **得到什么结果**：闸门判定只由需求自己声明的 `workspaceRoot` 决定，与窗口无关。
- **验收**：定向用例（会话根 ≠ 需求根、文档在需求根）经四条通道均放行；`rg` 复查 7 处调用点上方都有校正调用；`pnpm typecheck` 通过。

### t3 · 用正反两组测试锁住：该放行的放行、该拦的照拦

- **在做什么**：新增测试文件，覆盖正向（文档在需求根 → 放行）、反向（需求根下确实没有 → 仍拦）、四条通道、以及「7 处调用点无新增旁路」的聚合断言。
- **解决什么问题**：只有正向断言，把 `exists` 短路成 `true` 的假修复也能绿；只有反向断言，什么都不做也能绿——两个方向的假修复都得挡住。
- **得到什么结果**：两个方向的假修复都会被当场判死。
- **验收**：`pnpm vitest run tests/design-gate-workspace-root.test.ts` 全绿，且其中**反向用例断言** `gate_failure.code = design_doc_incomplete`；全量 `pnpm vitest run` 与基线对比无新增失败。

### t4 · 确认老需求与看板路径不受影响，并写好回滚方式

- **在做什么**：保证需求未声明 `workspaceRoot` 时校正为 no-op；确认看板无会话上下文路径按需求记录解析；写清回滚步骤。
- **解决什么问题**：怕为了修读取侧而把存量老需求或看板路径改坏。
- **得到什么结果**：存量行为逐字不变；出问题可按说明回滚，无数据风险。
- **验收**：存量需求（无 `workspaceRoot`）用例通过且行为与修复前一致；看板通道用例通过；`pnpm typecheck` 通过；回滚步骤可执行。
