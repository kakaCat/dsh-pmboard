# 用例走查（REQ-261006175040-12d4）

## UC-0 角色与场景总览 `serves: FR-1, FR-5, FR-6`

| 角色 | 什么场景 | 改前看到什么 | 改后看到什么 | 差别 |
|---|---|---|---|---|
| 人（需求 owner / 评审者） | 打开看板扫一遍，找「哪条在等我点确认」 | 四门恒红 `✗` + `产物 0/6`；无确认按钮 | 按台账事实三态 chips + `门 c/t`；待确认门给按钮 | 从「看不出来」到「一眼看出卡在哪道门、可直接落章」 |
| 人（设计期） | 6 份设计文档待确认 | 设计门同样恒红；只能等 agent 弹框 | `⏳设计文档` + 「确认产物（全部 6 份）」 | 成组确认在卡面可完成，份数写在按钮上 |
| 人（验收期） | 想确认验收材料交没交 | 交没交都显示「待验收材料」 | 未交 →「待验收材料」；已交 →「待人工审核」 | 谎报纠正 |
| 窗口 agent | 看板面与 `reqboard_status` 对照产物状态 | 页面与台账各说一套 | 页面读数与门禁同源（服务端同一份判定） | 人机对同一事实 |
| 宿主运维 / 维护者 | 插件版本与台账版本不同步（旧服务端 / 旧记录） | 现状是恒红（无法区分） | 读数不可得时整块不渲染，不冒充缺失 | 降级可辨识、不谎报 |
| 开发者 | 改卡面渲染或新增门读数 | 既有单测用全量记录夹具，跨缝缺陷测不出 | 摘要形状夹具常驻 + 读放大 / 载荷上界断言 | 同类缺陷下次必红 |

## UC-1 扫看板定位「在等我点确认的门」 `serves: FR-1, FR-3`

- **前置条件**：至少两条在途需求——一条四门全落章（`REQ-261006130057-7a43` 这类）、一条需求文档已登记未落章。
- **步骤**：打开看板 → 不点进详情，只扫泳道卡面 → 读四门 chips 与派生行。
- **可观察结果**：
  - 前者：`✓需求文档 ✓设计文档 ✓拆分计划 ✗验收材料` + `门 3/4`；**不出现** `产物 0/6`。
  - 后者：`⏳需求文档`（可点）+ `门 0/4`。
- **走查**：1280 与 900 两档各一遍；chips 换行时派生行仍在 chips 之后（DOM 顺序与 `renderReqCard` 一致）。

## UC-2 卡面点「确认产物」落章 `serves: FR-2, FR-4`

- **前置条件**：需求处于 brainstorming，需求文档已登记未落章（G1 在等）。
- **步骤**：卡面点「确认产物」→ 服务端落章 → 看板下一次刷新（≤1 个轮询周期，20s）重取 `/state`。
- **可观察结果**：chip 由 `⏳需求文档` 变 `✓需求文档`；`门 0/4` 变 `门 1/4`；按钮消失（该门已 `confirmed`）。
- **边界**：门为 `missing`（无产物）或 `confirmed` 时按钮**不渲染**——不给点了必被代码级拒绝的假按钮。

## UC-3 设计期成组确认（多份设计文档） `serves: FR-1, FR-4`

- **前置条件**：需求在 design 期，`design/` 下 6 份设计文档已登记，其中 1 份未落章。
- **步骤**：看卡面 → 读设计门 chip 与按钮文案。
- **可观察结果**：设计门为 `⏳设计文档`（**不是** `✓`：任一份未落章即整门待确认）；按钮文案
  「确认产物（全部 6 份）」——`count` = 该 kind 产物条数，由服务端读数带来，客户端不自己数。
- **边界**：6 份全部落章后该门才变 `✓设计文档`。

## UC-4 拆分期看计划状态 `serves: FR-5`

- **前置条件**：需求在 decomposing；计划已提交未批（另造一条已批的）。
- **步骤**：扫卡面标签行。
- **可观察结果**：未批 → 「计划待批」；已批 → 「计划已批」；被退回 → 「计划被退」。
- **边界**：记录里没有计划（未提交）→ 该 chip **不渲染**（不是渲染成「计划待批」）。

## UC-5 验收期材料状态 `serves: FR-5`

- **前置条件**：两条 accepting 需求——一条未交验收材料、一条已交待审。
- **步骤**：扫卡面标签行。
- **可观察结果**：未交 → 「待验收材料」；已交 → 「待人工审核」。
- **读数来源**：`verification` 门的 `status`（`missing` = 未交；`pending`/`confirmed` = 已交）。
  **不新增第四枚摘要键**——门的 kind 集合已由分类流程决定，验收门在全部六类里都生效。

## UC-6 归档后「归档材料待补」不再误报 `serves: FR-5`

- **前置条件**：一条 archived 需求，归档材料已备（有 archive 记录或 `kind=archive` 产物）。
- **步骤**：切到列表视图，看标题行的预警 chip。
- **可观察结果**：已备 → **不出现**「归档材料待补」；真未备 → 仍出现（判据不放松）。
- **口径同源**：`archivePrepared` 与 `domain/status/Predicates.closingGapOf` **同一谓词**
  （`archive` 记录在册 ∨ `kind=archive` 产物在册）；摘要层不再回读 `req.archive` / `req.artifacts`。

## UC-7 读数不可得（旧服务端 / 旧记录） `serves: FR-6`

- **前置条件**：新前端 + 旧服务端（摘要无 `gates`），或旧记录未回填读数。
- **步骤**：打开看板与列表视图，逐块看卡面。
- **可观察结果**：chips 行、派生行、确认按钮**整块不渲染**；其余卡面（进度、时间、窗口 chip、操作按钮）照常。
  页面上**不得**出现 `✗` 或 `产物 0/6`——「读不到」与「真缺失」必须可区分（本次事故的教训）。
- **边界**：门读数整块缺省才算不可得；单门缺项按异常处理并只告警，不猜。

## UC-8 维护者：跨缝夹具与读放大上界 `serves: FR-2, FR-7`

- **前置条件**：开发者改卡面渲染或摘要装配。
- **步骤**：跑 `tests/card-face-summary-shape.test.ts`（夹具只用摘要字段）与
  `tests/state-no-bigfield-read.test.ts`（读放大桩计数）。
- **可观察结果**：夹具里没有 `artifacts`/`plan`/`verification`/`archive` 也能渲染出正确门状态；
  预热一次后连续 3 次 `/state` 对四件大字段对象的读取**增量为 0**（读数在内存索引里）。
- **边界**：写路径（登记 / 落章 / 批准）顺带刷新读数，零额外 IO——不因修复引入新的读放大。
