这是本次事故的教训 —— 旧实现把「首屏读不到大字段」渲染成了「产物缺失」，于是每条需求都恒红、 红灯不再携带信息。降级口径：以「键是否存在」判可得性，不可得即整块不渲染（chips 行 / 派生行 / 按钮**各自独立**判定）； 单个门读数缺失（而非整块缺失）视为异常，按不可得处理并只告警，不猜。 对照 B-3：门读数**存在**且某门真缺失时，那一门照常显示红色 ✗（真缺失与读不到必须可区分）。

底部操作行 按真实 cardActions(req) 的**状态分支**逐字输出，而不是三张卡统一画「→ 验收」： B-1（brainstorming）= → 设计 / 退回 / 取消；B-2（design）= → 拆分 / 退回重谈 / 取消； B-3 / A / D（implementing）= → 验收 / 取消。统一画「→ 验收」会在需求分析期的卡上造出一个点了必被 状态机拒绝的假按钮 —— 与本需求 FR-4「不给假按钮」同一条纪律。此行的文案与 title 与 artifacts.ts 逐字一致。
