# 需求说明（REQ-261006175040-12d4 修看板卡面产物门误报「缺失」与产物 0/N）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。
> 本轮**原型先行**：卡面三态小样在 `prototypes/card-gates.html` 上做可视评审（`prototypes/INDEX.md`
> 标唯一 authoritative），评审意见逐条落 D-x 后才进设计。

## TL;DR <!-- serves: FR-1 -->

- **这是什么**：修看板泳道卡面的**产物门读数**——现在四道门恒红 ✗、派生行恒「产物 0/6」，与台账事实相反。
- **为什么现在做**：根因是「首屏只发摘要」（`GET /state` 不再下发 `artifacts`/`plan`/`verification`/`archive`
  这四个大字段），而卡面仍从这些字段算门状态；连带把卡面「确认产物」入口整条打死——那是 G1/G2 看板侧**唯一**的确认入口。
- **做完得到什么**：四门 chips 与「门 N/M」按台账事实渲染，卡面确认按钮恢复可用，计划/验收 chip 不再沉默；
  且 `/state` 载荷不因这次修复回涨（门读数进内存索引，不进大字段）。

## 业务流程图 <!-- serves: FR-1 -->

```
人打开项目看板
   |
   +-- GET /state ──▶ 每条需求摘要（含门读数 gates[]）──▶ 泳道卡面
   |                                                         |
   |                                                         +-- 四门 chips：✓ 已确认 / ⏳ 待确认(可点) / ✗ 缺失
   |                                                         +-- 派生行：门 3/4
   |                                                         +-- 计划 chip：计划待批 / 计划已批 / 计划被退
   |                                                         +-- ⏳ 点击 ──▶ 确认产物 ──▶ 落章 ──▶ 本行刷新
   |
   +-- 点开卡片 ──▶ GET /requirements/:id（全量记录）──▶ 详情页（本次不动）
```

## 产品定义 <!-- serves: FR-1 -->

看板卡面是「一眼读懂这条需求走到哪、卡在谁手上」的主视图。本需求的判定标准只有一条：
**卡面上任何一处门状态读数都必须与台账事实一致；读数不可得时宁可不显示，也不显示成「缺失」。**

现状与之相反：四门恒红、派生行恒 `0/6`，于是红灯不再携带信息——真缺哪一份、真卡在哪道门，
人在卡面上看不出来（本次截图就是人肉发现的）。

## 用户与角色 <!-- serves: FR-1 -->

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 人（需求 owner / 评审者） | 扫一遍看板，判断「哪条在等我点确认」 | 四门恒红 + 产物 0/6，红灯无信息量；真欠哪份产物看不出来 |
| 窗口 agent | 用 `reqboard_status` 看自己名下需求的产物状态，同时看板面 | 页面与台账各说一套时，人与 agent 对不上同一个事实 |

### FR-1: 卡面四门 chips 按台账事实渲染三态

**功能描述**：人在看板扫卡面时，四道门的 chip 反映该需求产物的**真实登记与落章状态**。

**详细说明**：
- **使用场景**：人打开看板，判断哪条需求在等确认、哪条已经走完前面几道门。
- **操作流程**：
  1. 人打开项目看板（或 20s 轮询自动刷新）。
  2. 卡面按分类生效门渲染 chip：feature 为 需求文档 / 设计文档 / 拆分计划 / 验收材料 四道。
  3. 每道门取三态之一：`✓ 已确认`（绿，产物已落章）/ `⏳ 待确认`（橙，已登记未落章，可点）/
     `✗ 缺失`（红，未登记任何该 kind 的产物）。
- **预期结果**：`REQ-261006130057-7a43`（需求文档、6 份设计文档、拆分计划均已登记且已落章；验收材料未登记）
  显示 `✓需求文档 ✓设计文档 ✓拆分计划 ✗验收材料`，而不是四红。
- **边界条件**：
  - `design` 是**成组确认**：多份设计文档只要有一份未落章，该门即 `⏳`（不是 `✓`）。
  - 分类跳过某些门（bug / refactor / spike / doc / chore）时，卡面只渲染该分类生效的门。
  - 已归档需求（archived）不进门 chips 判定范围之外的任何新逻辑。

**验收标准**：
1. `REQ-261006130057-7a43` 的卡面 → 前三门绿 ✓、验收门红 ✗（对照其 `artifacts.json`）。
2. 造一条 brainstorming 需求且需求文档已登记未落章 → 需求文档门为 ⏳ 且可点。
3. 落章后不重开页面 → 下一次看板刷新该门变 ✓。

### FR-2: 门读数由服务端计算、随首屏摘要下发

**功能描述**：客户端不再自己算门状态；`GET /state` 的每条需求摘要带上该需求的门读数与三枚有界状态。

**详细说明**：
- **使用场景**：任何一次看板首屏/轮询请求。
- **操作流程**：
  1. 服务端在摘要投影处算出该需求的生效门读数（kind + status）与计划/验收/归档状态。
  2. 读数随 `GET /state` 的 `requirements[]` 下发，**每需求有上界**（≤ 生效门数 ≤ 5 项 + 3 枚标量）。
  3. 客户端卡面只渲染读数，不做门状态推断。
- **预期结果**：客户端源码里不再存在「读 `req.artifacts` 判门状态」的路径；`/state` 载荷增量与需求数线性、
  与 `artifacts` / `comments` / `verification` 的体积**无关**。
- **边界条件**：
  - 门清单与「分类生效门」的唯一事实源仍是 `shared/protocol.ts` 的 `ARTIFACT_CONFIRM_GATES` / `flowProfileFor`，
    不在服务端另抄一份。
  - 大字段仍**不得**回首屏摘要（既有 `BIG_FIELD_KEYS` 断言继续成立）。
  - `/state` 每次请求**不得**新增对大字段文件的读取：读数在内存索引里，写路径（登记/落章）顺带刷新。

**验收标准**：
1. `curl -s '<board>/state'` → 目标需求摘要里带门读数与三枚状态，且不含 `artifacts`/`plan`/`verification`/`archive` 键。
2. 桩计数测试：连续 3 次 `/state` 不新增大字段文件读取。
3. 同一批需求改动前后 `/state` 体积差 ≤ 5%。

### FR-3: 派生读数改为「门 已确认/生效门总数」

**功能描述**：卡面那行派生读数从「产物 N/M」改为「门 已确认/生效门总数」（如 `门 3/4`）。

**详细说明**：
- **使用场景**：人想知道「还差几道门」，而不是产物条数。
- **操作流程**：卡面用与 chips **同一份**门读数算出分子（`confirmed` 门数）与分母（生效门总数），渲染成一行。
- **预期结果**：`REQ-261006130057-7a43` 显示 `门 3/4`；不再出现 `产物 0/6`。
- **边界条件**：
  - 旧口径 `present = 产物条数` 必须删除——它会把 83 条产物登记（含 `task_detail`/`task_output`）当分子，
    与分母「必备种类 6」不同量纲，即使拿到全量记录也必然说谎。
  - 生效门总数 = 0（无门的分类/终态）→ 该行不渲染。
  - 既有实现的**第二段**「N 门待确认」一并删除：它与 chips 的 ⏳ 状态信息重复（实际同时最多只有一个门待确认），
    本行只留 `门 c/总数` 一种读数。设计阶段若认为该段不可替代，须退回本阶段改 FR-3，不得在设计里静默加回。

**验收标准**：
1. 目标需求卡面出现 `门 3/4`；**卡面渲染输出与客户端源码**里不再出现 `产物 N/M`
   （`renderArtifactDerived` 的旧口径删除；本文件里作为缺陷描述提及不计）。
2. 无门分类（如 chore 之外的极端情况）→ 该行整行不渲染（不是 `门 0/0`）。

### FR-4: 卡面「确认产物」入口恢复可用

**功能描述**：当前生效门有产物且未落章时，卡面渲染「确认产物」主按钮，点击即落章。

**详细说明**：
- **使用场景**：人在看板上直接确认需求文档（G1）/ 设计文档（G2），不必等 agent 弹框。
- **操作流程**：
  1. 卡面按门读数判定「当前生效门是否为待确认」。
  2. 是 → 渲染主按钮；`design` 门文案写明份数（`确认产物（全部 N 份）`）。
  3. 人点击 → 走既有 `confirm-artifact` 通道落章 → 卡面刷新。
- **预期结果**：`confirm-artifact` 动作在生产环境**真的会渲染**（现状：全仓只有卡面一处渲染它，
  而该处恒不渲染 ⇒ G1/G2 看板侧确认入口完全失效）。
- **边界条件**：
  - 无产物（该门 `missing`）或已落章（`✓`）→ **不渲染**按钮（不给点了必被代码级拒绝的假按钮）。
  - 写路径、权限、落章语义一概不改（只改「读数从哪来」）。

**验收标准**：
1. brainstorming 需求（需求文档已登记未落章）→ 卡面出现「确认产物」，点击后 chip 变 ✓、门数 +1。
2. 已落章 / 无产物的门 → 卡面没有该按钮。

### FR-5: 计划 / 验收 / 归档 chip 同样由摘要读数驱动

**功能描述**：卡面的计划 chip（计划待批 / 已批 / 被退）、验收 chip（待验收材料 / 待人工审核）、
归档 chip（待归档材料 / 待归档）按台账事实渲染。

**详细说明**：
- **使用场景**：人扫卡面就知道「这条在等人批计划」「这条验收态但还没交材料」。
- **操作流程**：摘要携带计划状态、验收材料是否已提交、归档材料是否已备，卡面据此渲染对应 chip。
- **预期结果**：拆分态且计划未批 → 「计划待批」；批准后 → 「计划已批」；accepting 且未交材料 → 「待验收材料」，
  交了 → 「待人工审核」；done 且未备归档材料 → 「待归档材料」。
- **边界条件**：现状是 `plan`/`verification`/`archive` 缺失 → 计划 chip 恒不出现、accepting 卡恒谎报「待验收材料」；
  本次一并改由读数驱动（数据不可得时见 FR-6 的降级口径）。

**验收标准**：
1. 造一条 decomposing 需求且计划未批 → 卡面出现「计划待批」；批准后变「计划已批」。
2. accepting 且未交验收材料 → 「待验收材料」；提交后 → 「待人工审核」。

### FR-6: 读数不可得时降级为「不显示」，不冒充「缺失」

**功能描述**：摘要里没有门读数（旧服务端）或读数键缺省（旧记录未回填）时，卡面**不渲染**该项，
而不是渲染成 `✗ 缺失` / `门 0/N`。

**详细说明**：
- **使用场景**：宿主插件版本与台账版本不同步、或读数尚未回填。
- **操作流程**：卡面以「键是否存在」判读数可得性；不可得即整块不渲染（chips 行 / 派生行 / 按钮各自独立判定）。
- **预期结果**：读不到 ≠ 缺失——这是本仓「缺失 ≠ 0」的一贯口径；本次事故的教训正是把「读不到」渲染成了「缺失」。
- **边界条件**：单个门读数缺失（而非整块缺失）视为异常，按不可得处理并只告警，不猜。

**验收标准**：
1. 夹具喂一条**不带门读数**的摘要 → 卡面无 chips 行、无派生行、无确认按钮，且**不出现** `✗` 或 `产物 0/6`。
2. 夹具喂「门读数存在但某门 `missing`」→ 该门正常显示红色 ✗（真实缺失与读不到必须可区分）。

### FR-7: 回归防线（跨缝夹具 + 载荷与读放大上界断言）

**功能描述**：用测试锁死「摘要形状 → 卡面渲染」这条缝，并锁死载荷/读放大上界。

**详细说明**：
- **使用场景**：本次事故的成因是既有单测**直接用全量记录造夹具**，把「首屏只有摘要」这条缝整个绕过去了。
- **操作流程**：
  1. 新增跨缝用例：夹具只提供摘要字段（`id`/`title`/`status`/`category`/门读数…），断言 chips、
     派生行、确认按钮的渲染结果。
  2. 新增读放大用例：桩计数断言 `/state` 不新增读大字段文件。
  3. 新增载荷上界用例：断言摘要键集里没有大字段（既有断言）+ 门读数长度 ≤ 5。
- **预期结果**：把「夹具不得喂全量记录」变成机械事实；本次这类缺陷下次必红。
- **边界条件**：既有 `tests/card-face.test.ts` 的全量夹具用例保留（它测的是「有全量记录时的渲染」），
  但**必须**再有一条摘要形状的用例，两者不可互相冒充。

**验收标准**：
1. 新增用例在改动前必红（可用 `git stash` 复核）、改动后必绿。
2. `pnpm typecheck` 退出码 0；`pnpm baseline:check` 失败用例集合差为空。

## 边界（不做什么） <!-- serves: FR-1 -->

- **不做**：不动需求详情页的取数与渲染——详情页走 `GET /requirements/:id` 全量记录，本来就对。
- **不做**：不改落章 / 确认的写路径、权限、门禁判定（G1~G4 的裁决条件、成组确认语义、谁能确认）。
- **不做**：不把大字段（`artifacts`/`plan`/`verification`/`archive`）塞回首屏摘要——只补**有界派生读数**。
- **不做**：不改泳道、甘特、DAG、详情 Tab 的任何视觉与布局。
- **不做**：不给卡面新造「进度百分比」等第二套读数口径（本次只修既有读数的来源与口径）。
- **不做**：不改三态 chip 的**配色**。实测（WCAG 相对亮度公式，10px 正文）绿 2.76:1 / 橙 3.39:1 / 红 3.81:1，
  三者均低于 4.5:1；但三态另有 ✓ / ⏳ / ✗ 字形与中文标签，不靠颜色单独传达信息（可达性未失效）。
  配色调整属**新的视觉语言决策**，另立项处理——塞进本次「数据来源修复」会让一次变更同时承担两件事、
  无法分别回滚。本需求只保证「颜色含义与台账事实一致」。

## 非功能需求 <!-- serves: FR-2 -->

- **载荷上界**：`/state` 每条需求新增读数 ≤ 生效门数（≤ 5）× (kind + status) + 3 枚标量；
  实测目标 ≤ 250 字节/条；载荷随需求数线性，与 `artifacts`/`comments`/`verification` 体积无关。
  测法：改动前后各取一次 `/state`，比总体积与单需求 JSON 长度。
- **读放大**：`/state` 每次请求**不得**新增对大字段文件（`artifacts.json`/`plan.json`/`verification.json`/`archive.json`）
  的读取；门读数在内存索引里，写路径顺带刷新。测法：桩计数（FR-7 用例 2）。
- **兼容**：旧服务端（摘要无门读数）与旧记录（未回填）→ 卡面不渲染该项（FR-6），不报错、不空白整卡。
- **可回滚**：改动集中在摘要投影 + 卡面渲染 + 客户端 bundle；回滚 = `git revert` + `pnpm build:client`，
  台账数据零改动（本需求不写业务数据）。
- **规范**：`pnpm typecheck` 退出码 0；`pnpm baseline:check` 失败用例集合差为空（C-14/C-15）。

## 验收标准（整体） <!-- serves: FR-1 -->

1. 打开看板：`REQ-261006130057-7a43` 卡面显示 `✓需求文档 ✓设计文档 ✓拆分计划 ✗验收材料` + `门 3/4`，
   且**不再出现** `产物 0/6`。
2. 造一条 brainstorming 需求（需求文档已登记未落章）：卡面出现 `⏳需求文档` 与「确认产物」按钮；
   点击后 chip 变 `✓`、门数由 `0/4` 变 `1/4`，无需重开页面。
3. 拆分态计划未批 → 卡面出现「计划待批」；批准后变「计划已批」。
4. accepting 且未交验收材料 → 「待验收材料」；提交后 → 「待人工审核」。
5. 载荷对照：同一批需求改动前后 `/state` 体积差 ≤ 5%，且无对大字段文件的每请求读取。
6. 回归：新增摘要形状用例改动前必红、改动后必绿；`pnpm typecheck` 0；`pnpm baseline:check` 差集为空。
7. 原型对照：三态卡面出图与 `prototypes/card-gates.html`（authoritative）逐区块一致，人评审通过。

## 关键决策与取舍

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 门读数从哪来 | 卡面逐卡拉轻量端点（每次轮询读 `artifacts.json`、渲染前空档） | 摘要补有界门读数（服务端算、内存索引缓存） | D-2；看板 20s 轮询一次，把读放大留在客户端不可接受 |

## 依赖与约束 <!-- serves: FR-2 -->
