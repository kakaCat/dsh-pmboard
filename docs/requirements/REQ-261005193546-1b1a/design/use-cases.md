## 用例 3 · 活卡依赖了一张已取消卡，它仍然可开工 <!-- serves: FR-1 -->

| 项 | 内容 |
|---|---|
| 角色 | 干活的人 / 自动链调度（认领任务的人与系统） |
| 触发 | 活卡 x 的唯一未完成前置 y 被取消；x 自身处于 `todo` |
| 前置 | 台账里 y 为 `canceled`，x 的 `dependsOn` 含 y |
| 完成标志 | x **出现在可开工集合里**（画布亮绿点、能被认领开工），而不是被永久挡住 |
| 后置条件 | x 的层号与「把 y 那条边删掉后重算」一致（不掉层）；写路径能正常落盘（不被 V-5 假就绪拒掉） |

**主流程**

1. y 被取消（人工门）。按 D-8，y 永远不会完成，因此 x 依赖 y 的那条边**按已满足处理**（`isDependencySatisfied`：`undefined | done | canceled` = 满足）。
2. `splitDependencyEdges(x, byId)` 把该边落进 `satisfied` 桶；**唯一阻塞桶是 `pending`**，于是 `isReadyTask(x, byId)` 为真。
3. `/state` 出参里 `ready[reqId]` 含 x；画布给 x 画出可开工绿点（`ready-dot`）。
4. 人/调度认领 x 并开工——**改前这一步做不到**（见「改前」列）。

**改前为什么会卡死（核过的四处漂移）**

| # | 位置 | 「依赖是取消卡」时判定 | 结论 |
|---|---|---|---|
| ① | `src/application/use-cases/queue-access.ts:59 readyTasksOf` | 视为**已满足** | D-8 正确口径（语义源） |
| ② | `src/shared/protocol.ts:1817 readyTasks`（被 `/state` 用，`:99-101`） | 视为**未满足** | **漂移** → x 不进 `ready` → 无绿点 |
| ③ | `src/domain/queue/topology.ts:131 computeReady`（落盘 `ready[]`） | 视为**未满足** | **漂移** → 落盘 `ready` 也不含 x |
| ④ | `src/domain/queue/validateQueue.ts:245`（V-5 假就绪） | 视为**未满足** | **漂移，且会当场炸**：见下 |

**④ 为什么必须同批改（最易漏、且会当场炸）**：`QueueTaskStore` 写路径先 `recompute()`（用新的 `computeReady` 产出含 x 的 `ready`），随后 `JsonQueueRepository.save`（`QueueRepository.ts:203`）跑 `validateQueueFile(file)`；若 `:245` 仍按旧口径判「依赖未全部 done」→ 报**假就绪** → `QUEUE_VALIDATION_FAILED`，**一个字节都不落盘**。

⇒ 改前 x **永远不出现在任何可开工集合里**：画布永远没绿点，调度永远不投递，人看到的是「它还没轮到」。这是交付能力被冻结，比「掉层」严重得多。

> 原型锚点：`prototypes/dag-canceled-hidden.html#FR-1` 的 flow 分支——「若某卡在别处被置取消，则它从本视图消失」，而依赖它的活卡必须仍在位且可开工。

**判据（可执行）**

1. 构造「x 的唯一前置 y 已取消」标本 → 断言 `readyTasksOf` / `readyTasks` / `computeReady` / V-5(`:245`) 四处输出**逐字相等且都包含 x**。
2. 断言 `validateQueueFile` 对新语义的写盘载荷 `passed === true`（无假就绪），且 `QueueRepository.save` 不抛 `QUEUE_VALIDATION_FAILED`。
3. 断言 `GET /state` 的 `ready[reqId]` 包含 x；画布给 x 画了可开工绿点。
4. 断言 x 的层号 == 「把 y 那条边删掉后重算」的层号。
5. 逆验证：把任一处改回 `=== 'done'` → 本用例必红。

## 用例 4 · 验收的人过覆盖度前置门 <!-- serves: FR-2, FR-4 -->

| 项 | 内容 |
|---|---|
| 角色 | 验收的人（提交/复核验收材料的人）· 系统（门禁） |
| 触发 | 对上一条需求 REQ-261005105032-3b02 提交验收材料，触发「验收前置 = 测试覆盖度必须 ≥ 80%」这道既有关 |
| 前置 | 标本 B：该需求测试覆盖了 106 张**该做的卡**；台账里另有 26 张已取消卡（两次回退产生） |
| 完成标志 | 覆盖度门分母 = 106（不是 132）→ 覆盖度 100% → 提交放行 |
| 后置条件 | 门禁只读不改盘；追溯读数按活卡（**限定语见下**） |

**主流程**

1. 人提交验收材料；服务端在提交前跑覆盖度门探针（喂入该需求的任务集合）。
2. 喂入前剔除已取消卡：分母 = **106**（改前是 132）。收编点在**喂入侧**（RTM 同步的两个入口），不是 `coverageGateOf`（它只转门裁决、不读任务）。
3. 分子 = 被测试覆盖的**活卡**数（取消卡既不在分子也不在分母，不能靠「取消掉没覆盖的卡」把覆盖度刷上去）。
4. 覆盖度 = 106 / 106 = **100%** → 门通过。

**真实历史是两段（别混成一条）**

| 段 | 当时状态 | 门裁决 | 本需求修什么 |
|---|---|---|---|
| ① | `covers` 标注为 **0** | **被拒**（0%） | 不修（那段是标注缺失） |
| ② | 补上标注后 **106 / 132 = 80.3%** | 取值 80 ⇒ **压线通过**，但仍**点名 26 张** | **修分母**：132 → 106 ⇒ 100% |

**期望**

| 读数 | 改前 | 改后 |
|---|---|---|
| 覆盖度门分母 | 132（含 26 张取消卡） | **106** |
| 覆盖度 | 106 / 132 = **80.3%**（取值 80，压线通过，仍点名 26 张） | 106 / 106 = **100%** |
| 追溯 / RTM 行数 | 132（旧快照） | **106**（但**限**「新触发过 RTM 的需求」，见下） |

**⚠ 追溯读数的限定语（已知边界）**：RTM 是**快照**不是实时投影。存量需求若**永不再次触发 RTM**，追溯读数会停在含取消卡的旧快照上。实证（同一条需求两个文件两个数）：`docs/requirements/REQ-261005105032-3b02/rtm-implementing.yml:8 detail_count: 132`（`:409 tasks_total: 132`）vs `rtm-accepting.yml:1451 total_tasks: 106`（`:1447 total: 106`）。
⇒ 验收口径必须写「追溯读数按活卡 = **对新触发过 RTM 的**需求」；存量未再触发的**接受其快照陈旧**，不回填、不重写（守 FR-6）。

**判据（可执行）**

1. 对标本 B 重跑验收前置：断言分母 == 106、覆盖度 == 1.0、门裁决 `passed === true`；改前标本断言为 0.803（取值 80）且落在阈值边缘。
2. 断言两段分开记：第①段（`covers`=0）仍被拒；不把 0% 与被拒、80.3% 混成一条。
3. 断言「取消不能刷覆盖度」：把一张**未被测试覆盖**的活卡置取消 → 分母减 1、分子不变 → 覆盖度**不上升**。
4. **断言活卡 0 张不拦**：全部卡已取消的需求提交验收 → 覆盖度门**不执法**（沿用 `total <= 0` 既有边界），不误拒。
5. 断言两个 RTM 入口同源：分别走 `syncRTMYaml` 与 `syncRTMYamlWithSnapshot`（HTTP 三条直调路径）各算一次，断言两次分母相等且都 == 106。
6. 断言追溯陈旧快照是**已知边界且不写回**：对未再触发 RTM 的存量需求，读数允许含取消卡；全量读取前后 mtime 逐份不变。

| 前置 | 卡处于可取消的状态（`todo` / `in_progress` / `integrating` / `testing` / `in_review` / `done` 均有到 `canceled` 的人工门边）；agent 无权取消 |
| 完成标志 | 台账三字段按规则写入；视图与统计**立即**少一张，且界面不出现「少了一张」的交代 |
| 后置条件 | `revisions` 多一条（append-only）；任务卡文档保留在盘上；覆盖度门分母同步减 1；依赖它的活卡若因此解锁，立刻变成可开工 |

**主流程**

1. 人下取消指令并给原因。
2. 系统在一次写入里同时落（**字段是查询面、`revisions` 是历史面**）：
   - `status = 'canceled'`；`canceledAt = now`；
   - `canceledBy = { kind: 'human', sessionId }` —— **仅当取消者能解析为人**；真非人工路径（解析不出人）时**整个字段不写**（不写 `kind:'system'` 这类替身）；
   - `cancelReason = reason.trim()` —— **trim 后非空才写**，**不设硬上限**；
   - `revisions += { at, by, kind:'rollback', reason, changes:['status: x→canceled'] }`（与三字段**同源同刻**：同一个 `at`、同一个 `by`、同一段 `reason`）。

   **批量取消的语义（单卡与批量同规则）**：需求级回退 / 误物化清场这类**批量**取消，三字段取「**该批动作**」而非逐卡：
   | 字段 | 批量取消时取什么 |
   |---|---|
   | `canceledBy` | **触发该批动作的人**（`kind: 'human'` + `sessionId`）——回退/清场本身就是**人工门动作**，触发者是可解析的人 |
   | `canceledAt` | 该批动作的时刻（同一批的卡同一个 `at`） |
   | `cancelReason` | **该批动作的原因**（如「回退重拆」），不是逐卡理由 |
   ⇒ 因此权威原型 `#FR-3`「每行三个留痕列非空」的锚点**仍然成立**（26 行批量取消的 `canceledBy` 都有人）；**真非人工路径**仍不写该字段。
3. 界面与统计在**下一次读数**里就少一张：`/state` 的 `tasks` 少一条 → 卡面计数 / 甘特 / DAG 画布同时少一张；阶段详情分层少一个节点；覆盖度门分母减 1。
4. 取消可能**顺手解锁**别的活卡：若某活卡 x 的**最后一个**未完成前置就是这张被取消的卡，x 下一刻进入 `ready`（UC-3 的语义）→ 画布亮绿点。
5. 界面**不出现**该卡的任何痕迹（无灰卡、无删除线、无「已取消」标记行、无「另有 N 张已取消」，状态档位也不带 `canceled` 档）。
6. 审计路径（台账读取 / 归档材料）能读到这张卡与它的三字段。

**期望**

| 位置 | 取消发生后 |
|---|---|
| 台账记录 | 三字段按规则落值（可能只有 `canceledAt` / `cancelReason`）；记录**仍在**（不删除） |
| `revisions[]` | 多一条，与三字段同源同刻 |
| 任务卡文档 | `docs/requirements/<REQ>/tasks/<task_id>.md` 仍在、内容不变 |
| `/state` 的 `tasks` / `ready` | 该卡从 `tasks` 消失；依赖它的活卡（若因此解锁）进 `ready` |
| 卡面计数 / 甘特 / DAG 层级 / 追溯 / 详情计数 / 覆盖度分母 | 全部少 1，且**同一次读数里同时变** |
| 界面文案与档位 | 无任何变化可被察觉（含状态档位不带 `canceled`） |

> 原型锚点：`prototypes/dag-canceled-hidden.html#FR-3`（`#mock-ledger .ledger-row` → 26 行且每行三个留痕列非空）。**该锚点成立**：批量回退的 `canceledBy` 解析为**触发该次回退的人**（`kind:'human'` + `sessionId`），原因写成回退动作名（如「回退重拆」）——回退本就是人工门动作，触发者可解析（裁定 ②）。

**判据（可执行）**

1. 人取消一张卡后读台账：`canceledAt` 有值、`cancelReason` 非空、`canceledBy == { kind:'human', sessionId }`（验收 C7）。
2. 断言三字段与 `revisions` 新增那条**同源同刻**（`at` 相等、`by` 相等、`reason` 相等）。
3. **断言批量取消语义**：需求级回退 / 清场批量取消 26 张 → 26 行的 `canceledBy` 均 = **触发该批动作的人**（同一个 `sessionId`）、`canceledAt` 同批同一个值、`cancelReason` = 该批动作的原因（如「回退重拆」）⇒ 原型 `#FR-3`「每行三列非空」锚点通过。
4. **断言真非人工路径**：取消者解析不出人时，`canceledBy` **整字段不写**（不写替身值），`canceledAt` / `cancelReason` 照写。
5. 断言 `cancelReason` 规则：`'   '` → 不写该字段；超长原文 → **照写不拒绝**。
6. 断言复活语义：`canceled → todo` **不清空**三字段；再取消后三字段 = **最近一次**；`revisions` 两次都在。
7. 断言「同时变」：取消前后各取一次全部读数，每个读数都恰好减 1（若有读数没变 → 口径分叉）。
8. 断言解锁生效：把某活卡的最后一个未完成前置取消掉 → 该活卡下一刻在 `ready` 里。
9. 断言界面不交代：投影里既无该卡，也无任何「已取消 / 另有 N 张」文案，状态档位不含 `canceled`。
10. 断言权限不变：agent 发起取消被人工门拒绝。

## 用例 6 · 复盘的人从台账读「谁因什么取消了这 26 张」 <!-- serves: FR-3, FR-5, FR-6 -->

| 项 | 内容 |
|---|---|
| 角色 | 复盘的人（事故调查 / 归档的人） |
| 触发 | 要回答「上一条需求为什么少了 26 张卡、它们是怎么退出的」 |
| 前置 | 标本 A/B 的台账可读；界面**刻意不给**这些信息（D-7） |
| 完成标志 | 从台账逐行读到 26 张卡的「时刻 / 人 / 原因」（或如实读到未采集），并与回退记录对上；界面侧仍然零呈现 |
| 后置条件 | 读取过程**不产生任何写回**；历史追溯文件与任务卡文档不删不改 |

**主流程**

1. 复盘的人先试界面——**界面刻意答不了**（这是设计选择，不是缺陷）：取消卡不出现、也没有「另有 26 张」的入口。
2. 转到审计路径，按**两面**读：
   - **查询面**（三字段）：`canceledAt` → 何时退出；`canceledBy` → 谁退出的（人 + 会话）；`cancelReason` → 为什么退出。直接读、无需解析，**回答「最近一次」**。
   - **历史面**（`revisions[]`）：按时间顺序流式读，回答「这张卡被改过哪些次」，包含每次取消/**复活**/重开。当某张卡被复活过又再取消时，三字段只反映最新那次，历史看 `revisions`。
3. 与需求级回退的状态转移记录（`statusHistory`）在时间上对齐。
4. 归档材料可引用取消计数（`canceled_count: 26`）——只进归档材料，不进界面。
5. **旧取消卡的例外**：上线前取消的卡三字段为空（未采集），复盘时如实看到「未采集」而不是编造的值；此时退回到 `revisions[]` 与状态转移记录里读上下文。

**期望**

| 情形 | 查询面（三字段） | 历史面（`revisions`） | 界面 |
|---|---|---|---|
| 新取消（人） | 三字段均有值 | 多一条同源记录 | 什么都没有（卡不出现） |
| 新取消（非人解析） | `canceledAt` / `cancelReason` 有值，`canceledBy` 缺 | 多一条（`by` 仍在 revisions 里） | 同上 |
| 复活过又再取消 | = **最近一次**取消 | 两次取消 + 一次复活都在 | 复活期间它是活卡、出现在视图 |
| 旧取消卡（上线前） | 三键缺失 = **未采集**（不报错、不补写） | 视历史是否采集而定 | 同上，什么都没有 |
| 归档材料 | 可引用取消计数 | — | 同上 |

> 原型锚点：`prototypes/dag-canceled-hidden.html#FR-5`（`#mock-ledger` 带 `data-present-in-view="no"`；`#mock-after` 内 `.ledger-row` → 0）与 `#FR-6`（旧数据三列渲染为空字符串而非 `undefined`）。

**判据（可执行）**

1. 对标本 A 的台账断言：取消卡记录数 == 26，且每行按规则读取（已采集的三列非空；未采集的为空/缺键，**不出现 `undefined` 这类伪值**）。
2. 断言两面分工：三字段 == `revisions` 里**最新那条**取消的 at/by/reason；`revisions` 保留全部历史（含复活）。
3. 断言界面侧零呈现：全部界面投影里取消卡条数 == 0，且不含取消计数文案。
4. 断言读取零写回：读全量存量需求目录前后 mtime 逐份不变；历史追溯文件与任务卡文档未被删除或改写（验收 C8 / C9）。
5. 断言无迁移脚本：仓库里不存在为回填三字段而新增的迁移/回填脚本。

## 异常路径 <!-- serves: FR-1, FR-2, FR-3, FR-6 -->

### 异常 A · 活卡依赖了一张被取消的卡（D-8） <!-- serves: FR-1 -->

| 项 | 内容 |
|---|---|
| 情形 | 卡 x（活卡）的 `dependsOn` 指向卡 y，而 y 已被取消。y 永远不会完成——若把这条边当「未满足」，x 会被永久卡死 |
| 期望 | 该边按**已满足**处理：x 不掉层、不成孤岛、**且确实可开工** |
| 处理顺序 | ① 先剔节点（`liveTasksOf`）；② 再剪边（`splitDependencyEdges`，指向不在场节点的边落 `dangling`，不进分层）；③ 在 `layerInputOf` 的输入上算层（`liveLayers`）；④ 就绪用同一份桶（`isReadyTask`，**唯一阻塞桶 = pending**）；⑤ 出参写**剪边后**的依赖 |
| 判据 | x 的层号 == 「把该边删掉后重算」；x 的入边集合 == 剪边后的入边集合；`readyTasksOf`/`readyTasks`/`computeReady`/V-5 四处输出都含 x |
| 反例（必红） | **只剔节点不剪边**：`client/stage-panel.ts:347` 的 `topoLevels` 对未知 id 返回 0，幽灵边贡献 1 层 → x 掉到第 2 层 |
| 反例（必红） | **就绪判定没跟着改**：`readyTasks`/`computeReady`/V-5 仍只认 `done` → x 不掉层但**开不了工**（缺陷比掉层更重，见 UC-3） |
| 边界 | 「不成孤岛」= 不因取消卡产生悬空入边，**不是**「每张活卡都必须有边」；本来就无前置的活卡在第 1 层是正常形态 |

### 异常 B · 旧数据没有三字段（未采集，不报错） <!-- serves: FR-3, FR-6 -->

| 项 | 内容 |
|---|---|
| 情形 | 上线前被取消的卡，台账分片里没有 `canceledAt` / `canceledBy` / `cancelReason` 三键 |
| 期望 | 读取**不报错**、不产生写回、不补默认值；三字段如实标「未采集」；界面上**完全不体现** |
| 关键纪律 | 活卡判据**只看 `status`**，不看三字段——否则旧取消卡会被误判成活卡重新出现在界面上。反例：把 `isLiveTask` 写成「`status !== 'canceled' && canceledAt != null`」→ 旧取消卡全部复活 → **必红** |
| 判据 | 用旧形状分片跑生产读路径：无异常；三字段读作未采集；该卡在全部界面投影里条数为 0；全量读取前后 mtime 逐份不变 |
| 关联 | 与「零迁移」同一条边界：不写迁移脚本、不回填、不改写历史分片（FR-6） |

### 异常 C · 反方向：取消不能用来刷读数 <!-- serves: FR-2 -->

| 项 | 内容 |
|---|---|
| 情形 | 有人发现「取消卡不进分母」，于是把**没做完/没覆盖**的卡取消掉，企图让覆盖度或进度变好看 |
| 期望 | 分子与分母**同源**：取消一张未被覆盖的卡 → 分母减 1、分子不变 → 覆盖度**不上升**；进度同理 |
| 判据 | 构造「106 活卡中 100 张覆盖」标本 → 覆盖度 100/106；取消一张**未覆盖**的卡 → 断言覆盖度 == 100/105（**下降**） |
| 关联 | 取消是人工门（agent 无权），且每张卡留下留痕——刷读数的动作会留在审计线上（UC-6 可查） |

### 异常 D · 依赖判定不同源时的半成品形态 <!-- serves: FR-1, FR-4 -->

| 项 | 内容 |
|---|---|
| 情形 | 只改了显示侧（剔卡 + 剪边），漏改就绪判定（`readyTasks` / `computeReady` / V-5 仍只认 `done`） |
| 期望 | 这是**必须被拦下**的半成品：卡在界面上层号正确、也「看着该开工」，但永远拿不到绿点、永远不被投递 |
| 判据 | 专项用例：对「唯一前置已取消」标本断言**四处**就绪输出逐字相等（TC-R1）；任一处漂移即红 |
| 为什么单列 | 它**不会**被「取消卡条数 == 0」这类投影断言抓到（投影全对），只有依赖判定专项断言能抓 |

### 异常 E · 存量队列文件的 `ready[]` 与新语义不符 <!-- serves: FR-1, FR-2 -->

> **处置已定（裁定 ①，A+B 合体）**：按「**哪条 issue 可自愈**」区分——**派生值陈旧可自愈**（下次写路径重算即消失），**写坏不可自愈**。一句话口径：**校验的目的是拦住「写坏」，不是让「派生值陈旧」把存量需求判成没有任务。**

| 项 | 内容 |
|---|---|
| 情形 | 升级后，某个**只读不写**的存量需求的 `queue.json` 里，`ready[]` 是**旧语义**算的（不含「因取消而新解锁」的活卡） |
| 改前后果（比「读到过时值」严重） | `JsonQueueRepository` **读取路径**跑 `validateQueueFile`，失败即「按不可用处理 → 返回 `undefined`」；`QueueTaskStore.readQueue` 随之 `undefined`、`listByRequirement` 返回 `[]` ⇒ **该需求任务读作 0 张**（DAG 空、看板卡面 0、覆盖度分母 0）。触发点是 V-5 **漏就绪**（`validateQueue.ts:253`，它调 `computeReady`）：旧文件里新解锁的活卡不在 `ready` 中 → 报漏就绪 |

**三段式处置（读宽容 / 写严格 / 按可自愈性分档）**

| 段 | 落点 | 规则 | 为什么 |
|---|---|---|---|
| **① 读路径宽容** | `JsonQueueRepository` 读取路径的校验 | `validateQueueFile` 失败**不得让整条队列读成 `undefined`**；降级为 **warning + 继续返回队列** | 否则 DAG 空、卡面 0、分母 0——一个陈旧的派生值把整个需求判成「没有任务」，代价与原因完全不成比例 |
| **② 读路径的 `ready` 以重算为准** | `QueueTaskStore.readQueue` / `/state` | `ready` 一律**重算**，**不读落盘 `ready[]`**（现状已如此，`stages.ts:96-98` 注释即此口径） | 与裁定 2 一致；陈旧值不进入任何显示读数 |
| **③ 写路径保持严格** | `JsonQueueRepository.save`（`QueueRepository.ts:203`） | 仍**强校验**，失败照旧抛 `QUEUE_VALIDATION_FAILED`、一个字节不落盘 | 写路径必须先 `recompute()`（新语义自洽），此时还失败就是真写坏，必须拦 |
| **④ 分档（V-5 两半拆开）** | `validateQueue.ts` 的 V-5 | **「漏就绪」（`:253`）从 issue 降为 warning**——它是**可自愈的陈旧派生值**（下次写路径重算即消失）；**「假就绪」（`:245`）仍是 issue**——那是**真问题**（卡未就绪却被标记 ready） | 「可自愈」与「写坏」是两类东西，用同一条 issue 处置会把前者误判成后者 |

**期望**：存量需求**读得出**（任务数照给）、**写不坏**（写路径仍严格）、**零写回**（不重写存量文件、不改 mtime）。

**判据（可执行）**

1. 构造「`ready[]` 为旧语义」的存量队列文件 → 断言 `listByRequirement` 仍返回 132 张（**不是 `[]`**），且读取路径给出 **warning**（不是静默、也不是 `undefined`）。
2. 断言 V-5 分档：「漏就绪」标本 → **warning、`passed === true`**；「假就绪」标本（卡未就绪却被标 ready）→ **仍是 issue、`passed === false`**，且 `save` 抛 `QUEUE_VALIDATION_FAILED`。
3. 断言 `/state` 的 `ready` 现算正确（不受陈旧 `ready[]` 影响）。
4. 断言零写回：读取前后该需求目录 mtime 逐份不变。

### 异常 F · 存量需求的追溯读数停在旧快照 <!-- serves: FR-2, FR-6 -->

| 项 | 内容 |
|---|---|
| 情形 | 存量需求**永不再次触发 RTM**，其 `rtm-*.yml` 保持升级前的快照（含取消卡） |
| 期望 | **接受**为已知边界，不假装追溯实时；验收口径写明限定语「追溯读数按活卡 = **对新触发过 RTM 的**需求」 |
| 实证 | 同一条需求 REQ-261005105032-3b02：`rtm-implementing.yml:8 detail_count: 132`（`:409 tasks_total: 132`）vs `rtm-accepting.yml:1451 total_tasks: 106`（`:1447 total: 106`） |
| 判据 | 对未再触发的存量需求：读数允许含取消卡；**不回填、不重写快照**；全量读取前后 mtime 逐份不变 |
| 关联 | 与「零写回」同源：回填快照要改历史文件，越界 |

## 关键决策与取舍 <!-- serves: FR-1, FR-2, FR-3, FR-4, FR-5 -->

> 主体写在 `architecture.md` 同名节；本份只列**与角色/分支直接相关**的取舍。

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 界面要不要告诉人「少了 26 张」 | 给一行「另有 26 张已取消」 | **一个字都不给**（含状态档位不带 `canceled` 档） | 用户裁定（D-7）；显示 `canceled 0` 也是交代 |
| 取消卡能不能「显示出来」看看 | 加「显示已取消」开关 | **彻底不可见** | 用户裁定（D-3）；开关会让「132 vs 106」的分叉重新长回来 |
| 复盘需求怎么满足 | 在界面上给审计视图 | **转审计路径**，并分**查询面（三字段）/ 历史面（`revisions`）** | 界面是读数面、审计是另一个面；两面分工让「最近一次」与「全部历史」都可答 |
| 悬空依赖怎么判 | 当未满足（保守） | **当已满足，剪边 + 就绪同源 + V-5 同改** | 被取消的卡永远不会完成，当未满足会把活卡永久卡死（D-8）；漏改 V-5 会当场拒写 |
| 一致性在哪收 | 逐个消费点补 filter | **在 `/state` API 边界收一处 + 阶段详情在基类收一处** | 甘特 / DAG 画布 / 卡面 / 绿点共吃 `/state`；阶段详情病根是「某处漏了」，基类收一次才治本 |
| `canceledBy` 记谁 | 记 `ActorRef`（含 agent/system） | **只记人**（`{kind:'human', sessionId?}`）；**批量取消取触发该批动作的人**；真非人工路径不写 | 取消 = 人工门；批量回退/清场本身就是人工门动作，触发者可解析 ⇒ 原型 `#FR-3`「每行三列非空」锚点仍成立（裁定 ②） |
| 队列校验失败怎么办 | 读路径也严格（失败即整条队列不可用） | **读宽容 + 写严格 + 漏就绪降 warning** | 校验的目的是拦「写坏」，不是让「派生值陈旧」把存量需求判成没有任务（裁定 ①） |
| 复活时三字段 | 清空 | **不清空**，语义 = 「最近一次取消」 | 历史不丢（`revisions` 逐次留痕）；清空会让「最近一次为什么取消」永久丢失 |
| 活卡 0 张 | 门判不通过 | **不拦**（沿用既有 `total <= 0` 边界） | 分母为 0 时无所指；不改既有计量口径 |
| 存量追溯快照 | 回填/重写 | **接受 + 限定语** | 守零写回（FR-6） |
| 谁有权取消 | 让 agent 顺手清理 | **仍是人工门** | 本需求不改这条属性（UC-5） |
