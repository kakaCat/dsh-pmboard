# 用例设计 · REQ-261003204149-1e80 <!-- serves: FR-1, FR-2, FR-3, FR-6 -->

> 一句话：四个真实场景覆盖回退的全部分支——**退得动**（任意上游）、**半途也能退**、
> **退回去要重新过门**、**人和 agent 退的是同一件事**。

## TL;DR <!-- serves: FR-1 -->

回退不是"点一下撤销"：它是一次**带账的返工**。下面四个场景就是它的用户可见形
——每个场景都写清"谁在操作、系统做什么、人能看到什么"。

## UC-1 · 实施中发现需求描述不对：退回重新描述 <!-- serves: FR-1, FR-3 -->

| 项 | 内容 |
|---|---|
| 谁 | 实施 agent（自行判断，不需要人先点按钮） |
| 场景 | 做到一半发现需求文档里的边界与真实意图不符，继续做只会交付没人要的东西 |
| 做什么 | 调 `reqboard_move(to='design', reason='需求边界与真实意图不符：…')` |
| 看到什么 | 状态回到设计节点；返回体列出**作废了哪些章、旧卡全取消、物化了 N 张重做卡**；时间线多一条回退事件 |

**系统做什么**：撤掉 design 之后的全部确认章 → 撤掉计划批准 → 旧卡 `canceled` + 物化重做卡 →
断点改写为"设计阶段该做的事"。人重新审设计、重新批准计划，才可能再进实施。

## UC-2 · 计划还没写完就想退回去改设计（半途回退） <!-- serves: FR-2 -->

| 项 | 内容 |
|---|---|
| 谁 | agent |
| 场景 | 需求进到拆分阶段（`decomposing`），但拆分计划**还没提交**，此时发现设计前提错了 |
| 做什么 | 调 `reqboard_move(to='design')` |
| 看到什么 | **退成功**；提示"无可撤销的下游产物"（因为确实还没有） |

**关键**：这正是现状退不动的那一类——产物门要求"`from` 阶段的必备产物已就位"，
而 `from` 没做完才是要退的原因。修复后回退方向不套用该判据（安全由"退回去之后作废"兜住）。

## UC-3 · 退回去再走上来：每一道门重新过 <!-- serves: FR-3 -->

| 项 | 内容 |
|---|---|
| 谁 | agent + 人（配合） |
| 场景 | 需求被退回设计节点后，改完设计文档准备重新推进 |
| 做什么 | 1) `reqboard_submit(kind=design)` 重交设计 → 2) 请人确认设计 → 3) 写拆分计划 → 4) 请人批准计划 |
| 看到什么 | 第 2 步之前 `design → decomposing` 被 **`artifact_not_confirmed`** 拦下；第 4 步之前 `reqboard_decompose` 被 **`REQBOARD_PLAN_NOT_APPROVED`** 拦下 |

**这是本需求的核心不变量**：回退放宽的是**回退方向**，回程上的五道人工门一道不动
——"退过"不等于"免检"。

## UC-4 · 人在看板上点回退 <!-- serves: FR-1, FR-6 -->

| 项 | 内容 |
|---|---|
| 谁 | 需求方 / 维护者 |
| 场景 | 人在看板上发现需求方向不对，直接回退（不经过会话） |
| 做什么 | 看板对需求卡执行回退到目标节点 |
| 看到什么 | 与 UC-1 **同样的后果**：章作废、旧卡取消、重做卡出现；`rollback` 块与工具侧同形 |

**为什么要用例化**：现状工具侧与看板侧是两段独立实现，只改一处就会出现
"agent 能退、看板不能退"或两侧后果不一致——本用例就是 FR-5 的业务面表达。

## 不覆盖（属于其他需求的既有路径） <!-- serves: FR-1 -->

- **验收不通过自动返工**：`accepting → implementing` 由验收单裁决驱动，物化返工卡
  ——已有实现（`application/internal/verdicts.ts`），本需求不重写、只在数据对照表里保持一致。
- **取消需求 / 归档**：仍必须人操作，不是"回退"，不走本通道。
- **取消后回到 draft**：既有 `canceled → draft` 边，语义是"重新立项"，与回退无关。
