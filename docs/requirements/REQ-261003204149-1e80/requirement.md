## TL;DR

需求的回退边**早就在状态机里**（brainstorming→draft、design→brainstorming、decomposing→design、
implementing→design、accepting→implementing），缺的不是"一条边"，而是回退的**配套语义**：
从节点没做完时退不回去、退回去不撤销下游的章与批准、旧任务卡变成孤儿导致回不去也拆不了。
本需求把回退做成一条**可信的通道**：任意更早节点都能退、退的时候如实作废下游、旧卡有明确归宿。

**历史印记**：`src/domain/workflow/DecomposeSpec.ts` 的注释里已白纸黑字记录过这个死锁——
"需求被推进到 implementing，但一条任务卡都没落库——既不能重拆（本守卫拒），也不能退回上游
（implementing→design 的产物门要求 task_detail 产物）"。缺口 1 正是它没被一并解掉的那一半。

**已有范式（本次复用，不另造）**：验收不通过时的自动回退
（`src/application/internal/verdicts.ts`：failed → 同笔 mutate 内回退实施 + 物化返工卡）。
本需求把同一套"回退 + 物化卡 + 留痕"的形，从验收环节推广到需求级的任意上游回退。

## 本需求要修的条款

- **FR-1: 回退可退到任意更早节点，且由 agent 自行判断发起**——`reqboard_move(to=…)` 的目标早于当前阶段时即为回退：状态机承认"回退方向"的任意上游目标，agent 可自行发起，不再受人工门拦截。取消需求 / 归档 / 重开已完成卡仍**仅人可操作**（铁律不变）。回退必须留痕：写状态事件 + 评论（from → to + 理由），返回体如实回报"这次作废了什么"。
- **FR-2: 回退不套用出发节点的"已完成"产物闸门**——`assertArtifactGates` 的两级（产物存在门 / 人工确认门）语义是"离开一个已完成的节点"，对回退方向不成立：回退时跳过这两级，改为执行 FR-3 的撤销。判据：**from 阶段没做完也能退**（现状被 `missing_artifact` 拒死）。
- **FR-3: 回退作废下游产物章与计划批准（撤销语义）**——回退到节点 X 时：清空阶段晚于 X 的全部产物的 `confirmedAt/confirmedBy/confirmedVia`；X 早于计划批准所在阶段时清 `plan.approvedAt`；复用 `applyDocSync` 写 changelog 并标下游"待同步"；写一条"旧确认已作废、需重新确认"的评论。不变量：**退回去再往上走时每一道人工门必须重新过**，不得凭旧章白送。
- **FR-4: 旧任务卡标 canceled + 物化重做卡，且回退后能重新拆分**——回退到 design/decomposing 或更早时：该需求全部未取消旧卡标 `canceled`（留痕 reason + `revisions` kind=rollback），并按旧卡物化"重做卡"，让"这些活要重做"在 DAG 上可见；同时放开拆分幂等守卫在**显式回退态**下重建，新计划落库时与重做卡收敛（不得产生双份幽灵卡）。不变量：非回退态下"幽灵任务双倍落库"的防线**不得削弱**。
- **FR-5: 回退逻辑单点收敛，工具侧与看板侧同源**——回退的判定、撤销与任务处置只有一处实现，`reqboard_move` 与看板 move 路由共用它；同一 from→to 在两条通道上给出**同一结果与同一错误码**，不得两处各写一遍。
- **FR-6: 回退后注入、断点与边界按新阶段重算**——阶段动作表（`reqboard_move` 合法阶段集）、断点的 `pendingAction`、dive 边界守卫与 armed 状态、节点输入包在回退后一律按**新阶段**重建；不得残留旧阶段的"下一步"指引，也不得让回退后的窗口以为自己还在下游。

## 产品定义

**是什么**：需求流水线的一条**可信回退通道**——需求走错了方向时，能退回任意更早的节点重做；
退的时候如实交代"哪些确认作废了、哪些卡要重做"，退回去再走上来时每一步仍要重新获批。

**核心价值**：让"退回上游"从**事故级操作**（卡死、白送闸门、跑错卡）变成**有账可查的常规动作**。
现状最坏的一面不是退不回去，而是**退得半生不熟**：状态回去了、章还在、旧卡还在跑——
人以为重做了，系统却按旧确认放行、按旧卡实施，最后交付的是没人确认过的东西。

**与现状的区别**：现状是"改一个 status 字段 + 写条评论"；修复后是"回退 = 状态回退 + 下游作废
+ 旧卡处置 + 注入重算"的**一笔原子事务**，四个后果一次交代清楚。

**三要素检查**：

- [x] 说清"是什么"——需求级回退通道，退到任意更早节点
- [x] 说清"核心价值"——回退不再是事故：有账、可查、闸门不白送
- [x] 说清"与现状的区别"——从"改状态"到"状态 + 撤销 + 卡处置 + 注入"一并交代

| 角色 | 什么场景用 | 痛点 |

## 功能点（需求条款）

### 功能点详细说明

**详细说明 · FR-1**

- **使用场景**：实施中发现需求描述与真实意图不符；或设计阶段发现方案前提错了要退回去重新分析。
- **操作流程**：
  1. agent 判断该退到哪个更早节点（自行判断，不需要人先点按钮）。
  2. 调 `reqboard_move(requirement_id, to=<更早节点>, reason=<为什么退>)`。
  3. 系统执行 FR-2/FR-3/FR-4 的配套动作，一笔 mutate 内完成。
  4. 返回体回报：新状态、作废的产物清单、被取消的卡数、物化的重做卡数。
- **预期结果**：
  - 结果 1：需求状态等于目标节点，时间线上多一条**可辨识为回退**的状态事件。
  - 结果 2：返回体不是干巴巴的 `success`，而是"作废了什么"的清单。
- **边界条件**：
  - 边界 1：目标是当前节点或更晚节点 → 走既有前进路径（本需求不改前进语义）。
  - 边界 2：`canceled / archived / done` 仍是终点的语义：归档后不可回退，取消需求仍仅人可操作。

**验收标准 · FR-1**：

1. 造一个 `implementing` 需求 → 以 agent 身份调 `reqboard_move(to='design')` → 断言**不被 `REQBOARD_HUMAN_GATE` 拒绝**且状态变为 `design`。
2. 断言返回体含"作废产物清单 / 取消卡数 / 重做卡数"三项（缺一即算没交代）。
3. 断言时间线新增一条 status 事件，且评论里能看到 `implementing → design` 与 reason 原文。

**详细说明 · FR-2**

- **使用场景**：计划还没提交就想退回去改设计；实施开了个头但没有任务卡文档，要退回重写。
- **操作流程**：
  1. 回退请求进入闸门判定。
  2. 识别 `to` 早于 `from`（回退方向）→ **跳过**产物存在门与人工确认门。
  3. 转而执行 FR-3 的撤销（回退方向的安全责任从"出门前检查"移到"退回去之后作废"）。
- **预期结果**：
  - 结果 1：`from` 阶段必备产物缺失时，回退**仍然成功**（现状为 `missing_artifact` 拒绝）。
  - 结果 2：前进方向（`to` 晚于 `from`）的产物门与人工门**一字不改**。
- **边界条件**：
  - 边界 1：存量需求（无 `artifacts`）→ 与既有 `isLegacy` 口径一致，不硬拦。
  - 边界 2：目标为 `canceled` 时仍走既有"放弃路径"豁免（不适用节点完成闸门）。

**验收标准 · FR-2**：

1. 造一个 `decomposing` 需求且**不登记** `decomposition` 产物 → 调 `reqboard_move(to='design')` → 断言成功（判别力：撤掉本修复后此用例必红于 `missing_artifact`）。
2. 反向用例：同为 `decomposing`，调 `reqboard_move(to='implementing')` 且未确认拆分计划 → 断言**仍被拒**（不得因本改动把前进门一起放宽）。

**详细说明 · FR-3**

- **使用场景**：退回去必然意味着"下游那些确认不再作数了"——人要重新审、agent 要重新走门。
- **操作流程**：
  1. 回退到 X。
  2. 清空阶段晚于 X 的全部产物的确认章（`confirmedAt/confirmedBy/confirmedVia`）。
  3. X 早于计划批准所在阶段 → 清 `plan.approvedAt`。
  4. 调 `applyDocSync` 写 changelog、把下游标"待同步"；写评论列明作废清单。
- **预期结果**：
  - 结果 1：退回去后**不能**凭旧章推进（`artifact_not_confirmed` 如期拦下）。
  - 结果 2：`plan.approvedAt` 清空后，`reqboard_decompose` 被 `REQBOARD_PLAN_NOT_APPROVED` 拦下。
- **边界条件**：
  - 边界 1：重复回退幂等（同一目标退两次不产生重复 changelog）。
  - 边界 2：无 `artifacts` 的存量需求不因清章而报错。

**验收标准 · FR-3**：

1. 造一个已确认 design 章 + 已批准计划的 `implementing` 需求 → 回退到 `design` → 断言 `plan.approvedAt === undefined` 且下游产物 `confirmedAt === undefined`。
2. 回程验证：直接调 `reqboard_move(to='decomposing')` → 断言被 `artifact_not_confirmed` 拒（下一步必须人重新确认设计）。

**详细说明 · FR-4**

- **使用场景**：退回 design 重新描述需求后，原来那批任务卡已经不代表要做的事了。
- **操作流程**：
  1. 回退到 design/decomposing 或更早。
  2. 全部未取消旧卡标 `canceled`，附 reason 与 `revisions`（kind=rollback）。
  3. 按旧卡物化"重做卡"，使重做工作量在 DAG 上可见。
  4. 重新提交并批准计划后 `reqboard_decompose` 落库，与重做卡收敛（不出现双份）。
- **预期结果**：
  - 结果 1：回退后不存在"还在跑的旧卡"（不谎报在制）。
  - 结果 2：重拆**可执行**（现状被 `REQBOARD_ALREADY_DECOMPOSED` 拒死）。
- **边界条件**：
  - 边界 1：全部卡均已 done 的需求回退 → 旧卡是否重开由人定，本需求不自动重开已完成卡（人工门）。
  - 边界 2：非回退态的重复拆分仍被幂等守卫拒绝（事故 B 的防线不得削弱）。

**验收标准 · FR-4**：

1. 造 2 张卡（1 done、1 in_progress）的需求 → 回退到 `design` → 断言两张卡均 `canceled` 且存在对应重做卡（数量与旧卡一一对应）。
2. 走完 `design → 批准计划 → reqboard_decompose` → 断言落库成功且**不产生**与重做卡重复的任务（总数可核）。
3. 判别力：非回退态下重复调 `reqboard_decompose` → 断言**仍被拒**（防线未削弱的反证）。

**详细说明 · FR-5**

- **使用场景**：人在看板上拖/点回退，与 agent 在会话里调 `reqboard_move`，必须是同一件事。
- **操作流程**：
  1. 回退的判定、撤销、任务处置收敛到一个用例。
  2. 工具侧与看板路由都调用它。
  3. 错误码与返回体形状两侧一致。
- **预期结果**：
  - 结果 1：同一 from→to，两条通道的返回语义与错误码逐字一致。
  - 结果 2：改动只落一处，另一处无需复制逻辑。
- **边界条件**：
  - 边界 1：看板侧若不需要新的交互形态，复用既有节点移动通道（本需求不重做交互）。
  - 边界 2：actor 口径不变（工具侧 agent、看板侧 human），审计留痕各自如实。

**验收标准 · FR-5**：

1. 同一 from→to 分别走工具与看板路由 → 断言 `status` 与错误码一致。
2. 断点续跑：任一路径回退后，另一路径的下一动作指引与之一致（无分叉）。
3. 代码级：断言回退的撤销/卡处置没有第二处实现（同一断言在两个入口都被满足）。

**详细说明 · FR-6**

- **使用场景**：回退后窗口继续跑，注入的"下一步"必须指向新阶段的动作。
- **操作流程**：
  1. 回退写入状态事件。
  2. 断点 `pendingAction` 按新状态重算。
  3. 阶段动作表与边界守卫按新阶段放行/拦截；节点输入包重建。
- **预期结果**：
  - 结果 1：回退后注入不再出现下游阶段的指引（如退回 design 后不该再出现"提交验收"）。
  - 结果 2：dive armed 状态下的回退有明确处置（不残留自动链指向旧阶段）。
- **边界条件**：
  - 边界 1：读路径工具在全阶段放行的现状不变。
  - 边界 2：回退后需要人做的事照旧弹确认门（不因回退而免掉）。

**验收标准 · FR-6**：

1. 回退到 `design` 后取注入包 → 断言"下一步"为设计阶段动作，且**不含**验收/实施的指引。
2. dive armed 需求回退 → 断言 armed 被清除或重算为与新阶段一致（二者取其一并写明）。

## 边界（不做什么）

- **不做"撤销 / undo"**：只做**状态回退 + 下游作废**，不做事件回放、不删历史事件、不做时间倒流；已发生的留痕只增不改。
- **不做归档后的回退**：`archived / done` 仍是终点（无出边，保持现状）；取消需求仍**仅人可操作**（铁律不伸缩）。
- **不换存储、不重做看板交互**：可给记录加字段，但不改台账文件格式、不拆存储、不新增仓储端口；回退入口沿用既有节点移动通道，不新造交互形态。

## 验收标准（整体）

1. 端到端：造一个 `implementing` 需求（含 2 张卡 + 已确认的 design 章 + 已批准计划）→ agent 自行回退到 `design` → 状态、章、计划批准、旧卡、重做卡五项后果**一次交代清楚**。
2. 回程验门：从 `design` 重新走到 `implementing`，途中 G2 与计划批准**必须重新过**（凭旧章的推进一律被拒）。
3. 半途可退：`from` 阶段产物缺失时回退仍成功，而**前进方向的门一字未松**。
4. 双通道一致：同一 from→to 在工具侧与看板侧结果与错误码一致。
5. 回归：`npx vitest run` 失败数不高于开工前基线；`npx tsc --noEmit` 无新增错误；`pnpm build` 通过。

## 依赖与约束

- **复用（不另造）**：状态机与人工门唯一处 `src/domain/requirement/RequirementStatus.ts`；产物闸门唯一处 `src/application/internal/artifact-gates.ts`；下游同步 `applyDocSync`；物化卡范式 `src/application/internal/verdicts.ts`（验收返工）；拆分幂等守卫 `src/domain/workflow/DecomposeSpec.ts`。
- **强依赖**：既有五道人工门（`src/domain/gate/GateCatalog.ts`）——本需求只放宽**回退方向**，不得动门的数量与前进语义。
- **约束**：不得削弱事故 B（幽灵任务双倍落库）的防线；存量需求（无 `artifacts`）行为与现状一致。
- **约束**：本仓既有类型错误与测试失败为存量，不得纳入本需求范围。
- **范围外（已在本窗口顺手修掉，不属本需求交付）**：`reqboard_capture` 输出 schema 缺 `answers.workspace` 导致每次四问立项报 `invalid output`（需求建出来了、agent 只拿到错误回执）——已补声明并在 `tests/output-contract.test.ts` 补动态防线用例（判别力已 A/B 自证）。

## 档位依据

**L1 一句话目标 + 可证伪判定标准**

- **目标**：让需求级回退成为一条可信通道——任意更早节点退得动、下游如实作废、旧卡有归宿、两侧一致。
- **可证伪判定**：`npx vitest run tests/move-rollback.test.ts`（规划名）→ ① `implementing → design` 由 agent 发起成功且不被 `REQBOARD_HUMAN_GATE` 拒；② 回退后 `plan.approvedAt === undefined` 且下游 `confirmedAt === undefined`，直接推回上游被 `artifact_not_confirmed` 拒；③ 旧卡全 `canceled` 且重拆成功、无重复卡。三条都过才算达标。

**L2 范围边界**：见「边界（不做什么）」三条（不做 undo / 不做归档后回退 / 不换存储不重做交互）。

**L3 轻路径依据 + 单向升级**

- **为什么可以走轻档**：根因是**既有状态机缺"回退方向的闸门策略与撤销语义"**，修法收敛在既有表与既有用例内（状态机表、产物闸门、拆分守卫、注入重算），不新增子系统、不换存储引擎、不改人工门数量。
- **单向升级信号（出现任一即停手升级重档，不许反向降级）**：① 要做"撤销栈 / 事件回放 / 时间倒流"（新增子系统）；② 要改台账**文件格式**或拆存储、新增仓储端口；③ 要动人工门的**数量**或前进方向的闸门语义；④ 出现第二个未定决策（例如"归档后是否允许回退"、"已完成卡是否自动重开"）。
