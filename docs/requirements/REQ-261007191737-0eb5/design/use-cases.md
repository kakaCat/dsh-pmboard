## UC-1 弹框里人工项零输入通过 <!-- serves: FR-1, FR-2 -->

- **谁**：验收人；**前置**：`accepting` 态，验收单某人工项（如「与原型对照截图」）已带 agent `result`，且该 `result` 含观察事实。
- **主成功路径**：
  1. agent 调 `reqboard_accept_sheet` 弹出本批逐项裁决；
  2. 人在该人工项第 1 问选「✅ 通过」，第 2 问**留空**提交；
  3. 系统取 `result` 作为该项结论（`opinionSource='agent'`），本批其余项照常落库；
  4. 人看到回执：本批已记录，该项计入通过。
- **异常路径**：第 2 问写了字但太薄（如「通过」）→ 当场被拒（`opinion_required`），本批零落库，回执点名该项与补法（`design/backend.md` 错误处理）。
- **看到什么**：该项 `status=passed` 且 `opinion` = agent 原文；台账 `opinionSource='agent'`（人只点了通过）。

## UC-2 看板里人工项零输入通过 <!-- serves: FR-1, FR-2, FR-4 -->

- **谁**：验收人；**前置**：同 UC-1，人更愿意在网页上操作。
- **主成功路径**：
  1. 打开需求详情页的验收单，人工项那一行显示「agent 代写（人已确认）」来源徽标与「留空将通过采纳它」提示；
  2. 人勾「通过」、输入框留空，点提交；
  3. 提交落库后该行显示已通过 + 来源徽标。
- **异常路径**：该项**不是**候选（无 agent 事实文本）且人留空 → 前端拦下并点名 itemId，提示给一句可照抄样例（不发送请求）。
- **看到什么**：候选行留空可提交；非候选行留空被拦且提示具体差什么。

## UC-3 人工项没有 agent 事实文本 <!-- serves: FR-3 -->

- **谁**：验收人；**前置**：人工项无 `result`，或 `result` 不含观察事实（如只有「PASS」）。
- **主成功路径**：人自己写「现象 + 证据路径」（>6 字且含观察词）→ 该项通过，来源 `'human'`。
- **异常路径**：人零输入点通过 → 记 `unverified(blank_pass)`，回执说明要补什么；该项**不计入通过**，不得归档。
- **看到什么**：系统**不**代写、不静默放行；agent 侧没有任何把该项置为通过的入口。

## UC-4 提交前就地补问 <!-- serves: FR-4 -->

- **谁**：验收人；**前置**：本批里存在「人工项 + 无 agent 事实文本 + 人留空」的项。
- **主成功路径**：
  1. 系统在写台账**之前**就这些项补问一轮，题干含 itemId 与一句可照抄样例；
  2. 人补写 → 按正常裁决整批落库。
- **异常路径**：人没补（取消 / 留空）→ 沿用今天语义落库；台账在**拒绝**情形下零改动（逐项 `status` 不变）。
- **看到什么**：人不必等整批被拒后才猜原因；补问只在命中时出现，没有命中项时零行为变化。

## UC-5 开关回滚 <!-- serves: FR-5 -->

- **谁**：维护者；**前置**：需要临时回到今天的行为。
- **主成功路径**：设 `DSH_REQBOARD_NO_HUMAN_PROXY=1` → 重启宿主 → 人工项不再吃 agent 事实代写（弹框要人写、看板不置候选行）。
- **异常路径**：设成 `0` / `false` / 空 → 视为开启（与既有 `DSH_REQBOARD_NO_ITEM_RESULT` 同值域口径）。
- **看到什么**：行为与本需求上线前逐字一致（含报错文案）；已写入的 `opinionSource` 保留但不影响判定。

## 关键决策与取舍 <!-- serves: FR-1, FR-3 -->

| 取舍点 | 否掉了什么 | 为什么 |
|---|---|---|
| 场景只覆盖「人点通过」，不新增「agent 自动通过」的场景 | 让流水线自己在全通过后归档 | 人工门的存在意义就是人必须出现；自动归档会把「验收」变成读数（需求 D-2） |
| UC-3 保留「人零输入 → unverified」而不是报错 | 把零输入变成硬错误 | 硬错误会惩罚「agent 没交事实」的历史欠账（这正是上一版需求的裁定：不把欠账转嫁给点通过的人）；`unverified` 已经「不计入通过」，底线在 |
| UC-4 只补问一轮 | 循环问到填满为止 | 反复弹框是最差的交互形态（本仓铁律「一个节点只弹一次」的同精神） |

## 技术方案与亮点 <!-- serves: FR-1, FR-4 -->

- **五条场景里只有两条改变人看到的东西**（UC-1/UC-2 免录入、UC-4 提前告知），其余三条的价值在于**明确不变的边界**——需求的价值一半来自「没有放开什么」。
- 每个场景都能用一条命令回放（见 `design/test-cases.md`），不依赖人工想象。
