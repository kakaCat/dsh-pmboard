# 需求说明（REQ-261004183621-de3f 归档清单自动收录需求目录内文件）

> 本文档面向：产品、开发、测试、用户——**写给人看，不是写给代码看**。

## TL;DR

- **这是什么**：归档材料里那份「需求目录内有哪些文档」的清单，从"靠人/agent 记得逐份列"改成"系统按规则对账 + 漏登当场处置"。
- **为什么现在做**：REQ-261004174324-4195 归档实操实测——清单只列了 10 份，目录里 88 份被判「未列入清单」；想补录时需求已 `archived`（冷侧只读），警告成为**永久留痕、无法补救**。
- **做完得到什么**：要么不漏（系统对账 + 豁免规则），要么漏了当场被拦或显式声明（不是事后一句警告）；已归档的清单也有一次受控的补录通道。

**档位说明（L3 单向升级）**：立项按轻档起，需求分析期间出现**三个未定决策**（清单语义是"目录索引"还是"关键文档清单"、漏登是拦还是警告、已归档能否补录）——按铁律**升级为重档**，本文档按 feature 重档模板落盘。

## 业务流程图

```
agent 提交归档材料（docs 清单）
        │
        ▼
系统对账：目录内文件 × 已列清单
        │
        ├── 已列            → 通过
        ├── 命中豁免规则     → 自动豁免（机器生成物：rtm-*.yml / queue.json / state/*）
        └── 未列且未豁免     → ❗当场处置（这是本次改动的核心）
                 │
        ┌────────┴────────┐
        │                 │
   显式声明豁免        既不列也不声明
   （理由进留痕）           │
        │                 ▼
        ▼            拒绝提交（说清哪些、怎么处置）
     归档完成
        │
        ▼
归档后若仍需补录 → 走「补录清单」受控通道（只追加清单 + 留痕，不改产物本体）
```

## 产品定义

**一句话**：把归档清单从「人写的一份名单」变成「系统对账过的一份记录」。

**核心价值**：

| 痛点（实测） | 本次解决 |
|---|---|
| 清单靠手写，漏登靠事后警告 | 提交时对账：未列且未豁免的文件**必须处置**（列进去或声明豁免） |
| 警告只活在工具返回值里 | 漏登与豁免**写进台账留痕 + 看板归档页可见**（人不再依赖回执） |
| 已归档后想补录 → `冷侧只读` 被拒 | 新增受控**补录通道**（只追加清单与留痕，不改历史产物本体、不改状态机） |
| 机器生成物（rtm-*.yml 等）混在"未列"里刷屏 | 豁免规则落成**常量单点**，可在文档里查到 |

**与现状的区别**：

| 维度 | 现状 | 本次之后 |
|---|---|---|
| 未列文件的处置 | 归档完成后再遍历目录，提示 warning | 提交时对账；未处置 → 拒绝（或按人裁定的口径处置） |
| 豁免 | 无概念（全部算"未列"） | 有规则、有常量、有据可查 |
| 补录 | 无（已归档 = 冷侧只读，只能吃警告） | 有一次受控补录（幂等、留痕、不改产物本体） |
| 可见性 | 只在工具回执 | 台账留痕 + 看板归档页 |

## 用户与角色

| 角色 | 什么场景用 | 痛点（本次解决哪个） |
|---|---|---|
| 实施 Agent | 交付完成后提交归档材料 | 以前要"记得把目录里每一份都列上"，漏了就吃一条没人看的警告 |
| 维护者 | 事后复核某需求归档是否完整 | 以前只能读工具回执（早没了）；现在台账与看板都能看到未列/豁免 |
| 审计者 | 判断"这份归档是否可信" | 以前"未列 88 份"是噪音（机器生成物混在内）；现在分三类，噪音被豁免规则吸收 |

### FR-1: 归档提交时对账并把三类清单如实给出

**功能描述**：agent 提交归档材料时，系统当场把需求目录内的文件与已列清单对账，返回「已列 / 命中豁免 / 未列未豁免」三份清单。

**详细说明**：

- **使用场景**：任何 `kind=archive` 的提交。
- **操作流程**：
  1. agent 给 `dir` + `docs` 清单（与今天相同）。
  2. 系统遍历 `dir` 下全部文件（跳过点文件），按 FR-3 的规则判定豁免。
  3. 返回体给出三份清单与计数。
- **预期结果**：
  - `listed[]` / `exempted[{path, rule}]` / `unlisted[]` 三键；计数与目录实际一致。
  - 现有 `unlisted_files` / `warning` 字段**保留兼容**（老客户端不炸），但语义由 FR-2 决定。
- **边界条件**：
  - 目录不存在/不可读 → 如实失败（不假装"没有未列"）。
  - 目录为空 → 三份都为空数组（不是报错）。

**验收标准**：

1. 构造 fixture 需求目录（含 `rtm-*.yml`、`queue.json`、`tasks/t-1.md`、一份未列的 `evidence/x.txt`）→ 提交后返回体三份清单分类正确。
2. `listed + exempted + unlisted` 的并集 = 目录内文件全集（用单测断言集合相等）。

### FR-2: 未列未豁免必须显式处置，否则拒绝提交

**功能描述**：对"既没列进清单、又不属豁免规则"的文件，agent 必须显式处置——要么加进 `docs`，要么在新增参数里声明豁免并写明理由；两者都不做 → **拒绝提交**。

**详细说明**：

- **使用场景**：agent 有意只收关键文档时（现状允许，但要留痕）。
- **操作流程**：
  1. 提交时若存在未列未豁免文件：
     - 传了 `unlisted_ack: [{path, reason}]` 且覆盖全部未列文件 → 通过，理由进留痕；
     - 未覆盖 → **拒绝**，错误信息列出缺处置的文件与两种处置方式（照本仓"失败要响亮"）。
  2. 拒绝时**不写任何台账**（不产生半截归档）。
- **预期结果**：漏登不可能"悄悄发生"；有意豁免是显式决定且有理由。
- **边界条件**：
  - `unlisted_ack` 里的 path 不存在于未列集合 → 拒绝（防"声明了不存在的文件"）。
  - `reason` 为空串 → 拒绝（豁免必须有理由）。
  - **这是一次行为变更**：现行是"警告不拦"（[SubmitArchive.ts](../../../../src/application/use-cases/SubmitArchive.ts) 注释写明"可能有意只收关键文档"）——故配回退开关（见 FR-6），并由本需求的人工批准闸门确认。

**验收标准**：

1. fixture 有 1 份未列未豁免文件 → 提交被拒，错误信息含该 path 与两种处置方式；台账零变化。
2. 传 `unlisted_ack` 覆盖该文件（带理由）→ 提交成功，留痕含理由。
3. `unlisted_ack` 含不存在的 path / 空 reason → 分别被拒。

### FR-3: 豁免规则常量单点

**功能描述**：哪些文件属"机器生成、不进清单"由一份常量定义，可查、可测、单点修改。

**详细说明**：

- **使用场景**：对账时判定；维护者想知道"为什么这些不算漏"。
- **规则（初稿，设计阶段可微调）**：

| 规则 | 匹配 | 理由 |
|---|---|---|
| `rtm-*` | `dir/rtm-*.yml`、`dir/rtm-*/**.yml` | 追溯报告由工具重建，每个需求必然一堆 |
| `queue.json` | `dir/queue.json` | 台账镜像，工具重建 |
| `state/*` | `dir/state/**` | 运行态留痕，工具重建 |

- **预期结果**：规则以常量导出（含理由），README/说明书可引用；测试锁定"新增机器生成物必须显式登记"。
- **边界条件**：`tasks/*.md`、`evidence/*`、`design/*`、`tests/*`**不豁免**（它们是人的工作记录与证据，正是清单该收的）。

**验收标准**：

1. 单测：对 fixture 目录，`rtm-*.yml` / `queue.json` / `state/*` 命中豁免；`tasks/t-x.md` 不命中。
2. 常量以 `as const` 导出且带理由字段（静态断言：每条规则必有 reason）。

### FR-4: 已归档需求的一次受控补录

**功能描述**：需求归档后，若发现清单不完整，可走一次**受控补录**：只追加清单条目与留痕，不改产物本体、不改需求状态、不重写历史。

**详细说明**：

- **使用场景**：本次 REQ-261004174324-4195 的实测场景——归档后才发现有 88 份未列，而冷侧只读。
- **操作流程**：
  1. agent/人在看板发起补录，给出**新增**的清单条目（`docs[]` 增量）+ 理由。
  2. 系统校验：只允许**追加**（不得修改/删除既有条目）、需求必须是 `archived`、幂等（同 path 已存在 → 跳过并如实回报）。
  3. 写一条留痕（谁、何时、补了什么、为什么），台账 archive 记录追加条目。
- **预期结果**：清单可补救，但**历史不可改写**——原提交记录保持原样，补录是独立、可追溯的一件事。
- **边界条件**：
  - 非 `archived` 状态 → 拒绝（该走正常归档）。
  - 试图修改既有条目 → 拒绝（只能追加）。
  - 与"冷侧只读"的关系：补录**不碰冷侧产物**（不改 verification.md 等文件、不改 `merged_into`/`manual_updates`），只追加清单与留痕——这是本 FR 的硬边界。

**验收标准**：

1. 对已归档需求调补录（新增 3 条）→ 台账 archive.docs 增加 3 条、留痕可见、状态仍 `archived`。
2. 同一 path 再补一次 → 幂等（不重复追加），回报 `skipped`。
3. 尝试"修改既有条目"或对非归档需求补录 → 分别被拒。

### FR-5: 漏登与豁免持久可见

**功能描述**：未列/豁免不再只活在工具回执里——写进需求台账留痕，并在看板归档页展示。

**详细说明**：

- **使用场景**：事后复核归档完整性。
- **操作流程**：提交（或补录）时把三份清单的计数与未列明细写进需求评论；看板归档页读取并展示。
- **预期结果**：任何人在看板上能看到"这次归档列了哪些、豁免了哪些、若未列则为何"。
- **边界条件**：看板读取失败不影响归档主流程（只读展示）；无归档记录的需求不显示该区块。

**验收标准**：

1. 归档后 `GET /dashboard/api/reqboard/`（归档页数据源）含三份清单计数；断言样例。
2. 台账评论里能找到同样的计数（命令 + 输出摘要）。

### FR-6: 门禁、测试与行为变更的回退

**功能描述**：这次改动含一次**行为变更**（未列：警告 → 拒绝），必须有回退开关与明确的测试覆盖。

**详细说明**：

- **使用场景**：改动上线后若发现"拒绝"过严（合法场景被拦），维护者可一键回退到"只警告"。
- **操作流程**：配置项（如 `archive.unlistedGate: 'enforce' | 'warn'`，缺省 `enforce`）；`warn` 时不拒绝、只按 FR-5 留痕。
- **预期结果**：新旧两种语义都有用例；缺省行为在需求文档与说明书里写清。
- **边界条件**：非法配置值 → 装配期抛错（与 `knowledge.autoBootstrap` 同口径）。

**验收标准**：

1. `npx vitest run tests/archive-manifest*.test.ts` 全绿（对账分类 / 豁免 / 拒绝 / 补录 / 回退五组）。
2. `pnpm typecheck` 错误数 ≤ 223；`pnpm test` 失败数 ≤ 基线（改动前同窗口实测 97）。

## 接口与数据契约

| 项 | 变更 |
|---|---|
| `reqboard_submit(kind=archive)` 入参 | 新增可选 `unlisted_ack?: { path: string; reason: string }[]`（FR-2） |
| 入参 `docs[]` | 语义不变（清单条目）；补录通道复用同一形状，只做增量（FR-4） |
| 出参 | 三份清单 `listed[] / exempted[{path, rule}] / unlisted[]`；保留 `unlisted_files`/`warning` 兼容（FR-1） |
| 新增动作 | 补录清单（工具/看板入口；只追加 + 留痕）（FR-4） |
| 配置 | `archive.unlistedGate`（`enforce` 缺省 / `warn`）；非法值装配期抛错（FR-6） |
| 台账 | `archive.docs` 追加条目 + 需求评论留痕；**不改** `merged_into` / `manual_updates` / 状态机（FR-4、FR-5） |
| 豁免常量 | 新模块（如 `src/domain/requirement/archive-exemptions.ts`），`as const` + 每规则带 reason（FR-3） |

## 迁移与回滚

- **存量已归档需求**：不受影响（不追溯、不批量补录）；需要时可对个别需求走 FR-4 补录。
- **提交行为变更**：`enforce`（缺省）会让"以前只警告"的提交变成拒绝——首次遇到时按错误信息处置即可；紧急回退 `warn`。
- **回滚**：配置回 `warn` = 回到旧语义（仍保留对账与留痕，比旧版信息更多）；revert 提交 = 完全回到旧行为。

## 边界（不做什么）

- **不把目录内全部文件自动塞进清单**：清单是「选出来的关键文档」，不是目录索引——否则"人挑过"的信息量就没了（本次只做对账与显式豁免，不做"全量收录"）。
- **不改冷侧只读语义本体**：补录只追加清单与留痕，不允许改写既有归档记录与产物文件。
- **不动 `merged_into` / `manual_updates` 的必填规则与金字塔生长要求**。
- **不新增必须人工点按的归档步骤**：默认路径上 agent 一次提交即可完成。

## 非功能需求

- **性能**：对账遍历目录一次，需求目录典型 ≤200 文件；不引入第二次全目录扫描（P95 < 100ms，单测计时断言）。
- **兼容**：老客户端读不到新字段即忽略；`unlisted_files`/`warning` 不删。
- **幂等**：补录同 path 重复调用不产生重复条目（单测断言）。
- **响亮**：拒绝时错误信息必须给出"哪些文件 + 两种处置方式"，不写"参数错误"这类空话。

## 验收标准（整体）

1. 在 fixture 需求目录（含 `rtm-*.yml`、`queue.json`、`tasks/t-1.md`、未列 `evidence/x.txt`）上：提交被拒 → 处置后通过 → 归档后补录 3 条 → 台账与看板都能看到三份清单。
2. `npx vitest run tests/archive-manifest*.test.ts` 全绿。
3. `pnpm typecheck` ≤ 223 错；`pnpm test` 失败数 ≤ 基线 97（新增用例全绿）。
4. 回退演练：`archive.unlistedGate='warn'` → 回到"不拒绝、只留痕"，其余行为不变。

## 依赖与约束

- **强依赖**：`SubmitArchive` 现有对账遍历（[SubmitArchive.ts](../../../../src/application/use-cases/SubmitArchive.ts) 第 159–176 行）——本次在同一处升级为三分类，不新建第二套遍历。
- **强依赖**：`reqboard_submit` 工具 schema（`SubmitTool`）与看板归档页数据源（`http/routers`、`client/views`）。
- **约束**：零新增运行时依赖；豁免常量放 domain（纯数据，可单测）。
- **约束**：`pnpm kb:check` 必须保持退出码 0（改源码后按 C-13 重跑 `--write`）。
