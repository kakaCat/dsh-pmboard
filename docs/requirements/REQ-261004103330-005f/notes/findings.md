# 实施期发现（REQ-261004103330-005f）

> 这里记的是**实施过程中真的撞上的东西**：既有代码的缺陷、设计文档没覆盖到的情况、以及环境层面的硬约束。

## 发现 A · 既有缺陷（已核实，**本需求不修**，建议单独立项）

**位置**：`src/repositories/ShardedRequirementWriter.ts:316-332`

```ts
const version = before.record.version + 1                       // 自增后的新版本
const merged: RequirementRecord = { ...(draft as ...), version, comments: [...] }
await repo.writeRecordAtomic(root, id, hot)                     // 盘上写的是新版本 ✓
const finalRecord = { ...merged, ...(draft as ...) }            // ← draft.version（旧）把新值盖回去 ✗
this.deps.notify(kind, id, summarize(finalRecord), revision, factsOf(finalRecord))
return { requirement: finalRecord, version, revision, changed: true }   // 两个 version 字段互相矛盾
```

**机制**：`merged` 里 `version` 是新值，但紧接着用 `...draft` 展开，`draft` 带的仍是**自增前**的版本号，于是把它盖回旧值。

**影响**（属"读己所写不成立"那一类）：
1. 广播出去的记录（SSE → 看板投影）里 `version` 是旧的；
2. `mutate(...)` 返回的 `result.requirement.version` 是旧的，而同一返回体的 `result.version` 是新的——**同一个返回体自相矛盾**；
3. 任何拿 `result.requirement.version` 去做下一次 `mutateIf(expectedVersion)` 的调用方会拿到**假冲突**（`REQBOARD_CONFLICT`），或按旧版本继续写。

**运行时复现（2026-10-04，一次性脚本，跑完即删）**：用假分片文件系统搭一个分片 store，种子版本 3，调一次 `mutate` 改标题：

```
权威读（落盘后）版本      : 4     ← 盘上是新版本，写没问题
mutate 返回的 version 字段: 4     ← 返回体的标量字段是对的
mutate 返回的记录版本     : 3     ← 旧值：result.requirement.version 落后
订阅帧摘要里的版本        : 3     ← 旧值：SSE 推给看板的投影落后
写入前版本                : 3
```

**结论**：盘上与"返回体标量字段"是一致的新版本，而**同一返回体里的记录对象**与**广播出去的摘要**停在旧版本。
这不是理论推演，是实测——`{ ...merged, ...draft }` 那一处展开把 `draft.version` 盖回去了。

**为什么不在这里修**：它属于分片存储实现（另一个需求的产物），本需求的卡不越界。**已单独立项**（bug）。
**本需求侧的处理**：本次新增的 SQLite 实现（t3）**不回带旧版本**，即不复制这个缺陷。

## 发现 E · 三条实施期裁定（都经代码核实，写给验收与后续读者）

### E1 `seq` 不进记录形状——**不是缺陷**（t9 实测上报，已裁定）

现象：经端口读回的 `comments[]` 与 `statusHistory[]` 里**没有** `seq`（也不含 `kind` 的位置信息）。
核实：分片侧与 SQLite 侧**共用同一个 `commentOf`**（来自 `src/domain/requirement/Journal.js`）——
`seq` 是**日志位置元数据**，本来就属于日志层，不属于记录形状。
裁定：**不是缺陷，两实现等价**（同一份映射函数，等价性由构造保证）。
给后续调用方的话：**要 `seq` 请用日志/库表，不要从记录形状里取**。

### E2 迁移用「暂存库 + 顶上」而非「事务内校验」（t9 的偏离，**接受**）

设计 `data-model.md` 写的是"单事务内导入、不过就回滚"。实现改为**先建暂存库、校验通过后顶上目标库**。
接受理由（比设计更硬）：端口 `replaceAll` 的事务在返回时**已提交**、且没暴露"提交前回调"，
脚本**无法在事务内校验**；暂存库让校验作用在"**将要成为目标库的那份字节**"上，
失败时**目标库从头到尾没被碰过**，还少一类"回滚本身失败"的风险。
代价：多一次文件改名，且需要清理暂存库（反向演练已锚定：移除清理 → 用例精确变红，残留恰为暂存库 + wal + shm）。
若要严格照设计，需给端口加"事务内校验钩子"——那是 t3 的契约变更，本轮**不做**。

### E3 `GET /settings` 顶层多了一个 `settingsFile`（**新增，不是漂移**）

设计写的是 `system.paths`——**它确实在**（实现里 `paths` 与分片根/库文件合并后返回）。
实现另外在**顶层**给了 `settingsFile: { exists, path }`，供「打开配置文件」按钮少拉一次请求。
裁定：接受这条新增；**设计文档无需改**（没有少给什么，只是多给了一个便利字段）。
注意：`system.paths` 是**条件出现**的（系统记录未就绪时不带该键），前端必须先看 `system.ok` / `system.exists`。

## 发现 F · 迁移留痕缺口（**已补**，含修法与三处加强）

**缺口**：`scripts/migrate-ledger-to-sqlite.ts` 结束时**一处都没写系统记录**——
FR-14 要的"迁移留档"落空：看板「系统记录」屏看不到迁移发生过，"上次迁移何时、成没成、备份在哪"全查不到。

**修法的关键在位置（值得后来人照抄）**：脚本内部有 **8 处返回路径**（预检 / 读源失败 / 备份失败 / 旧库备份失败 /
导入失败 / 校验不过 / 写设置失败 / 顶替失败 / 成功）。**逐处补写必然漏一处**——"某条失败路径忘了留痕"正是这么来的。
故在**最外层包一层**：内部原实现改名，包装器拿到报告后**统一记一次**事件；返回路径再多也只写一次。

**三处超出指令的加强（都接受）**：

| # | 加强 | 为什么必要 |
|---|---|---|
| 1 | `--dry-run` **不写**档案，并补断言"记录文件不存在" | 它承诺"不写任何文件"——**档案也算写盘**；不处理就会在"不写"的路径上偷偷留一条事件 |
| 2 | 留痕实现放 support 文件、用布尔 `ok` 传参 | 尺寸门禁 + 避免 helper 反向依赖主脚本的退出码常量（无循环） |
| 3 | 既有用例「源不是分片布局 → 不写任何东西」改为**如实**措辞并补断言 | 台账确实不碰，但**档案会留一条 `failed`**——那是诚实留档，不是副作用 |

**口径澄清（与 t10 那条裁定不冲突）**：**请求阶段**不写事件（事件的语义是"发生了什么"，不是"请求了什么"）；
**脚本真的跑过**（哪怕预检就没过）就留一条 `result:'failed'`——它确实"发生"了一次失败的迁移尝试。

## 发现 G · 一条**仍未闭合**的留痕保真度缺口（如实报，不在本轮掩盖）

**现象**：`migration` 事件的两个关键字段在生产路径上取不到值：
- `windowKey`（哪个窗口干的）与 `confirmedBy`（谁在什么时候确认的）由脚本写入，但**脚本的 CLI 没有对应参数**；

## 发现 I · 「打开配置文件没有反应」（**归档后由人实测报出，已修**）

**现象**：人点页头「打开配置文件」，没有任何反应。

**根因（两层，都是"静默"）**：

1. 设置文件**惰性创建**——`~/.dsh/dsh-reqboard-settings.json` 在人第一次保存上限或确认切库之前**不存在**，
   而按钮此时渲染成 `disabled`：**浏览器不给禁用的按钮派发点击**，所以点了必然"没反应"；
   唯一的解释只写在 `title` 里（要悬停才看得到）。
2. 即使文件存在，点击走右侧栏打开通道，**返回失败时也没有任何提示**（`openDoc` 的返回值被忽略）。

**修法（三处 + 一条断言改强）**：

| 处 | 改前 | 改后 |
|---|---|---|
| 页头按钮 | `disabled`（死点击） | `aria-disabled="true"`（外观仍置灰）+ **可见旁注「尚未创建」**（不靠悬停） |
| 点击行为 | 什么都不做 | 抽成纯函数 `openConfigIntent(state)`：文件在 → 打开；**没创建 → 跳到「通用」屏**看整句解释（首次保存上限或确认一次切库后落盘） |
| 打开失败 | 静默 | 状态条（`aria-live`）给话：通道不可用 / 宿主未提供通道 |
| 断言 | 只断言"有 disabled" | 断言 **aria-disabled + 可见旁注 + 三条点击意图**（改强，不是放松） |

**同类风险（值得记）**：任何"禁用即静默"的控件都会长成人报的这样——**点了没反应**。
判据：不可用时要么给**页面上看得见**的理由，要么让点击给出解释；**只给 `title` 等于没给**。

## 发现 K · 同一个错误我犯了三次：CSS 注释里的反引号（**必须制度化**）

| 次序 | 位置 | 后果 | 谁发现 |
|---|---|---|---|
| 1 | 我改标题间距时的注释（`.pane-title .muted`） | 样式表后半段失效、`SETTINGS_CSS` 类型变 `number` | 后续卡跑 `tsc` |

- 设置样式表里**不得**出现原型私有令牌字样（**注释也算**）——已有用例拦着，这条是它拦出来的。

## 发现 L · 生产装配漏了五个接口（**归档后由人实测报出，已修**）——本次最严重的一处

**人看到的那条**：「系统记录通道未装配（fetchSystemRecord 缺失）」。

**真实范围比报的大得多**：`src/client/settings/singleton.ts` 里只注入了 `fetchRunSettings` **一个**函数，
而弹窗要用**六个**。所以生产环境里：

| 功能 | 症状 |
|---|---|
| 系统记录屏 | 「系统记录通道未装配（fetchSystemRecord 缺失）」 |
| 保存上限 | 「保存未执行：保存通道未装配（patchRunSettings 缺失）」 |
| 切库/迁移的确认门 | 「确认通道未装配（requestStorageAction 缺失）」 |
| 改路径 / 切后端 / 起迁移 | 同样报未装配 |

**整块功能在生产里是残的**——而我把四张前端卡 + 端到端 + 形态断言全跑绿了。

**为什么一路测试都绿（这次要记牢）**：

1. 单测一律注入**假 api**——「真装配给了什么」从来没人测；
2. 控制器把 `api` 的方法设计成**可选**，缺省时"如实报未装配而不假装成功"。这个**优雅降级**本身是好设计，
   但它把「装配漏了」**藏进了正常输出里**——报错文案长得像一句正常提示。

**修法**：抽出具名工厂 `boardSettingsApi()`（六个接口整体注入），并在 `singleton.ts` 导出以便测装配。

**守卫**：`tests/settings-wiring.test.ts`（5 条）。**这里有个必须写下的过程**：
我的**第一版守卫照样全绿**——因为它测的是**工厂函数齐不齐**，测不到"装配有没有用它"。
反向演练（把装配改回只给一个）实测：第一版 5 条全过。改成**源码级静态判据**
（装配处必须是 `api: boardSettingsApi(),`、不许出现 `api: {`）后，同一次演练**精确变红**，恢复即绿。
本仓已有同类先例（A7 门禁锚定标识符）。

**顺带把整个装配审了一遍**（同类漏洞可能还有）：`jumpToWindow` / `openDoc` / `focusReturn` 由看板注入（`board-mount` 已传）；
`host.el` 有（`createBodyHost` 返回 `el: host`）→ 改路径的编辑器能挂上。
结论：修完 `api` 这一处，生产装配齐全。

## 发现 N · 「改路径」要**像操作系统那样**弹窗口选地址（2026-10-04 人要求，已实现）

**人要求原文**：「存储与数据库 改路径应该和操作系统的一样打开窗口选择地址」。

**为什么必须落在宿主进程**：看板跑在浏览器里，而**浏览器拿不到真实绝对路径**
（安全边界：`<input type=file>` 只给 `fakepath`）。所以真正的选择只能由宿主（Node）执行。
macOS 上用 `osascript` 的 **`choose file name`**（「存储为」式窗口：能选目录、能起文件名，返回 POSIX 绝对路径）——
选它而不是"选目录"，因为这要的是**库文件路径**（含文件名）。

**实现（四层 + 一条可注入缝）**：

| 层 | 落点 | 说明 |
|---|---|---|
| 端口 | `application/ports.ts` 的 `StoragePathPickerPort` / `StoragePathPickOutcome` | **只有三态**：`picked` / `cancelled` / `unavailable(reason)` |
| 适配器 | `adapters/StoragePathPicker.ts` | `execFile` 跑**常量脚本**；`timeout` + `killSignal: SIGKILL`；非 darwin / 缺 osascript → unavailable |
| 路由 | `POST /settings/storage/pick-path` | 200 `{ok:true,path}` / 200 `{ok:false,cancelled:true}` / **501 `path_picker_unavailable`**（已登记进 `STATUS_BY_CODE`） |
| 界面 | `render/storage.ts` 的「选择…」+ `storage-path.ts` | 选中 → **填入并标脏**（保存仍由人点）；取消 → 什么都不改；501 → "请手动输入路径" |

**两条硬纪律（都有用例）**：
1. **脚本是常量**：`-e` 的文本不含任何请求内容，参数只走 `execFile` 的 argv，**shell 不参与** →
   路由层用例发一个恶意请求体（含 `"; rm -rf / #`、`$(whoami)`），断言端口**收到的入参为空**；
   适配器层用例断言传给进程的 argv **恒等于 `['-e', PICK_PATH_SCRIPT]`** 且脚本里没有 `do shell script`；
2. **超时即杀**：没人理的对话框不能把 HTTP 请求挂到天荒地老（默认 10 分钟，`SIGKILL`）。

**与上一版的关系（如实记）**：本卡先前实现过一版 `pick-directory`，走 DSH 的 `ctx.directoryPicker` 服务
（那是**选目录**的缝）。本卡规格要求的是**文件路径** + 「存储为」窗口 + 可注入端口，故**统一替换**为现在这一版，
旧版的路由/适配器/端口/用例与三个 `directory_picker_*` 错误码**已全部回收**，不留两套竞争实现。

**过程中的一处连带修复**：`client/settings/controller.ts` 在本卡开始时已被并行改动顶到 **419 行**（超尺寸门禁 400），
其中 2 行是本卡上一版加的。本卡**把两个纯类型块（注入契约 + 宿主抽象）外移到 `controller-api.ts`**，
控制器回到 **399 行**，尺寸门禁里不再出现它（现存的超标项都是别的文件/存量）。

## 发现 O · 系统记录屏永远停在「正在读取…」（**人报，已修**）

**现象**：切到「系统记录」屏，一直显示「正在读取系统记录…」。

**查法（先排除宿主）**：直接 `curl` 宿主接口 → **HTTP 200 / 4ms / 1920 字节**，宿主好好的；
再用**真实响应**喂渲染模型 → 解析出**两种形状**的差别：
`data`（解包后）→ `ready`；**整信封** → `loading`。

**真因（两处，都在客户端）**：

1. **形状包了一层**：宿主这条接口回的是 `{ ok, record: { …真记录… }, paths, historyTotal, … }`，
   真记录在 `record` 里；而客户端把**外壳**当成了记录 → `plugin/history/compat/stores` 全读不到（界面一片「未知」）。
2. **永不收敛的加载态**：渲染层只要 `record.ok !== true` 就判「读取中」——**任何不被识别的形状都会变成一个永远转的加载态**。
   这正是"卡在读取中"这条报障的机制：**静默的类型不符伪装成了「还在加载」**。

**修法**：取数处**形状归一**（有 `record` 就用它），并且**认不出来就如实报错**（`record-fail` + 把收到的键名说出来），
**绝不留一个永转的加载态**。

**验证**：新增 2 条断言（外壳 → 取里面那条真记录；形状不认识 → 必须 `record-fail` 且**不得** `record-ok`）；
设置相关 7 个文件 **147 passed**；构建通过；本需求文件类型错误 0。

**教训**：**「加载中」不能是终端态**。凡是"拿到响应但形状不符"就必须落到一个**说人话的错误**上——
否则最糟的 bug 会伪装成最无辜的界面。
