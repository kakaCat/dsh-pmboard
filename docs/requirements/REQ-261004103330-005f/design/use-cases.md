## UC-1 需求在实施阶段空转：把上限收小，当场停手 <!-- serves: FR-1, FR-2, FR-3, FR-4, FR-5 -->

- **用例角色**：看板使用者（人）。
- **前置条件**：有一条需求停在"实施"阶段，自动续跑已转了很多回合却没有进展；该阶段当前用的是内置默认上限（1000）。
- **主流程**：
  1. 打开看板 → 右上角「设置」→ 左菜单「运行上限」。
  2. 找到「实施」一行：看到"内置默认 1000 / 当前生效 1000 / 来源：内置默认"。
  3. 把上限改成 5 → 该行高亮为"待保存"，来源徽章变「待保存」，底部浮出保存条，左菜单项挂上「1 项未保存」。
  4. 点「保存」→ 提示已保存；该行来源徽章变为「设置文件」。
  5. 回到看板：该需求在**下一个回合**被判已达上限 → 停手，「实施」泳道卡面亮出"已达上限"。
- **异常分支**：
  - 填 0 / 10001 / 小数 → 当场标红「需 1–10000 的整数」并禁用保存键；**磁盘上没有任何变化**。
  - 保存时后端拒绝（权限 / 磁盘满）→ 明确报错并保持原值，界面**不谎报已保存**。
  - 设置文件被人手工改坏 → 看板仍按内置默认值显示（来源标「内置默认」），并在系统记录里留一条"某键被作废"的痕迹。
- **后置状态**：设置文件里只多了"实施=5"这一项；系统记录追加一条保存留痕（谁、什么时候、哪个插件版本）。
- **成功判据（可观察）**：泳道卡面从"还能续跑"变为"已达上限"；设置页该行来源显示为「设置文件」。

## UC-2 需求跑飞：收紧上限，但不打断正在跑的那一回合 <!-- serves: FR-2, FR-3, FR-4, FR-5 -->

- **用例角色**：看板使用者（人）。
- **前置条件**：某需求在"设计"阶段已跑到第 30 回合，上限原为 200；人决定收紧到 20。
- **主流程**：
  1. 设置 → 运行上限 → 把「设计」改为 20 → 保存。
  2. 观察正在跑的那一回合：**不被中断**，照常跑完（不打断已经开工的活）。
  3. 该回合结束后按新上限判定：已超 20 → 不再起下一回合，停手并**如实给出停手原因**"已达上限（20）"。
  4. 若人改主意想让它继续：把上限调到大于已跑回合数 → 下一回合即恢复续跑。
- **异常分支**：
  - **向下调过头**（例：已跑 5 回合，人把上限改成 3）→ 允许；**下一回合的判定即停手**，停手原因如实写"已达上限（3）"，而**正在执行的那一回合不被中断**。
  - 已跑回合数**小于**新上限（例：已跑 5 回合、上限改成 10）→ 照常续跑，不停手。
  - 同一阶段有多条需求 → 新上限对该阶段所有需求一视同仁（这是全局设置，不是单需求设置）。
- **后置状态**：新上限对后续所有该阶段的需求生效；已停手的需求保留"已达上限（值）"的停手原因，便于人事后看出它是被哪个值停下的。
- **成功判据（可观察）**：改动后当前回合完整跑完；此后该需求的回合数不再增长；停手原因里能看到生效的那个上限值。
- **一句话给人听**：改小不会掐断正在跑的那一次，但从下一次判定起不再续跑。

## UC-3 第一次把台账切到 SQLite：确认 → Agent 五步 → 重启生效 <!-- serves: FR-1, FR-6, FR-7, FR-10, FR-11, FR-14 -->

- **用例角色**：看板使用者（人）+ 迁移 Agent（新开的窗口）。
- **前置条件**：台账目前存在分片目录里（128 条需求）；机器上还留着一个更早时候迁过的旧库（44 条）。
- **主流程**：
  1. 设置 → 「存储与数据库」→ 选「SQLite」。
  2. 面板显示"待人工确认：迁移完成并重启后才生效"，数据位置切换为库文件路径；「生效时机」写明未生效。
  3. 面板主动提示旧库的存在与差异（44 条 · 更早的日期 · 比当前少 84 条），并说明会"先备份旧库再重建"。
  4. 点「交给 Agent 处理」→ 弹出确认框：逐条列出要做什么、动什么、不动什么，并写明"确认会留痕（谁、什么时候、哪个插件版本）"。
     确认框写清授权范围：**这一次确认覆盖全部五步，包含最后那步"写设置"**（不是只批准"开始迁移"）。
  5. 点「确认执行」→ 弹窗关闭；面板出现"迁移与校验 · Agent 窗口 <窗口码>"与五步进度。
  6. Agent 依次执行：备份分片目录 → 建库建表 → 事务迁移 128 条（只读源数据）→ 校验条数并抽样比对 → 校验通过后写设置。
     （"写设置"由 Agent 执行已确认任务时带上；人手跑脚本时它默认关，那**只是手动路径的保守缺省**，不代表还要再确认一次——确认是许可，缺省关是保守值。）
  7. 面板给出结论："128 条 → 128 条，抽样一致；已记入系统记录；下一步重启宿主"，并给出备份目录。
  8. 人重启宿主 → 再打开设置页：「当前后端」显示 SQLite，「生效来源」显示「设置文件」。
- **异常分支**：
  - 窗口没开起来 → 明确报"没有开起来"，**不写迁移事件**、不显示"进行中"（不伪造已开始）。
  - 已经有迁移在跑 → 提示先去看那个窗口，不重复开。
  - 校验不通过 → 走 UC-6。
  - **迁移完成、还没重启时分片又被写了新需求**（例：另一个窗口刚建了两条）→ 重启前**检出并标"已陈旧"**，提示"重启前请重跑迁移（会先备份旧库再全量重建）"；**绝不静默合并**，重跑仍要过一次确认。
- **后置状态**：库里有 128 条；设置文件写明目标后端为 SQLite；系统记录多一条迁移事件（含窗口码、确认人、插件版本、备份目录）。人的确认是**一次许可覆盖五步**，留痕里能看到被许可的范围。
- **成功判据（可观察）**：重启后设置页显示 SQLite 且来源为「设置文件」；看板上的需求 / 任务 / 评论数量与切换前一致。

## UC-4 在确认框上点「取消」：零副作用 <!-- serves: FR-11 -->

- **用例角色**：看板使用者（人）。
- **前置条件**：已经走到确认框，还没点确认。
- **主流程**：
  1. 读完确认框里的影响清单后点「取消」（ESC、点遮罩外同理）。
  2. 弹窗关闭，回到设置页。
  3. 面板提示"已取消：未开窗口、未写任何文件"。
- **异常分支**：
  - 取消后又想切 → 重新点「交给 Agent 处理」会**重新弹确认框**：每一次执行都要当场确认，不"记住上次同意"。
  - 取消前已经选了 SQLite → 面板仍显示"待人工确认"，不因取消而回退成 JSON（选择与执行是两件事）。
- **后置状态**：磁盘上不多任何文件；系统记录里不出现迁移事件。
- **成功判据（可观察）**：设置页仍显示"待人工确认"；库文件与设置文件都无变化。

## UC-5 试点不理想：切回原来的分片存储 <!-- serves: FR-6, FR-11, FR-14 -->

- **用例角色**：看板使用者（人）。
- **前置条件**：SQLite 已生效并跑了一段时间，人决定回退。
- **主流程**：
  1. 设置 → 「存储与数据库」→ 选「JSON 分片」。
  2. 弹确认框：列出"把目标写回分片、库文件保留不删、重启后生效"。
  3. 点「确认切回」→ 提示已写入，需重启生效。
  4. 重启宿主 → 分片重新生效；设置页「当前后端」回到 JSON 分片。
- **异常分支**：
  - 库文件在这期间被手工删掉 → 面板标"库不存在"，但**不影响回滚**（回滚只依赖分片）。
  - **两侧已分叉**（切库之后、重启之前分片又被写过：分片条数多于库，或分片的最后写入时间晚于库的迁移时间）→ 面板**检出并标"已陈旧"**，提示"重启前请重跑迁移（会先备份旧库再全量重建）"；**绝不静默合并**，也不悄悄挑一边用。
  - 回滚方向上发现库里有分片没有的写入 → 同样**如实提示分叉**并给对照入口，由人决定以哪边为准；不静默丢弃。
- **后置状态**：分片为生效源；库与备份留在盘上；系统记录多一条"切回"事件（含确认人与原因）。
- **成功判据（可观察）**：重启后设置页显示 JSON 分片且来源为「设置文件」；系统记录时间线里能看到"SQLite → JSON 分片"这一条。

## UC-6 迁移跑到一半失败：自动回滚，重试仍要重新确认 <!-- serves: FR-10, FR-11, FR-14 -->

- **用例角色**：迁移 Agent + 人。
- **前置条件**：五步跑到第 3 步（事务迁移）时报错（磁盘满 / 权限不足 / 库损坏）。
- **主流程**：
  1. 面板变红并说明："失败在第 3 步；事务已回滚；源数据未改动；设置未写入；库文件留着可续跑"。
  2. 人打开 Agent 窗口看原始报错，处理原因。
  3. 回到设置页点「打开迁移窗口」（或「重来一次」）。
  4. 因为要重新动数据，**仍需再点一次确认**——失败不构成"已同意"。
  5. 重试成功后进入 UC-3 的第 7 步。
- **异常分支**：
  - 反复失败 → 面板显示失败次数（系统记录里有计数），并提示"可以先切回分片，什么都不动"。
  - 失败后源分片被别的窗口写入了新需求 → 重试**一律以当前分片为准做全量重建**（迁移算法本就是全量重建，天然覆盖"重试前分片被写了新需求"，不是照抄第一次的清单）。
  - 重试时**旧库与旧备份保留不删**，面板与确认框明示"会重建库（先备份现有库）"，让人知道旧的那份还在。
- **后置状态**：失败期间系统记录里有一条失败事件（含原因与步号）；源数据逐字节未变。
- **成功判据（可观察）**：失败后分片里的需求数、评论、历史与失败前完全一致；设置页「当前后端」仍是原后端。

## UC-7 迁移没做完就重启：拒绝服务并给指引 <!-- serves: FR-6, FR-12 -->

- **用例角色**：看板使用者（人）。
- **前置条件**：设置里目标后端是 SQLite，但库还是空的（迁移没跑或没跑完），分片里却有 128 条需求。
- **主流程**：
  1. 重启宿主。
  2. 看板**不显示"空板"**，而是显示未就绪提示 + 可复制的指引。
  3. 指引**按两种不同的未就绪分别给**——不能合并成一句"去迁移"（要跑的脚本、要动的数据都不同）：
     - 已选 SQLite、库空而分片非空 → "点设置页的『交给 Agent 处理』，或跑 `migrate-ledger-to-sqlite`"；
     - 单册旧数据还在、分片还没迁移（既有情形）→ "跑 `scripts/migrate-ledger-v10.ts`"。
  4. 人照指引完成迁移（或直接用设置页的按钮）。
  5. 再次重启 → 正常打开，SQLite 生效。
- **异常分支**：
  - 分片与库都为空（全新机器）→ 属于**正常启动**，打开就是空看板，不报"拒绝服务"。
  - 两种未就绪**同时**成立（单册在场 + 已选 SQLite）→ 先后给出**两条**指引（先解决单册迁移、再解决库迁移），不因先看到一条而漏掉另一条。
- **后置状态**：未就绪期间不产生任何写操作，不建空台账、不覆盖任何数据。
- **成功判据（可观察）**：未就绪时接口返回"服务未就绪"而不是空需求列表；指引能复制、照做后能恢复。

## UC-8 检出旧库：先备份旧库再重建 <!-- serves: FR-13, FR-14 -->

- **用例角色**：看板使用者（人）。
- **前置条件**：机器上曾迁过 SQLite（44 条），后来切回了分片，旧库留在盘上；分片现在已涨到 128 条。
- **主流程**：
  1. 切到 SQLite 时，面板主动提示旧库的存在与差异（条数、日期、差多少）。
  2. 确认框里写明"会先备份旧库再重建"，**不是**直接连上旧库继续用。
  3. 迁移完成后，旧库被放进备份目录；库里是 128 条。
- **异常分支**：
  - 旧库损坏、读不出条数 → 仍按"先备份再重建"处理，并在面板标注"旧库无法读取，已备份保留"。
  - 旧库路径不可写（不能改名备份）→ 拒绝执行并给指引（先处理权限），**不冒险覆盖**。
  - "陈旧"的另一种来源：迁移完成、还没重启时分片又被写过（分片条数更多，或分片写入时间晚于库的迁移时间）→ 与"旧库"**同一条判定**，同样标"已陈旧"并提示**重跑迁移**（先备份旧库再全量重建），不静默合并。
- **后置状态**：备份目录多一份旧库；系统记录记下"检出陈旧库"与处置方式。
- **成功判据（可观察）**：迁移后条数等于当前分片值（不是旧库的 44）；备份目录里能找到那份旧库。

## UC-9 排查"以前用过 SQLite 吗、上次是谁改的后端" <!-- serves: FR-3, FR-14, FR-15 -->

- **用例角色**：复盘者 / 接手这条线的人。
- **前置条件**：距上一次后端切换已过了一段时间，当时操作的人不在。
- **主流程**：
  1. 打开设置 → 「系统记录」。
  2. 读"后端使用史"时间线：启动 / 插件升级 / 迁移 / 切回 / 启动——每条带时间、结果、谁确认的、哪个插件版本、备份在哪。
  3. 读"数据路径档案"：分片在哪、库在哪、备份在哪、旧单册在哪，各自多大。
  4. 需要原始凭据时点「查看原始记录」导出整份记录。
- **异常分支**：
  - 记录文件曾被删 → 时间线只从重建那天开始，面板明确注明"记录自 <时间> 起"，**不假装历史完整**。
  - 记录文件不可写 → 面板红字显示"记录不可写（原因）"与"已丢弃 N 条事件"。
- **后置状态**：无需登录服务器、无需翻命令行历史即可回答三个问题。
- **成功判据（可观察）**：能答出"哪天切过 SQLite / 谁确认的 / 库与备份在哪"，且信息全部来自面板。

## UC-10 插件刚升级：旧库还能不能直接用 <!-- serves: FR-15, FR-16 -->

- **用例角色**：看板使用者（人）。
- **前置条件**：插件版本从 0.1.0 升到新版本；机器上有一个旧库。
- **主流程**：
  1. 升级后首次启动：系统记录自动追加一条"插件升级"（旧版本 → 新版本，附两侧构建指纹）。
  2. 打开设置 → 「系统记录」→「版本一致性核对」：看到当前插件版本、上一次迁移由哪个版本完成、旧库写入时的结构版本。
  3. 三者一致 → 绿字"旧库可直接用于重建，不需要额外升级脚本"。
  4. 不一致 → 红字报警 + "重建库"指引；**不会硬读旧表**（避免把数据读坏）。
- **异常分支**：
  - 记录被删（没有升级历史）→ 显示"无升级历史"，一致性按"当前版本 vs 库结构版本"单点判定。
  - 构建指纹相同但版本号不同（本地构建）→ 面板以版本号为准并注明指纹差异，供排查。
- **后置状态**：升级历史可查；不一致时不会误用旧库。
- **成功判据（可观察）**：面板能回答"这个库还能不能用"，且结论同时给出**版本**与**结构版本**两个依据。

## UC-11 全新安装：第一次打开设置页（记录已有，设置文件还没有） <!-- serves: FR-1, FR-3, FR-5, FR-14, FR-15, FR-17 -->

- **用例角色**：新机器上的使用者（新人）。
- **前置条件**：从没装过，或刚清空数据；机器上既没有分片也没有库。
- **主流程**：
  1. 启动插件 → 系统记录**自动创建**：写入插件版本与构建指纹、数据路径（此刻指向空目录）、首条"启动"事件（0 条需求）。
  2. 打开设置 → 「系统记录」：能看到"这是本机的第一次启动""数据会放在哪里""当前后端是什么"。
  3. 「运行上限」屏：所有行来源都显示「内置默认」（因为设置文件还不存在）。
  4. 点右上角「打开配置文件」→ 提示"设置文件尚未创建，第一次改动才会生成"（或给出默认值预览）。
  5. 人改一次上限并保存 → **这时**设置文件才出现，里面只有他改的那一项。
- **异常分支**：
  - 档案文件不可写（权限 / 磁盘）→ 看板照常可用；「系统记录」屏红字显示「记录不可写（原因）+ 已丢弃 N 条事件」，**不阻断启动**。
  - 日后我们调整内置默认值（例如实施从 1000 改成 300）→ 没改过设置的人自动跟随新默认；改过的人保持自己的值。
  - 人在设置文件里手写了非法值 → 该键作废、其余键照常生效，来源标回「内置默认」，并记一条"某键被作废"。
- **后置状态**：设置文件里**不出现**插件抄写的默认值——避免把默认值冻在文件里、也避免日后分不清"是人改的还是插件抄的"。
- **成功判据（可观察）**：删掉两份文件后重启 → 系统记录被重建且含首条启动事件；设置文件**仍不存在**；调一次上限后才出现。

## UC-12 换库前后，人在看板上看到的东西必须逐字一样 <!-- serves: FR-7, FR-8, FR-9 -->

- **用例角色**：人（验收者）。
- **前置条件**：同一批 128 条数据，先在分片存储上看一遍，再切到 SQLite 看一遍。
- **主流程**：
  1. 分片存储下记录：需求总数、每条的状态与版本、评论条数、状态历史条数、任务与甘特、产物列表、Token 数字。
  2. 切到数据库存储并重启（同一批数据，不新增不删除）。
  3. 逐项对比：上述每一项都必须一致。
  4. 打开大字段（需求描述、设计 / 验收材料、自动续跑的断点记录）确认内容一致。
- **异常分支**：
  - 任何一项不一致 → 视为迁移失败：按 UC-6 回滚并排查；**不允许"看起来差不多"**。
  - 两个后端跑**同一份数据契约测试**，任何一方语义漂移都会在测试里当场暴露，而不是等到人肉比对时才发现。
- **后置状态**：两种存储互为等价投影；记录结构版本不因换后端而变化。
- **成功判据（可观察）**：对比清单逐项一致；同一份契约测试同时跑三个实现（内存替身 / 分片 / 数据库）全绿。
