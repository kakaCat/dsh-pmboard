## 一、评审抓出的实质问题（按价值排序）

| # | 问题 | 怎么发现的 | 处置 |
|---|---|---|---|
| 1 | **「切库后重启生效」这句承诺是假的**——设置文件里写 `storage.backend=sqlite`，重启也不生效，装配永远按 json 起 | **端到端**（E2E-2 重启后断言从库读） | 已修：适配器构造期同步读一次盘灌初值；读失败按"无文件"处理不抛。**根因值得记住**：适配器卡测的是自身的异步刷新，装配卡测的是"后端直接传进去"——从没走过"从设置文件读出后端"这一步，所以每张卡都绿、接起来是断的 |
| 2 | **人工确认门可以被绕过**：票据"已落章"包含**否定作答**——人在确认框点「取消」，`consume` 照样返回成功；只看成功标记就执行的调用方会「点了取消照样切库」 | t8 实测（写路由时读 t7 的代码） | 两道防线：源头（否定作答 → `denied`，不消费不置位）+ 路由（`confirmed !== true` → 403）。反向演练 C 证明两道**各自独立**（删一道，另一道照常挡住） |
| 3 | **迁移留痕整体缺失**：脚本结束时一处都没写系统记录，FR-14 的"迁移留档"落空（看板看不到迁移发生过） | 我在派 t10 前核"事件里到底有没有 `migration-requested`"时发现 | 已补：最外层包一层统一留痕（脚本内部有 8 处返回路径，逐处补写必然漏一处）；`--dry-run` 不写档案；写事件失败不改退出码 |
| 4 | **设计里有一句按字面不可实现**：陈旧判定要比"分片 `headRevision`"与库的 `migratedAt`，但分片 `meta.json` 只有 revision 计数器、**没有时间戳** | t1 复核（读 `ShardMeta`） | 改用"全部记录 `updatedAt` 的最大值"（摘要索引里本就有，零额外读盘），并补上"条数相同但内容被改过"这一原先漏掉的场景 |
| 5 | **契约里一段死代码**：`withDroppedEvent` 只在内存累加，写成功一次就丢——"响亮"没进档案等于不响亮 | t2 实现时发现 | 已接上并落盘；限定一次操作最多记 1 条 |
| 6 | **系统记录无法刷新路径档案**：只在首次建档时写对路径，数据搬家后档案里仍是旧路径（看板那屏会骗人） | t5 自报 | 我判定"不能只记一笔"：当场派修（端口方法 + 幂等实现 + 每次启动调用 + 3 条用例，含只读目录降级） |

## 二、偏差审定（接受 / 记录）

| 偏差 | 判定 | 理由 |
|---|---|---|
| 迁移改用「暂存库 + 顶上」而非"事务内校验" | **接受**（比设计更硬） | 端口 `replaceAll` 的事务在返回时已提交、没暴露提交前回调；暂存库让校验作用在"将要成为目标库的那份字节"上，失败时目标库从未被碰过 |
| `settings` 表加一整块 `payload` 列 | **接受** | 历史条目是**判别联合**（状态行 / 推进事件行），推进事件整条记录放不进设计的列清单 |
| 客户端确认面板**不是**"那个同意" | **裁定保持** | 真正的同意发生在作答通道；若把落章挪进路由，这个门就可被任何能打接口的人伪造 |
| 切到"当前已在用"的后端 → 400 | **裁定** | 且判断放在消费票据**之前**，避免一次"没有可做之事"的请求烧掉合法票据 |
| 系统记录损坏 → 200 + 无效标记（不 500） | **裁定** | 档案设施坏掉不该让设置页白屏，但也不能静默当空 |
| 新增 `settings/singleton.ts`、`storage-action-types.ts` 等文件 | **接受** | 为守住"不撑大既有大文件"这条硬约束；注释原样搬、未删 |
| 我的一条指令写错（"同票改判为肯定仍可用"） | **被开发者纠正，纠正成立** | 落章首写优先，否定一旦落章不可改写——这正是审计留痕该有的样子 |

## 三、未闭合限制（在验收材料 §六 一并列明）

1. **浏览器手测未做**（无 GUI 通道）：DOM 级用例 + 构建产物验证只覆盖到能覆盖的部分；
2. **留痕保真度缺口**：`migration` 事件取不到"谁确认的 / 哪个窗口执行的"（脚本 CLI 没这两个参数）；
3. **`ports.ts` 文件增长留账**：HEAD 版即 589 行（早超标），本需求又加约 94 行——红线不是我们画的，但我们在红线边上又加了一笔；
4. **端口缺显式写后端方法**：当前以单点类型放宽顶上。
