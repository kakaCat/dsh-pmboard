# 需求说明（REQ-261007160829-1991）

> 台账类型记的是 **feature**，实质是缺陷修复（详见「讨论与裁定记录」D-3）。
> 本文档的根因一节与立项时的描述**不一致**：立项描述记的「多问只渲染第一问」已被实测推翻，以本文档为准。

## TL;DR

- **现象**：验收入点「通过」后长期停在 `unverified`，回执一律说「点了通过却没结果」——人无从知道差什么，重试无效。
- **真因**：结果文本**没有可核验锚点**时，`passed` 被**静默降级**为 `unverified`；弹框与看板共用这条判据，且回执把原因归错了。
- **做完得到**：不合格的实测结果在**提交那一刻**被挡下并点名（FR-1）；降级不再静默、原因落账（FR-2）；人自填的无锚点文本当场被拒（FR-3）；弹框一开始就写明形态要求（FR-4）。

## 业务流程图

```
agent ──reqboard_submit(kind=verification)──▶ 提交侧锚点校验（FR-1）
                                                  │
                        ┌─── 无锚点 ──▶ 拒绝 + 逐条点名 + 给样例（不再流到人面前）
                        └─── 有锚点 ──▶ 落验收单
                                            │
人 ──弹框 / 看板点「通过」──────────────────▶ applyVerdicts
                                                │
        ┌───────────────────────────────────────┼────────────────────────────┐
        │ 有锚点 → passed                        │ 人工自填无锚点 → 拒绝（FR-3，可当场改）
        │ 文本为空 → unverified(blank_pass)      │ agent 旧数据无锚点 → unverified(anchor_missing)
        └───────────────────────────────────────┴────────────────────────────┘
                                                │
                                   原因落账 + 回执按真实原因措辞（FR-2）
                                   + 弹框第 2 问题干写明形态要求（FR-4）
```

## 产品定义

这是 reqboard 插件验收通道的**结论可解释性**修复：让「点了通过却没通过」从**静默降级**变成**有原因、可预防、可执行**的闭环。

- **是什么**：验收裁决的三处收口——提交侧前置校验（不合格不进单）、裁决侧降级可见（原因落账 + 回执说真话）、人机界面侧要求前置（题干写明形态）。
- **核心价值**：把「永远过不了且不知道为什么」变成「当场就知道差什么、怎么补」。当前形态下，一次无锚点结果会让人与 agent 一起在错误方向上反复重试（实测 5 次）。
- **与现状的区别**：现在的判据本身是对的（「有字」改成「有据」），错的是**它的结论不可见、责任方错位**——惩罚落在点通过的人身上，而交出无锚点结果的是 agent。

## 用户与角色

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 人（验收裁决者） | 在弹框 / 看板点「通过」 | 点了不通过、且不知道差什么；同一文本重试必然同样结果，只能放弃改用别的方式 |
| agent（交付方） | 提交 `kind=verification` 的逐项 `result` | 不知道结果文本要带锚点；交出的证据「看着很完整」，却让人无从裁决 |
| 后续窗口 / 验收人 | 读台账复盘为什么卡住 | 台账只有 `unverified`，没有原因，分不清是「没写」还是「写了不认」 |

### FR-1：提交侧拒绝无锚点实测结果

**功能描述**：agent 提交验收材料时，无锚点的普通项结果被拒并逐条点名。

**详细说明**：

- **使用场景**：agent 已跑完验证，调 `reqboard_submit(kind="verification", results=[…])` 逐项交结果。
- **操作流程**：
  1. agent 提交 `results`（每项 `{ref, result}` 或 `needsHuman+humanReason`）。
  2. 提交侧对每个「普通项」的 `result` 跑锚点判据（**复用裁决侧同一个纯函数 `hasResultAnchor`**，不新写第二份词表）。
  3. 命中不合格 → 整体拒绝，报错点名每一项并给出合格样例。
- **预期结果**：
  - 无锚点的 `result` **不进验收单**，人不面对它。
  - 报错文本直接给出可照抄的形态（如 `npx vitest run tests/x.test.ts → 10 passed`）。
- **边界条件**：
  - `needsHuman: true` 的项**不吃**本判据（它的判据是事实形态，见 `hasHumanFact`）。
  - 系统缺口项**不吃**本判据（它写的是处置，判 `isValidDisposition`）。
  - 未给 `result` 的项走既有的「既没给 result 也没标 needsHuman」拒绝路径，与本条互不覆盖。

**数据契约**：`results[]` 的入参形态**不变**（不新增字段）；变的是校验强度与错误语义 —— 错误码沿用 `REQBOARD_INVALID_INPUT`，`message` 里逐条列出 `ref → 问题`。

**迁移与兼容**：只作用于**提交动作**，不追溯存量验收单；已落库的无锚点 `result` 不回填、不改写（存量解锁路径见「边界」）。

**验收标准**：
1. 提交 `result="已按 D-1 落实"`（无命令 / 路径 / 计数）→ 提交被拒，报错点名该项并含「锚点」与样例。
2. 同一项改交 `result="npx vitest run tests/subtask-budget.test.ts → 17 passed"` → 提交成功。
3. 同一批里 `needsHuman: true` + `humanReason` 的项不受影响，仍可提交成功。

**判据**：`npx vitest run tests/result-anchor-submit.test.ts`（退出码 0）；读数 = 台账 `verification.sheet.items[].result` 与工具回执 `message`。

### FR-2：降级原因落账并按真实原因措辞

**功能描述**：`passed→unverified` 的降级必须写清原因，两条通道的回执按真实原因措辞。

**详细说明**：

- **使用场景**：裁决侧把「点了通过」判成「未复核」时（人、agent、后续复盘的任一方都在问「为什么」）。
- **操作流程**：
  1. 裁决侧判定降级，按**同一处**判据分流：文本为空 → `blank_pass`；文本非空但无锚点 → `anchor_missing`。
  2. 把原因写进该项（新可选字段），并在 status 变为 `passed` / `failed` 时清空，避免残留误导。
  3. 弹框回执与 HTTP 回执由**同一处文案**生成，各按真实原因给结论与补法。
- **预期结果**：
  - 台账上能直接读出「为什么未复核」，不必再人肉复现。
  - 回执不再一律说「点了通过却没结果」；`anchor_missing` 时说明「文本无可核验锚点（命令 / 路径 / 明确计数）」并给出补法。
- **边界条件**：
  - 老验收单无该字段 → 行为与今天一致（不迁移、不回填、不报错）。
  - `pending` / `not_verifiable` 不写该字段（未复核之外的裁决不该带降级原因）。

**数据契约**：验收项新增可选字段 `unverifiedReason?: 'blank_pass' | 'anchor_missing'`；缺省即「非降级」。字段只增不改，读取方（回执、看板取数、RTM）按可选处理。

**迁移与兼容**：纯新增可选字段，无 schema 版本升级；回写与 `status` 在**同一次** mutate 内完成（不新增第二次写盘）。

**验收标准**：
1. 对一条结果为空的普通项点「通过」→ 回执含「没写实际结果」语义，台账该项 `unverifiedReason='blank_pass'`。
2. 对一条 `result` 无锚点的普通项点「通过」→ 回执含「锚点」字样与补法，台账 `unverifiedReason='anchor_missing'`。
3. 对一条带锚点的项点「通过」→ `status='passed'` 且 `unverifiedReason` 缺席。

**判据**：`npx vitest run tests/verdict-downgrade-reason.test.ts`；读数 = 台账 `unverifiedReason` 取值 + 回执 `note` 字符串。

### FR-3：人工自填文本无锚点当场拒绝

**功能描述**：人自己改写的文本无可核验锚点时，当次提交被拒并给出可读原因。

**详细说明**：

- **使用场景**：人在弹框第 2 问里自写一段结论，或在看板把预填的实测原文改写成自己的话。
- **操作流程**：
  1. 「人工自填」的判据复用既有单点语义：`opinion` 非空且**与该项 `result` 不同**（即人真的动了原文，与 `isResultOverride` 同口径）。
  2. 该文本无锚点 → **拒绝**当次裁决（不是静默记 `unverified`），报错写清「缺什么 + 怎么写才算数」。
  3. 人补上锚点后重交即可；该项 `result` 未被改动时（零输入通过）**不走本条**，仍按 FR-2 记 `anchor_missing`。
- **预期结果**：
  - 人在提交那一刻就知道自己的文本不合格，能当场改（看板客户端对**拒绝**已有 `window.alert` 展示路径，无需改前端）。
  - 「永远过不了且没人说为什么」这一形态消失。
- **边界条件**：
  - 代价必须写明：拒绝是**整批**的，同批其它项的裁决也需在改后重交（与既有「不通过必须写意见」「needsHuman 必须写事实」的前端守卫同一取舍）。
  - **该项 `result` 为空、人自填文本时不走本条**（仍按 FR-2 降级 + 留原因）。理由：那时人写的是本项**唯一**文本、没有可改的原文；在此拒收会把人逼到无路可走（既过不去、又拿不出锚点），且与既有刻意口径冲突（`tests/verdict-result-anchor.test.ts` TC-10：无 result + 无锚点文本 → `unverified` **不抛错**）。
    > **实施期修正（2026-10-07，卡 t-b44770 提出、本窗口裁定）**：本条原写「该项 `result` 为空且人自填文本时，同样适用本条」，与上文「操作流程」第 1 步的窄口径自相矛盾。裁定**收窄**为「仅当该项原有 agent `result` 且被人改写时才拒绝」：破坏性改写值得当场拦，人自填首份文本不拦。
  - 真的不需要锚点的场合（纯人工判断）应由 `needsHuman` 承载，那条判据是事实形态，不受本条影响。

**数据契约**：`applyVerdicts` 的裁决入参形态不变；新增的是**拒绝语义**（域错误）与错误文案。「人工自填」由 `isHumanAuthored`（文本非空 + 该项原有 `result` 非空 + 两者不同）就地判定，不新增线上字段。

> **传输面已知差异（2026-10-07 实测）**：域错误经 `src/application/internal/verdicts.ts` 的既有映射（`invalid_input → opinion_required`）后，工具 / HTTP 回执上的**错误码显示为 `opinion_required`**，而文案是本条要求的精准 anchor 文案（含 itemId / 前 40 字 / 补法）。要显示专用码需动 2 个卡外文件（`src/domain/errors.ts` 注册 + 该映射补分支），本轮未做，列为验收可见项。

**迁移与兼容**：存量验收单不受影响（只在人**新提交**裁决时触发）；回滚方式 = 复用既有 `DSH_REQBOARD_NO_ITEM_RESULT` 开关口径（开关生效时整段回到改造前行为）。

**验收标准**：
1. 对一条 `result` 带锚点的项，人把意见改写成无锚点散文后点「通过」→ 提交被拒，报错点名该项并说明补什么；该批台账零改动。
2. 同一项意见保持预填原文（零输入）→ 提交成功，`status='passed'`（回归：不误伤零输入通过）。
3. 同一项意见改写成带锚点的文本 → 提交成功，`status='passed'`，并按既有规则记录覆盖。

**判据**：`npx vitest run tests/verdict-human-anchor-reject.test.ts`；读数 = 工具 / HTTP 回执的错误码与 `message`，以及该批台账 `version` 未变。

### FR-4：弹框第 2 问题干写明可核验形态

**功能描述**：弹框第 2 问的题干写明要写成什么形态，让填的人一开始就知道。

**详细说明**：

- **使用场景**：弹框对「无结果 / 人工项」的验收项追问实际结果时。
- **操作流程**：
  1. 第 2 问题干在既有文案后追加形态要求（命令 / 路径 / 明确计数三者之一）。
  2. 该形态文案与 FR-2 的补法文案**引用同一常量**，避免两处各写一份而漂移。
- **预期结果**：人看到的不是「通过必填」，而是「写成可核验的形态：某条命令 + 读数 / 某文件路径 / 某明确计数」。
- **边界条件**：
  - 不改两问的结构（不把两问合成一问，理由见「边界」）。
  - 不改宿主问答通道（那是宿主分步向导，已支持多问）。

**数据契约**：题干文案常量位置调整（收口到一处），弹框协议 `AskQuestion.question` 字段形态不变。

**迁移与兼容**：纯文案，无数据兼容问题。

**验收标准**：
1. 对一条无 `result` 的普通项调 `reqboard_accept_sheet` → 弹框第 2 问题干同时含「命令」「路径」「计数」三类形态提示。
2. 该提示与 FR-2 回执中的补法文案取自同一常量（删改一处即两处同步的单元用例通过）。

**判据**：`npx vitest run tests/accept-result-question-wording.test.ts`；读数 = 断言题干字符串包含三类形态词。

## 失败与并发路径

- **失败路径（校验器故障）**：锚点判据是纯函数，抛错即**不改台账**并如实报错（不吞成「未复核」）；回执文案生成失败不回滚已落库的裁决，只降级为通用措辞。
- **失败路径（提交侧拒绝）**：`kind=verification` 因锚点不合格被拒时，**验收单零改动**（与既有「results 漏项 / 坏 ref / 空结果」的拒绝同址），可原地补交。
- **并发与重复**：同一验收单被两处同时裁决 → 沿用既有乐观锁（状态 + `sheet.version` 必须仍是计算时那份），后到者被拒并报 `REQBOARD_STORE_INCONSISTENT`，台账零改动；重复投递同一批裁决幂等（`unverified` 项会被重新问，`passed` 项不重复计）。
- **状态机**：`unverifiedReason` 的写路径锁定在降级那一次赋值内 —— `status` 取值与原因同生同死（同时写、同时清），不存在「status=passed 却残留 anchor_missing」的中间态。

| 起始状态 | 事件 | 结果 | 非法迁移的响应 |
|---|---|---|---|
| `pending` | 人点通过 + 有锚点文本 | `passed` | — |
| `pending` | 人点通过 + 文本为空 | `unverified(blank_pass)` | — |
| `pending` | 人点通过 + 人工自填无锚点 | 拒绝（状态不变） | 报错点名，不改台账 |
| `unverified` | 再次裁决（补锚点） | `passed`，原因字段清空 | — |
| `failed` | 再次裁决 | 按新裁决覆盖 | — |

- **写路径**：原因字段与 `status` 在同一次 `mutate` 内写；写失败即整体回滚（不产生「状态已降级、原因丢失」的半成品）。`verification.md` 的表格回填沿用既有重写，失败不阻断裁决落库。

## 边界（不做什么）

- **不改宿主问答通道**：宿主是**一问一屏的分步向导**（`1 / N` 翻页 + 下一步 / 提交），多问本就渲染得出来——立项描述里的「只渲染第一问」经实测不成立，故不在本仓范围，也不推动宿主改动。
- **不把两问合成一问**：`REQ-261001154450-b918` 已推翻「选项或自定义二选一」的旧形态（选「通过」就拿不到文本，会逼出占位文案冒充通过），合成一问等于回退那条裁定。
- **不调整锚点判据的松紧（词表）**：本轮只让判据的**结论可见、可预防**，不动它认什么（改词表需要台账数据支撑，属另一条需求）。
- **不回填存量验收单**：已落库的无锚点 `result` / `unverified` 保持原样。存量解锁路径 = 由人把该需求的验收意见改写成带锚点的形态（该项 `evidence` 里本就有可照抄的命令）后重交；本需求不代改历史数据。
- **不做看板 UI 展示新原因字段**：看板对**拒绝**已有 `window.alert` 展示路径，FR-1/FR-3 把不合格挡在提交那一刻即已闭环；渲染新字段属「更好看」而非「能解开」，且会牵出前端产物（原型）。需要时另立小需求。
- **不改 `needsHuman` 项的判定口径**：真人工项走「事实形态」判据且失败是**响亮报错**（不是静默吞），本轮不动它。

## 非功能需求

- **向后兼容**：新增字段为可选、只增不改；老台账 / 老验收单读取路径不变（用 `REQ-261007100513-6749` 的存量单做回归读数）。
- **判据单点**：锚点判据与「人工自填」判据各只允许一处实现（前者 `hasResultAnchor`，后者沿用 `isResultOverride` 的「与原文不同」口径），提交侧与裁决侧**共用**，不得各写一份。
- **可回归**：四条 FR 各至少一个单元用例；整体回归用一条含「有锚点 / 空文本 / 无锚点 / 人工项」四类项的验收单跑通。

## 验收标准（整体）

1. 提交一条 `results` 中某普通项 `result` 无锚点的验收材料 → **被拒并点名**，验收单未生成；补上命令 + 读数后重交 → 成功。
2. 对生成的验收单，用弹框逐项裁决：有锚点项点「通过」→ `passed`；空文本项点「通过」→ `unverified(blank_pass)` 且回执说「没写实际结果」。
3. 对一条人工自填无锚点文本的项点「通过」→ **当场被拒**并给出补法；改成带锚点文本后重交 → `passed`。
4. 含 `needsHuman` 项的验收单：人写清「看到的现象 + 证据路径」即可通过（回归：本轮不改变真人工项的行为）。
5. 全项 `passed` 后 `gate_status` 转绿、可进入归档（回归：不出现「全通过却卡在未复核」）。
