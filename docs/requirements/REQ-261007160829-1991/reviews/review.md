## 三、评审发现（已处置）

### 1. 设计错误一：S-1 第 3 条（t1 提出 → 本窗口裁定修正）

原设计写「无文本但有 result → passed」。若照字面实现，「人留空点通过 + agent 交来的无锚点散文」会从 `unverified` **变成 passed** —— 正是本需求要消灭的静默放行（存量已观测 131 个无锚点通过项），且与设计自己的「边界：不改判据松紧」自相矛盾。

**处置**：按既有行为修正设计，加用例 `result: '功能正常，没有问题'` → `unverified(anchor_missing)` 钉住；`design/backend.md` S-1 附实施期修正说明。

### 2. 设计错误二：FR-3 边界条件（t2 提出 → 本窗口裁定收窄）

原设计写「该项 result 为空且人自填文本时同样拒绝」，与同卡「操作流程」的窄口径（复用 `isResultOverride`）自相矛盾，且会让既有刻意口径 TC-10（无 result + 无锚点文本 → `unverified` 不抛错）变红。

**处置**：收窄为「只拦破坏性改写」（原有 agent 结果被人改写成无锚点文本）；`requirement.md` FR-3 边界条件与 `design/backend.md` S-2 同步修正。

### 3. 并发碰撞（t2 与 t4 同改提交链）

t2 的子代理发现回归红 9 条，**没有甩锅也没硬改**：把工作树复制到 `/tmp` 后单独短路兄弟卡代码，证明自己的改动兼容、红是兄弟卡半成品所致，并附 A/B 证据。

**处置**：本窗口判定那 9 条红属**设计预期内的连带影响**（FR-1 就是要普通项结果带锚点），指令 t4 把受影响夹具锚点化、**禁止**改判据或加后门；t4 另多找出 1 个同因文件（`verify-item-result.test.ts`）。

### 4. 假绿陷阱（流程教训）

本窗口给 t7 的验收命令里点名了 `tests/accept-plain-language.test.ts`，**该文件本仓不存在**；vitest 把位置参数当过滤模式、静默退出 0。t7 查 `git log --all` 证明文件不存在并如实上报，没有被假绿骗过。

**处置**：写入本轮经验——跑用例前先确认文件真实存在。

## 八、验收期现场发现：弹框对**系统缺口项**的引导与域要求不一致

验收时用弹框给最后两项（`v1-11` 孤儿用例 / `v1-12` 锚点失效，都是系统缺口项）打勾，**整批被代码级拒绝**：

```
记录失败：系统项通过必须写明处置（v1-11）——它报的是缺口，点通过却不写处置等于把缺口静默吞掉。
处置须命中两义之一并给出对象或理由：① 已处置（如「补了 E2E 用例：tests/e2e-x.test.ts」）；② 确认无需（…）
（system_item_disposition_required）
```

**台账零改动**（复核读数：10 passed / 2 pending，sheet 版本仍 v1，v1-11 处置字段为空）——拒绝发生在写盘之前，符合设计。

**这是引导与要求不一致的问题**（不是本需求的锚点/原因改动引起）：

- 这两项**没有** `result`，故弹框确实问了第 2 问（`needsResultInput` 为真）；
- 但第 2 问的题干按「实际结果」口径写：**「请贴实际结果（命令输出摘要 / 看到的界面 / 数据）… 通过必填」**（本需求 FR-4 又在后面追加了「可核验形态：命令 + 读数 / 路径 / 计数」）；
- 而系统缺口项要通过，域要求的是**处置**（命中「已处置 / 确认无需」两义 + 给出对象或理由）——两套口径不是一回事。

于是「照着题干写」的人（写命令 + 读数）会**必然**被拒；这与本需求立项时的病根同族：**弹框通道的引导只能把人引向被拒的写法**。

- **处置（2026-10-07 验收期，经人工裁定「修理」后已修）**：把第 2 问的**结尾引导按项类型分派**——
  - 系统缺口项（`isSystemItem`）→ 问「处置」，附两义模板与两个正例，**不追加**「可核验形态：命令 + 读数」（那是实测结果的形态要求，对处置是误导）；
  - 普通项 / 人工项 → 维持原引导（实测结果 + 形态），FR-4 判据不变。
  - 落点：提示常量 `SYSTEM_ITEM_DISPOSITION_HINT` 与处置判据**同址**（`AcceptanceSheetSpec.ts`，改判据必同时改它）；分派逻辑抽成纯函数 `resultQuestionTailOf(item)` 收口进文案单点模块（`VerdictNotices.ts`），弹框用例只调它（不再内联三元）。
  - 自证：`npx vitest run tests/accept-result-question-wording.test.ts` → **26 passed**（新增 3 条：系统项问处置且不含形态提示 / 普通项回归 / 提示里的正例真的能过判据且旧引导写法必被拒）；`pnpm typecheck` → 退出码 0；相关 8 个文件 **163 passed**。
  - **这是验收单提交之后的改动**（`AcceptSheet.ts` / `AcceptanceSheetSpec.ts` / `VerdictNotices.ts` + 用例），已在此如实披露；它只影响系统缺口项的第 2 问题干，**不影响验收单 v1 中已通过的 10 项**（那些项的依据是命令读数，不是题干文案），两项目前仍为 `pending`、未据此改判。
  - 另一处**未改**（同族、范围外）：系统项被拒时，报错文案仍说「点通过却不写处置」——把人写过的「写了但不认」说成「没写」。该文案在改动前就存在，修它需另立需求（附：`已添加` 这类同义写法也会被判无效，词表见 `DISPOSITION_TEMPLATE`）。
- 建议后续需求：报错文案按「空 / 不命中词表」两种情形分别措辞（前者说「请补」，后者给命中样例）。
