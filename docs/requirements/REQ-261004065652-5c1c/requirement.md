# REQ-261004065652-5c1c · Dive 死循环根治：投影同源 + 失败熔断 + 中断即闭锁

## TL;DR

- **是什么**：给 Dive 自动续跑补"该停就停"的判据（今天只有"该不该起轮"）。
- **为什么现在做**：2026-10-03 上游额度 403 后空转 4 小时 36 分、6605 次无效请求，两个窗口同刻阵亡。

## 产品定义

Dive 是 reqboard 的"自动续跑"通道：需求在 `armed` 状态下，窗口一空闲就投一回合把工作推下去。
本需求是给它补**停机判据**——今天它只有"起轮的判据"（`isDrivableRequirement`），
没有"该停就停"的判据；而且那条起轮判据本身读的是一份可能陈旧的快照。

**核心价值**：把"自动跑"从"可能无限自旋"变成"**有限步内必然停手、且停手状态当拍可信**"。
一次自旋的代价实测是一夜 4.5 小时 + 6605 次无效请求 + 166 MB 会话文件 + 一份被打爆的额度。

**与现状的区别**：不改"要不要自动跑"的产品语义（`activation` 仍只有人能改），
只补**运行时停机与恢复**的判据，并把判据的数据源从"快照"换成"当拍可信"。

### FR-1: 上游致命错误停手（AUTH/额度类不可重试）

**功能描述**：窗口的回合因上游鉴权/额度类错误收尾时，系统立即停手，并阻止所有窗口继续起轮。

**详细说明**：
- **使用场景**：多人多窗口共享一份模型额度（本机实测 2 个窗口同刻撞 5 小时限额）。
- **操作流程**：
  1. 回合以 `error.code === 'AUTH'`（或 403 / `permission_error` / quota 文案）收尾；
  2. 系统判定为**不可重试**：不投下一回合，写 `driverHealth={state:'paused',reason:'upstream-auth'}`；
  3. 同时置**全局额度闩**（进程内共享），所有 Dive 窗口在闩存在期间一律不起轮；
  4. 看板把该需求标红，并在评论里给一句人话原因与恢复方式。
- **预期结果**：不再产生任何新回合；人恢复（看板「继续」/确认推进/重启）后闩清除。
- **边界条件**：闩必须**有失效期**（缺省随额度窗口，如 5 小时，可由人手动清）；
  单窗口的 `pausedReason` 与全局闩分家——清闩不等于自动恢复某条需求的意图。

**验收标准**：
1. 注入 `AUTH` 失败 → 投递次数 == 1（不再投第二回合）→ 台账 `reason=upstream-auth`。
2. 闩生效期间，另一条 `armed+healthy` 需求也不起轮 → 解除闩后恢复正常起轮。
3. 反向演练：移除致命错误分类 → 用例红并点名。

### FR-2: 瞬时错误退避熔断

**功能描述**：非致命的上游错误（流超时 / 传输失败 / 畸形响应）按指数退避重试，连续同因达阈值即熔断停手。

**详细说明**：
- **使用场景**：夜间网络抖动、provider 5xx、流被中断。
- **操作流程**：
  1. 记录"上一次失败原因 + 时刻"，同因失败计数 `attempts + 1`；
  2. 退避窗口 = `min(base × 2^(n-1), 10min)`；退避期内**不投回合**；
  3. `attempts >= 阈值（默认 3）` → 写 `driverHealth={state:'paused',reason:'agent-error-loop'}` 并停手；
  4. 原因**变化**时计数重置（不同病因分开数）。
- **预期结果**：单次抖动只多花 1–2 个回合；持续故障在 3 次内停手并留痕。
- **边界条件**：退避与熔断计数活在**进程内存**（驱动自己的账），台账 `attempts` 只作展示与跨重启线索。

**验收标准**：
1. 连续注入同因失败 5 次 → 实际投递次数 ≤ 3，且第 4 次起零投递。
2. 注入"失败 2 次后成功"→ 不再熔断，计数归零。
3. 假时钟下断言退避序列为 1/2/4 分钟（不靠真实等待）。

### FR-3: 驱动侧内存闭锁（fail-closed）

**功能描述**：回合异常收尾（error / aborted / interrupted）时，驱动器在**内存**里立刻闭锁，不依赖台账是否读得回来。

**详细说明**：
- **使用场景**：任何"台账写了但驱动读不到"或"写盘失败"的场景（本次事故的放大器）。
- **操作流程**：
  1. `onAgentError` / 异常 `turn/end` / 人工中止 → 置内存 `latch = {reason, at}`；
  2. `readyToDrive()` 在 `latch` 存在时恒假（**先闭锁再谈台账**）；
  3. 只有①人显式恢复、或②`requirement-moved` 且 revision 变化、或③闩失效期到，才清 `latch`；
  4. 清 `latch` 时同时要求台账 `driverHealth` 已不处于 `paused`（双条件，避免"台账说停、内存说跑"）。
- **预期结果**：即使投影缺陷复发，也不可能出现"没人推进却一直起轮"。
- **边界条件**：闭锁只影响**自动起轮**，不影响人手动调工具、不影响看板操作。

**验收标准**：
1. 注入一次 `agent-error` → 立即断言 `readyToDrive() === false`（不等台账写入）。
2. 台账写入失败（注入假 store）+ 回合异常 → 仍零新增回合。
3. 人恢复后 `latch` 清除且能起轮。

### FR-4: 投影读己所写（根因修复）

**功能描述**：写入路径产生的 `dive` / `advance` 变更，必须**同拍**可从同步窄投影 `peekFacts()` 读到。

**详细说明**：
- **使用场景**：`round-driver` 的 idle 拍是同步缝，只能用 `peekFacts()`；它读的正是自己刚写的健康位。
- **操作流程**：
  1. 在存储层的写通知路径上同步刷新窄投影快照（写入器手里已有新记录）；
  2. 或：把判定字段（`dive` / `advance.pausedReason`）改为从实时来源取，快照只留展示字段；
  3. 补 store 层契约测试：任意 `mutate` 后同拍 `peekFacts()` 必须反映该次写入；
  4. 测试替身改为与生产同形的快照实现（消灭"测试活投影、生产死快照"的分叉）。
- **预期结果**：`isDrivableRequirement(peekFacts()[i])` 与台账一致；`roundsInStage` 不再恒 0。
- **边界条件**：不得把整条 `advance.history`（append-only 无上界）拉进同步口；只投影必要标量。

**验收标准**：
1. `mutate(driverHealth=paused)` → 同拍 `peekFacts()` 读到 `paused`（现状读不到）。
2. `persistAdmission` 写 `roundsInStage=1` → 下一拍 `round` 为 2（现状恒 1）。
3. 反向演练：把刷新拿掉 → 用例红。

### FR-5: 人工门即停手

**功能描述**：需求处于"等人裁决"时，Dive 一次都不唤醒窗口。

**详细说明**：
- **使用场景**：验收单待逐项裁决（实测 9 项 pending）、产物待确认、拆分计划待批准。
- **操作流程**：
  1. 起轮前查"人工门是否在途"：验收单存在未裁决项 / 存在未确认的待确认产物 / 计划未批准；
  2. 命中 → 不起轮、不写健康位（这是**正常等人**，不是故障），只更新停手位与评论（幂等）；
  3. 人裁决完成（或计划批准、产物确认）→ 停手位自动清除，恢复起轮。
- **预期结果**：待裁决期间回合数增量为 0；看板上该需求显示"等人"而不是"自动跑"。
- **边界条件**：停手位不得改写 `activation`；不得阻止人手动操作。

**验收标准**：
1. 造一条 `accepting` + 验收单 9 项 pending 的需求 → 10 分钟内零新增回合。
2. 全部裁决后 → 下一次空闲即可起轮（不等人再点一次）。
3. 产物待确认 / 计划待批准两种形态各一条用例。

### FR-6: 中止当拍生效

**功能描述**：用户点「停止」或宿主 abort 在飞回合时，驱动器**当拍**闭锁并停止投递。

**详细说明**：
- **使用场景**：实测用户按「停止」后 20 秒内仍有 84 个回合并行被中止。
- **操作流程**：
  1. 收到 `turn/end` 的 `aborted:user`（或宿主 stop 信号）→ 置内存 `latch`（同 FR-3）；
  2. 停止投递并放弃在当前拍已排队的投递；
  3. 写一条停手留痕（人主动停手，不是故障）：`driverHealth={state:'paused',reason:'aborted:user'}`。
- **预期结果**：停止生效 ≤ 1 个 tick；后续不再出现新回合。
- **边界条件**：`aborted` 与 `error` 的停手语义不同——前者不自动恢复（等人才动），后者可退避重试。

**验收标准**：
1. 注入 `aborted:user` → 断言此后投递次数为 0，且不再出现新回合。
2. 停止后重启插件：需求仍停手，等人恢复（不停留成 `armed+healthy`）。

### FR-7: 弹框默认有界宽限

**功能描述**：`reqboard_ask_confirm` 缺省不再无限阻塞，超宽限即返回 `pending=true + ticket`。

**详细说明**：
- **使用场景**：实测一次弹框吞掉了宿主 3600000ms（1 小时）工具超时后被中止。
- **操作流程**：
  1. 缺省宽限（建议 5–10 分钟，可配置）内仍阻塞等人作答；
  2. 超宽限 → 返回 `pending=true` + `ticket`，并把"等人在此"登记进台账（停手位）；
  3. agent 可继续做别的、或用 `reqboard_confirm_receipt(ticket)` 取回执；
  4. 人作答后由后台落章并推进（现有非阻塞语义不变）。
- **预期结果**：任何弹框都不会让窗口死等超过宽限；人随时作答都有效。
- **边界条件**：显式传 `inline_grace_ms` 的行为不变（继续作为覆盖入口）；看板确认路径不受影响。

**验收标准**：
1. 假时钟推进超过缺省宽限 → 工具返回 `pending=true` 且带 `ticket`，**不抛超时错**。
2. 宽限内作答 → 仍走"确认 + 落章 + 推进"原子路径（既有用例不回归）。
3. `reqboard_confirm_receipt(ticket)` 能取回执。

### FR-8: 断点留痕去重限流

**功能描述**：失败回合的断点留痕按原因**类别**去重并按需求限流，死循环不再按分钟刷台账。

**详细说明**：
- **使用场景**：实测 `error:AUTH…` ↔ `aborted:user` 交替，按"原因原文"判等的幂等失效。
- **操作流程**：
  1. 去重键改为"原因类别 + 阶段 + pendingAction"（把 `error:AUTH:<长文案>` 归到 `error:AUTH`）；
  2. 同需求同类留痕最小间隔（建议 10 分钟）内的重复写入丢弃；
  3. 限流丢弃次数可观测（评论或日志里累计，不静默）。
- **预期结果**：一次 4.5 小时自旋产生的留痕从 15+ 条降到个位数。
- **边界条件**：**状态变化**（阶段/下一步变了）必须立刻写，不受限流影响。

**验收标准**：
1. 交替注入 `error:AUTH` 与 `aborted:user` 各 10 次 → 台账新增断点评论 ≤ 2。
2. 阶段推进产生的留痕不受限流（立即出现）。

### FR-9: 终态收手与启动对账

**功能描述**：终态（`done`/`archived`/`canceled`）需求永不被唤醒；存量"终态却 armed"记录在启动时归一。

**详细说明**：
- **使用场景**：实测 3 条已归档需求仍是 `armed + active + paused`（状态自相矛盾）。
- **操作流程**：
  1. 起轮判据补"状态必须开放"（部分已有，需覆盖全部起轮入口与心跳入口）；
  2. 启动对账：终态需求的 `dive` 归一为 `disarmed`（不改人意图之外的字段，留痕说明是迁移）；
  3. 对账幂等、可复核、给出计数。
- **预期结果**：`reqboard_kb`/看板读到的"自动意图"与需求状态一致。
- **边界条件**：只对**终态**归一；`disarmed+idle`（人主动手动）绝不自动改写。

**验收标准**：
1. 造 archived + armed 记录 → 启动对账后为 `disarmed`，并有一条迁移留痕。
2. 心 tick 对终态需求零唤醒（用例断言）。

### FR-10: 子卡引擎开工预检

**功能描述**：父卡开工前预检子卡执行引擎（作业控制器）是否可达；不可达则响亮报错并给明确出路。

**详细说明**：
- **使用场景**：本 profile 关了 `dsh-tool-jobs` → 实测 `subtask_engine_unreachable`，10 张父卡只 1 张落子卡，其余在本窗口自证完工。
- **操作流程**：
  1. 开工前探测引擎可达性（与现状 `inject/get/byGet` 判据同源）；
  2. 不可达 → 回执与台账写清楚"为什么不可达 + 两条出路"（自证过凭证门 / 修好引擎重跑），**不静默降级**；
  3. 同一需求只报一次（幂等），避免刷屏。
- **预期结果**：人一眼知道"不是卡坏了，是这台机器的配置没开"。
- **边界条件**：**不**替人决定打开 `dsh-tool-jobs`（环境选择归人）。

**验收标准**：
1. 注入不可达引擎 → 开工回执含原因与两条出路，且不落"假成功"的子卡。
2. 引擎可达 → 行为逐字不变（既有用例不回归）。

### FR-11: 全局 WIP 与额度预算闸

**功能描述**：跨窗口限制同时在跑的自动链数量与 token 消耗，超限即拒绝起新链并留痕。

**详细说明**：
- **使用场景**：实测多窗口共享一份额度、单需求 implementing 阶段烧 14.07 亿 cacheRead。
- **操作流程**：
  1. 维护进程内/台账级的"在跑链数"与"本额度窗口累计 token"；
  2. 起新链前检查上限（WIP 上限、token 预算），超限 → 拒绝起轮并写一条可读原因；
  3. 指标在需求评论/看板可见（谁被挡、挡在哪个阈值）。
- **预期结果**：不会出现"多窗口同时把额度打爆"；超限是可解释的停手，而不是故障。
- **边界条件**：已在跑的链不被强杀（只挡新链）；阈值可配置，缺省值需在设计阶段用实测数据定。

**验收标准**：
1. 造 N+1 条可起轮需求 → 第 N+1 条被拒且留痕原因含阈值名与当前值。
2. 在跑链结束 → 名额释放，下一条可起轮。

## 边界

- **不做 A：不改需求分类枚举、不动五道人工门语义、不改凭证门既有的写入族/结论族判定逻辑。**
  理由：本次只动"驱动何时该停 / 何时能起轮"的判据；碰门禁语义会把范围炸开，
  且那部分（阶段模板补段）已由 REQ-261003203909-55f2 另行交付。
- **不做 B：不替人打开本 profile 的 `dsh-tool-jobs`。**
  理由：那是环境选择不是代码缺陷（见 `docs/architecture/automation-chain-contract.md` §4）；

- **不做 C：不新增客户端看板页面、不改台账 schema 版本。**
  理由：停手/闭锁/预算状态用既有泳道、健康位与评论呈现即可；
  新增字段一律可选、旧记录按缺省读（零迁移），避免把本次改动做成数据模型变更。

### E-3 根因：投影陈旧（读己所写不成立）

- `peekFacts()` 的 `description` / `dive` / `advance` / `artifacts` 取自 `factsCache`
  （`src/repositories/ShardedRequirementStore.ts` 的 `peekFacts`），
  该快照**只在建索引（`summarizeHot`，cache=true）与 `create` 时写入**；
  写通知路径只刷 `index`（`version`/`status` 实时）。
- 判定用的正是死快照里的字段：`isDrivableRequirement` 读 `activation` / `driverHealth` / `advance.pausedReason`。
- **实证**：18:03:52.266 台账已写 `[Dive] 已暂停自动续跑（运行时原因：agent-error）`；
  此后 4.5 小时的回合消息带 `revision: 70`（实时索引的新值）却**恒为 `round: 1`**（陈旧 `roundsInStage`）
  —— 同一次 `peekFacts()` 里版本是新的、`dive` 是旧的。
- 测试为何没拦住：用例的 `peekFacts` 是**活投影**（`ledger.requirements.map(factsOf)`），
  生产实现是**快照** —— 测试替身与生产实现不同形。

### E-4 护栏为何一个都没生效

- `driverHealth.attempts` 只在 `pause-runtime` 里累计，**全仓无任何读它做熔断的代码**；
- 同因幂等让 attempts 停在 1；
- 回合上限判据 `roundsInStage` 来自死快照 → 恒 0 → 永远 `round=1 < limit=10`；
- 人工门不是停手条件（只挡"弹框在途"），台账自己写着"连续唤醒回合均无新输入"。

### E-5 中断与写放大

- `reqboard_ask_confirm` 缺省阻塞吞掉宿主 `3600000ms` 工具超时后才 abort（REQ-261003222428-3556 台账断点原文）；

- 断点留痕按原因原文判等 → 两种原因交替时幂等失效，按分钟刷 revision。
