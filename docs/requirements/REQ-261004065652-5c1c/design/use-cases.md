## UC-1: 夜间挂机撞上额度上限 `serves: FR-1, FR-3, FR-11`

**前置**：两个窗口各跑一条 `armed` 需求；共享同一份 provider 额度；人在睡觉。

**主流程**：
1. 18:03 两个窗口的回合先后以 `AUTH 403`（5 小时额度）收尾；
2. 第一个窗口的驱动器把该错误判为 **fatal** → 置内存闭锁 + 写 `driverHealth=upstream-auth` + `trip` 全局闩；
3. 此后任何 idle 拍（包括第二个窗口与心跳）都被闩拦住 → 零投递；
4. 看板显示两条需求"停手：上游额度"，并说明恢复方式。

**预期结果**：当晚新增回合数 **0**；第二天人**购买/等待额度恢复**后点「继续」→ 清闩、清闭锁、恢复起轮。

**异常路径**：人在睡眠中额度重置（5 小时窗口过去）→ 闩 TTL 到期 → 自动清闩；
但**需求仍停在 `paused`**（fatal 不自动恢复），等人点一次「继续」——宁可少跑，不可自旋。

## UC-2: 需求卡在人工门 `serves: FR-5`

**前置**：需求进入 `accepting`，验收材料已提交，验收单 9 项全部 `pending`。

**主流程**：
1. 驱动空闲拍 → `humanGateOf(req)` 命中 `acceptance-pending` → **不起轮**；
2. 台账只保留停手位（幂等，不刷评论、不写健康位）；
3. 人到看板逐项裁决 → 全部裁决后，下一次空闲拍自然起轮（不需要人再点一次）。

**预期结果**：待裁决期间回合增量为 0（现状：Dive 反复唤醒并留下"连续唤醒均无新输入"的评论）。

**边界**：若验收单**不存在**（材料都没提交）→ 门不开 → agent 该干活干活（不误停）。

## UC-3: 网络抖动 `serves: FR-2`

**前置**：`armed` 需求正在跑，provider 偶发 `TRANSPORT` 失败。

**主流程**：失败 1 次 → 退避 30s → 重试成功 → 退避账清空。

**预期结果**：抖动只多花 1 个回合；连续同因失败 3 次才熔断（`agent-error-loop`），
且原因类别变化时计数归零（不把"抖动 + 额度"混成一笔账）。

## UC-4: 用户按「停止」`serves: FR-6`

**前置**：驱动正在投递回合（可能是自旋中）。

**主流程**：
1. 人点「停止」→ 宿主 abort 在飞回合并发 `turn/end = aborted:user`；
2. 驱动器**当拍**置内存闭锁（`aborted:user`），不再投递；
3. 写一条停手留痕（人主动停，不是故障）。

**预期结果**：停止生效 ≤ 1 拍；后续回合数 **0**（现状：20 秒内仍有 84 个回合被中止）。

## UC-5: 弹框等人，人不在 `serves: FR-7`

**前置**：agent 调 `reqboard_ask_confirm`（不传 `inline_grace_ms`），人离开了。

**主流程**：
1. 阻塞至缺省宽限（10 分钟）→ 返回 `pending=true + ticket`；
2. agent 继续做别的或结束本回合；停手位在台账生效；
3. 人回来在弹框/看板作答 → 后台落章 + 推进；
4. agent（或新窗口）凭 `ticket` 调 `reqboard_confirm_receipt` 取回执。

**预期结果**：窗口不再死等；**不出现** `工具调用 3600000ms 无人作答被中止`。

## UC-6: 多窗口并行起链 `serves: FR-11`

**前置**：已有 3 条 `armed + autoRun + implementing` 的链在跑（缺省 WIP 上限）。

**主流程**：第 4 条需求进入 idle 拍 → `checkChainBudget` 返回 `wip-limit` → 不起轮，
写一条含阈值名与当前值的留痕。

**预期结果**：被挡的链显示"排队中：WIP 3/3"；某条链结束后名额释放 → 排队者自动起轮。

**边界**：已在跑的链**不被强杀**（只挡新链）；token 预算同理（粗闸，按需求级累计读）。

## UC-7: 子卡引擎不可达 `serves: FR-10`

**前置**：本 profile 关了 `dsh-tool-jobs`；某需求进入实施，父卡准备开工。

**主流程**：
1. 开工**前**预检引擎 → 不可达；
2. 本次推进以 `engine_unreachable` 结束，回执写明"本次未落任何子卡" + 两条出路
   （① 本窗口自证过凭证门；② 让人决定是否打开 `dsh-tool-jobs`）；
3. 同需求再次推进 → 短路零写入（不刷屏）。

**预期结果**：人一眼知道"不是卡坏了，是这台机器没开作业控制器"（现状：反复得到无法行动的原因，诱使重试）。

## UC-8: 终态需求被归一 `serves: FR-9`

**前置**：台账存在 3 条 `archived` 且 `armed + active + paused` 的记录（实测状态自相矛盾）。

**主流程**：插件启动 → 对账发现"终态 ∧ armed" → 应用 `disarm-terminal` →
`activation='disarmed'`，并写一条 `terminal-reconciled` 留痕（`from → to`）。

**预期结果**：看板读到的自动意图与需求状态一致；对账幂等（第二次启动零写入）；
`scripts/rollback-terminal-reconcile.ts` 能按留痕还原。
