# 评审报告（REQ-261004065652-5c1c）

> 评审对象：Dive 死循环根治（投影同源 + 失败熔断 + 中断即闭锁），10 张任务卡全部 done。
> 评审口径：**每条结论都要有可复跑证据**；设计偏离一律点名，不藏。

## 一、这次修的到底是什么（一句话版）

2026-10-03 的实机事故：上游额度 403 之后 Dive 没有停手，4 小时 36 分空转 **7257 个回合**、
**6605 次 403**，烧掉约 **43 亿 cacheRead**（全仓累计），两个窗口同刻阵亡。
本需求把"它凭什么一定会停"变成三条硬机制 + 四道起轮前置。

## 二、根因与修法对照（三条根，逐条闭合）

| # | 根因（现场证据） | 修法 | 判据用例 | 反向演练 |
|---|---|---|---|---|
| ① | 驱动读**陈旧同步投影**：写路径只刷新索引、不刷新快照 ⇒ "刚写下的暂停位"自己读不到 | 写路径同源刷新（`ShardedRequirementStore` 通知回调同步更新 `factsCache`） | `tests/store-projection-ryow.test.ts`（8） | 注释掉刷新 → **红 5** |
| ② | 失败**不分类、不熔断**：额度 403 被当可重试抖动 | 上游失败分类（致命/瞬时/中止）+ 同因连续 3 次熔断 + 退避 | `tests/upstream-failure.test.ts`（16）、`tests/dive-loop-breaker.test.ts`（7） | `fatal=false` → **红 4** |
| ③ | 停机位**不唯一**：`driverHealth` 与 legacy `phase` 两处判、两种口径 | 收敛到 `driverHealth` 一个权威字段；legacy 仅在台账未写停时补写 | 同上 | 同 ② |
| ④ | 真被掐断（abort）后**没有闭锁**，靠台账自愈形同虚设 | 中断即闭锁（fail-closed，纯内存、不依赖 I/O）；解锁需"台账复位 healthy **且** 我方停手位写成功" | `tests/dive-abort-latch.test.ts`（5） | 删掉闭锁判定 → **红 1** |

> ④ 的"双条件解锁"是反向演练逼出来的设计修正：只查台账时，一次**失败**的停手位写入会让
> `driverHealth` 缺席，而缺席在旧口径下"看起来健康" ⇒ 假解锁。改为要求显式 `healthy` 后闭合。

## 三、四道起轮前置（顺序 = 实现顺序）

`内存闭锁(+退避)` → `全局上游闩` → `人工门` → `预算闸`，全在**构造回合之前**；前两道不依赖任何 I/O。
判定顺序与 `round-driver.ts` 行号逐一对齐（L270/L271/L398/L442/L456），判据表见
[automation-chain-contract.md 第六节](../../../architecture/automation-chain-contract.md)。

**"超限/等待"与"故障"分家**（这是本次最重要的一条认知）：人工门与预算闸命中**不写健康位、不改人的意图**；
只有致命错误与连续同因失败（≥3 次）才写 `paused` 叫人。否则抖动会把人反复叫醒去点「继续」。
