## UC-1 打开需求详情 <!-- serves: FR-1, FR-4 -->

- **用例角色**：看板主人（PM/维护者）、实施窗口 agent（把详情页当交付面自检）。
- **前置条件**：看板已挂载（`/state` 成功、`state.requirements` 为该需求的**摘要**）；
  需求存在且台账可读。
- **交互流程**：
  1. 用户点击卡片（`data-action="open-req" data-req="REQ-…"`）→ 视图切到详情模式。
  2. 客户端立刻渲染**摘要级骨架**：进度点、6 个 Tab、标题、状态、操作条。
  3. 客户端调用 `GET /requirements/<id>`（1 次）。
  4. 取回全文 → 渲染评论列表与条数、文档记录、产物 chip、验收材料、归档材料、时间线。
- **异常流**：
  - 步骤 3 返回 404 → 转 UC-3；返回 5xx / 超时 → 转 UC-4；断网 → 转 UC-4。
  - 步骤 4 记录缺 `comments` 等本体字段（旧数据）→ 对应区段空态，其余照常渲染（FR-4）。
  - 步骤 4 返回的 `id` 与请求 `id` 不一致 → 丢弃该响应，维持骨架态（FR-2 边界）。
- **后置条件**：`req-detail-store` 中该 `reqId` 条目 = `ready`（含 `revision` 与 `version`）。
- **完成标志**：详情页显示的评论条数/内容与该需求台账一致；Network 面板中该需求**恰 1 条**
  `requirements/<id>` 请求（200）；控制台无未捕获异常。

## UC-2 详情在屏时的台账变化 <!-- serves: FR-3 -->

- **用例角色**：看板主人（长开详情页看着）、旁观者（另一窗口只读）。
- **前置条件**：UC-1 已完成（条目 `ready`），用户当前停在某个 Tab（如「时间线」）或已选中某阶段节点。
- **交互流程**：
  1. 另一窗口对同一需求做变更（推进状态 / 加评论 / 登记产物 / 任务状态变化）。
  2. 本窗口收到 SSE 台账事件（或 20 秒轮询到点 / 用户点「刷新」）。
  3. `fetchAll()` 更新 `/state`；`render()` 重新进入 `case 'req'`。
  4. store 判定失效（`version` 变大或 `revision` 变化）→ 发 1 次详情请求 → 替换条目 → 重绘。
  5. 重绘后回填 Tab / 阶段选中 / DAG 视图状态 / 评论草稿。
- **异常流**：
  - 同一 tick 内 SSE 与轮询各触发一次 → 第 2 次 `ensure` 复用在途 Promise，**只 1 次请求**。
  - 详情请求失败 → 保留上一次 `ready` 内容**还是**转 `error`？→ 定死为：**转 error 占位**
    （不展示可能过期的数据），hint 原样呈现；用户可点重试。
  - 需求在期间被删除 → 详情请求 404 → 转 UC-3。
- **后置条件**：条目为最新 `ready`（或 `missing`/`error`）；用户视觉位置未被重置。
- **完成标志**：用户看到新评论/新状态；Tab 未跳回「概览」；评论输入框草稿仍在。

## UC-3 需求不存在或已删除 <!-- serves: FR-2 -->

- **用例角色**：看板主人（从旧标签页 / 收藏的深链进入）。
- **前置条件**：看板已挂载；目标 `reqId` 不在 `/state` 的摘要列表里，或详情端点回 404。
- **交互流程**：
  1. 用户（或深链）请求打开 `REQ-…` 详情。
  2. 若摘要里没有该 id → 仍按详情模式进入并发起详情请求（不静默回看板）。
  3. 详情端点回 `REQBOARD_NOT_FOUND` → 渲染「未找到需求 <id>（可能已被删除或不在当前工作区）」。
  4. 页面提供「← 看板」按钮返回。
- **异常流**：
  - 详情端点回 200 但 `requirement.id` 不匹配 → 按 UC-4 的失败态处理（数据不可信）。
  - 用户在未找到态点「刷新」→ 重新发 1 次详情请求（允许，不限流）。
- **后置条件**：视图仍在详情模式（`mode.kind === 'req'`），**未被**改成看板。
- **完成标志**：屏幕上出现「未找到」文案与返回按钮；控制台无 `TypeError`。

## UC-4 取数失败（服务端异常 / 离线） <!-- serves: FR-2, FR-4 -->

- **用例角色**：看板主人。
- **前置条件**：详情请求返回 5xx / 超时（8 秒）/ 网络不可达。
- **交互流程**：
  1. 用户打开详情 → 请求失败。
  2. 渲染失败占位：`加载失败：<服务端 error>`，若有 `hint` 则按可复制命令呈现。
  3. 提供「重试」按钮（`data-action="retry-detail"`）。
  4. 用户点重试 → 强制取数（清该条目后 `ensure`）→ 成功则进 UC-1；仍失败则停留在失败态。
- **异常流**：
  - `hint` 缺失 → 不渲染 hint 块（与 `buildError` 同口径），不留空标签。
  - `error` 文案为空 → 用兜底文案「取数失败」，不显示「加载失败：」这样的半截句子。
  - 重试连点 → 在途去重同 UC-2（只 1 次在途请求）。
- **后置条件**：条目为 `error`（重试成功后为 `ready`）。
- **完成标志**：用户看到失败原因 + 重试入口；页面不白屏、不静默返回看板。
