# 提示词上下文的头尾分层与易变段投递（L2 领域篇）

> **TL;DR**：把「每轮都要重发的东西」拆成两半——**头部**只放随窗口绑定关系变化的常量，
> **易变段**（看板状态行 / 当前任务块 / 阶段纪律正文 / 待捕获命中提示）改从**会话尾部增量投递**。
> 四条不变量，改这条通道前请先读完：
> ① **头部只随绑定关系变**——状态、当前任务、阶段纪律一律不进头部；
> ② **让位是一次性永久的，且只在「到达确认」后上闩**（投出去 ≠ 到达）；
> ③ **覆盖靠协调层状态比对**（写路径 / 装配缝 / 回合末三处），不靠穷举生产者；
> ④ **按 kind 分化窗口**：`capture`/`stage` 立即，`task`/`status` 30 秒合并翻版；**空态不单独投递**。

**来源**：REQ-261007100513-6749（2026-10-07）。前情实测见
`docs/reviews/REQ-261006130057-7a43-token-cost-diagnosis.md`（基线 31 会话 / 2,324 请求 / 21h）。

## 一、为什么要分层（改造前的代价）

改造前只有一个 system prompt 段，其 `text` 每轮重算：需求状态、当前任务、阶段纪律正文一变，
头部就换版本。实测基线窗口注入 **30 次 / 16 个不同版本**。

**缓存代价是供应商相关的**（这点必须记清，别把它当普遍规律）：

| 供应商 | 观测 | 代价 |
|---|---|---|
| `kimi-coding/k3` | 16 次重写，每次紧邻请求 `cache≈16K`、`uncached≈整段上下文` | 该条浪费线 **3.9M 全价 token** |
| `deepseek-flash` | 9 次重写，紧邻请求 `cache=384K / uncached=5K`（缓存保住） | ≈0；该窗口唯一一次全量重算是**其前 163.6 分钟空档**后的 TTL 过期（29.5 分钟空档未触发） |

⇒ 与供应商无关的价值是：**消除 30 次冗余注入、让头部可断言、换模型时不再付这笔钱**。

## 二、头 / 尾分界表（唯一口径）

| 内容 | 变化频率 | 落点 |
|---|---|---|
| 未绑定静态引导（含 windowKey 前 16 位） | 每会话 0–1 次 | 头部 |
| 已绑定需求清单 `- <id>《标题》`（**不含状态**） | 绑定 / 换绑 / 改标题 | 头部 |
| 常量块（流水线 / 设计 / 拆分 / 推进 / 验收 / 归档纪律） | 从不 | 头部 |
| 看板状态行 `- <id> 当前状态：<status>` | 每次阶段推进 | **尾部** |
| 当前任务块 `## 【当前任务执行中】` | 每次任务切换 | **尾部** |
| 阶段纪律正文 | 每次阶段切换 | **尾部** |
| 待捕获命中提示（含用户消息节选） | 每条用户消息 | **尾部** |

## 三、投递契约

- 取 agent：`agents.get(windowKey)` → `inboxOf(agent).prepend('next-step', message)`；
  `InboxTarget` 全集只有 `next-turn | next-step`。
- 消息**自署来源**：`{role:'user', content:[{type:'text',text}], source:{kind:'dive', …}}`。
  **不得**冒充 `kind:'user'`（否则窗口会把系统提示当人话执行）；也**刻意不带** `revision`/`round`
  ——带上就成了回合准入判据 `isDiveRoundSource` 的合法来源，pre-step 栅栏会把整步判 reject。
- **禁用** `agent.followup()` / `deliver()`：它们会**新起一整轮** agent loop（本机制立项的动因之一）。
- 注入不会被当成人类消息：四道判据都按 `source.kind` 挡住（`session-driver` 的 `user/message` 分支、
  round 的 messageId 认领、`isDiveRoundSource`、宿主 `isOwned`）。

## 四、让位与到达确认（一次性、永久）

- **让位判据** = 该窗口的 `sealed` 闩；`sealed` **只在 `agent/inbox/claimed` 到达确认时**置位，
  此后永不自摘（唯一回收路径是迟滞：连续 `LIMITS.noticeReclaimAfterFailures`=3 次未确认）。
- **不要**用「当前内容哈希 == 已投哈希」逐段决定是否让位——那样每次变更头部都要重写一次
  （实测等价于没省）。
- `agent/inbox/discarded`（用户 stop / cancel 清空 inbox）→ **忘掉那次送出**（`delivery.drop`）+ 记一次失败
  → 下一次协调**补投**；未确认期间头部继续承载该段（**不静默丢**）。
- `agent/disposed` → 清理该窗口的定时器与状态。
- 成本：每窗口头部重写 **≤1 次**（判据：剧本「连续 8 次变更后头部段版本数 = 1」）。

## 五、协调层（覆盖不靠穷举生产者）

状态变化**不一定**经由写路径生产者发生（rollup 自动推进、看板 HTTP 路由、confirm-settle、verdicts
都没有"窗口"可通知）。因此覆盖由 `notice-reconciler` 的**状态比对**保证，三处触发：

| 触发点 | 时机 | 额度命名空间 |
|---|---|---|
| 写路径 | 用例写成功后 | 不受限 |
| **装配缝** | 每次 system prompt 装配前（`available()` 内扫差异） | `a<回合号>` |
| 回合末 | `session/event` 的 `turn/end` | `t<回合号>` |

- **不用 `agent/pre-step`**：那是 dispatch 型事件，round 驱动的返回值被当作**整步放行/reject 的决定**，
  再挂监听器会插进那条决策链。
- 装配缝是每回合必经的同步点，故「下一次装配前必被扫到」成立；`next-step` 的 prepend 在同一回合
  后续 step 即被模型读到，不构成"纪律迟到一回合"。

## 六、窗口与空态

- **按 kind 的窗口表**（单一落点 `DEBOUNCE_MS_BY_KIND`）：`capture=0`、`stage=0`、
  `task=status=LIMITS.noticeDebounceMs`（30 秒）。
  - `capture` 必须是 0：它的意义是让窗口**本回合**先做显式裁定，且每条消息一次 + 哈希去重，从不翻版；
  - `stage` 是**一次性事件**，无翻版形态。30 秒对二者只有延迟、零合并收益；
  - `task/status` 保留 30 秒：实测两态往返间隔为 **16s / 24s / 71s**，1 秒级窗口合并不了。
- **空态不单独投递**：「无在制任务」是收尾与开工之间的瞬态、零信息量；把它当一次状态变化投递，
  正是实测「`13,338 ↔ 13,897` 来回翻版」的根因。规则：空态不单独投；只在阶段变化时随阶段通知一并投；
  空态**持续超过 5 分钟**（`LIMITS.noticeEmptySettleMs`）且期间无新任务/阶段变化，才补投一次。
- 去重键 = **内容哈希**（sha1，经端口注入——application 层禁 `node:` 前缀），规范化后比较。

## 七、降级与失败语义

- 通道不可得 / 投递失败 → **实现侧**退回头部并写 `InjectionLog`（`origin='system-prompt'`、`delivered=true`）
  + 诊断留痕；用例侧**不搬**降级逻辑（意图/实现分离）。
- `VolatileNoticePort.notify` **永不抛**：失败以返回值回报，写路径不因通知失败而回滚。
- 通道可用性判据在装配缝侧还要 **try/catch 按不可用**（装配处抛错会让整轮跑不起来）。

## 八、已知边界与后续项

1. `volatile-notice.ts` **400 行零余量**，后续任何改动**先拆分**（`notice-delivery` 387 / `notice-reconciler` 377）。
2. `tests/stage-prompts.test.ts` 的源码扫描面**未包含** `volatile-notice.ts`（文案搬出后扫描面缩小）。
3. 验收 ⑪ 的 token 增量是**等价有界断言**，不是真实请求读数（需真读数应单列测量卡）。
4. 本机制在 `deepseek-flash` 上的**token 收益≈0**（见 §一）；不要在缺少对照组的情况下宣称成本下降。
