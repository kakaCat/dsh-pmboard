# 验收单机制（L2 领域篇）

> **TL;DR**：验收单由 `reqboard_submit(kind=verification)` 那一刻**由运行中的代码**生成，逐项列出
> 「这张卡/这条需求要确认什么」。它有三条硬不变量——**只收顶层父卡**、**编号连续无空洞**、
> **需求级项标题按缺口类型区分**；另有六类**系统项**把"人看不见的缺口"变成可见项（不阻断提交）。
> 两条裁决通道（看板 / 会话弹框）同口径：**有结果即可零输入通过；两者皆空记「未复核」**（不计入通过）。

## 一张验收单长什么样

```
submit(kind=verification)
        │
        ├─ ① 任务项：队列任务里**只收顶层父卡**（parentId === undefined）
        │     └─ 子卡的验收由父卡项覆盖（同一交付不重复占验收位）
        ├─ ② 需求级项：交付结论可复核（证据齐全 / 与设计一致 / 无范围蔓延）
        └─ ③ 系统项（有则追加，全部 pending、全部不阻断提交）
              孤儿用例 · 不可照着验 · E2E 覆盖 · 三方一致性 · 锚点失效 · FR 追溯断链
                        │
                        ▼
        编号一次性连续分配：v<version>-1 … v<version>-N
        （顺序锁定：任务项 → 需求级 → 孤儿 → 不可照验 → E2E → 三方一致性 → 锚点失效 → 追溯断链）
```

## 三条硬不变量（改坏了会被测试当场抓住）

| 不变量 | 为什么 | 守卫 |
|---|---|---|
| **只收顶层父卡** | 否则一个 6 父 + 23 子的交付会产出 29 个任务项，同一交付被重复验收 | 投影单点 `toSheetTasks` 必须**透传 `parentId`**；domain 侧 `buildSheet` 再过滤一次（双保险）。测试：`tests/sheet-projection.test.ts`（删掉透传即变红） |
| **编号连续 `v<ver>-1..N`** | 编号是人对验收项的引用键；跳号（如 `v1-7 → v1-9`）让人以为丢项 | `buildSheet` 先组装草稿再一次性分配编号；不再使用 `taskCount+N` 预留位。测试：`tests/sheet-items-format.test.ts` |
| **需求级项标题按缺口类型区分** | 三行同名「需求级验收」时，人分不清哪行在说什么 | 标题单点 `requirementItemTitle(criterion, gapKind)`，**三处消费点共用**（渲染 / 裁决后回填 / 弹框 header）。测试：同上（标题去重后数量 === 项数） |

## 六类系统项（缺口可见化）

| 系统项 | 触发条件 | `gapKind` | 阻断提交？ | 通过时 |
|---|---|---|---|---|
| 孤儿用例 | 设计点名、文件头未声明覆盖的测试文件 | `orphan` | 否 | 须写处置方式 |
| 不可照着验 | 验收项没写「怎么验」（历史/直种数据） | — | 否 | 须有人看过并决定 |
| E2E 覆盖 | 需求文档有测试策略表且声明无 E2E | 缺口时 `e2e` | 否 | 缺口项通过须写理由 |
| 三方一致性 | 做什么 × 怎么做 × 实际做了什么对不上 | `consistency` | 否 | 须写处置方式 |
| **锚点失效** | 验收标准引用的 `tests/*.{test,spec}.*` **在工作区不存在**（护栏：连 `tests/` 目录都没有时整段跳过） | `consistency` | 否 | 须写处置方式 |
| FR 追溯断链 | `rtm-accepting.yml` 里某 FR 的 `fr_to_tests` 为空 | `traceability` | 否 | 须补标注或说明 |

> 设计原则：**"靠人记得"不算机制**。缺口必须成为验收面上可见的一项，但不阻断流程——是否放行由人裁决。

## 两条通道与「零输入裁决」（REQ-261006092213-4f5b 起）

| 通道 | 入口 | 结果从哪来 | 备注 |
|---|---|---|---|
| 看板 | 需求 → 验收页逐项勾选 | 输入框**预填** `item.result`；留空点「通过」→ 服务端取该项 `result` | 前端**不再判必填**；改动输入框 ⇒ 写 `result` 且 `resultSource='human'` |
| 会话弹框 | `reqboard_accept_sheet` | 有 `result` 的项**只问 1 问**（通过 / 改进 / 其他）；`needsHuman` 项保留第 2 问 | `needsHuman` 是**唯一**必须人填的分支（题干带理由，无理由即拒） |

- **结果先落章**：agent 提交验收材料（`reqboard_submit(kind=verification)` 的 `results`）时逐项写 `result` +
  `resultSource='agent'`；缺项 / 坏 ref / 重复 / 空结果**拒绝并点名到项**（三段式）。
- **底线**：`opinion` 与 `item.result` 皆空 ⇒ `unverified`（未复核）——不计入通过，
  归档放行判据是「无 `pending` **且**无 `unverified`」（六处实现同口径，见 project-manual 机制备忘）。
- **硬门范围**：可预见项 = 顶层父卡任务项 + 需求级项 + 对照项；**系统项豁免**（提交时才由代码算出）。
- **两层响亮**：形状级坏参数在**绑定层**被工具 schema 拒（`INVALID_ARGS`，点名到字段路径）；
  语义级（载荷缺 / 漏项 / 重复 / 指不到项）由用例回 `REQBOARD_RESULT_*`——都不静默。
- **回滚一行**：`DSH_REQBOARD_NO_ITEM_RESULT=1` ⇒ 提交侧不结构化绑定（`results_coverage='legacy'`）、
  裁决侧恢复 `evidence[0]` 兜底且不写 `result`（两个效果缺一即算开关失效）。

**最终归档**：所有项裁决完（且无未复核项，或人显式覆盖）后，人点「验收通过并归档」——agent 不能自行归档。

## 三层判据：占位符 / 结果锚点 / 处置模板（2026-10-06，REQ-261006201920-2adc）

「验收不再形式合规」这条需求把三层判据各补了一刀。**三层为什么必须分开看**：它们判的是三件不同的事，
混用必然误伤——把「结果锚点」判据套到系统缺口项上，`确认无需 E2E：纯函数模块，无外部接口`
（一句合法的处置）会被当成「无锚点的通过」而卡住归档。

### 一、计划期：占位符必须替换掉，且判据要**窄**

| 项 | 口径 |
|---|---|
| 判据 | 命令的操作数仍是尖括号占位符 ⇒ 拒（`Acceptability.PLACEHOLDER_OPERAND`） |
| 为什么**不**用裸 `/<[^>]{2,40}>/` | 它会误伤四类**合法**标准：TS 泛型 `Record<StageKind,string>`、产品字面量 `<svg>`/`<ts>`、路径形态 `prototypes/<name>.html`、「断言不含 `<单册>`」 |
| 实测 | 全量 2013 张卡：裸正则命中 948、窄口径命中 923（召回 97.4%），命中的 token 全是真模板占位符 |
| 子卡落库 | 模板占位符改成**声明式闭集**（`ACCEPTANCE_PLACEHOLDERS`）+ 回填器：父卡验收标准里点名的测试文件与脚本被搬进子卡，取不到落声明的兜底（`tests/` / `*.mts`），残留即抛 |

**关键设计**：模板字面量**照旧保留占位符**（`STAGE_ACCEPTANCE` 不改），回填发生在**落库那一刻的唯一构造点**
（`lazy-expand.makeChild`）。改模板会让「模板是不是可执行」失去单一版本；改构造点则一条路径覆盖
`expandSubtasks` 与 `regenerateChain`。

### 二、裁决期：三类项**分开判**（本节最容易被改坏的地方）

| 项类 | 判据 | 不满足时 |
|---|---|---|
| 普通项 | 文本要**可复核锚点**（命令 / 路径 / 明确计数 / 证据介质如 `.png`） | 记 `unverified`（不冒充通过，不阻断继续裁决其它项） |
| 「只能人看」项（`needsHuman`） | 要**事实形态**（现象 + 证据路径）且长于 6 字 | **拒收**并给出「该写什么」 |
| 系统缺口项（`gapKind`） | 写的是**处置**：命中两义模板（已处置 / 确认无需）并给出对象或理由 | **拒收**；且处置无效即不放行归档 |

**判据单点**：`isResultOverride`（覆盖判定）与 `dispositionMissingItems`（处置完备）各只有一份实现，
看板收集 / 弹框补问 / 应用层写入三处**共用**——各写一份必然漂移，代价是「UI 不问、服务端要」。

### 三、覆盖是**原子四元组**

人改写 agent 的实测原文时，一次性写全 `result` + `resultSource='human'` + `resultSuperseded`（被取代的原文）
+ `resultChangeReason`（变更理由）；**缺理由则该批被拒且台账零改动**（前置校验排在落状态之前）。
重复覆盖时 `resultSuperseded` 保留**最初那次**原文。三条排除：人工项（其 `result` 只是参照材料）、
系统缺口项（写的是处置）、本无实测结果（首次填写，没有东西被覆盖）。

两个新字段**加性可选、零迁移**：旧台账照常读且不产生额外写入；旧调用方不传 `changeReason`
且不构成覆盖时不报错。

### 四、判据类改动的验收：**双向跑**

每条判据的负向读数都要留档（**只跑绿的那一向等于没跑**）：

| 演练 | 关掉什么 | 红 | 还原后 |
|---|---|---|---|
| RV-1 | 计划期占位符分支 | 2 failed / exit 1 | sha256 逐字节相同 → 复绿 |
| RV-2 | 子卡落库回填调用 | 5 failed / exit 1 | 同上 |
| RV-3 | 裁决结果锚点分支 | 2 failed / exit 1 | 同上 |
| RV-4 | 覆盖理由校验（改恒真） | 2 failed / exit 1 | 同上 |
| RV-5 | 处置模板（退回非空即可） | 2 failed / exit 1 | 同上 |

**「处置无效即不可归档」的逆验证**（TC-17）：直接**构造**「系统项 `status=passed` 且 `opinion` 为空」的验收单
⇒ `isFullyDecided` 必须为 false、门状态必须为 `pending`。这条不是"写个用例"，是构造那个状态再断言。

## 变更须知（改这些地方会连带破坏什么）

- **动 `SubmitVerification` 的任务投影** → 必须保持 `parentId` 透传，否则 domain 过滤变死代码（历史事故）。
- **动 `buildSheet` 的项顺序或编号** → 同步更新 `tests/sheet-items-format.test.ts` 的顺序断言；编号是读侧**不透明键**，存量单据不回填。
- **新增缺口类系统项** → 复用既有 `gapKind` 枚举值并用 criterion 前缀区分标题，别新增 protocol 枚举（要迁移评审）。
- **改动验收项文案** → 同步 `requirementItemTitle` 的前缀常量，否则标题会退化回同名。
- **动「通过要什么」的口径** → 六处放行判据必须同改（`sheetGateStatus` / `isFullyDecided` /
  `isFullyDecidedItems` / `finalizeIfAllPassed` / RTM 门禁映射 / 看板「验收通过」的不合规通过判定）；
  任何一处漏改都会让「未复核」从那条路悄悄放行（REQ-261006092213-4f5b 的教训）。
