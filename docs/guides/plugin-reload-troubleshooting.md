# 桌面端控制台：插件包 404 / `plugins/events` ERR_FAILED 排查

> 面向**下一个看到这两条红字的人**。先给结论：它们几乎总是「页面手里的包地址过期了」，**刷新页面**即可；
> 只有当下面「判据」跑出不符时，才需要继续排查。
> 机制性根因（插件加载链路）见 [插件运行前提](../architecture/plugin-runtime-prerequisites.md)。

## 症状

两条红字形态不同、**成因也不同**，不要当成一件事：

| 控制台那行 | 地址形态 | 指的是什么 |
|---|---|---|
| `Failed to load resource: the server responded with a status of 404 (Not Found)` | `dsh-app://app/plugins/??<包>/client.js&rev=<rev>`（页面里是文档相对形态 `plugins/??…&rev=…`） | 某个**客户端插件包**的 combo 地址——地址里带 `rev` |
| `Failed to load resource: net::ERR_FAILED` | `dsh-app://app/plugins/events` | DSH 自己的**客户端插件 HMR 通道**（SSE 长连接），不是业务插件的接口 |

两条的共同点：都发生在**页面已经开着、而宿主或构建产物刚变过**的时候。

## 判据

三条命令，几十秒出结论。`<host>` = 当前宿主（本机 2026-10-06 实测 `127.0.0.1:19387`），
`<rev>` 直接从 C-1 的输出里抄——**端口与 rev 逐次实测取值**，不要照抄本文的示例值。

| 编号 | 命令 | 期望输出 | 不符时怎么办 |
|---|---|---|---|
| C-1 | `curl -sS -i -m 3 http://<host>/plugins/events` | 头部 `HTTP/1.1 200` + `content-type: text/event-stream`，首帧含 `"type":"graph"` | 非 200 或不是事件流 → HMR 通道本身没起来（真问题，见「非目标」） |
| C-2 | 从 C-1 输出里抄出 `plugins/??<包>/client.js&rev=<rev>`，原样请求：`curl -sS -o /dev/null -w '%{http_code}\n' 'http://<host>/<抄来的地址>'` | `200` | `404` → 页面手里的地址已过期：**这就是本条目覆盖的噪声**（重建 / 重启竞态） |
| C-3 | 同 C-2 的地址，把 `rev=<rev>` 改成一个不存在的值再请求一次 | `404` | `200` → 宿主不按 `rev` 校验，本判据失效，按「非目标」重查 |

**读法**：C-1 通过 + C-2 得 `404` + C-3 得 `404` = 噪声（刷新页面即可）；
C-1 失败、或刷新后 C-2 仍是 `404` = 真问题（走「处置」第 2 步）。

**本次交付实测定标（2026-10-06 12:11；逐次重测会变，别照抄）**：`<host>` = `127.0.0.1:19387`，
当前 `rev` = `30507b9b5434` → C-1 = `200` + `text/event-stream`；C-2 = `200`（656260 字节）；C-3 = `404`（0 字节）。
本条目的时效边界值得记住：**任何人重建客户端都会让 `rev` 变**——本次交付期间就观测到
`lib/client.js` 在 12:09:49 被重建、构建戳从 `cfd7e0c0d56c` 变成 `33a6b5c8ce65`，与本文描述的现象同源。

## 机制

- **包地址为什么带 `rev`**：宿主按每个包入口产物的 mtime / ctime / size 合成 `rev`；重建
  （如 `pnpm build:client`）后 `rev` 变，**旧 `rev` 的地址在宿主侧不再存在** → `404`。
  页面是**文档装载时**拿到这批地址的——页面一直开着、你在外面重建，它手里的地址就过期了。
- **为什么多数会自愈**：HMR 客户端会重试最新的插件图（revision 未变也重试；后续重建会重试受影响的插件），
  所以这类 `404` 常常一闪而过，随后自己恢复。
- **`plugins/events` 是什么**：`@deepseek-ai/dsh-client-hmr` 的 SSE 通道（宿主提供、桌面壳转发给页面），
  推送「插件图 + 重建通知」。宿主重启或页面卸载会把它掐断，浏览器就记一条 `net::ERR_FAILED`；
  `EventSource` 自带重连，所以这条同样不代表「插件坏了」。
- **桌面壳的转发规则**：`dsh-app://app/` 下只有 `/`、`/index.html`、`/assets/**`、`/favicon.svg`、
  `/manifest.webmanifest` 走壳内静态文件，其余路径（含 `/plugins/**`、`/dashboard/**`、`/api/**`）
  一律转发宿主——所以 `plugins/events` 的 404 **不可能**来自「壳里没这个文件」。

## 处置

1. **先刷新页面**（`F5` / `⌘R`）。刷新后页面拿的是当前 `rev`，两条红字都应消失。
2. 刷新后**仍红**，或判据段出现「不符」→ 按「非目标」定位，并留下取证材料：
   - DevTools → Network，按状态码筛 `404`，**保留完整 URL**（右键 → Copy link address）；
   - 记下 C-1 / C-2 / C-3 的实际输出（状态码 + 响应字节数）；
   - 把这几样交给插件排查——本条目只负责**判定**，不负责给出根因。

## 非目标

| 你看到的情形 | 说明 | 去哪查 |
|---|---|---|
| 404 的 URL 不是 `…/plugins/??…`（如 `/dashboard/…`、`/api/file?path=…`） | 不在本条覆盖范围 | 查该路径自己的路由 / 文件是否存在 |
| 地址里没有 `rev=`（如 `/plugins/??dsh-pmboard/client.js`） | 形态不对；实测这类地址一律 `404` | 用带 `rev` 的地址复现（从 C-1 输出里抄） |
| `curl` 连不上宿主 | 宿主没起，不是竞态 | 先起宿主 / 桌面端，再回本条目 |
| `/assets/**` 返回 404 | 那是桌面壳内的静态资源 | 属另一类问题（壳 / 装机产物），不在本条 |
