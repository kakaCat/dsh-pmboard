# 同口径成本度量：`pnpm cost:report`

> **TL;DR**：一条命令把「一条需求烧了多少 token / 多少墙钟 / 缓存有没有被作废」量出来。
> 口径固定（按会话 `createdAt` 过滤**自身请求**、按 `parentSession` 建树），所以**改造前后可比**。
> **三条免责声明先读**（§三），否则很容易把供应商差异读成改造效果。

## 一、怎么跑

```bash
pnpm cost:report --req REQ-261006130057-7a43            # 按需求（读 record.json 的 sourceSessionId 作根）
pnpm cost:report --root session-d71bdc25-ede6-…          # 按会话根（递归收全部后代）
pnpm cost:report                                         # 当前工作区全部会话（355+ 会话时约 2 秒）
pnpm cost:report --req <REQ> --until 1791338511286       # 只算该时刻之前的请求（epoch 毫秒或 ISO）
```

- `--sessions-root <dir>` 可覆盖会话目录（缺省 `~/.dsh/sessions/--<工作区转义>--`）。
- `--until` 只用于**按时间点回溯复现历史快照**（诊断文档写就之后会话仍在增长），缺省不生效。

## 二、口径（必须照此理解读数）

| 项 | 口径 |
|---|---|
| 自身请求 | 只算 `event.time >= 首行 session.createdAt` 的 `assistant/message`——**排除 fork 继承父历史造成的重复计数** |
| 四桶 | `inputTokens`（未命中）/ `cacheReadTokens`（命中）/ `outputTokens`；请求数 = 计数的条数 |
| 树归属 | 按会话首行 `parentSession` 递归收后代（一个需求 = 主窗口 + 它的全部子代理） |
| **缓存失效点** | `cacheReadTokens < 20,000 且 inputTokens > 40,000` 的请求；逐条标注**其前 60 秒内有没有 `system/message`** |

**读失效点的方法**：`cache≈16K` 且 `uncached≈整段上下文` = 前缀缓存整段作废。
但**「前 60 秒有 `system/message`」不等于就是重写造成的**：实测 24 条里 19 条有、5 条没有——
那 5 条属于「同轮内两次重写」与「跨期缓存 TTL 过期」。判因要看**前一条请求的时间间隔**。

## 三、三条免责声明（别把差异读成效果）

1. **供应商相关**：同一份诊断里，`kimi-coding/k3` 上每次头部重写都让整段前缀缓存作废
   （16 次 × 整段 `uncached`，合计 3.9M 全价）；而 `deepseek-flash` 上 9 次重写**全部保住缓存**，
   该窗口唯一一次全量重算发生在**其前 163.6 分钟空档**之后（TTL 过期；29.5 分钟空档未触发）。
   ⇒ 同一改动在不同 provider 上的 token 收益可以差一个数量级。
2. **做法差异不是代码差异**：紧凑输入包 + 不用 `subagent_fork` 的派发纪律会显著降低子代理成本；
   把它记成"改造效果"是错的（实测基线有 9 个 fork 带整段父上下文）。
3. **本需求改造在自身执行期可能还没生效**：例如批量收尾是在末期才落地的，
   之前一直走旧单卡路径（还会撞 60 秒节流）。⇒ 效果证据请用**单测与剧本断言**，或做**同 provider 的对照**。

## 五、它不能回答什么

- 不能区分「哪一段提示词贵」——那需要 token 级归属（本仓 `prompt-cost.ts` 只覆盖 system prompt 装配投影）。
- 不能证明因果：任何"改造前后对比"都必须**同 provider、同派发纪律**，否则读数不可比。
